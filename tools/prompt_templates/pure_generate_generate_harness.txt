Pure-function leaf turn (host-mediated): you are the `generate.generate` producer of the atmofab workflow, run as a host-mediated pure function, on a node whose bundle shape is `harness` — an `infrastructure` self-test. You have no gate or repository write authority. Do not use filesystem or shell tools: everything you need is inlined below. Return EXACTLY ONE JSON document — a CodegenBundle — as your ENTIRE reply, with no surrounding prose, no markdown code fence, and no explanation. The host parses your whole reply as that one document, validates it, and writes the files itself.

What makes this shape different from the ordinary one: on a physics node the host renders the program that drives the generated code, and the leaf authors a callback module for it. Here the host renders NOTHING of the kind. This node IS the plumbing a physics node's driver is built out of, so you author BOTH halves: the model, which publishes the operations the IR's `public_api` names, and the unit's EXECUTABLE ENTRY, which drives them once per case and is the artifact the run executes. There is no callback module on this shape, and no callback ABI to satisfy.

Output contract (CodegenBundle, schema 1.1.0): return one JSON object with these REQUIRED top-level keys — `bundle_schema_version` (e.g. "1.1.0"); `optimization_unit` (`{"members": [<this node's node_key>]}`); `files` (an array where each entry has `logical_path` (the source filename, NOT `path`), `role`, `language` (the `toolchain.language` value the Target profile below declares), `member_node_key` (this node's node_key, or null for a unit-shared private file), `content` (the FULL source text, NOT `text`), and `modules` (the module names that file defines)); `entrypoints` (an array where each entry has `symbol`, `kind`, `node_key`, `defined_in`, and `module`); `target_lowering_plan` (`{"precision": {...}, "state_residency": ...}`); and `capability_requirements` (an array of `<capability>@<version>` strings). File shape (this is checked exactly, and a mismatch costs you a repair turn — emit it right the first time). EXACTLY TWO roles are admissible here beyond the private ones: `model` and `runner`.
- EXACTLY ONE file of role `model`, whose `logical_path` is `<spec_id>_model` with the source extension the declared language uses, `member_node_key` this node's node_key, and a `modules` list DECLARING the module named `<spec_id>_model` — the same stem as the file, with no extension. That module name is not a convention you may vary: a consuming node imports this surface by a name DERIVED from `<spec_id>`, never read from your bundle, so a different one certifies a node nothing can link against. `<spec_id>` is `meta.spec_id` of the IR below, verbatim — never an abbreviation of it. The file may declare further modules beside that one.
- EXACTLY ONE file of role `runner`, whose `logical_path` is `<spec_id>_runner` with the same extension, `member_node_key` this node's node_key, and `modules` set to the EMPTY array `[]`. `runner` is the unit's executable entry: it defines no module, because nothing else may `use` it, and it is the ONE role for which an empty `modules` is admissible.
- NO file of role `checks`. This shape has none, and one is rejected.
- `helper` / `internal_module` files are permitted as private additions (a `member_node_key` of null is admissible only for those two roles). They are optional; do not add one without a reason.
- `entrypoints`: one entry per published operation, each with `kind: "operation"`, `defined_in` the model file's `logical_path`, and `module` the module that file defines. The `runner` file may NEVER appear as an entrypoint's `defined_in`.
- `state_bindings`: OMIT the key entirely. A binding must name a module published by a `checks`-role file, and this shape has none, so a binding cannot be satisfied here whatever the IR declares — emitting one is rejected. (On this node the IR declares no `algorithm.state_variables` either, so there is nothing to bind.)
- `capability_requirements`: exactly ONE execution-model capability, and it must be one the harness manifest below actually provides. On this shape the manifest shown to you is THIS NODE'S OWN: a harness declares the execution model it IMPLEMENTS. Declare no capability your code does not use, and none the manifest does not list. `target_lowering_plan.state_residency` must be `host` unless a capability backing another residency is listed (it is not).

Authoring rules (obligations on the source you emit; deterministic gates run over it AFTER you return, and you get no second look, so satisfy them on the first emission).
(1) Published surface. The IR's `public_api.published_operations` names your model's published operations. Publish EXACTLY those names — no more, no fewer — and render each one's interface from `public_api.signatures`, which is a language-NEUTRAL structured description you LOWER into the declared language: keep every argument's name, its ORDER, its type, its rank, its direction, and its declared bounds where the signature carries them. `public_api.published_types` are published the same way, each by its fully-qualified name and never by a short alias. `public_api.module_parameters` are declared once each, at module level, with the neutral kind value lowered to the language's spelling — a deterministic gate renders the same lowering and compares it against your source, so emitting a neutral token verbatim fails, and so does binding one of those names any other way (an alias import, a second declaration anywhere in the file, one inside a contained procedure included). Publish every listed operation even where the self-test's own path could inline it: a consuming node links against exactly this surface.
(2) The executable entry CALLS the model; it never reimplements it. Every published operation the entry needs it obtains by calling the model's published procedure — a locally re-derived emitter, writer or parser is a fail, and so is duplicating one of them. This is the whole point of the node: the entry is the first consumer of the surface it certifies.
(3) Case fan-out from argv. The entry receives the cases to run on its command line — the IR path followed by one case id per case the run selects — and must run every case id it is GIVEN, not a set compiled into it. Anywhere the run's output is addressed per case, build that address by concatenating the RECEIVED case id; a sequential or otherwise invented name is rejected by a deterministic scan (for a literal) or by the deliverable gate (for a runtime-built one). The declaration order of `case.test_case_set[]` is NOT the order the ids arrive in.
(4) What the entry writes, and what it must never write. It writes the diagnostics document, the performance document, and the primary evidence under the raw-evidence directory, and NOTHING else. It must NOT write the run's judgment artifacts — `verdict.json`, `aggregate_verdict.json`, `summary.json`, `trial_meta.json` — and its source must not contain any of those four names ANYWHERE, comments and string literals included: the check is a plain substring match over the lowered text, so quoting one that an inlined document happens to mention is enough to fail it. Say "the judgment output" in prose instead. (A `verdict` FIELD inside the diagnostics document is a different thing and is required where the IR's `diagnostics_contract.verdict.required` is true.)
(5) The evidence index. The primary-evidence index is a per-test list holding one entry per (`test_id`, target case) pair: every `test_id` of `io_contract.test_evidence_requirements`, once for each case named in that test's `io_contract.test_predicates[].target_cases`. A single-target test yields one entry; a multi-target test one per targeted case. Each entry carries the `test_id`, the case id, and that test's `required_raw_variables` FOR THAT CASE, without omission. The gate pins the matrix in BOTH directions, so an omitted or an extra row fails. It holds the primary evidence only and never a copy of the diagnostics document.
(6) The performance document carries, per case and without omission, the fields the runner-output contract inlined below fixes — a smaller schema of your own design is rejected by the deterministic gate, which checks the required fields by name.
(7) Serialization. The diagnostics and performance documents, and every primary-evidence document, must be UTF-8 JSON an ordinary parser restores. The numeric and boolean formatting rules for the declared language are §4 of the runner-output contract inlined below, and they are SYNTACTIC: a deterministic scan flags the forbidden output-format spellings by their mere presence in a write statement, so a runtime fixup does not pass — the spelling must not appear. Follow the reference snippet that section gives rather than inventing a formatting helper.
(8) No external interpreter. The entry must not launch a general-purpose interpreter or shell as a subprocess to do part of its work.
(9) The diagnostics document satisfies `io_contract.diagnostics_contract`: an entry for every declared check id, an honest per-case status for each, and — where `verdict.required` is true — the top-level verdict object holding the declared fields. A custom per-case array that omits the contracted entries is a fail. Per-case statuses stay honest: report a failing check as failing even in a case the tests expect to fail, because the fold that excludes it is the judgment's job, not yours.
(10) Impl-defaults reflection: the `impl_defaults` shown under Target profile below are OBLIGATIONS on the source you emit, not background description. Both layers bind — the fixed layer (`target.*`, `toolchain.*`) and the knob layer (`abstract` and `backend_overrides`) — each reflected to the extent the target language expresses it. Read the knobs by MEANING, not by key name; their spelling varies from node to node. Never force a parallel construct onto work that is not parallelizable; where the knobs are silent or say `none`, saying so honestly in the source is the sanctioned answer.
(11) Every source you emit is compiled and linted by deterministic gates under the standard the Target profile declares. Identifier lengths, the column limit, the accessibility statements, and the import forms those gates enforce are the language's own; author to the standard the profile names rather than to a dialect extension, and do not add a suppression comment — the lint gate disables them, so the finding is reported anyway.
