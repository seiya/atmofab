Review checklist: your canonical sources are the tests document and the IO contract; every other seed is evidence about one run, and the runner-output contract states what that evidence is obliged to be. (a) The verdict document is HOST-AUTHORED and deterministic — every test's `basis.predicates[]` was valued by the host from the captured state itself (the predicates of the IO contract: each record carries the expression `expr`, the `op`, and under `evaluated` the host-computed `value` and the threshold `rhs` per case, with `cases_read`, the cases whose captured state it read), and a predicate failure would have ended the phase before you were launched. These records alone decide each test. Read them as the result you are reviewing; never re-derive them, never report a finding that merely restates them, and never ask for them to be changed. A capture is what the host-rendered driver wrote from what the published operations left in their arguments, and on a node whose `drive` declares `loop` a run-wide extremum is read from the driver's own `series` fold, never from a kernel's report. (b) Reconcile those records with the raw evidence excerpt. **Know what the excerpt can and cannot establish, because this is the difference between a finding and a false one.** It is a host-computed summary of the run's raw primary evidence — per-array shape, extent (`min`/`max`), counts of non-finite values, whether an array is entirely zero, and whether it is ragged; on a case of a `loop` node also `history_samples`, the count of its `history/` samples, and `series`, the same summary of each name of its `series/` file — and no numeric array is inlined at any size, so it can CONTRADICT a value but it cannot SUPPORT most of them. That asymmetry is expected and is not a defect in the run: most judged values are sums, norms, ratios, drift fractions and convergence orders, which no array's extent bears on. **The inability to support a value is therefore NEVER a finding.** What IS a finding: a value the excerpt CONTRADICTS — a record's value outside the extent of the arrays it reduces (a run-wide minimum over `series` above the end-state minimum of that array, on a case with a committed step), or a record over a variable the excerpt shows was never produced. Fail those with `attribution=code`, or `attribution=evidence` when the raw evidence itself is missing or malformed. **Separately, and on their own merits**, a non-zero `nan_count` or `inf_count`, a `ragged` array, or a `shape` whose RANK disagrees with the declared `shape_expr` (a `scalar` reported as an array, a `[nx]` reported with two dimensions) are defects in the evidence whatever the tests say — report them. One row is not that defect: a state array (a row with a `declared_shape_expr`) with `count` 0 on a zero-extent guard case reports only what its JSON can spell, because nested lists stop at the zero: `[ncomp, nx, ny]` at `nx=0` is `[[],[],[]]`, reported `[3, 0]` with `min` and `max` null. The host's driver writes that capture, and the host refuses a zero extent among a case's inputs unless only `xfail` tests target that case; the runner-output contract's refusal of an empty capture is the rule for a runner a leaf writes. Your seeds hold no case's inputs, so read its extents from the tests document: a state array of `count` 0 on a case where that document gives all of the array's extents non-zero stays a defect, and where it does not say, record that in `notes` and report nothing. A `series` name of `count` 0 is a case stopped before its first step, and this paragraph does not concern it. A symbolic EXTENT you were given no binding for (`[nx_face]` against `shape: [7]`, with no value for `nx_face` anywhere in your seeds) is not something you can settle: do not infer one and do not report a disagreement you cannot evaluate — say so in `notes` instead. Know which of these defects something else catches, and spend your attention on the rest: before you are launched, the deterministic `post_execute` gate refuses a `raw/state_snapshots/` array whose RANK, or a literal or repeated-symbol extent, disagrees with its declared `shape_expr` (a symbolic extent binds, per array, to whatever it finds, so two arrays of one capture sharing a symbol may disagree unrefused — the excerpt's per-array shapes show it; an array holding a zero extent in a capture the host's driver wrote is not compared), or that is ragged or of unsupported shape, and the host's predicate evaluation refuses a non-finite value in any variable of a capture a predicate ranges over, as a structural failure of the host verdict; NOTHING checks the finiteness of a capture of a case no predicate ranges over, so if you pass over one of those it is not caught downstream. **`all_zero` is the one flag that is NOT a defect on its own**: a flat bed, a zero transverse momentum component, a zero-diffusivity case and a lake-at-rest source term are legitimately zero everywhere, they are common in this repository's specs, and the excerpt cannot tell them from an unwritten array because `min` and `max` are `0.0` for both — so make it a finding only where the tests document or the IO contract says that variable should have varied. (c) `declared_variables_absent`, on each snapshot case, lists schema-declared variables that snapshot omits: the deterministic `post_execute` gate has already refused such a snapshot, so a non-empty list means this run reached you in a state that gate should have refused; report it with `attribution=evidence`, say so in `notes`, and do not treat it as your primary contribution. If `problems` is non-empty the host could not read part of the evidence at all: report that with `attribution=evidence`. Its `required_evidence` section is the IO contract's own declaration against what the run actually produced — check the composition against THAT, and do not impose a fixed set of artifacts of your own. (d) Confirm the physics semantically satisfies the tests document's INTENT beyond what a mechanical predicate can express: that invariants stated in prose actually hold, and that the run is not a degenerate or trivial artifact. Judge degeneracy from what you were actually given — the array extents and shapes, the host's per-case values, and what the tests document says the case was supposed to exercise — and say in `notes` what you were unable to determine. Do NOT manufacture a basis you do not have: "I could not establish X from the evidence I was given" is a legitimate and useful thing to record, and is not a reason to fail the run. For an `infrastructure` harness node, "the physics" is the runner-plumbing behaviour — emitter round-trips, case fan-out, the input guard on the case selection argument — so confirm THAT satisfies the tests document, and do NOT fail such a node for having no physics. (e) Attribution decides where the workflow returns: `code` for a defect in the generated program, `ir` for one in the intermediate representation, `evidence` for raw evidence that is missing or malformed, and `spec` for a defect in the human-authored specification — `spec` terminalizes the run for an operator rather than retrying, so use it only when no downstream repair could fix what you found. (f) Two limits are absolute: you do not author or repair the run's artifacts, so report what is wrong and why rather than emitting a correction — your own review document is the one file you write, and you rewrite it in place when the host asks; and you never run a validator or a gate, because the deterministic gates around you have already run and are the authority for what they check.
