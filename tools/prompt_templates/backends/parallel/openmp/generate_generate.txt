@@ target_lowering_floor
For a `cpu` target whose `parallel.backend` is `openmp` and whose language is `fortran`, the default is `!$omp parallel do` on the parallelizable loops, declared as `"parallelization": {"model": "openmp", ...}`. The inverse is equally binding — never force a directive onto a loop that is not parallelizable (a carried dependence, a reduction you cannot express correctly), and a `do concurrent` loop already IS the parallel construct, so it needs no directive beside it. The floor here is deterministic: on a `component` or `problem` node the `Generate.gate` static check FAILS a `cpu`+`openmp`+`fortran` model source whose `target_lowering_plan.parallelization` does not decline OpenMP and that has counted `do` loops and not one `!$omp` directive at the start of a line (a mention inside a comment or a string is not a directive). It does NOT run on an `infrastructure` node, on a whole-array source, on a source using `do concurrent`, or when your plan's parallelization `model` explicitly names `none` (or another model) — a plan that names no model gets the target's backend, OpenMP. So when no loop can be parallelized, declare `"model": "none"` and say why in the plan for the reviewer, who holds that declaration to the loops; never emit a directive you believe is wrong, and never decline one a loop can take. Directives are compiled, not ignored: the syntax gate passes `-fopenmp` on an openmp target, so a malformed clause is a hard error, and a directive too long for rule 1's column limit continues by repeating the sentinel on the next line (`!$omp parallel do &` then `!$omp& schedule(static)`) — a bare `&` continuation of a directive is a syntax error. Whether the directives you do emit cover the loops your plan names and carry its schedule is then reviewed by the independent `generate.verify` reviewer, so satisfying the floor alone is not the bar. The host runs the binary at several thread counts — the profile's `threads_per_rank` and each count of its `execution.sweep` — and requires every run's check statuses, verdict and captured state to agree with a one-thread run, so a race or a result that depends on the team size fails there: let every parallel region take the width the launch environment sets (its `OMP_THREAD_LIMIT` caps a `num_threads(...)` clause at that width anyway), and never pin a region to one thread or switch it off on the cases the tests run (`num_threads(1)`, `omp_set_num_threads(1)`, an `if(...)` clause false on those cases): such a region never runs at more than one thread, so the comparison cannot see its race, and it is the reviewer's finding.
