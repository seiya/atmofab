(1) Every warning is an error, and a few spellings are refused outright. The `Generate.gate` lint check compiles each `.cu` of `src/` with `nvcc -std=c++17 -Xcompiler=-Wall,-Wextra,-Werror --Werror all-warnings -Xcompiler -fsyntax-only -rdc=true -c` (the rule set declared in `tools/backends/linter/nvcc/lint.py`), so an unused parameter of a HOST function (a kernel's or a `__device__`-only function's is not reported, and is still yours to remove; a `__host__ __device__` function is compiled for the host too, so its unused parameter is), an unused variable, an unused function, a signed/unsigned comparison, a missing `return` on a path of a non-`void` function, and a device-front-end warning each FAIL the gate. A parameter an interface FIXES but your body never reads — an inert input a published signature pins — keeps its name, and the body's first statement is `(void)<name>;` (that cast is the one binding for it: an arithmetic no-op such as `0 * <name>` is forbidden, and it computes nothing on purpose). A parameter of a helper YOU declared that no body reads is deleted from the signature and from every call site instead, and an unused local is not declared at all. The static check (`tools/backends/language/cuda_cpp/source.py` `preprocessor_violations`) then refuses, by presence anywhere in a leaf source: any preprocessor directive but `#include "<file>"`, `#include <header>` and `#pragma unroll [<n>]` (the last in DEVICE code only — in a host function, a `__host__ __device__` one included, the host compiler reports it unknown, which fails the lint), so no `#define`, no `#if` / `#ifdef` / `#endif`, no other `#pragma` (a diagnostic pragma above all), no line marker; a `_Pragma` / `__pragma` operator, `##`, and every digraph; an `#include <...>` of anything but a C++17 standard library header or `cuda_runtime.h` (a bundle or host file is included with `"..."`); an identifier starting with `_` and a capital letter, or with `__`, except the CUDA keywords `__global__`, `__device__`, `__host__`, `__shared__`, `__constant__`, `__managed__`, `__restrict__`, `__launch_bounds__`, `__forceinline__`, `__noinline__`, `__syncthreads`, `__syncwarp` and `__func__`; and a backslash at the end of a line, in a comment or a literal included.
(2) Files and translation units. Your bundle's file is `<spec_id>_model.cu`, a `.cu` source at the TOP level of `src/` (a `.cu` in a subdirectory is refused, and a leaf ships no header). Every `.cu` is compiled on its own and the objects are linked, so a source reaches another's declarations only through a HEADER, and every header here is host-rendered and staged beside your sources: `<spec_id>_model.cuh` (your node's published surface, 6a), `<dep>_model.cuh` for each dependency, and the harness's header, which is the runner's alone. Include each one you use with `#include "<name>"`, and never `#include` a `.cu` (the code would then be defined in two objects, which fails at link). Your model defines its operations inside `namespace <spec_id>_model { ... }`; a helper kernel or function your model uses and no other file calls goes inside an unnamed namespace (or is `static`), so an unused one is refused by the lint (`#177-D ... declared but never referenced`) instead of passing silently.
(3) Syntax gate (the `Generate.gate` syntax check): `nvcc -std=<toolchain.standard> -Xcompiler -fsyntax-only -rdc=true -c` (with `-arch=<hardware.architecture>` when the target profile names one) over every `.cu` of `src/`, each its own translation unit, staged with the host-rendered headers and the certified sources of your dependency closure — so an include the headers do not resolve, a type your definition gives that differs from the header's declaration (`declaration is incompatible with ...`), and an overload the declaration never reaches are compile errors here or link errors at Build. A published identifier keeps its literal `spec_id` prefix: if `<spec_id>__<op>` would be over-long, report it as a spec-level problem, never shorten it (a depending node calls it by that name).
(4) Dependency-dataflow gate (the `Generate.gate` static check — it inspects `problem` nodes with dependencies, and every function there with an OUTPUT, a parameter it can write through — a non-const reference `T&`, a non-const `spec2science::View<K, R>`, a pointer to non-const — or a returned value): your `public_api.signatures` fixes each published parameter's direction, so transcribe it (6b): an `in` dummy is an input parameter (`K`, `const T&`, `spec2science::View<const K, R>`), and an `out` or `inout` one an output parameter, because the operation can write through it. What the gate checks is NOT merely that each output is written — it is that what a load-bearing `<dep>_model::<dep>__<op>(...)` call WRITES (the storage handed to that operation's OUTPUT parameters, as its header `<dep>_model.cuh` declares them: a local vector, the vector a view you built was made over, a scalar reference) reaches one of your outputs through an ASSIGNMENT chain — `<dep>_model::<dep>__<op>(u, spec2science::View<double, 1>{flux.data(), {n}}, dt);` then `u_new.data[i] = ... flux[i] ...;` in a loop, or `out = ...;`. The gate follows assignment right-hand sides, a view or pointer back to the storage it was built over (`fv{flux.data(), ...}`, `double* p = flux.data();`), `cudaMemcpy` / `cudaMemcpyAsync`, and calls to the functions and kernels YOUR sources define (a non-const reference, pointer or `spec2science::View` parameter — `__restrict__` or not — is what such a call writes, from the arguments its BODY reads into that parameter: a kernel that ignores its flux argument does not carry the flux; a namespace-scope buffer a function reads without receiving it as an argument is not followed into that function) — so a device round trip (`cudaMemcpy` the flux to the device, a kernel you define writes the update, `cudaMemcpy` it back into `u_new.data`) is followed; a call to anything else (a standard-library function, a function you do not define, a TEMPLATE function or kernel — templates are not read) is NOT followed, so routing a dependency result through one does NOT count and FAILS; assigning every output from your own local computation does not satisfy it either — `does not propagate dependency operation outputs to its output dataflow` names the candidates it could not trace. When the operation writes an array (a view, an array or vector reference, a pointer), one of its ARRAY results must reach an output: its scalar outputs — a guard flag you pass on to `ok` — do not count for it. A name assigned before the call by an assignment STATEMENT (`x = ...;`, `x[i] = ...;` — a declaration's initializer does not count, and neither does resetting a pointer to `nullptr`) is read as an input the call consumes, not a result; a function that returns a value has that value as one more output, whatever its `return` spells. The IR's `io_contract.semantic_dependency.required_sources` must likewise reach your outputs.

Such a node's `target_lowering_plan.parallelization` declares `"model": "none"`, with the reason that its operation is pointwise and its consumers' kernels call it once per element — otherwise the deterministic floor below counts the operation's component loop and asks for a kernel the operation must not launch. @@ target_lowering_floor
For a `gpu` target whose `parallel.backend` is `cuda` and whose language is `cuda_cpp`, the default is to run the parallelizable loops on the device: a `__global__` kernel launched with `<<<grid, block>>>`, declared as `"parallelization": {"model": "cuda", ...}` with the loops it covers and the launch shape. The inverse is equally binding — never force a loop onto the device when it is not parallelizable (a carried dependence, a reduction you cannot express correctly). The floor here is deterministic: on a `component` or `problem` node the `Generate.gate` static check FAILS a `gpu`+`cuda`+`cuda_cpp` model source whose `target_lowering_plan.parallelization` does not decline CUDA and that has counted `for` loops and not one kernel (`__global__` or `<<<`, in code — a mention inside a comment or a string is not one). It does NOT run on an `infrastructure` node or when your plan's parallelization `model` explicitly names `none` (or another model) — a plan that names no model gets the target's backend, CUDA. So when no loop can run on the device, declare `"model": "none"` and say why in the plan for the reviewer, who holds that declaration to the loops. State residency is `host` (the output contract above): the state your published operation takes and returns lives in host memory — nothing a caller holds is a device pointer. Inside the operation (a pointwise one, which launches nothing, aside), the DEFAULT use of the device is the following three points: they are the lowering you use when your `target_lowering_plan` says nothing else, and a plan that states a different allocation, transfer or launch shape — with its reason, inside the plan's `accelerator_mapping` object — is your own claim, which the reviewer holds the source to in place of the default (the optimization flow varies exactly these choices through override variants of the plan and measures them); a launch shape there is how the work maps onto blocks and grid, never the number of threads per block, which is the host's (below). (a) A device buffer is allocated once and reused: keep it at namespace scope (an unnamed-namespace variable holding the pointer and its capacity), allocate it on the first call that needs it, and when a later call needs more, free it, set it to `nullptr` and allocate the larger one in its place; otherwise do not free it in the operation; and hand it AS AN ARGUMENT to every kernel and helper function whose signature you choose, rather than naming the namespace-scope variable inside it (the dependency-dataflow gate, rule 4, follows a result through parameters); a callback whose signature an interface fixes (a function-pointer alias a dependency's header declares) cannot take it and reads it by name — the runner's `finish` resets the device, which releases every buffer. (b) Within one call, data crosses the bus once each way: each input a kernel reads is copied in once, each output is copied out once, and a value one kernel produces for another kernel of the same call stays on the device. A `problem` model's step keeps the state its own kernels pass between the stages of one step on the device; it crosses the bus at the operation's own boundary and where a host callee's arguments require it. (c) Element-wise work the plan puts on the device is one launch over the whole range (a grid sized to the element count), not a launch per element from a host loop; a dependency whose header declares it `__host__ __device__` is called from inside that kernel, one call per element, on views into the device buffers — calling it from a host loop instead keeps that loop on the host, which the plan names with a reason about the loop itself (below). Why this is the default: an allocation, a round trip or a launch per element inside a time loop costs more than the loop's work (a run of the channel problem authored without this default did not finish inside its site's time bound), and `Validate.execute` has a time bound. A failed CUDA call is a FAILURE of the operation, never a reason to compute the same result another way: check what each `cudaMalloc` / `cudaMemcpy` / launch (`cudaGetLastError`) / `cudaDeviceSynchronize` returns, and on a failure stop computing — the published operation returns without its result (a persistent buffer stays allocated), still assigning every `out` argument the language requires it to — with no host loop that recomputes a kernel's work when the device fails. The IR's input guard (`guard_pass` and the like) is a formula over the inputs and does not report a device failure: leave it as the IR defines it. A host fallback makes a run whose kernels never executed look like a correct GPU run: `Validate.execute` runs the binary under a device trace, and a deterministic gate fails a run in which any kernel your sources define never executed on the device — so a fallback buys nothing (the reviewer refuses it too), and every kernel you define must be launched by at least one of the cases the run covers. Each launch must do its loop's work: a kernel that exists only to satisfy the floor while a host loop computes the result, or one launched only above a size no case reaches, is refused by the reviewer. When a repair tells you a kernel never executed, launch it where the cases reach it, in blocks of the run's `spec2science::launch_block_size` threads (below) with a grid computed from it; remove it only when its work is not needed, never by moving that work to a host loop. A loop of the model source you do keep on the host is named in the plan with a reason about the loop itself (a carried dependence, a reduction you cannot express correctly, a copy that only reshapes host state) — "the kernel did not execute" is not one. Whether the kernels you emit cover the loops your plan names is then reviewed by the independent `generate.verify` reviewer, so satisfying the floor alone is not the bar. On a `component` or `problem` node the launch configuration is the HOST's (an `infrastructure` node launches no kernel): the run's threads per block is `spec2science::launch_block_size`, an `int` the host-rendered header declares and the host-rendered runner sets, before the first case, to the block size the host imposed on the run — and the host runs the binary once more per block size of the target's execution-shape sweep (each of them one of 32, 64, 128, 256, 512 or 1024 threads) and requires every run to report the same checks and verdict, and the same captured state wherever the IR's cross-target predicates compare it. So launch every kernel with `spec2science::launch_block_size` threads per block, read when the operation runs (a namespace-scope copy initialized before `main` holds 0, which the device refuses), and compute its grid from it to cover the range: `(n + block - 1) / block` blocks for `n` elements, with the threads past `n` guarded in the kernel (a two- or three-dimensional block is a product equal to it). Size any shared-memory array or block-level reduction from it at run time (dynamic shared memory, the launch's third configuration argument), and stride a grid-stride loop by `gridDim.x * blockDim.x`. Never launch with a literal block size, one chosen from the device's properties or an occupancy query, or a different one per launch, and never assign `spec2science::launch_block_size`: the comparison across block sizes would then compare runs of one configuration. The `Generate.gate` static check refuses a source whose code launches a kernel (`<<<`) and never names `spec2science::launch_block_size`, and a source that writes it (an assignment or an increment); the reviewer refuses a literal or device-chosen block in a source that passes that check. Reading it does not name the harness (the rule below still holds).
