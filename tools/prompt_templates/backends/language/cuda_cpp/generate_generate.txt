@@ state_binding_convention
What the entry declares is the binding convention your `<spec_id>_checks.cu` implements. The host renders `<spec_id>_checks.cuh` beside your sources — you do not emit it and are not shown it — and it DECLARES, inside `namespace <spec_id>_checks`, the five callbacks and one `extern` per snapshot variable, typed by the variable's rank: `extern double <name>;` for `shape_expr: scalar`, `extern std::vector<double> <name>;` for rank 1, and `extern atmofab::Array<double, R> <name>;` for rank R ≥ 2 (`atmofab::Array<T, R>` owns its data: members `std::vector<T> data` and `long extent[R]`, column-major — the element at 0-based `(i1, ..., iR)` is `data[i1 + extent[0] * (i2 + extent[1] * (... + extent[R-2] * iR))]`, the first index fastest, and `extent[k]` is the IR `shape_expr`'s k-th dimension). The host-rendered runner (shown below) includes that header and reads each variable directly as `<spec_id>_checks::<name>`, serializing it through the certified harness right after `case_setup` (into `raw/state_snapshots/initial/<case_id>.json`) and right after `case_run` (into `raw/state_snapshots/<case_id>.json`) — BEFORE any `checks_compute` or `metric_compute` of that case is called. There is no snapshot getter to write: no function of yours computes, filters or returns a snapshot value, and a value your checks compute (a norm, a maximum, a flag, an echoed input) is not a snapshot variable but a metric. So your `<spec_id>_checks.cu` begins with `#include "<spec_id>_checks.cuh"` and DEFINES, inside `namespace <spec_id>_checks { ... }`, one namespace-scope variable per snapshot variable, named EXACTLY as the IR names it (C++ is case-sensitive), with exactly the declared type — `double <name> = 0.0;`, `std::vector<double> <name>;`, `atmofab::Array<double, R> <name>;` — and with external linkage: never `static`, `const`, `constexpr`, `extern` or inside an unnamed namespace (a gate refuses each with `must define every bound state variable`, and a definition of another type is a compile error against the header). `case_setup` sizes every array on EVERY path — including the path that rejects a guard / xfail input, which must still leave every array sized (a defined placeholder such as zeros): a `std::vector` non-empty (`<name>.assign(n, 0.0);`), an `atmofab::Array` with every `extent[k]` set positive and `data` holding exactly their product (`<name>.data.assign(n1 * n2, 0.0); <name>.extent[0] = n1; <name>.extent[1] = n2;`) — because an empty vector, or an array whose `data.size()` is not the product of positive extents, stops the run at the capture point (`bound state <name> is not allocated at capture`). Keep the case's state IN those variables, updated in place by `case_run`, so that what the runner captures after `case_run` is the state the run actually computed.
@@ authoring_rules_1_to_4
(1) Every warning is an error, and a few spellings are refused outright. The `Generate.gate` lint check compiles each `.cu` of `src/` with `nvcc -std=c++17 -Xcompiler=-Wall,-Wextra,-Werror --Werror all-warnings -Xcompiler -fsyntax-only -c` (the rule set declared in `tools/backends/linter/nvcc/lint.py`), so an unused parameter, an unused variable, an unused function, a signed/unsigned comparison, a missing `return` on a path of a non-`void` function, and a device-front-end warning each FAIL the gate. A parameter an interface FIXES but your body never reads — an ABI-fixed `case_id` or `name`, an inert input a published signature pins — keeps its name, and the body's first statement is `(void)<name>;` (that cast is the one binding for it: an arithmetic no-op such as `0 * <name>` is forbidden, and it computes nothing on purpose). A parameter of a helper YOU declared that no body reads is deleted from the signature and from every call site instead, and an unused local is not declared at all. The static check (`tools/backends/language/cuda_cpp/source.py` `preprocessor_violations`) then refuses, by presence anywhere in a leaf source: any preprocessor directive but `#include "<file>"`, `#include <header>` and `#pragma unroll [<n>]` (the last in DEVICE code only — in a host function the host compiler reports it unknown, which fails the lint), so no `#define`, no `#if` / `#ifdef` / `#endif`, no other `#pragma` (a diagnostic pragma above all), no line marker; a `_Pragma` / `__pragma` operator, `##`, and every digraph; an `#include <...>` of anything but a C++17 standard library header or `cuda_runtime.h` (a bundle or host file is included with `"..."`); an identifier starting with `_` and a capital letter, or with `__`, except the CUDA keywords `__global__`, `__device__`, `__host__`, `__shared__`, `__constant__`, `__managed__`, `__restrict__`, `__launch_bounds__`, `__forceinline__`, `__noinline__`, `__syncthreads`, `__syncwarp` and `__func__`; and a backslash at the end of a line, in a comment or a literal included.
(2) Files and translation units. Your bundle's files are `.cu` sources at the TOP level of `src/` (a `.cu` in a subdirectory is refused, and a leaf ships no header): `<spec_id>_model.cu` and `<spec_id>_checks.cu`, plus any helper. Every `.cu` is compiled on its own and the objects are linked, so a source reaches another's declarations only through a HEADER, and every header here is host-rendered and staged beside your sources: `<spec_id>_model.cuh` (your node's published surface, 6a), `<spec_id>_checks.cuh` (the checks ABI and bound state, above), `<dep>_model.cuh` for each dependency, and the harness's header, which is the runner's alone. Include each one you use with `#include "<name>"`, and never `#include` a `.cu` (the code would then be defined in two objects, which fails at link). Your model defines its operations inside `namespace <spec_id>_model { ... }` and your checks inside `namespace <spec_id>_checks { ... }`; a helper kernel or function your model uses and no other file calls goes inside an unnamed namespace (or is `static`), so an unused one is refused by the lint (`#177-D ... declared but never referenced`) instead of passing silently.
(3) Syntax gate (the `Generate.gate` syntax check): `nvcc -std=<toolchain.standard> -Xcompiler -fsyntax-only -c` (with `-arch=<hardware.architecture>` when the target profile names one) over every `.cu` of `src/`, each its own translation unit, staged with the host-rendered headers and the certified sources of your dependency closure — so an include the headers do not resolve, a type your definition gives that differs from the header's declaration (`declaration is incompatible with ...`), and an overload the declaration never reaches are compile errors here or link errors at Build. A published identifier keeps its literal `spec_id` prefix: if `<spec_id>__<op>` would be over-long, report it as a spec-level problem, never shorten it (a depending node calls it by that name).
(4) Dependency-dataflow gate (the `Generate.gate` static check — it inspects `problem` nodes with dependencies, and every function there with an OUTPUT, a parameter it can write through — a non-const reference `T&`, a non-const `atmofab::View<K, R>`, a pointer to non-const — or a returned value): take the incoming state as input parameters (`K`, `const T&`, `atmofab::View<const K, R>`) and the updated state (the IR's `io_contract.outputs` / `algorithm.required_update_paths` variables) as output parameters. What the gate checks is NOT merely that each output is written — it is that what a load-bearing `<dep>_model::<dep>__<op>(...)` call WRITES (the storage handed to that operation's OUTPUT parameters, as its header `<dep>_model.cuh` declares them: a local vector, the vector a view you built was made over, a scalar reference) reaches one of your outputs through an ASSIGNMENT chain — `<dep>_model::<dep>__<op>(u, atmofab::View<double, 1>{flux.data(), {n}}, dt);` then `u_new.data[i] = ... flux[i] ...;` in a loop, or `out = ...;`. The gate follows assignment right-hand sides (and a view back to the storage it was built over), NOT further calls, so routing a dependency result through another call (`copy(flux, u_new)`) does NOT count and FAILS; assigning every output from your own local computation does not satisfy it either — `does not propagate dependency operation outputs to its output dataflow` names the candidates it could not trace. A name assigned before the call is read as an input the call consumes, not a result. The IR's `io_contract.semantic_dependency.required_sources` must likewise reach your outputs.

(6) Public-API surface. (6a) The host renders `<spec_id>_model.cuh` from your IR's `public_api` before the gates run: inside `namespace <spec_id>_model` it declares every module parameter (`using dp = double;` for a `float64` kind, `inline constexpr int <name> = <value>;` for an integer), every published type as a `struct`, every `interfaces` entry as a function-pointer alias, and every published operation's declaration, each lowered from the language-neutral `public_api.signatures` (an `intent(in)` real / integer / logical scalar is `K name`, an `out` / `inout` one `K& name`; a rank-R `intent(in)` array `atmofab::View<const K, R> name`, an `out` / `inout` one `atmofab::View<K, R> name`; an `alloc: true` array or a string / derived array the owning `std::vector<X>` (rank 1) or `atmofab::Array<X, R>` passed `const O&` / `O&`; a string `const std::string&` / `std::string&`; a derived `T` `const T&` / `T&`; a `procedure` argument its alias; a `subroutine` returns `void`, a `function` its result type). A string's `len` and an argument's `dims` are not part of a C++ type — an array argument's bounds are its view's `extent` members at run time. So your `<spec_id>_model.cu` begins with `#include "<spec_id>_model.cuh"` and, inside `namespace <spec_id>_model`, DEFINES each published operation with EXACTLY the declared return type, parameter types and parameter NAMES, in order (the `Generate.gate` static check pins the definition against §5.1 whitespace-insensitively and case-sensitively, and a definition whose types differ from the declaration is another overload it refuses), and declares NONE of the header's declarations again (a second declaration of a type is a compile error, of a module parameter a gate refusal). A published operation is a HOST function: no `__global__`, `__device__` or vendor attribute on it; the device work sits in kernels it launches, whose names do not start with `<spec_id>__`. A `problem` node's `public_api` carries no signatures, so its header declares nothing of the surface and your model DEFINES its operation `<spec_id>__<op>` in `namespace <spec_id>_model` with the parameters the IR's algorithm implies. (6b) Component published surface applies to a `component` node whose IR `public_api.published_operations` is present: that list names your node's published operation NAMES. Emit EXACTLY those names as your `operation` entrypoint `symbol`s AND define EXACTLY those `<spec_id>__<op>` functions in `namespace <spec_id>_model` — a deterministic gate checks BOTH directions (a published name with no matching `<spec_id>__` definition, or an extra `<spec_id>__` function absent from the list, is rejected: name an internal helper without the prefix), so copy each `operation_id` VERBATIM and neither rename, add, nor drop one. The names are not the whole of it: the signature pins every parameter's name, its ORDER, its type and its rank, and a consumer of this component was certified against the ABI it linked, so transcribe the header's declaration exactly rather than choosing an order that reads better.
@@ target_lowering_floor
For a `gpu` target whose `parallel.backend` is `cuda` and whose language is `cuda_cpp`, the default is to run the parallelizable loops on the device: a `__global__` kernel launched with `<<<grid, block>>>`, declared as `"parallelization": {"model": "cuda", ...}` with the loops it covers and the launch shape. The inverse is equally binding — never force a loop onto the device when it is not parallelizable (a carried dependence, a reduction you cannot express correctly). The floor here is deterministic: on a `component` or `problem` node the `Generate.gate` static check FAILS a `gpu`+`cuda`+`cuda_cpp` model source whose `target_lowering_plan.parallelization` does not decline CUDA and that has counted `for` loops and not one kernel (`__global__` or `<<<`, in code — a mention inside a comment or a string is not one). It does NOT run on an `infrastructure` node or when your plan's parallelization `model` explicitly names `none` (or another model) — a plan that names no model gets the target's backend, CUDA. So when no loop can run on the device, declare `"model": "none"` and say why in the plan for the reviewer, who holds that declaration to the loops. State residency is `host` (the output contract above): the state your published operation takes and returns lives in host memory, so the operation copies what a kernel reads to the device, launches, synchronizes, and copies the result back BEFORE it returns (`cudaMalloc` / `cudaMemcpy` / `cudaDeviceSynchronize` / `cudaFree` from `cuda_runtime.h`, with every buffer freed on every path) — nothing a caller holds is a device pointer, and a checks callback never sees one. Whether the kernels you emit cover the loops your plan names is then reviewed by the independent `generate.verify` reviewer, so satisfying the floor alone is not the bar.

@@ checks_behavioral_contract
(A) Author an honest `status` for each id. The runner drives the check ids: it calls `checks_compute(case_id, check_id, status)` once per (case, IR-declared id), passing `check_id` as a string literal taken VERBATIM from `io_contract.diagnostics_contract.checks[].id`. Your source authors NO id — renaming, dropping, or adding one is structurally impossible. Your one job is `status`, a `std::string&` the runner hands you empty: for the check this (case, check_id) evaluates set it to `"pass"` or `"fail"` from this case's real computation, and for a check this case cannot evaluate (a cross-case reduction not yet computable, a check that does not apply) set `status = "na  ";` — the contract's width-4, right-padded not-applicable value, which the harness trims before it writes; the only three values are `"pass"`, `"fail"` and `"na  "`. Branch on `check_id` (an `if` / `else if` chain comparing it with each declared id) and assign `status` on EVERY path, the final `else` included, which assigns `"na  "`.
(B) `metric_compute(case_id, name, val, is_na, reason_na, found)` semantics. The runner calls it once per (case, metric address) exactly as its body shows, with every output freshly initialized. When this case produces the named metric, set `found = true` and `val` to the real computed value; when the value is honestly unavailable for this case set `found = true; is_na = true; reason_na = "<short reason>";`; when this metric does not belong to this case at all set `found = false` (it is then omitted — a sparse metric is normal). A CROSS-CASE reduction (a convergence order, a symmetry residual) is returned as a per-case metric of the FIRST case where it becomes computable — earlier cases return `found = false` for it.
(C) Bound state is shape-valid at both capture points, always. The runner captures the bound namespace-scope variables (`state_bindings` above) right after `case_setup` and right after `case_run`, in the shape the IR snapshot schema fixes (`shape_expr`: `extent[k]` is its k-th dimension, column-major storage). So `case_setup` sizes every bound array to that shape and defines every bound scalar on EVERY path — a case whose `case_setup` set `ok = false` (a rejected guard / xfail case) STILL leaves every bound array sized with a defined placeholder (e.g. zeros of the correct shape); an unsized bound array stops the run. `case_run` updates the state in those same variables in place (never in a private copy the capture cannot see, and never only on the device: copy the result back to the bound host variable before `case_run` returns). A run whose captured state is uniformly zero across every case is rejected by `post_execute` (`trivial placeholder detected`), so the accepted cases must leave the values the run actually computed. Anything written to a bound variable by `checks_compute` / `metric_compute` is invisible to the snapshot — both captures of the case precede the first callback — so those callbacks compute from the state, they do not stage it.
(D) Checks are honest, never pre-judged. `checks_compute` reports `"fail"` for a failing check even in an xfail case; the xfail exclusion and the top-level verdict fold are the harness writer's job. Pre-adjusting here double-counts and breaks the guard-passes-at-top-level rule.
(E) Accumulator ordering. The runner delivers `case_id`s in SORTED order, so a cross-case accumulator may depend only on cases whose `case_id` sorts before the emitting case's (`test_case_set` declaration order is NOT the run order). Key any cross-case accumulation by `case_id` in namespace-scope state of your checks source — in variables OTHER than the bound snapshot variables (an unnamed namespace keeps them internal), which hold the current case's state only.
(F) `case_run(case_id, steps, cells_updated, ok)` counters are the real work done (a non-time-stepping component uses `steps = 1`, `cells_updated` = cells touched); they are summed into `perf.json`.
