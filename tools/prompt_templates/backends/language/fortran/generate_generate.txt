@@ state_binding_convention
What the entry declares is the binding convention your `<spec_id>_checks` module implements: the host-rendered runner (placed in your tree) imports each snapshot variable directly from your module with `use <spec_id>_checks, only: sb_<name> => <name>` and serializes it through the certified harness right after `case_setup` (into `raw/state_snapshots/initial/<case_id>.json`) and right after `case_run` (into `raw/state_snapshots/<case_id>.json`). There is no snapshot getter to write: no procedure of yours returns a snapshot value, and what each one holds is its IR `source`: `operation` (the default) is an argument of your published operation; `record` is what your checks module records of the operation's observable behaviour without judging it (its logical result as -1 / 0 / 1, a count of callback invocations, a state copied at a callback or after an intermediate call); `reported` is the run-wide scalar the operation returns as an output argument, passed through; `reference` is a field your checks module computes from the closed forms the tests document's §2 names. A quantity the end state defines (a norm, a mass, a per-case extremum) is evaluated by the host from the state and is not a snapshot variable. So declare, in the specification part of `<spec_id>_checks`, one module-level `real(dp)` variable per snapshot variable, named EXACTLY as the IR names it (identifiers are case-insensitive, so keep the IR's spelling): a rank-N array as a deferred-shape `real(dp)` array `<name>(:, ...)` with N colons matching the IR's `shape_expr` (the runner tests `allocated(sb_<name>)` before it reads, so it is the kind of array `case_setup` allocates), a `shape_expr: scalar` variable as `real(dp) :: <name>`; list every one of them in a `public ::` statement (a gate reads that statement, and a bare `private` with no `public ::` naming the variable is REJECTED with `must publish every bound state variable`); allocate every array to its declared shape in `case_setup` on EVERY path — including the path that rejects a guard / xfail input, which must still leave every array allocated (a defined placeholder such as zeros), because an unallocated bound array stops the run at the capture point (`bound state <name> is not allocated at capture`); and keep the case's state IN those variables, updated in place by `case_run`, so that what the runner captures after `case_run` is the state the run actually computed.
@@ authoring_rules_1_to_4
(1) Style lint (the `Generate.gate` lint check, fortitude, under the rule set declared in `tools/backends/linter/fortitude/lint.py` — not the linter's own default): keep every source line UNDER 100 columns — 99 is the longest that passes on every supported linter build (on some of them S001 fires at exactly 100, `line length of 100, exceeds maximum 100`; on others only above it, so 99 is the only width that is safe everywhere); split with a trailing `&` continuation; import with an explicit `use <module>, only: <names>` list — never a bare `use` (C121); import from an intrinsic module with the `use, intrinsic :: iso_fortran_env, only: ...` form (C122); PORT011 rejects a number-literal kind on EITHER a real or an integer, so always declare with a named kind from `iso_fortran_env` — `real(dp)` (never `real(8)`), `integer(int64)` (never `integer(8)` or `integer(4)`). HOW you bind that named kind depends on your IR, and getting it wrong is a gate failure rather than a style finding: when your `public_api.module_parameters` declares the name (every `component` and `infrastructure` node — see 6a), bind it with a module-level `integer, parameter ::` DECLARATION of that name to the lowered value, importing the value itself with `use, intrinsic :: iso_fortran_env, only: <value>`, because the `Generate.gate` static check value-pins that declaration — an aliasing `use` of the form `only: <name> => <value>` declares no parameter for it to pin and FAILS. Only when your IR declares NO module parameters (a `problem` node) is that aliasing form the idiom. Either way the named kind comes FROM `iso_fortran_env`, so adding that import is itself subject to the C122 rule above: "fixing" PORT011 with a bare `use iso_fortran_env` is the classic cascade that earns a fresh C122 on the next attempt, so add the `intrinsic` modifier in the same edit; give every module BOTH a default accessibility statement (C131) — a bare `private` in the specification part — AND a `public :: <spec_id>__<op>` line for EVERY name the module must expose, because each half without the other fails a DIFFERENT gate and neither is optional: a bare `private` alone publishes nothing, so it silences C131 and then breaks the next gate, where a consumer staged alongside you (your own checks module, a depending node) fails the `Generate.gate` syntax check with `Symbol '<name>' referenced at (1) not found in module '<spec_id>_model'`; and the `public ::` lines alone leave the module's default accessibility unstated, so it compiles and then fails the `Generate.gate` lint check with fortitude `C131` (`module '<spec_id>_model' missing default accessibility statement`) — a `public :: <names>` list is NOT a default accessibility statement. Emit both, never just one; give every `select case` a `case default` arm (C011), even one that only guards an unreachable value; put the plain line rule (2) requires inside EVERY interface body you write — an `abstract interface` prototype (6a) included — because C002 (`interface-implicit-typing`) fires on a prototype without one, and put `import` before it so the prototype can see the module's kind parameter; a `character(len=*)` dummy is legal ONLY with `intent(in)` — fortitude C072 rejects an assumed-length character dummy declared `intent(out)` or `intent(inout)`, so give every character `intent(out)`/`intent(inout)` dummy an EXPLICIT length.
(2) The `implicit none` form — one line, no decoration. Write a plain `implicit none`. Do NOT write `implicit none (external)` or `implicit none (type, external)`: the build runs `-std=f2008`, where that spec-list is a COMPILE ERROR. Do NOT write an `! allow(...)` comment above it or anywhere else: the lint gate runs `--ignore-allow-comments`, so such a comment suppresses nothing — the finding you meant to silence is reported anyway, and the comment itself may earn a FORT00x finding on top of it. The rule that used to demand one (C003) is not in the gate's rule set. A prior run burned its whole retry budget oscillating between the two wrong spec-list forms; there is now exactly one form, and it is the plain one.
(3) Syntax gate (the `Generate.gate` syntax check — a real `gfortran -fsyntax-only -std=f2008` front-end run over your source staged with its dependency closure, so a `! allow(...)` directive CANNOT suppress anything here — nor at the lint gate, which disables allow comments outright): identifiers must be 63 characters or shorter, and if `<spec_id>_model` or `<spec_id>__<op>` would itself exceed the limit, do NOT abbreviate it — the literal `spec_id` prefix is load-bearing (a depending node is required to `use <spec_id>_model`), so an overlong one is a spec-level problem to report, never a name for you to shorten; `stop` and `error stop` accept only a CONSTANT expression as their code/message — to report a runtime value, `print` it first and then `error stop` with a literal; the gate promotes `-Werror=unused-dummy-argument`, `-Werror=unused-variable` and `-Werror=ampersand`, which has three consequences — (a) a dummy an interface FIXES but your algorithm never consumes (an inert input, an ABI-fixed `name` / `case_id`) stays a live `intent(in)` dummy and is bound immediately after the declarations with the EMPTY block `associate (unused_<name> => <name>); end associate` — an arithmetic no-op such as `0*<name>` is forbidden as the binding, and it computes nothing on purpose, so put no work inside it; an unused LOCAL is deleted rather than bound — and (b) an `intent(out)` dummy your body never sets is this gate's error too (`declared INTENT(OUT) but was not set`), so assign every `intent(out)` you declare; and (c) a CONTINUED CHARACTER LITERAL must resume with a leading `&` (`'a message that is &` / `      &continued'`) — gfortran accepts a resume line without one as an extension, and this gate rejects it; Fortran identifiers are case-INSENSITIVE, so `Flux` and `flux` collide — when a local or dummy would collide with an IR-derived name, keep the IR name verbatim and rename YOUR side.
(4) Dependency-dataflow gate (the `Generate.gate` static check — it inspects `problem` nodes with dependencies, and every subroutine there that declares at least one `intent(out)` dummy): declare the incoming state `intent(in)` and the updated state (the IR's `io_contract.outputs` / `algorithm.required_update_paths` variables) `intent(out)`. What the gate checks is NOT merely that each `intent(out)` gets assigned — it is that the values a load-bearing `call <dep>__<op>(...)` — or a `call <local>(...)` of the local name any `use …, only: <local> => <dep>__<op>` rename of the file binds, in any scope (this dataflow check; the dependency-USE gate, which runs on every node with a component dependency and requires the import and one call per dependency, reads a rename only in the model module's specification part, so place it there) — RETURNS reach an `intent(out)` dummy through an ASSIGNMENT chain: capture the dependency's result in a call output argument, then ASSIGN it (directly or through a chain of assignments) into an `intent(out)` — `call <dep>__<op>(..., unext)` then `h_out = unext(...)`. The gate follows assignment RHS, NOT further calls, so routing a dependency result through another `call` (e.g. a `call copy(tmp, h_out)`) instead of assigning it does NOT count and FAILS. Assigning every `intent(out)` from your own local computation does not satisfy it either: a dependency result consumed only by an `intent(inout)` in-place update reaches no `intent(out)` and FAILS with `does not propagate dependency operation outputs to intent(out) dataflow`. The IR's `io_contract.semantic_dependency.required_sources` must likewise reach the `intent(out)` dataflow.

your `<spec_id>_checks` module must define and publish ALL THREE of the fixed checks ABI names — `case_setup`, `case_run`, `get_time` — each as a SUBROUTINE (a deterministic gate checks the three). Every ABI name is a subroutine by contract, and the runner reaches each with a `call`, so a FUNCTION of any of these names can never satisfy it. The runner's `call` sites below are authoritative for each subroutine's dummy arguments — match them exactly. Rules 1 and 3 bind these bodies in full: every one of the three needs a `public ::` statement (a bare `private` publishes nothing on its own), every dummy the ABI fixes but a body never consumes needs its `associate (unused_<name> => <name>); end associate` binding, and every `intent(out)` needs an assignment. The runner's `use <spec_id>_checks, only:` list also names, as `sb_<name> => <name>`, every snapshot variable it captures: each is a module-level `real(dp)` VARIABLE of your module (see `state_bindings` above), not a procedure — there are NO snapshot getters in this ABI (the former `get_scalar` / `get_r1..get_r4` were retired when capture moved to the host; do not define them). Read the runner for the ABI and the call sites ONLY, and copy NONE of its plumbing: it is the one file allowed to touch the harness's plumbing, and a deterministic gate (the `Generate.gate` static check) rejects your sources for three things it does openly. (a) NEITHER your checks NOR your model source may `use` the harness module in any form (`use harness_...`, `use :: harness_...`, `use, non_intrinsic :: harness_...`) — with ONE exception: when the target's parallel rules in rule (7) name harness operations a physics source may call, a `use <harness>_model, only: <those operations>` naming nothing else is how you reach them. The runner's own `use <harness>_model, only: ...` block and its plumbing calls are the runner's job, never yours; your model publishes `<spec_id>__<op>`, your checks module drives it and holds the state, and the runner alone carries that state to the harness. (b) Your checks module does NO file I/O — no `open(` — because the harness owns every write. (c) Your checks module must not contain the judge-artifact filenames `verdict.json`, `aggregate_verdict.json`, `summary.json`, or `trial_meta.json` ANYWHERE in it, including inside comments and string literals: the scan is a plain substring match over the lowered text, so quoting a filename the seeded tests document happens to name is enough to fail it. @@ authoring_rule_6
(6) Public-API surface. (6a) Neutral-token lowering applies to any node whose IR `public_api` carries `signatures` and `module_parameters` — every `infrastructure` AND every `component` node (a `problem` `public_api` carries neither, so 6a never applies there): the IR's `public_api.signatures` and `public_api.module_parameters` use language-NEUTRAL tokens you must LOWER to Fortran when you emit the `<spec_id>_model`. A string `spec.len` of `deferred`→`character(len=:)` and `assumed`→`character(len=*)` (a fixed width / symbol passes through verbatim); a `module_parameters[]` kind value of `float64`→`real64` and `float32`→`real32` (a number passes through verbatim), declared `integer, parameter :: <name> = <value>` with the LOWERED value, EXACTLY ONCE in the file — a second declaration of that same name anywhere, a local one inside a contained procedure included, is refused, because the published ABI binds to the module-level one and two bindings make which one ambiguous; an import is a binding too, so a further module declared in the model file does not `use <spec_id>_model, only: <name>` (nor import the name from a `<dep>_model`) — it spells the kind or length under a name of its own (`real64` from `iso_fortran_env`, a literal length), while your checks module and any private file import the names from `<spec_id>_model` normally. An argument's RANK lowers two different ways and the signature says which: when it carries `dims`, declare the EXPLICIT shape from those bound expressions verbatim (`dims: ['nx - 1']` → `flux_adv(nx - 1)`); only an argument with a rank and NO `dims` is assumed-shape (`(:)`, one `:` per rank). Rendering an explicit-shape argument as `(:)` is a drift the static check refuses, and it is the likeliest way to lose a first attempt on a node whose signature declares bounds. An argument whose `spec.type` is `procedure` is a dummy PROCEDURE: declare it `procedure(<spec.interface>) :: <name>` — no `intent` (the compiler refuses one on a dummy procedure), no rank, no `dims` — and it names an entry of `public_api.interfaces`, which you lower to ONE `abstract interface` block in the module's specification part holding every entry as a PROTOTYPE: the entry's header and its argument declarations lowered exactly as 6a lowers a published procedure, closed by its own end statement, with `import` and then the plain line rule (2) requires as the first two statements of the body — and nothing else, because the prototype is the shape of the procedure a CALLER passes, so do NOT define a procedure of that name anywhere in your module (the static check refuses a defined prototype, a missing one, and any argument drift between the prototype and its `interfaces` entry, compared as declaration atoms; the two scope statements are not atoms, so they never drift the comparison — write both). The `Generate.gate` static check renders the same lowering and value-pins the Fortran spelling against your source, so emitting a neutral token verbatim (`character(len=deferred)`, `integer, parameter :: dp = float64`) FAILS — the neutral tokens are the IR's carrier, never Fortran source text. (6b) Component published surface applies to a `component` node whose IR `public_api.published_operations` is present: that list names your node's published operation NAMES. Emit EXACTLY those names as your `operation` entrypoint `symbol`s AND publish EXACTLY those `<spec_id>__<op>` subroutines in your `<spec_id>_model` — a deterministic gate checks BOTH directions (a published name with no matching `<spec_id>__` subroutine, or an extra `<spec_id>__` subroutine absent from the list, is rejected), so copy each `operation_id` VERBATIM from `public_api.published_operations` and neither rename, add, nor drop one. The NAMES are not the whole of it: your `public_api.signatures` pins each published operation's full ABI — every argument's name, its ORDER in the list, its type, its rank, its `intent`, and its `dims` where present — and the `Generate.gate` static check compares your emitted source against it, so transcribe each signature exactly (after the 6a lowering) rather than choosing an order that reads better. The HEADER is compared as published, so emit it with NO procedure prefix unless the signature carries one: adding a prefix that marks the operation side-effect-free is a drift the static check refuses even though every argument is correct. A consumer of this component was certified against the ABI it linked; changing one argument's position is a breaking change its `spec_version` has to carry, not something to decide while emitting source.

@@ checks_behavioral_contract
(A) Bound state is shape-valid at both capture points, always. The runner captures the bound module-level variables (`state_bindings` above) right after `case_setup` and right after `case_run`, in the shape the IR snapshot schema fixes (`shape_expr`, with the IR's leading index the outermost). So `case_setup` allocates every bound array to that shape and defines every bound scalar on EVERY path — a rejected guard / xfail case STILL leaves every bound array allocated with a defined placeholder (e.g. zeros of the correct shape); an unallocated bound array stops the run. Assign `ok` on every path like every other `out` argument; the runner does not read it, and what a rejected input leaves in the captures (the `record` the IR declares for it, or the state) is the evidence, not `ok`. `case_run` updates the state in those same variables in place (never in a private copy the capture cannot see). The accepted cases must leave the values the run actually computed: the host's predicates are evaluated over them.
(B) `case_run(case_id, steps, cells_updated, ok)` counters are the real work done (a non-time-stepping component uses `steps=1`, `cells_updated` = cells touched); they are summed into `perf.json`. `case_run` does that work by calling your model's published operation `<spec_id>__<op>` — from `case_run` itself or from a procedure of your checks module that it calls (a procedure in another file, a helper module included, is not followed) (a `use <spec_id>_model, only: name => <spec_id>__<op>` rename is fine), with that `use` in the specification part of your checks module — and outside your model source the operation's name appears ONLY in that `use` statement and right after `call` (a `call` behind a logical `if (...)` is fine): never as a declaration, procedure pointer, interface body, dummy, construct name, generic name, or actual argument; the `Generate.gate` static check refuses a `case_run` from which no published operation is reachable (`case_run reaches no published operation`), so never compute the update inside the checks module.
