# MCP command-log & program-output placement

> **Audience: child agents of the Generate / Build / Validate.execute phases.**
> This is the canonical source for where the MCP side output `command_log.jsonl`, the
> Make `src/Makefile`, and the Validate.execute program output
> (`diagnostics.json` / `perf.json` / `raw/*`) must be placed in `allowed_output_paths`, and
> for the routing / forge-prevention rules the post_generate / post_build / post_execute gates
> enforce. (The pipeline `lineage.json` is NOT a leaf output — the conductor authors it
> host-side; see below.) It lives under `docs/`, which the host reads when it assembles a prompt. The
> substep launch prompt carries a one-line pointer to this doc instead of inlining the full
> content (per-launch token-cost reduction); `record-launch` also defensively auto-injects the
> canonical `command_log.jsonl` / `src/Makefile` paths, so this doc is the
> explanatory canonical, not the sole enforcement path.

## Canonical `allowed_output_paths` placement of `command_log.jsonl`

- **Always include the MCP side output `command_log.jsonl` in `allowed_output_paths`.** The canonical placement per phase is the following:
  - Generate substep: `<pipeline_ref>/source/<source_id>/src/command_log.jsonl` (run_linter / run_syntax_check). **The `run_linter` / `run_syntax_check` side outputs are produced by the conductor's deterministic `generate.gate` substep (its lint and syntax checks)** (no LLM leaf runs either; `run_syntax_check` executes in a throwaway staging dir under `workspace/tmp/` but logs to this same canonical path). Because the `allowed_output_paths` of the `generate.verify` substep does not authorize the `run_linter` side output (`command_log.jsonl`), do not write `run_linter` execution in the verify launch prompt. `generate.verify` launches **no** validator gate: `post_generate` and `validate_workspace_root.py` moved to the conductor's deterministic `generate.gate` substep (its static check) (`generate.verify` maps to `(none)` in the "substep ↔ allowed validator gate correspondence table").
- **The pipeline `lineage.json` is NOT a leaf output — do not list it in any `allowed_output_paths`.** It sits at the pipeline root. No leaf can write it — since Z4 ([issue #171](https://github.com/seiya/atmofab/issues/171)) a leaf holds no tool and the host writes every artifact — and before that the root had to stay non-writable because the Edit/Write tools' atomic temp-sibling+rename would have needed the whole root writable. The conductor authors it host-side (`tools/workflow_conductor.py:_write_lineage`) before `Generate.verify` runs, per `docs/WORKSPACE_LAYOUT.md`. `Generate.verify` only **reads** it (it was in verify's `skill_must_read_refs`; that field is empty on every launch since Z4, and what a pure verify leaf is given is inlined into its `pure_context`).
  - Build step (in-phase, CMake/Meson out-of-source): `<pipeline_ref>/binary/<binary_id>/command_log.jsonl` (compile_project, project_dir=<binary_id>/)
  - Build step (cross-phase, Make in-source for Fortran/C-family): `<pipeline_ref>/source/<source_id>/src/command_log.jsonl` (compile_project, project_dir=<gen>/src/). Bound by the `source_id` of the launch request, and `record-launch` verifies `verification_status=pass` of `source_meta.json`
  - Validate.execute substep (in-phase): `<pipeline_ref>/runs/<run_id>/<node_key_safe>/command_log.jsonl` (run_program etc.)
  - Validate.execute substep (cross-phase quality_check): `<pipeline_ref>/source/<source_id>/src/command_log.jsonl` (`phase_04_validate.md` — with `toolchain.build_system=make` + Fortran/C-family, `run_quality_checks` runs with `project_dir=source/<source_id>/src/`, so the log is side-output into the generate tree). When `source_id` is included in the launch request of the Validate.execute substep, the runtime auto-injects the cross-phase canonical placement and exempts it from the phase-contract check (the `write_roots` half of that exemption went with the capability in [issue #171](https://github.com/seiya/atmofab/issues/171) PR-2). `source_id` is verified by the existence of `<pipeline_ref>/source/<source_id>/source_meta.json`, and passing an unknown source_id (a value not corresponding to an actual generate execution) makes `record-launch` reject with a `ValueError` (prevention of cross-phase write authorization injection by an arbitrary caller).

  In addition, `validate_pipeline_semantics.py` restricts all `command_log_ref` it trusts as MCP tool execution evidence to only the canonical placement:
  - conductor lint evidence `run_linter[].command_log_ref` (`<pipeline_root>/lint_evidence/<source_id>.json`): `<gen_dir>/src/command_log.jsonl`
  - conductor syntax evidence `stages[].command_log_ref` (`<pipeline_root>/syntax_evidence/<source_id>.json`): `<gen_dir>/src/command_log.jsonl`
  - `source_command_ref.<run_program-key>.command_log_ref`: `<execute node_dir>/command_log.jsonl` (sibling of trial_meta)
  - `source_command_ref.run_quality_checks.command_log_ref`: `<pipeline_ref>/generate/<source_source_id>/src/command_log.jsonl` — bound to **only the single gen_id** by `trial_meta.source_source_id`. The canonical placement of a sibling/older generation of the same pipeline is not accepted.

  A placement to a non-canonical path (e.g. `<execute>/raw/forged.jsonl`) is rejected by the post_generate / post_execute gate (prevention of forged MCP execution evidence).

  Furthermore, `_validate_trial_meta` requires that the log record each entry of `source_command_ref` points to include a **recognized MCP `tool_name`** (`run_program` / `run_quality_checks`). `compile_project` is a build-phase tool and is not accepted in the execute trial_meta. A forge record with a missing / unknown `tool_name` is rejected (blocking the path where a tool-specific validator silently skips).

  The cross-phase canonical placement of the Validate.execute substep is bound only to the `source_id` field of the launch request. Including `<pipeline_ref>/generate/<other_gen>/src/...` (a generation different from the request's `source_id`) in `allowed_output_paths` is rejected by the phase contract. On the trial_meta side too, `source_source_id` is a required record, fixing the bind between execute and generate.

  **Single-namespace enforcement:** the `allowed_output_paths` of a generate / build / validate step (Validate.execute substep) must target only a single `<source_id>` / `<binary_id>` / `<run_id>`. Mixing and listing multiple ids under the same pipeline makes `record-launch` reject with a `ValueError` (prevention of granting write authority to the audit log of a sibling/older run). For Generate / Validate.execute, it additionally requires that the request's `source_id` / `run_id` matches the ids of the listed paths (a mismatch is rejected with `does not match request ...id`).

  **Canonical form of `run_id` (Validate execute/judge):** `run_id` is the only one in the id family with a **fixed literal `run_` prefix**, in the form `run_<YYYYMMDD>_<seq3>` (e.g. `run_20260605_001`). The `<slug>_<YYYYMMDD>_<seq3>` form of `ir_id` / `pipeline_id` (slug being hyphen-separated) **must not be reused** — for example `run-rsn-p0_20260605_001` matches the slug form (slug=`run-rsn-p0`) but is not a canonical `run_id`, and the phase contract of `record-launch` rejects it with `outside phase contract`. Even if it passed, the run discovery of Validate `post_execute` recognizes only the literal `run_` layout and silently fails with `no execution artifacts found`. Good example `run_20260605_001` ✓ / bad example `run-rsn-p0_20260605_001` ✗.

  **Quality_check stale-generation countermeasure:** the `source_meta.json` that `trial_meta.source_source_id` points to must have `verification_status=pass`. Referencing a failed / old generation as quality_check evidence is rejected by the post_execute validator. Furthermore, **`record-launch` also** checks `verification_status` and rejects, at launch time, granting write authority to the MCP audit log under a failed generation (prevention of provenance contamination of a failed gen tree).

  **Build lineage bind (specific build):** the launch request of the Validate.execute substep requires recording `source_binary_id`, and the `source_source_id` of `<pipeline>/binary/<source_binary_id>/binary_meta.json` must match the request's `source_id`. A missing `source_binary_id`, an absent binary_meta.json, an unrecorded `source_source_id`, or a value mismatch is rejected by record_launch. This prevents a mixed-build forge (reusing the quality_check evidence of build B while running the binary of build A). The Build step records `source_source_id` in `binary_meta.json` as required (see `phase_03_build.md`).

  **Make-only gate of cross-phase auto-inject:** the cross-phase write authority to `<pipeline>/source/<source_id>/src/command_log.jsonl` is auto-injected only when `toolchain.build_system=make` (a Fortran/C-family in-source build). For an out-of-source toolchain such as CMake/Meson/Ninja, cross-phase is not injected, and the build/execute log allows only the in-phase canonical (`<binary_id>/command_log.jsonl` or `<exec_id>/<node_key_safe>/command_log.jsonl`). `record-launch` reads `toolchain.build_system` of the target profile the request's `pipeline_ref` names (`spec/targets/<target_id>.yaml`, issue #284) and judges automatically.

  **Out-of-source dir override of a Make build (`build_system=make`):** the in-source Make's `compile_project`/`run_quality_checks` runs with `project_dir=<pipeline>/source/<source_id>/src/`, but emitting build artifacts into `src/` would contaminate the certified source tree with build output. Because the generated `src/Makefile` is already parameterized with `OBJDIR ?= .` / `BINDIR ?= .` / `RUNDIR ?= .` (`tools/prompt_templates/pure_generate_generate.txt`, the producer's launch template since Z4 — issue #171 — deleted the phase SKILLs), pass an absolute-path override at launch to route artifacts out of `src/`:
  - **Build step:** `compile_project extra_args=["OBJDIR=<repo_abs>/workspace/tmp/<build_agent_run_id>/build", "BINDIR=<repo_abs>/<pipeline_ref>/binary/<binary_id>/bin"]`. object/`.mod` land in a per-run tmp (`workspace/tmp/<agent_run_id>/` — auto-authorize + auto-clean on success), and the execution binary lands in `binary/<binary_id>/bin/`. Include the execution binary `<pipeline_ref>/binary/<binary_id>/bin/<exe>` in `allowed_output_paths` in **file form** (it contains `/bin/`, so it passes the build phase contract). The `allowed_file_tool_paths` half of this rule described a leaf's `Edit` / `Write` eligibility and is deleted with it ([issue #171](https://github.com/seiya/atmofab/issues/171) PR-2). `binary_meta.json#binary_artifact_ref` points to `binary/<binary_id>/bin/<exe>`.
  - **Validate.execute substep:** `run_quality_checks env={"OBJDIR":"<repo_abs>/workspace/tmp/<exec_agent_run_id>/build", "BINDIR":"<repo_abs>/<pipeline_ref>/binary/<source_binary_id>/bin", "RUNDIR":"<repo_abs>/workspace/tmp/<exec_agent_run_id>/qc_run", "BIN":"<spec_id>_runner", "SPEC":"<repo_abs>/<ir_ref>/spec.ir.yaml", "CASES":"<case_id> <case_id> …"}` (`run_quality_checks` is a fixed command but propagates `env` to make; `SPEC`/`CASES` make the `test`/`check` target invoke the runner as `$(BINDIR)/$(BIN) --cases $(SPEC) $(CASES)` — the same argv `run_program` uses — so the make-test re-run's diagnostics match for the `quality_check` value comparison). `make test` does not relink (it references the existing binary via the Makefile's fail-closed guard), and the `diagnostics.json` / `raw/*` emitted by the `make test` binary re-run are confined under tmp (`workspace/tmp/<exec_agent_run_id>/qc_run`, a separate subdir from `run_program`'s `run/`). Pointing `RUNDIR` at the canonical run node dir would have the make-test binary write clobber the agent-promoted `run_program` copy with provenance-mismatched output, so always point it at tmp (for details see "Validate.execute program output routing — direct binary write forbidden" below). All canonical `.json` is re-authored after both `run_program` and `run_quality_checks` complete (the final step) — by the conductor's own `Validate.execute` body, which is a deterministic in-process substep. The only write to `src/` is the cross-phase audit log.

  **`ok=true` requirement for execute evidence:** the post_execute validator requires `ok=true` in the `run_program` / `run_quality_checks` record. A record with `ok=false` or a missing `ok` is regarded as a failed execution and is not accepted as tool-execution evidence (the same policy as the lint validator).

  **Role binding for source_command_ref:** each entry of `source_command_ref` of the Validate.execute trial_meta declares the `tool_name` field (= `run_program` or `run_quality_checks`), and it must match the `tool_name` of the log record. `compile_project` is build-phase-only and is not accepted in the validate trial_meta. The trial_meta must include at least 1 `tool_name='run_program'` entry (the actual program-execution evidence). A role mismatch (e.g. a compile_project record in the run_program slot) is regarded as a forge and rejected.

  **Run_program log canonical placement:** the log belongs at `<pipeline_ref>/runs/<run_id>/<node_key_safe>/command_log.jsonl`. Set `project_dir` to the execute node dir, or name the path explicitly with `command_log_path`. The `post_execute` validator is what checks it. A pre-call gate in the MCP server (`validate_mcp_build_tool_invocation`) rejected a non-canonical placement at call time until [issue #171](https://github.com/seiya/atmofab/issues/171) PR-2; it existed because the CALLER might be a leaf, and the caller is the conductor. At a remote `execution site` ([issue #293](https://github.com/seiya/atmofab/issues/293)) no server runs the command: the host writes the entry after collecting the job, through the same `_append_command_log`, at the same placement and in the same shape plus a `site` object — `cwd` and `command` name the local directory and the local files the command stands for, and `site.remote_cwd` / `site.remote_command` what the site executed (`docs/ORCHESTRATION.md` §Execution sites).

  **Validate.execute program output (`diagnostics.json`/`perf.json`) routing — direct binary write forbidden:** `command_log.jsonl` is an **MCP-owned audit log** for which a canonical direct write is permitted (the trust model above). On the other hand, `diagnostics.json` / `perf.json` are the **program output of the binary (runner)** that `run_program` runs, and the canonical copy must be the agent-authored evidence with correct `run_program` provenance — not whatever the binary happened to drop. Having the binary write directly to the canonical run dir (`<pipeline_ref>/runs/<run_id>/<node_key_safe>/`) lets the later `run_quality_checks` make-test re-run clobber the `run_program` evidence and mixes `run/` vs `qc_run/` provenance. The launch specifies the following routing:
  - **Point the binary output destination at tmp:** make `run_program`'s `project_dir` (= the binary's cwd) or the case's output destination `allowed_tmp_root` (`workspace/tmp/<exec_agent_run_id>/run/`), and have the binary drop `diagnostics.json` / `perf.json` / raw / logs to **tmp (auto-authorize)**. **`run_quality_checks` (`make test`) likewise**: point `env.RUNDIR` at `workspace/tmp/<exec_agent_run_id>/qc_run` (a separate subdir from run_program's `run/`), and confine the `diagnostics.json` / `raw/*` emitted by the `make test` binary re-run to tmp too. Pointing `RUNDIR` at the canonical run node dir would have the `make test` direct binary write clobber the agent-authored copy already re-authored after `run_program` and produce a provenance mismatch (a typical ordering defect).
  - **Make command_log_path canonical explicit:** because making `project_dir` tmp would drop the MCP log into tmp too, make `<repo_abs>/<pipeline_ref>/runs/<run_id>/<node_key_safe>/command_log.jsonl` explicit with the `command_log_path` argument to satisfy the "Run_program log canonical placement" gate above.
  - **The agent re-authors the canonical `.json` (final step):** the execute body reads the `diagnostics.json` / `perf.json` / `raw/*` of the **`run/` tmp tree** (`workspace/tmp/<exec_agent_run_id>/run/`, = the output of the `run_program` execution with `spec.ir.yaml.case` as arguments), and re-authors the canonical `runs/<run_id>/<node_key_safe>/diagnostics.json` / `perf.json` / `raw/metrics_basis.json` / `raw/state_snapshots/*` itself. **The runner's program output (`diagnostics.json` / `perf.json` / `raw/metrics_basis.json` / `raw/state_snapshots/*`) is always promoted from `run/`, and must not be promoted from `qc_run/` (the output of the make-test re-run)** — if `qc_run/` is promoted, the canonical evidence does not correspond to the required `run_program` invocation (the `spec.ir.yaml.case` and its `command_log`), and `Validate.judge` consumes evidence with a provenance mismatch. The output of `qc_run/` is referenced only for the quality-check comparison (the verdict computation of `quality_check.json`). `trial_meta.json` and `quality_check.json` are **not runner output but metadata the host authors** (`trial_meta.json` is composed from the MCP command refs / `source_source_id` / `source_command_ref`, and `quality_check.json` from the comparison result. The runner must not output either file directly), and are written directly rather than promoted from tmp. **The re-author is the final step after both `run_program` and `run_quality_checks` complete**, ensuring an order in which a subsequent binary re-run does not overwrite the agent-authored copy (the ordering of authoring after run_program then running make test in the canonical RUNDIR is an overwrite defect).
  - **raw `.json`, non-`.json` and the logs are re-authored the same way** — the `.json` under `raw/` (`metrics_basis.json` / `state_snapshots/*.json`), the non-`.json` files under `raw/`, `stdout.log` and `stderr.log`. (The `Write`-tool / `allowed_file_tool_paths` protocol this bullet stated was the agentic leaf's and is deleted with it.)

  **MCP audit log trust model — what it rests on NOW.** `validate_pipeline_semantics.py` reads these logs and trusts their records (`tool_name`, `ok`, `command`) as evidence that a tool actually ran, so the question is who can write one. Until Z4 ([issue #171](https://github.com/seiya/atmofab/issues/171)) the answer was a stack of hook policies refusing every other route from a leaf that held `Edit` / `Write` and a shell. **No leaf holds any of them now**, and a leaf's sandbox does not hold the checkout at all (an empty tmpfs at `repo_root`, [issue #227](https://github.com/seiya/atmofab/issues/227)), so the only writer that can reach the path is the MCP server, called from the conductor's own process. That is a structural closure rather than a pattern-matching one — but it is still not a cryptographic proof: a defect in the HOST could write a record no tool produced, and the server keeps no signed ledger the validator could cross-reference. That extension stays future work.

  **Make build's `src/Makefile`:** for a `make` ∧ `fortran` node (leaf **or** with dependencies) the conductor authors `src/Makefile` host-side (`_resolved_makefile_host_authored`). A `record-launch` auto-inject of that path into a leaf's `allowed_output_paths` / `allowed_file_tool_paths` covered the other make families (c/cpp/mixed), where the extension-less name fell outside the directory allowlist's source-extension set; it is deleted with the leaf's write authority ([issue #171](https://github.com/seiya/atmofab/issues/171) PR-2), and the `Compile.static` toolchain gate rejects a non-`fortran` `language` on every non-`infrastructure` node anyway, so no physics node ever reached it.

  `_allowed_output_paths_for_launch()` of `tools/orchestration_runtime.py` still injects the canonical log placements into a DETERMINISTIC substep's declared outputs, so `determine_substep_status` and the `post_execute` validator agree with what the server actually wrote. What that declaration no longer is, is an authority: nothing enforces it against the conductor's own process. The list of write paths this bullet used to enumerate as REFUSED — the `Edit` / `Write` tools, Bash redirects, `tee`, `sed -i`, `cp` / `mv` / `install` / `ln` / `touch` / `truncate` / `dd` — was refused by hook policies over a leaf that held those tools, and no leaf holds any of them
