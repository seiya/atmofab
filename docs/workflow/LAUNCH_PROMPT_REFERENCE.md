# Launch Prompt Reference

Human-facing reference for the conductor's launch-prompt render path. The **machine-parsed
templates** live as plain-text files under [`tools/prompt_templates/`](../../tools/prompt_templates/),
one `pure_*.txt` per `(step, substep)` and bundle shape — this document holds the non-parsed
reference material around them.

The render path: the conductor supplies the launch-request parameters; `record-launch` renders the
prompt from `tools/prompt_templates/` (substituting the `<...>` placeholders and inlining the host-
resolved `pure_context` documents) and returns the rendered `launch_prompt_text`, which the conductor
passes to the leaf on its stdin. `tools/workflow_conductor.py:build_launch_request` reproduces the
same payload field-for-field.

**Two sections stood here until Z4 ([issue #171](https://github.com/seiya/atmofab/issues/171)) and are
deleted with the agentic leaf.** The *phase ↔ skill correspondence table* mapped each `(step, substep)`
to the `SKILL` its leaf was told to read: no leaf reads a `SKILL`, and the five phase `SKILL`s are
deleted. The *substep ↔ allowed validator gate correspondence table* canonicalized which
`validate_pipeline_semantics --stage` invocation a launch prompt body could state, enforced by a scan
of the rendered text: a pure leaf holds no shell, states no gate call, and invokes nothing — every
gate is run by the conductor in its own process, and `docs/workflow/phases/phase_0{1,2,4}_*.md` are
canonical for which deterministic substep runs which stage. The *usage contract of `allowed_tmp_root`*
went the same way: a pure leaf writes no file at all, temporary or otherwise.

#### Z2 pure-function leaf launch prompt (`leaf_mode = "pure"`)

A pure-function leaf (`docs/design/zero_base_architecture.md` Z2, canonical `tools/pure_leaf.py`) is a host-mediated closed-context turn: the host inlines all required context, and the model returns **exactly one JSON document** (the IR document `{ir, last_fail_reason}` for `compile.generate`, a `CodegenBundle` for `generate.generate`, a verify verdict for `compile.verify` and `generate.verify`, a semantic review `{decision, findings, notes}` for `validate.judge`) which the host validates and writes itself. Claude uses a `claude -p` turn with tools disabled. Codex uses `codex exec --output-schema` in a read-only sandbox: a sandboxed structured-output approximation, not strict tool-free isolation. A pure launch is confined to the migrated substeps — the KEYS of `PURE_CONTEXT_REQUIRED_KEYS`, which is the single source and today holds `(compile, generate)`, `(compile, verify)`, `(generate, generate)`, `(generate, verify)`, `(validate, judge)` and the four `(<phase>, diagnose)` pairs of the escalate diagnostician (whose one document is a routing directive, not an artifact the host writes); any other `(step, substep)` with `leaf_mode=pure` is rejected at `_validate_launch_request_payload`, whose message is spelled from that table rather than restating the set.

Because the pure leaf has **no workflow gate and no repository write authority**, its launch prompt has no skill section, no gate runbook, and no write-authorization / `capability_token` constraint lines — none of those apply. It directs the model not to use filesystem or shell tools, while Codex's read-only sandbox remains an approximation rather than an absence-of-tools guarantee. Its identity is the reduced marker set below, and its whole first line is the sentinel `Pure-function leaf turn (host-mediated)` (the module constant `pure_leaf.PURE_PROMPT_SENTINEL`, imported — not copy-pasted — by `orchestration_runtime.py` and `validate_pipeline_semantics.py`; every `tools/prompt_templates/pure_*.txt` template pins its line 0 against it — six of them since the escalate diagnostician joined, and the count is derived by the test rather than restated here):

| pure launch marker | note |
| --- | --- |
| `Pure-function leaf turn (host-mediated)` | sentinel; MUST be line 0 (anchored `startswith`). A non-pure request whose prompt opens with it — or a pure request whose prompt does not — is rejected. |
| `Target node_key:` / `Target step:` / `Target substep:` | identity (both migrated substeps carry a substep). |
| `orchestration_id:` / `agent_run_id:` | ids. |
| `prompt_contract_version:` | must equal `pure_leaf.PURE_PROMPT_CONTRACT_VERSION` exactly (a contract change is an observable event). |

The pure launch prompt's **static prefix** (byte-stable, ahead of every variable document) is the persona sentinel, the output contract (the `CodegenBundle` schema), and — for `(generate, generate)` — the `Authoring rules` paragraph distilling the deterministic-gate closure the producer must satisfy — plus, since `pure-16`, the one obligation that is only PARTLY deterministic (rule 7, `impl_defaults` reflection: a gate-enforced zero-`!$omp` floor with a `Generate.verify` G6 band above it) (`docs/workflow/phases/phase_02_generate.md` §Generate-executor). A cold-fallback repair lifts the `Output contract` paragraph plus every paragraph named in `orchestration_runtime.PURE_REPAIR_STATIC_PARAGRAPH_PREFIXES` verbatim from the launch template rather than duplicating them, so a paragraph must carry no interior blank line (the lift splits on `\n\n`). That list is the enumeration to maintain — and it is a list precisely because the `**Host-rendered runner` paragraph (the checks ABI + the `Generate.gate` static-check prohibitions) was added to the template and silently NOT lifted, leaving a cold repair to re-author the bundle with no statement of the rules. The `**Checks-module behavioral contract` paragraph (the §2/§3 per-id `status` honesty + metric/getter/accumulator semantics, distilled for the closed-context producer) is lifted for the same reason: a cold-repaired bundle must still satisfy the `post_execute` diagnostics-contract fold (`_validate_diagnostics_contract_output`). (Since `pure-8` the runner supplies each check id per-call, so id coverage is structural — the former `codegen_bundle.m3c_checks_ids_violation` acceptance gate was removed.) Since `pure-24` the list carries the VERIFY template's `Review checklist` and `**Checks-module contract (` paragraphs for the same reason on the reviewer side: issue #142 put the inlined contract into `pure_context`, which a cold repair re-inlines automatically, while the text that governs it — the checklist's statement that the deterministic gate already settled the ABI and that the reviewer must not re-check it, and the contract's scope bound — was lifted by nothing. Since `pure-25` it carries that template's `**Severity rubric (` paragraph on the same ground (issue #143): the inlined rubric arrives in a cold repair through `pure_context`, and the label that makes it the rule for `issue_severity` was lifted by nothing. Neither runner-region paragraph is part of the byte-stable static prefix: they sit after `<ir_document>` / `<tests_document>` because the first introduces `<runner_document>`; the lift drops any trailing slot line, since `<pure_context>` re-inlines the runner below it anyway. The conductor-injected certified sibling **exemplar** (R5) renders inside its own `--- BEGIN EXEMPLAR ---` … `--- END EXEMPLAR ---` fence, which the gate-allowlist carve-out strips along with the data fences below; it is attached only on a turn that renders the launch template (the repair template has no exemplar slot). Since issue #209 a cold-fallback repair can also be the FIRST turn of a PRODUCER substep run — an outer `reuse` reopen on a provider without warm resume (`openai_compatible` / `anthropic_api`), or one whose session is gone (a GC'd claude transcript, a rotated codex home). There `<findings>` is the reopening gate's excerpt and `<prior_document>` is the failed attempt's own artifact, read back by the host from the directory that attempt's launch record names (`<ir_ref>/spec.ir.yaml` re-serialized as `{ir, last_fail_reason}`, or `<source_dir>/codegen_bundle.json` verbatim); it is empty on the routes that reopen without an accepted artifact (bundle- or IR-document repair exhaustion). A reopen carrying no findings excerpt, or one whose repair target the launch validator would refuse (`"none"`), still renders the launch template. Since `pure-42` the repair template also carries a slot of its own ahead of `<findings>`, **`<repair_scope>`**, rendered only for the verdict-bearing pairs (`orchestration_runtime.PURE_VERDICT_PAIRS`: the two `verify` pairs and `validate.judge`) and empty for a producer. For those three every repairable class is a violation of the verdict document's SHAPE, and the schema's joint invariant couples the conclusion to the evidence — so flipping the conclusion is a one-token correction of a shape violation, and an accepted one. The paragraph states the invariant in BOTH directions, because either half can be the one that is wrong and only the leaf knows which: supply the evidence a `fail` is missing, or record the `fail` the evidence already listed calls for; what is forbidden is the dishonest edit — dropping a finding that was made, or recording a conclusion that was not reached. It is a SLOT and not a shared sentence because a producer's repair legitimately changes what its document says: `pure-41` tried one persona-neutral sentence, and it was measured to make two reviewer routes worse than saying nothing (it froze `severity`, which the correct repair of a `fail` with `issue_severity: "none"` must change, and it forbade `pass -> fail`, which is the only correct repair of a `pass` carrying findings).

The host-resolved `pure_context` documents each `(step, substep)` requires are the single source `PURE_CONTEXT_REQUIRED_KEYS` (`orchestration_runtime.py`); a cold launch missing one is rejected at `_validate_launch_request_payload`. For `(compile, generate)` they are `controlled_spec_document`, `tests_document`, `deps_document`, `profile_spec_document` (the `controlled_spec.md` of each `profile` this node ADOPTS — which profiles, and at which version, is read from the sidecar's `profiles` record, not re-derived from `deps.yaml` — or the host's fixed sentence when it adopts none), `dependency_graph_document` (the host-derived closure, which the leaf READS and must not copy into the IR; since issue #175 it also carries the `profiles` record, which is where the leaf's `direct_deps` and its per-case `profile_selection` both come from), `phase_contract_document` (`docs/workflow/phases/phase_01_compile.md` in full), `ir_algorithm_example_document` and `ir_algorithm_2d_example_document` (the two `docs/examples/spec_ir_algorithm*` reference forms), `impl_defaults_schema_document` (`spec/schema/ir/impl_defaults.schema.json`, the canonical parallelization knob names), `checks_module_contract_document` (the same §1-4 slice the generate reviewer gets), and `toolchain_document` — a host-composed JSON list of the `(language, build_system)` pairs the backend registry says this repository can build and render for, which exists so the template can direct the producer's toolchain choice WITHOUT naming a target-stack technology in a `neutral core` file (`docs/BACKEND_BOUNDARY.md`). For `(compile, verify)` they are `controlled_spec_document`, `tests_document`, `deps_document`, `ir_document` (the IR under review), `dependency_surface_document` (`<ir_ref>/dependency_surface.json` verbatim — the producer receives the same facts through the rendered `<dependency_facts>` block instead), `phase_contract_document`, and the two example documents. The compile reviewer takes its severity rubric from the phase document it already carries in full, so it has no separate rubric slice. For `(generate, generate)` on the DEFAULT (m3c) shape they are `harness_capabilities`, `target_profile`, `ir_document`, `tests_document`, and `runner_document` — the last being the host-rendered `<spec_id>_runner.f90` inlined verbatim, because it is the consumer of the checks-module ABI the producer must author against and a closed-context leaf is not expected to read `docs/workflow/CHECKS_MODULE_CONTRACT.md` (`docs/design/deterministic_followups.md`, Z2 defect D). The producer does NOT carry `controlled_spec_document`: the `pure-5` interim carve-out that inlined it (to close a producer-blind / checker-sighted asymmetry against a thin IR roll) was **removed at `pure-10`** once the `compile` side began guaranteeing IR self-sufficiency (the strengthened lowering rule + the deterministic `Compile.static` local-op lowering presence floor; `docs/workflow/phases/phase_02_generate.md` §Generate-executor, [issue #181](https://github.com/seiya/atmofab/issues/181#issuecomment-5559625628)). `(generate, verify)` carries `controlled_spec_document` by design (the reviewer verifies against it) but NOT `runner_document`: the deterministic layer owns the ABI and the reviewer is semantics-only, judging the bundle against the distilled **G1-G7** review checklist in its static prefix. Since `pure-24` it also carries `checks_module_contract_document` — the `## 1.`-`## 4.` slice of `docs/workflow/CHECKS_MODULE_CONTRACT.md` (`workflow_conductor._checks_contract_abi_sections`), which the template's scope paragraph makes the authority for what the runner does with each callback's result; §5 is excluded because it is the deterministic legality/gate section the reviewer is told not to re-check (issue #142). Unlike the four node artifacts, an unreadable or unsliceable contract does not degrade to `""` — it fails the substep closed before any leaf is spawned, as `pure_checks_contract_document_missing` (absent or undecodable) or `pure_checks_contract_document_unsliceable` (readable, but an anchor is gone), recovered by the caller into a `pure_context_assembly_failed` transport outcome. Both names reach the operator only through the run log and that outcome, so they are spelled here: the repair is to restore the document and `--resume`. Since `pure-25` it also carries `severity_rubric_document` — the `#### Severity of a finding` subsection of `docs/workflow/phases/phase_02_generate.md` §2-2 (`workflow_conductor._generate_verify_severity_rubric_section`), which is the sole rule for the `issue_severity` a verdict carries; G1-G7 are excluded because the template already states them (issue #143). It has the same non-degrading disposition and the same two operator-facing names in the same shape, `pure_severity_rubric_document_missing` (absent or undecodable; restore the document and `--resume`) and `pure_severity_rubric_document_unsliceable` — whose causes are NOT the checks pair's "an anchor is gone": the rubric must be the LAST subsection of §2-2, so it also fires when both anchors are intact and a subsection was added after the rubric, or when the `## On-failure behavior` heading line changed at all — the terminator is matched exactly, so an appended word is a rename. The raised message names which of the two it found; the repair is to restore the document's shape and `--resume`. The rubric's text was narrowed at `pure-26` and again at `pure-27`. For each `(<phase>, diagnose)` pair the single key is `diagnosis_document` — the host's JSON composition of the failed node and phase, the failed substeps' `agent_run_id`s, the workflow mode, and the CONTENT of the failure artifacts it could read, each artifact budgeted individually (`_bounded_context_json`) so the failed phase's own evidence gets the large slices and none is dropped. The diagnostician reads nothing else: its persona, its directive schema and its rollback / severity criteria are the template's static body. For `(validate, judge)` there are eleven keys: `tests_document` and `io_contract_document` (the judge's two canonical sources — the IR's `io_contract` section alone, `yaml.safe_dump`ed, never the 52 KB IR in full), `runner_output_contract_document` (the §1 + §3 slice of `docs/workflow/RUNNER_OUTPUT_CONTRACT.md` — `workflow_conductor._runner_output_contract_sections`; §2, §4 and §5 are excluded because they are `Validate.execute`'s deliverable gate and the deterministic layer), the run's own `diagnostics_document`, `verdict_document`, `perf_document`, `trial_meta_document` and `quality_check_document`, the `binary_meta_document` / `source_meta_document` the agentic judge force-read, and `raw_evidence_excerpt_document` — the host-computed bounded summary of `raw/` (`tools/raw_evidence_excerpt.py`), which is the judge's whole view of the primary evidence because `raw/` is 13 MB of float arrays. Canonical for what that excerpt contains: `docs/workflow/phases/phase_04_validate.md` §4-2-1. EVERY judge document raises rather than degrading to `""`, and the REASON is not the one an earlier version of this paragraph gave: a blank value does NOT reach the leaf, because `_validate_pure_launch_request_payload` counts a whitespace-only `pure_context` value as missing and raises. What degrading buys is a refusal one frame too LATE — a `ValueError` out of `record_launch`, escaping the reviewer loop's named `pure_context_assembly_failed` branch and aborting the conductor instead, which is issue #168's recorded shape. Raising at assembly time keeps the named outcome. The names, spelled here for the same reason the `compile.verify` pair's are (they reach an operator only through the run log and that outcome): `pure_<key>_missing` for each of the nine file-backed documents; `pure_io_contract_document_missing` for a DIFFERENT condition — the IR is readable but declares no `io_contract`; `pure_io_contract_document_unreadable` when it does not parse as YAML; and `pure_runner_output_contract_document_unsliceable` when the contract is readable but a section anchor is gone. The repair for all of them is to restore the artifact and `--resume`. A cold-fallback repair re-inlines every `pure_context` key automatically.

Since `pure-37` a launch request may also carry a **`pure_shape`** (issue #169), which selects both the template and the required-key set: the vocabulary is `orchestration_runtime.PURE_LAUNCH_SHAPES` and the sets are `PURE_CONTEXT_REQUIRED_KEYS_BY_SHAPE`, keyed by `(step, substep, shape)`, with the tables above serving a request that declares none. A value outside the vocabulary, a non-string or blank one, and a shape declared on a pair the by-shape table does not carry are each refused at `_validate_pure_launch_request_payload` rather than falling back to the default — the shape decides which admissibility rules the returned document is judged against. Today the one non-default shape is `harness`, an `infrastructure` self-test whose leaf authors the executable entry itself. Its `(generate, generate)` keys are `harness_capabilities`, `target_profile`, `ir_document`, `tests_document`, `runner_output_contract_document` (`docs/workflow/RUNNER_OUTPUT_CONTRACT.md` in FULL — a leaf that writes the program reads every section, where the judge that only reads its output is shown two) `gate_guards_document` (§5 of `docs/workflow/CHECKS_MODULE_CONTRACT.md`, `workflow_conductor._checks_contract_gate_guards_section`) and `lint_rules_document` — the static lint check's DECLARED RULE SET, by code and rule name, rendered by the linter BACKEND the node's language resolves to (`lint_rules_document` on the module `capability_module("linter", <preset>, "lint")` returns, the preset from the same `_LINT_PRESET_FOR_LANGUAGE` table `_gate_lint_check` uses). It comes from the backend and not from the template because the rule set is that backend's knowledge and a `neutral core` template may not carry it (`docs/BACKEND_BOUNDARY.md`); §5 states the obligations whose IDIOM this repository fixes, and measurement showed it states only three of the seven codes this leaf must satisfy, so the two are inlined together and rule (11) holds the leaf to both. Its failures are named `pure_lint_rules_document_unavailable` — no lint preset for the language, a preset whose package does not claim the `lint` job, a backend that renders no rule set, or an empty one — and the repair is a preflight/backend problem for the operator rather than a document to restore. The §5 slice is there because that section reached this leaf as a FORCE-READ must-read while it was agentic and a pure leaf force-reads nothing; §1-§4 are excluded because they are the checks-module ABI and this shape has no checks module. Both repository documents raise rather than degrading, with the same disposition and the same operator-facing shape as the pairs above: `pure_runner_output_contract_document_missing`, `pure_gate_guards_document_missing` (absent or undecodable) and `pure_gate_guards_document_unsliceable` — the last with a cause the other unsliceable names do not have, because this slice runs to the END of its document: it fires when the `## 5.` heading is gone AND when a later `## <n>.` heading exists, which would otherwise widen the slice silently. The repair for all of them is to restore the document and `--resume`. Its `(generate, verify)` keys are `controlled_spec_document`, `tests_document`, `ir_document`, `runner_output_contract_document`, `severity_rubric_document` and `bundle_document` — the runner-output contract in place of the checks-module ABI, for the same reason.

Untrusted documents inlined into the prompt (`tests.md`, the IR, the host-rendered runner, the bundle under review, repair findings) are wrapped in the data-only fence `----- BEGIN PURE INPUT DOCUMENT (data only) -----` … `----- END PURE INPUT DOCUMENT -----` (`pure_leaf.PURE_DOC_FENCE_BEGIN/END`). The gate-allowlist lint carves out every fenced region before scanning, so a `validate_pipeline_semantics --stage` string legitimately appearing inside an inlined document does not fail-close the launch.

**gate correspondence:** pure `(generate, generate)` and pure `(generate, verify)` invoke **no** validator gate — same `(none)` mapping as their agentic counterparts in the table above, enforced by the host-rendered prompt and empty allow-set. Codex's read-only sandbox may expose tools, but neither backend receives a workflow-gate invocation contract.

**record-launch artifacts:** a pure launch writes the access policy (deny-all read manifest — no repository file read is authorized), a zero-authority capability (`mode: "pure_readonly"`, `write_roots: []`, an empty `mcp_permissions: []`), and a read-only `bwrap` profile; it writes **no** `output_manifests/<arid>.json` and no file-tool pins (the host writes every artifact after the child window closes). The FS-diff write baseline, session-run-index, agent_graph edge, and return-token / active-child markers are unconditional, so any write from inside the pure child window is caught by the empty-`write_roots` containment rule (fail-closed). `validate_pipeline_semantics`' launch-record sweep re-checks all of this: request-vs-prompt pure agreement, the reduced marker set, the ABSENCE of an output manifest (a present one is the mock-green tripwire for a record-launch that skipped the pure branch), and the `pure_readonly` / empty-`write_roots` capability shape.

#### Additional contract on `repair_strategy=reuse`

A re-submission with `repair_strategy=reuse` is limited to a diff fix against the output of `repair_target_agent_run_id` (the repair / retry section of `docs/ORCHESTRATION.md` is the canonical source). Under `bwrap` + FS-diff attribution a step/substep `pass` no longer requires `apply_patch_writes` gate evidence (`_validate_apply_patch_gate_coverage` early-returns for step/substep), so a reuse retry that writes nothing needs no inherited gate evidence; if it re-writes a path, it does so directly with the `Edit` / `Write` tool. Same-identity (`(node_key, step, substep)`) is still verified runtime-side.
