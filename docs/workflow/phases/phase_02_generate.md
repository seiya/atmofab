# Phase 2: Generate

## Overview
The phase that, with `spec.ir.yaml` as the canonical input, generates the source code of the target `node`'s `model` (physics computation) and `runner` (input/output / execution coordination). `Generate.generate` reads only `spec.ir.yaml` (§2-1); `Generate.verify` also reads `controlled_spec.md` (§2-2).

## Generate-executor (`pure`)
Since `M-F` the `generate-executor` is no longer selectable (`docs/GLOSSARY.md`): legacy generate execution was removed and `pure` is the only executor. The value is still recorded in `orchestration_meta.json#invocation.generate_executor` (always `pure`) as provenance, and a resume whose recorded executor is not `pure` (a `legacy` record, or the field absent) is rejected fail-closed (`generate_executor_legacy_removed`). The authoring rules of §2-1 and the verification items of §2-2 are properties of the emitted source and hold whether the leaf runs pure or as an agentic residual; only the transport and the write path differ.
- Residual (agentic) path: a node the pure producer cannot express — a node whose runner/Makefile are not host-rendered — runs the shared **agentic** leaves with tools enabled and the forced document reads described below. `Generate.generate` writes `source/<source_id>/src/` directly; `Generate.verify` re-authors `source_meta.json`. This is a recorded residual of the migration scope (its invocation still stamps `generate_executor=pure` and it is not rejected on resume), not a selectable executor.
- `pure` (`Z2`, an `M3c` node on either supported backend): the `Generate.generate` leaf is a `pure-function leaf` — it reads no `SKILL` and no injected must-read (the host inlines the target IR, `<dependency_facts>`, exemplar, target profile, harness capability ABI, and the host-rendered runner into the launch prompt) and returns exactly one `CodegenBundle`. Claude uses strict tool-free isolation; Codex uses the sandboxed structured-output approximation with `codex exec --output-schema` and the read-only sandbox. Per §2-1 the producer does **not** read `controlled_spec.md`: `spec.ir.yaml` is the sole carrier of the algorithm it implements. A `pure-5` interim carve-out once inlined `controlled_spec.md` into the producer context to close a producer-blind / checker-sighted asymmetry against a thin `compile` roll (a step lowered to a name + I/O shape with no mathematical definition, which a tool-less `spec/`-blind leaf then had no path to, while the reviewer WAS shown it — structurally unwinnable when the IR is thin). It was **removed at `pure-10`** once the `compile`-side IR self-sufficiency guarantees landed: the strengthened lowering rule (`skills/workflow-compile-generate/SKILL.md`) plus the deterministic `Compile.static` local-op lowering **presence floor** (`validate_pipeline_semantics._validate_local_operation_lowering`, which de-certifies the zero-signal thin-IR shape) and the `Compile.verify` V2 finding (which covers the present-but-incomplete band above the floor). (`pure-6` through `pure-9` all kept the carve-out live — `pure-8` added the runner-driven per-id checks ABI and its own removal was reverted pending the verification run; `pure-9` was an unrelated distillation.) The pure `Generate.verify` reviewer still reads `controlled_spec.md` by design (§2-2) — it verifies the source against it. Because it reads no `SKILL`, the authoring rules of §2-1 that a deterministic gate (the `Generate.gate` lint / syntax / static checks) fails the source on are distilled into the launch prompt's static prefix as an `Authoring rules` paragraph; a cold-fallback repair turn re-states them (a warm resume already holds them). Rules the inlined IR or harness capability ABI already carries are deliberately not restated there. The one rule stated there WITHOUT a gate behind all of it is the `impl_defaults` reflection obligation (rule 7, issue #22): its zero-`!$omp` slice is gate-enforced (the presence floor under §2-1's static check) while the band above that floor is `Generate.verify` G6's. It earns its place because the producer was previously punished for a rule only the reviewer had ever been told. The fixed checks-module ABI (`docs/workflow/CHECKS_MODULE_CONTRACT.md`) reaches the `pure` producer two ways, because it is two facts. WHICH names are required is fixed at the full ten for every `M3c` node (the checks ABI the language backend publishes, read through `tools/host_render.checks_public_names` — the same set the `Generate.gate` static check enforces — never the subset a given node's runner imports), so the prompt states them; what each imported callback's dummy arguments must be is carried by inlining the host-rendered `<spec_id>_runner.f90` verbatim, whose `call` sites are their authority. The host acceptance gate rejects a bundle whose `<spec_id>_checks` module does not publish all ten as subroutines, making a mis-authored ABI a bounded repair rather than a `Generate.gate` static-check / syntax-check failure that reopens the phase. The **checks-module §2/§3 behavioral contract** ([docs/workflow/CHECKS_MODULE_CONTRACT.md](../CHECKS_MODULE_CONTRACT.md)) — author an honest `status` for every `io_contract.diagnostics_contract.checks[].id` (using `'na  '` for a check a case does not evaluate), the `metric_compute` / snapshot-getter / cross-case-accumulator semantics — is likewise unreadable by the pure producer, so it is distilled into the launch prompt as the "Checks-module behavioral contract" paragraph. Since `pure-8` the host-rendered runner supplies each check id to `checks_compute` per (case, IR id), so id coverage is **structural** — a dropped or renamed id is impossible, the distilled paragraph governs only per-id `status` honesty, and `post_execute` (`_validate_diagnostics_contract_output`) stays the backstop; the phase-late Z2 defect-E class the former `codegen_bundle.m3c_checks_ids_violation` acceptance gate guarded is now closed at the ABI (that gate and its literal extractor were removed). The pure `Generate.verify` reviewer's static prefix carries the §2-2 **G1-G7** review checklist distilled from this phase doc (the deterministic lint/syntax/static gates already ran before it, so its checklist covers only the code-vs-IR semantics, G5 explicitly including the per-id `status` honesty and `verdict.fields` coverage of the diagnostics contract). Since `pure-24` the reviewer additionally receives §1-4 of [docs/workflow/CHECKS_MODULE_CONTRACT.md](../CHECKS_MODULE_CONTRACT.md) as a data-fenced document (`checks_module_contract_document`), because before it the reviewer failed a contract-conforming `case_setup` on its own guess about what the host-rendered runner does with `ok=.false.` — the issue #22 asymmetry with the roles swapped (issue #142). **The document OVERRULES; it does not narrow.** It settles one kind of claim — what the runner does with the RESULT a callback returns (an `ok` flag, a `found` flag, a `status`, a metric value) — so a finding whose justification the contract CONTRADICTS is dropped. Its SILENCE settles nothing: where the contract says nothing, the obligation is judged in the model and checks themselves, and every G1-G7 item stays fully in scope. This binds the agentic `Generate.verify` leaf too, which reads [CHECKS_MODULE_CONTRACT.md](../CHECKS_MODULE_CONTRACT.md) as a force-read must-read rather than through the pure template. Since `pure-25` the reviewer additionally receives the `#### Severity of a finding` subsection of §2-2 as a data-fenced document (`severity_rubric_document`), narrowed at `pure-26` and again at `pure-27`; that subsection is the sole rule for the `issue_severity` a finding takes (issue #143). The agentic leaf is NOT handed it — no phase document is a `Generate` leaf must-read (`docs/AGENT_SKILLS.md`) — it reaches the rubric through the pointer in `skills/workflow-generate-verify/SKILL.md`. After the leaf terminates, the host validates the bundle (`validate_bundle`, the post-generate gate), writes the declared files under `source/<source_id>/src/`, assembles the runner/Makefile build graph, and authors `source_meta.json`. `Generate.verify` is likewise a `pure-function leaf` reviewing the bundle and assembled source in an independent conversation; it returns a verify verdict the host projects onto `source_meta.json`. A pure leaf holds no repository write authority (`write_roots` empty); its terminal record carries `output_refs == []` and the deliverable is vouched by the host-written artifact's on-disk existence (`docs/ORCHESTRATION.md`). Under `pure` the source directory additionally holds `codegen_bundle.json` (the accepted bundle) and `bundle_meta.json` / `verdict_meta.json` (per-attempt provenance — each superseded attempt's `per_attempt` row additionally carries the `failure_category` and a bounded `failure_excerpt` for why that turn failed, an observability field; the accepted attempt carries neither). A non-`M3c` node runs the shared agentic leaf instead (a recorded residual, above). Launch-prompt shape: `docs/workflow/LAUNCH_PROMPT_REFERENCE.md`.

## I/O contract
- execution input: `spec.ir.yaml`
- verification input: `spec.ir.yaml`, `controlled_spec.md` (verify-only), the generated `source/<source_id>/src/`
- output: `workspace/pipelines/<node_key_safe>/<pipeline_id>/source/<source_id>/src/`, `source_meta.json`, `gate_meta.json` (the single conductor-authored `Generate.gate` deliverable; see substep structure below). Under the `pure` `generate-executor` the source directory additionally holds `codegen_bundle.json`, `bundle_meta.json`, and `verdict_meta.json` (see Generate-executor above).

## substep structure
- `Generate.generate`: the LLM substep that generates the full source set. On a `pure` leaf it returns one `CodegenBundle` the host validates and writes; on a residual agentic node it reads `spec.ir.yaml` and writes `src/` directly (see Generate-executor above).
- `Generate.gate`: a **deterministic** substep the conductor runs **in-process** (no leaf) between `Generate.generate` and `Generate.verify`. It runs three checkers as internal steps — a lint check, a syntax check, and a static check — and writes ONE `gate_meta.json` at the source root (`source/<source_id>/gate_meta.json`) with a `checkers` object carrying `lint` / `syntax` / `static` sub-sections, a `failure_categories` list (canonical order `syntax_error` → `lint_findings` → the static-family categories), and a composed `failure_excerpt` (per-checker sections tagged `[syntax]` / `[lint]` / `[static]`). The lint check always runs; the syntax check always runs (independent of lint); the static check runs **only when the lint check and the syntax check both pass** — the `post_generate` certifier hard-fails on lint / syntax evidence that is not ok, so running the static check over a dirty source would double-report; when it is skipped its checker section records `status="skipped"` and `skipped_reason="lint_or_syntax_failed"`. A gate content failure re-runs `Generate.generate` via a warm-resume reopen (the same leaf fixes its source with context intact), with route reason `gate_<cat1>+<cat2>+...` (e.g. `gate_syntax_error+lint_findings`). **A finding the leaf did not author is not a content failure** (issue #112): every finding is attributed to a file, and a file to an author — the leaf, or this repository, which writes the build control file and (on an M3c node) the runner glue before the leaf runs and removes both from its `allowed_output_paths`. A finding on the host-authored side terminalizes the node on the FIRST attempt with a reason naming the producer (`host_rendered_lint_findings` from the lint check, `host_authored_artifact_violation` from the static check — both in `GATE_FAILURE_TERMINAL`, both dominating a co-occurring warm category), so the retry budget is spent only on findings the leaf can act on. A lint finding the gate can attribute to NEITHER side is `lint_finding_unattributed` and also terminal: assuming the leaf is how an unwinnable loop hides. A syntax attribution error (canary / dependency-closure, described under the syntax check) instead raises to a transport `fail_closed` with no `gate_meta.json` written, and dominates a co-occurring lint content failure. See `tools/workflow_conductor.py:_gate_inproc`, which composes `_gate_lint_check` / `_gate_syntax_check` / `_gate_static_check`.
  - **lint check** (`_gate_lint_check`): runs the MCP `run_linter` `preset` for `impl_defaults.toolchain.language` over `source/<source_id>/src/` and writes the host-authored lint evidence (`<pipeline_root>/lint_evidence/<source_id>.json`). A lint finding is a gate content failure (`lint_findings`) — but only once it has been ATTRIBUTED. On a failing run the same declared invocation is re-run over two isolated copies of `src/`: the host-authored basenames in one, everything else in the other. The partition is total and the decision is the linter's own verdict on each half, never a read of the diagnostics text (a file name appearing in the output proves nothing, and the leaf chooses those names). Leaf half fails → `lint_findings`, and the repair excerpt is the LEAF half's output, so a warm retry is never handed a diagnostic about a file it cannot write. Leaf half clean, host half fails → `host_rendered_lint_findings` (terminal). Both fail → terminal, with both halves in the excerpt. Neither half reproduces the whole-directory verdict → `lint_finding_unattributed` (terminal). The probe runs pass no `command_log_path`: they certify nothing, so `<src>/command_log.jsonl` stays the record of the gate proper.
  - **syntax check** (`_gate_syntax_check`): for `impl_defaults.toolchain.language=fortran` it runs the MCP `run_syntax_check` compiler front-end gate (`gfortran -fsyntax-only -std=<toolchain.standard> -Werror=unused-dummy-argument -Werror=unused-variable -Werror=ampersand`, plus `-fopenmp` when `target.backend=openmp`) over the node's `src/*.f90` staged together with the certified dependency-closure `<dep>_model.f90` (per-compiler throwaway dir under `workspace/tmp/<agent_run_id>/syntax/<compiler>/`, isolated `.mods` — never Build's `$(OBJDIR)`). This surfaces the whole class of syntax / standard-conformance `compile_error`s here instead of at Build. Three warning classes are promoted to errors over the whole staged set. An unreferenced dummy argument or an unused local variable is a gate failure, so a dummy the interface fixes but the algorithm defines as inert stays a live dummy bound by the `associate (unused_<name> => <name>); end associate` idiom (canonical: [CHECKS_MODULE_CONTRACT.md](../CHECKS_MODULE_CONTRACT.md) §5). The third is `-Werror=ampersand` (issue #25): gfortran EXTENDS the standard by accepting a continued character literal whose resume line carries no leading `&`, and that shape let a counted-`do` spelling written inside a string reach a physical line start, where the `!$omp` presence floor below counted it — a false reject on a source this gate had passed. Rejecting the shape here is what lets the floor stay line-anchored and stateless; a conforming `&`-led resume is unaffected. It writes the host-authored syntax evidence (`<pipeline_root>/syntax_evidence/<source_id>.json`). A compiler finding in the node's own source is a gate content failure (`syntax_error`). A failing stage is first attributed by re-compiling two isolated source sets with the same argv: a canary valid under every standard (a failure there means the invocation is unviable — typically an `impl_defaults.toolchain.standard` the compiler driver does not accept; it is passed verbatim as `-std=<value>`), then the staged dependency closure alone (a failure there means the closure is at fault — either a dependency's certified source is defective, since a dependency certified before a gate rule existed is not clean by induction, or this node's declared `standard` is narrower than the sound closure needs; the compiler's diagnostics say which). Both are transport `fail_closed`: the leaf authors neither the IR nor a dependency's source, so no retry of this node could clear them. Since issue #153 the closure branch is a **backstop** rather than the first line: the route that produced it in practice — a certified consumer skipped as ready and then staged against a dependency source regenerated after it was certified — is closed at readiness by the closure-binding comparison (`docs/ORCHESTRATION.md` §13b), which re-runs the consumer instead of letting it reach this probe. What still arrives here is a dependency source that is defective on its own terms, and a `standard` narrower than the sound closure needs. A third probe compiles the LEAF-authored sources alone and records the answer in `checkers.syntax.attribution` (`leaf` / `unattributed_interaction` / `unprobed`). There is deliberately no value for the dependency closure: that attribution is decided by the probe ABOVE this one and RAISES, so no `gate_meta.json` is written at all and the field is never reached. It is an OBSERVATION and routes nothing, and that is deliberate: the host-rendered runner `use`s the leaf-authored checks module, so a diagnostic printed at a runner line can be caused by the leaf having missed the fixed checks ABI — real, common, and repairable by exactly this warm retry. "The leaf's files pass alone" therefore does not mean the host is at fault, and terminalizing it would convert a leaf-fixable defect into a permanent `fail_closed`. So issue #112's rule that an unattributable finding fails closed is applied to the lint check, which can partition files, and NOT to this one, which cannot; the residual — a finding caused by the runner alone — is held at the source instead by the language backend's own renderer test, which compiles and lints the rendered runner under the gate's own flags and rule set. The excerpt is likewise not narrowed to the leaf probe's output, because an interaction diagnostic is printed at a runner line and is exactly what the leaf needs. A missing mandatory `gfortran` is likewise a transport `fail_closed` (environment problem). A staged source whose NAME the tool refuses (an option-shaped `-o.f90`, a response file, a name that is not a Fortran source file) is a gate content failure (`syntax_error`) rather than a transport one: the leaf authored the name and can rename it. No compiler runs on that path, so the stage is recorded `skipped` (there is no command to cite) and the evidence certificate is written `ok=false` — a `skipped` MANDATORY gfortran stage never certifies, so `skipped` gates here even though an uninstalled OPTIONAL target compiler does not. Optional **target-compiler stages** come from the `ATMOFAB_SYNTAX_COMPILERS` env var (comma-separated adapter ids, default `gfortran`; e.g. `gfortran,frt` once a Fujitsu adapter exists) — a stage whose compiler has no registered adapter or no installed binary is recorded as `skipped` and does not gate, so one configuration runs on machines with and without the target compiler. Non-fortran languages pass through (no adapter; Build stays their backstop). See `mcp_servers/build_runtime_server.py:tool_run_syntax_check`.
  - **static check** (`_gate_static_check`): runs only when the lint and syntax checks both pass; it runs `validate_workspace_root.py` then `validate_pipeline_semantics --stage post_generate` over the generated source. These are the purely-static gates the `Generate.verify` leaf used to own; running them here means the LLM `Generate.verify` pass is reached only on a deterministically-clean source. A violation is a gate content failure — unless its SUBJECT is a file this repository authors, which on an M3c node the host-rendered runner gates are given nothing but. The validator marks such a violation by TYPE and answers a dedicated exit code (5), and the conductor classifies on that code alone, never on the text: `host_authored_artifact_violation`, terminal. A node whose runner the leaf really does author (the `infrastructure` harness self-test) keeps the ordinary content failure. When the check is skipped (lint or syntax failed) its section records `status="skipped"` / `skipped_reason="lint_or_syntax_failed"`. Among those gates is the **`!$omp` presence floor** (`_validate_openmp_presence_floor`, issue #22): on a `component/` / `problem/` node whose `impl_defaults` resolve to `target.class=cpu` + `target.backend=openmp` + `toolchain.language=fortran` **and whose `abstract` knobs affirmatively claim OpenMP as the model**, a model source carrying counted `do` loops must carry at least one `!$omp` directive. The claim is what licenses the gate to fail a source: the violation reopens `Generate.generate`, whose leaf authors source and cannot touch the certified IR, so the gate may only demand what the IR itself states. A node whose parallelization knob is silent — or names some other model, which `Compile.static` deliberately permits — is out of scope, which leaves the soft "cpu defaults to OpenMP" rule with `Generate.verify` G6. It is a floor in the same sense as `Compile.static`'s local-op lowering floor — it decides only the unambiguous case (the profile says OpenMP, there are loops to parallelize, and there is not one directive anywhere) and is fail-open in every other direction: whole-array sources, `do while`, non-OpenMP / non-CPU / non-Fortran profiles, and `infrastructure/` (host measurement code) / `profile/` (composition-level init loops) nodes all pass. A file containing a `do concurrent` passes whatever else it holds — the construct IS the parallelism, so counted loops beside it do not make the file serial. Detection is line-anchored: a `do` opener and an `!$omp` sentinel count only at the start of a physical line. That is the free-form language rule (a comment line begins with `!`, a continued character literal resumes with `&`), and it is what puts a mention inside a comment, or inside a literal, structurally out of reach. That covers every literal that reaches this floor because the syntax check above rejects the one shape it would not — gfortran's extension of resuming a literal with no `&`, which does put a counted-`do` spelling at a line start (measured as an accepted residual by issue #23, closed by issue #25). The cost is three further fail-opens, all recorded in the checker: a `do` reached only through a `;` or a joined continuation is not counted, and a `do` header that WRAPS before it can be classified takes the whole file out of scope — it might be a `do concurrent`, and a false reject costs more than a miss. **A genuinely non-parallelizable node is out of scope either by saying nothing about parallelization or by saying `impl_defaults.abstract.parallelization: none`** (which `Compile.static` blesses). If such a node's IR nevertheless claims OpenMP, the contradiction is in the IR rather than in the source, and the violation says so — the fix is a Compile-side knob change, not a directive the producer does not believe in. The escape is at the IR level so that "this node is serial" is reviewable where every other implementation obligation lives. Everything above the floor — *which* loops are parallelized, whether the schedule matches `backend_overrides.openmp.schedule` — stays `Generate.verify` G6.
- `Generate.verify`: an independent LLM substep that verifies the source is consistent with the `case` / `algorithm` / `io_contract` / `dependency` / `impl_defaults` sections of `spec.ir.yaml`. It launches **no** validator gate (those are the `Generate.gate` static check's, above); it performs only the LLM semantic checks. Under `pure` it is a `pure-function leaf` reviewing the bundle and assembled source and returns a verify verdict the host projects onto `source_meta.json`.

## `source_id` format
- Format: `src_<YYYYMMDD>_<seq3>`, e.g. `src_20260511_001`

## `source_meta.json` required keys
- Common: `attempt_count`, `verification_status`, `last_fail_reason`, `debug_mode`, `context_isolated`

## substep details

### 2-1. Generate.generate substep
- `Generate` runs per `node` and generates source dedicated to the target `node_key`.
- The `generate substep` generates `source/<source_id>/src/` and `source_meta.json`.
- `Generate` must not take `controlled_spec.md` as direct input. The required operation composition is interpreted from the `algorithm` section of `spec.ir.yaml`. This holds for the `pure` `Generate.generate` producer too: the `pure-5` interim carve-out that inlined `controlled_spec.md` into its context (scoped strictly to interpreting the math of operations the IR already declared, to close a producer-blind / checker-sighted asymmetry against a thin IR roll) was **removed at `pure-10`** once the `compile` side began guaranteeing IR self-sufficiency (the strengthened lowering rule + the deterministic `Compile.static` local-op lowering presence floor); see the Generate-executor section above. Only the `Generate.verify` reviewer reads `controlled_spec.md`, by design (§2-2).
- **M3c host-render scope (R1/M3c-β → M3d).** On an *M3c node* (a make+fortran physics node with exactly one `infrastructure`/harness `direct_dep`) the `runner` is **host-rendered by the conductor**: the leaf authors `<spec_id>_model.f90` + `<spec_id>_checks.f90` (fixed ABI, [docs/workflow/CHECKS_MODULE_CONTRACT.md](../CHECKS_MODULE_CONTRACT.md)) and `<spec_id>_runner.f90` / `src/Makefile` are NOT in its write set. The runner-output and Makefile bullets below then describe the **host-rendered** output (still the contract `Validate.judge` reviews), not a leaf write; they apply as **authoring** rules only to a runner-authoring leaf — an `infrastructure` self-test runner, the only remaining one — for which `RUNNER_OUTPUT_CONTRACT.md` remains the injected must-read. It is NOT injected for an M3c physics generate leaf (node-aware; see `AGENT_SKILLS.md` / `leaf_contract_doc_refs`).
- Regardless of language, generate `model` (physics computation) and `runner` (input/output / execution coordination) separately.
- The `runner` calls the `model` via `call` / `use` / `import`, and must not duplicate the physics-update logic.
- **Runner program output** (`diagnostics.json` / `perf.json` / `raw/` composition, per-case snapshot naming, forbidden judge-artifact filenames, and the Fortran JSON numeric/boolean descriptor rules) is canonical in [docs/workflow/RUNNER_OUTPUT_CONTRACT.md](../RUNNER_OUTPUT_CONTRACT.md) — the must-read for a **runner-authoring** `Generate.generate` leaf (per the M3c scope above, that is an `infrastructure` node; an M3c physics leaf authors no runner and does not read it). The bullets below restate it for this phase's context; on any divergence, `RUNNER_OUTPUT_CONTRACT.md` governs.
- The `runner` source must not contain, as a substring of its **full text including comment lines**, any of the strings `verdict.json`, `aggregate_verdict.json`, `summary.json`, or `trial_meta.json`.
- The tokens the `runner` writes to JSON output (`diagnostics.json` / `perf.json` / `raw/metrics_basis.json` / `raw/state_snapshots/*.json`) must be restorable by a standard JSON parser. With `impl_defaults.toolchain.language=fortran`, the `F0` / `F0.d` format, which can omit the leading zero for a number, and the `L`-family edit descriptors that produce `T`/`F` for a logical value (`L1` etc.) must not be used directly for a JSON token. Output booleans as the literals `true` / `false`. For the canonical serialization rules and the safe `jnum()` / `jbool()` idiom, refer to [docs/PERFORMANCE_DIAGNOSTICS.md](../../PERFORMANCE_DIAGNOSTICS.md) §6. The post_generate static analysis detects this violation **by descriptor presence** (it does not inspect the runtime output, so a manual leading-zero fixup does not satisfy the gate) and fails it.
- The `perf.json` the `runner` outputs must have, without omission, the required fields of [docs/PERFORMANCE_DIAGNOSTICS.md](../../PERFORMANCE_DIAGNOSTICS.md) §2: `case_id` / `target` / `walltime_sec` / `steps` / `cells_updated` / `throughput_cells_per_sec` / `parallelism` (object: `mpi_ranks` / `threads_per_rank` / `gpu_devices` / `parallel_degree_total`). These are not derived from the IR but are a runner output contract that the canonical doc uniformly requires, and the `post_execute` gate of `Validate.execute` mandatorily verifies `walltime_sec` / `throughput_cells_per_sec` / `parallelism`. A custom minimal schema (e.g. `{case_count, wall_seconds}`) fails.
- The `raw/metrics_basis.json` the `runner` outputs must have a **`per_test` list** carrying one entry per (`test_id`, target `case_id`) pair — every `test_id` of `io_contract.test_evidence_requirements`, once for each case named in that test's `io_contract.test_predicates[].target_cases`. Each entry must hold, without omission, the `test_id`, the `case_id`, and that test's `required_raw_variables` valued from that case (needed for the per-test recomputation of `Validate.judge`). A custom structure without a per-test index (e.g. a single `evidence[]`) is rejected by the `post_execute` gate (`must contain per_test list or tests object`); the legacy `tests` object form is keyed by `test_id` and so cannot express a multi-target test's several entries — it is deprecated.
- When `state_snapshots` is required, the `runner` writes **one snapshot per case** to `raw/state_snapshots/<case_id>.json`, with `<case_id>` taken from its argv (`--cases <spec.ir.yaml> <case_id>...`, one positional per `case.test_case_set[]`). Build the path from that `case_id` (`trim(case_id)//'.json'`), never a fixed/sequential literal (`snapshot_0001.json`) or a single combined file: a wrong name is flagged by `post_generate` static analysis (string-literal names) or fails `Validate.execute`'s per-`<case_id>.json` deliverable gate (runtime-built names). Canonical filename rule: `phase_04_validate.md` §43.

- **Inert dependency call.** Each dependency `operation` is judged individually by whether `spec.ir.yaml` declares a sink for its results. An operation whose result corresponds to a variable in any `algorithm.steps[]` entry (`inputs` OR `outputs` — a result can flow straight from a step's `outputs` to an `io_contract` output with no intervening `steps[].inputs` reference), to a `derived_field_rules` / `invariants` quantity, an `io_contract` output, or a `semantic_dependency.required_sources` variable is **load-bearing**: its results are bound to those declared variables and flow exactly as declared (IR variable names carry no provenance marker, so the correspondence is resolved from the step semantics; an uncertain correspondence is treated as load-bearing). An invented purpose for an inert call — a probe configuration, an acceptance threshold or tolerance, a validity/binding flag folded into an output, a conditional branch on the call's results — is an execution path absent from `spec.ir.yaml.algorithm` and a `Generate.verify` `fail`. The inert form does not collide with the deterministic gates: an actual assigned before the call is not counted as a dependency result by the `Generate.gate` static-check dependency-dataflow gate (which also scopes to `problem/` nodes), and a variable passed as an actual argument is a use for the `Generate.gate` syntax-check unused-variable gate.

- **fortitude rule idioms (write Fortran source that passes `static lint` on the first attempt — this is the canonical checklist; a finding warm-resumes `Generate.generate` and costs a regenerate cycle):** the conductor's `Generate.gate` lint check runs `fortitude check` under a rule set this repository DECLARES (`tools/backends/linter/fortitude/lint.py`, `RULE_CODES`), not under whatever the installed build enables by default, so a rule absent from that set cannot fail a node however the host is configured. The rules below are the subset a generated source most often trips; satisfy them up front:
  - **S001 (line length < 100 columns — 99 is the longest that passes on EVERY supported linter build):** the comparison itself differs across the supported range — `>=` on 0.8.x, so a line of exactly 100 already fails there (`line length of 100, exceeds maximum 100`, despite the message's wording), and `>` from 0.9.0, where the same line passes. Write under 100 and the difference cannot reach you. Split long `subroutine` signatures and `write` statements at a `&` continuation (break between arguments or `//`-concatenated pieces, never inside a string literal).
  - **C121 (`use` must have `only:`):** every `use` names the imported entities, e.g. `use <dep>_model, only: dp, <dep>__<op>`.
  - **C122 (intrinsic module `use` needs the `intrinsic` modifier):** import from an intrinsic module as `use, intrinsic :: iso_fortran_env, only: error_unit, int64` (the `, intrinsic ::` form), not a bare `use iso_fortran_env, only: ...`.
  - **PORT011 (no number-literal integer kind):** declare kind-qualified integers with a named kind (it fires for any literal kind, e.g. `integer(4)` too), `integer(int64) :: clock0` — never `integer(8)`. `int64` comes from `iso_fortran_env`, so importing it pairs with **C122**: write `use, intrinsic :: iso_fortran_env, only: int64`. (Fixing PORT011 by adding a bare `use iso_fortran_env` is the common cascade that introduces a fresh C122 finding on the next attempt — add the `intrinsic` modifier in the same edit.)
  - **C011 (`select case` needs a default):** every `select case` block ends with a `case default` arm (even if it only guards an unreachable value).
  - **C131 (module needs a default accessibility statement) — write BOTH halves, they fail different gates:** give every module a bare `private` in the specification part AND a `public :: <name>` line for every name it must expose. A `public :: <names>` list is NOT a default accessibility statement, so the list alone still fails lint with `module '<spec_id>_model' missing default accessibility statement`; the bare `private` alone publishes nothing, so it silences C131 and then fails the `Generate.gate` syntax check when a consumer cannot resolve the symbol.
  - **C072 (assumed-length character dummy must be `intent(in)`):** a `character(len=*)` dummy declared `intent(out)` / `intent(inout)` is rejected — give it an explicit length (in `checks_compute(case_id, check_id, status)` the `intent(out)` `status` must be `character(len=4)`, never `character(len=*)`).
  - **No suppression directive, and none is needed:** the rule set the gate applies is imposed with `--ignore-allow-comments`, so an `! allow(...)` comment suppresses nothing. Write no allow directive. Do not expect to be told when one is inert: a code the gate does not run earns `FORT005`, a code it does run earns `FORT002` on otherwise clean source, and on source that actually violates that code you simply get the finding you tried to suppress. This replaces the former workaround — an allow directive naming **C003**, written above every `implicit none` — which existed because that rule wants the F2018 spec-list `implicit none (type, external)` while `impl_defaults.toolchain.standard=f2008` (Makefile `FFLAGS=-std=f2008`) makes that form a `compile_error` (`Error: Fortran 2018: IMPLICIT NONE with spec list`). **C003 is no longer in the declared set**, so plain `implicit none` — no spec list, no directive above it — is correct and passes. ❌ `implicit none (external)` or `implicit none (type, external)` remain build-breaking `compile_error`s under `-std=f2008` that the deterministic `Generate.gate` syntax check (real `gfortran -fsyntax-only -std=f2008`) rejects, warm-resuming `Generate.generate`. ❌ an allow directive of any kind, naming any rule, is no longer a fix — it changes no verdict, and the finding it was meant to silence is reported anyway.
- **Write standard-conforming f2008 — the `Generate.gate` syntax check compiles your source.** The conductor's deterministic `Generate.gate` syntax check runs the REAL compiler front-end (`gfortran -fsyntax-only -std=f2008`, with the dependency closure staged) over `source/<source_id>/src/*.f90` before the `Generate.gate` static check, so **every** syntax / standard-conformance `compile_error` — not a curated subset — is caught there and warm-resumes `Generate.generate` (this replaced the former `post_generate` text heuristics). Known instances that used to slip through to Build and are now caught at the gate: an identifier over the 63-char f2008 name limit (keep generated names within the limit; if `<spec_id>_model` / `<spec_id>__<op>` itself would exceed it, that is a spec-level problem — do not abbreviate); a non-constant `STOP` / `ERROR STOP` code (❌ `error stop 'unknown case_id: '//cid` — under `-std=f2008` the code must be a scalar CHARACTER/INTEGER **constant** expression; ✅ use a fixed literal, or `print`/`write` the run-time value first and then `error stop <integer>`); the `implicit none (...)` spec-list form above. The gate additionally promotes `-Werror=unused-dummy-argument -Werror=unused-variable -Werror=ampersand` over the whole staged set, so a dummy argument the interface fixes but the body never consumes (an inert input the algorithm defines as unused; an ABI-fixed `name` / `case_id`) is a `compile_error` — ✅ keep it a live `intent(in)` dummy and bind it immediately after the declarations with `associate (unused_<name> => <name>)` / `end associate`; ❌ an arithmetic no-op (`0*<name>`); ❌ `! allow(...)` — not because of which rule it names, but because the lint gate runs `--ignore-allow-comments`, so no directive suppresses anything (and this class is a compiler error, which a lint directive could never have reached). An unused local variable is deleted, not bound. Canonical: [CHECKS_MODULE_CONTRACT.md](../CHECKS_MODULE_CONTRACT.md) §5. The third promoted class is the continuation of a character literal: a wrapped literal must resume with a leading `&` — ✅ `'a message that is &` / `      &continued'`; ❌ the same wrap with the resume line's `&` omitted, which gfortran accepts as an extension and this gate rejects. Getting these right up front avoids a regenerate cycle, exactly as with the fortitude idioms.
  - **Fortran identifiers are case-insensitive.** A pair of names differing only in case (a dummy `g` and an output `G`; a dummy `U_L` and a local `u_l`) is one identifier in the same scope, so it is a `compile_error` — a duplicate declaration, or an `intent` conflict on the dummy. When an IR-derived name collides this way, rename the **local / dummy** side; the IR-derived name stays verbatim.
- **The `Generate.gate` static check traces the dependency dataflow into `intent(out)`.** On a `problem` `node` with dependencies, declare the incoming state `intent(in)` and the updated state (the `io_contract.outputs` / `algorithm.required_update_paths` variables) **`intent(out)`**, and reach each `intent(out)` dummy by an assignment chain from the values the `call <dep>__<op>(...)` results carry. The gate inspects each `subroutine` **and each `function`** that declares at least one definable output; an actual of such a call is treated as a dependency result unless it is a dummy of that procedure, assigned before the call, or a name the file declares as a constant (`parameter` / `enumerator`) and never declares as anything else, and `&` continuations are joined before any of this is read. A procedure's definable outputs are its `intent(out)` dummies, plus — for a `function` — its **result variable** (the name in `result(...)`, or the function's own name when it declares none). That clause is file-wide and deliberately strict rather than scope-accurate: a name that is a constant in one procedure and a variable, an `associate` binding or a `use ..., only:` import anywhere else in the same file is still a dependency result, as is a constant imported from another module. In each case the remedy is the inert-call rule's, to assign the actual before the call. A dependency result consumed only by an `intent(inout)` in-place update reaches no `intent(out)` variable and is a `Generate fail` (`does not propagate dependency operation outputs to intent(out) dataflow`) that warm-resumes `Generate.generate`. A `subroutine` with no `intent(out)` dummy is skipped by the gate (a `function` always has a definable output — its result — so it is never skipped for that reason), but such a procedure exposes no output expression tree for the G5 review below either. **Write a separate module subprogram in its FULL form** (`module subroutine s(u, v)` / `module function f(x) result(y)`, with its own `intent` declarations): the abbreviated `module procedure s` form is REFUSED by the gate with a rewrite instruction, because F2008 forbids that body from redeclaring its dummies, so no `intent` ever appears in it and every gate would pass it in silence. This is the deterministic counterpart of G5; canonical authoring rule: `skills/workflow-generate-generate/SKILL.md`.

The relevant target references the existing binary in `$(BINDIR)` with a **non-relinking** guard that fails closed when the binary is absent — `test -x $(BINDIR)/$(BIN) || { echo "error: $(BINDIR)/$(BIN) not built; run 'make all' first" >&2; exit 1; }` — and **must not** invoke `$(MAKE)` in the guard. Relinking inside `Validate.execute` writes into the read-only-bound `binary/` (outside the execute `runs/` write_root) and escalates a mere binary-name/availability mismatch into an `unauthorized_write_violation` → `fail_closed`; the fail-closed guard instead yields a clean retryable `make test` failure. For local use, run `make all test` (the `?=` in-source defaults are unchanged). The target generates the output destination with `mkdir -p $(RUNDIR)` (and the `raw/` required subdirectories the runner writes) **before** `cd $(RUNDIR)`, then runs the runner as `$(BINDIR)/$(BIN) --cases $(SPEC) $(CASES)` and confines the run output under `$(RUNDIR)`. The `--cases $(SPEC) $(CASES)` argv is **required**: the runner consumes its case set from `--cases` (and aborts without it), and `Validate.execute` imposes the same `SPEC`/`CASES` `run_program` uses so the make-test re-run's diagnostics match — a bare `$(BINDIR)/$(BIN)` makes the make-test candidate emit no `diagnostics.json` and fails `quality_check` (`post_generate` flags a `test`/`check` recipe that runs the binary without `--cases`). Because `$(RUNDIR)` can point to a not-yet-created run node dir, omitting `mkdir -p` makes `cd` fail.

### 2-2. Generate.verify substep
The `post_generate` static gate is **not** run by `Generate.verify`. The conductor's deterministic `Generate.gate` substep — the syntax check (the compiler front-end gate) and then the static check running `validate_workspace_root.py` then `python3 tools/validate_pipeline_semantics.py --stage post_generate --pipeline-root workspace/pipelines/<node_key_safe>/<pipeline_id>/ --source-id <source_id>` (`exit code 0` required) — runs **before** `Generate.verify`; a violation warm-resumes `Generate.generate` and `Generate.verify` never starts. So verify is reached only on a deterministically-clean source and performs only the LLM semantic checks below.

`Generate.verify` must not run the write-family tools of the `build-runtime` MCP including `run_linter` (`run_linter` / `run_syntax_check` / `compile_project` / `run_program` / `run_quality_checks`) (`static lint` is the `Generate.gate` lint check and the compiler syntax gate is the `Generate.gate` syntax check, both conductor-run). `Generate.verify` launches **no** external validator gate: `validate_workspace_root.py` and `validate_pipeline_semantics --stage post_generate` both run in the conductor's `Generate.gate` static check (the `post_generate` run there certifies the conductor lint AND syntax gate by *inspecting* the host-authored `<pipeline_root>/lint_evidence/<source_id>.json` / `<pipeline_root>/syntax_evidence/<source_id>.json` and the referenced `command_log.jsonl` records). `Generate.verify`'s only authorized output is `source_meta.json` — `allowed_output_paths` lists just that file and its `bwrap` `write_root` is pinned to it (it inspects the producer sources but never rewrites them; a fail requests regeneration under a new `source_id`). So the `command_log.jsonl` side output of `run_linter` (under `src/`) is refused by the sandbox (`EROFS`) and fails the leaf from inside, rather than only tripping the terminal write-attribution check.

`Generate.verify` required verification items:

#### G1. case coverage
- All `case_id` of `spec.ir.yaml.case.test_case_set` and all expanded `case` are reachable from the implementation path of the `runner` or `model`.
- When an unimplemented `case`, an unreachable branch, or a fixed-`case_id`-limited implementation is detected, it is a `fail`.
- When an implementation in which the `model` composes the judgment metric only with `case_id` branching and fixed-numeric assignment is detected, it is a `fail`.

#### G2. case input acceptance
- The `runner` and `model` accept each runtime input of `spec.ir.yaml.case.test_case_set[].inputs`.
- When the input-propagation or recording path corresponding to at least `case_id`, the grid conditions, the time conditions, the initial-condition identifier, the boundary-condition identifier, the `profile`- or `component`-selection result, and the `test_profile_id` and `test_profile_version` derived from `tests.md` cannot be confirmed, it is a `fail`.

#### G3. implementation of case-dependent differences
- The per-allowed-selection-value difference implementation in `case.test_case_set[].inputs` is not collapsed into a fixed constant or a single default value.
- When an implementation that ignores case-dependent inputs such as `boundary`, `initial_profile`, `topography_profile`, `dt_rule`, `refinement`, or the `sweep` expansion result is detected, it is a `fail`.

#### G4. algorithm reflection
- Based on `spec.ir.yaml.algorithm.steps`, `ordering`, `control_condition`, and `iteration_contract`, the `test case set` coverage, operation composition, dependency `operation`, and the data dependency of the output metrics are reflected in the generated code.
- `algorithm.update_semantics`, `temporaries`, `derived_field_rules`, `invariants`, and `splitting_policy` are reflected in the generated code. When a missing state-update target, an unimplemented derived-quantity computation, an update order that breaks an invariant that should be conserved, or a `splitting_policy` mismatch is detected, it is a `fail`.
- The generated code does not introduce an additional operation, additional iteration, additional conditional branch, or additional dependency `operation` call not described in `algorithm`. When a guessed re-introduction of `controlled_spec.md`-derived information is detected, it is a `fail`. The `associate (unused_<name> => <name>)` / `end associate` binding of an intentionally-unused dummy argument ([CHECKS_MODULE_CONTRACT.md](../CHECKS_MODULE_CONTRACT.md) §5) is **not** an additional operation: it computes nothing, it is required by the deterministic `Generate.gate` syntax check, and it needs no `algorithm` step to license it. Failing a source for carrying it would oscillate against that gate (remove the binding → the gate rejects the dead dummy → restore it), so its **absence** on an inert dummy, not its presence, is the defect. An **inert dependency call** (the requirement above; `docs/GLOSSARY.md`) is likewise **not** an additional dependency `operation` call: `spec.ir.yaml.dependency.direct_deps` licenses it without an `algorithm` step, and failing a source for carrying it would oscillate against the dependency-call mandate — its results feeding a declared output, not the call itself, is the defect.

#### G5. io_contract consistency
- When a constant output unrelated to the `model` output, a fixed-`JSON` output, or `diagnostics` generation by direct assignment of an analytic expression is detected, it is a `fail`.
- Verify that the final expression tree of an `intent(out)` variable reaches the group of output variables declared in `spec.ir.yaml.io_contract.semantic_dependency.required_sources` and `io_contract.outputs`.
- Reconcile `spec.ir.yaml.io_contract.raw_requirements.required_evidence` and `test_evidence_requirements` with the `runner`'s raw-evidence output design, and verify that the raw evidence needed for `Validate.judge` recomputation is held for every `test_id`. When a configuration in which the `runner` writes out only a whole-suite summary, a configuration that overwrites and aggregates the primary evidence of multiple `test` into one, or a missing `required_raw_variables` is detected, it is a `fail`.
- Verify that the `runner` emits, in `diagnostics.json`, a `checks.<id>` entry for every `io_contract.diagnostics_contract.checks[].id`, and — when `io_contract.diagnostics_contract.verdict.required=true` — a top-level `verdict` object holding the `verdict.fields` keys. When a `checks.*` key required by the contract is missing, or the required `verdict` object is absent, it is a `fail`.

#### G6. impl_defaults reflection
- `spec.ir.yaml.impl_defaults.target.class`, `target.backend`, `target.architecture`, `toolchain.language`, `toolchain.standard`, `toolchain.build_system`, and `selected.backend_key` are reflected in the generated source composition and the `build` artifacts.
- Verify that the execution-algorithm choices specified in `impl_defaults.abstract` and `backend_overrides` — parallelization, layout, fusion, tiling, vectorization, asynchrony, etc. — are reflected in the generated code or `build` settings to the extent expressible in the target language and target. When ignoring of a specified knob, the mixing-in of an optimization for a forbidden target, or a violation of the default `OpenMP` rule for `target.class=cpu` is detected, it is a `fail`. Where the `Generate.gate` presence floor runs (above) the zero-`!$omp` slice of this rule is already settled, so on those nodes spend the judgment on whether the directives cover the loops the `abstract` parallel-scope knob names and honor the `backend_overrides`, not on whether any exist. The floor's guarantee is scoped to its trigger — `component`/`problem`, cpu+openmp+fortran, an `abstract` knob that affirmatively claims a parallel model, at least one line-anchored counted `do` loop, and no wrapped `do` header — so on an `infrastructure`/`profile` node, a whole-array or `do concurrent` model source, or a declared-serial node, the existence of any reflection at all is still this check's responsibility. The floor also reads only `<spec_id>_model.f90`, so directive-free counted loops in a checks module are always yours.

#### G7. dependency consistency
- Verify that the generated code does not introduce a reference to a dependency `node` not present in `spec.ir.yaml.dependency` or to an undeclared `operation`. When a call outside `direct_deps`, an unresolved `component` reference, or an implementation choice contradicting a `profile` constraint is detected, it is a `fail`.
- Verify that each emitted `call <dep>__<op>(...)` passes its positional arguments in the order **and rank/shape** of the conductor-resolved published-operation interface in `<dependency_facts>` (each dummy's type/intent/rank is listed under its header): confirm the actual argument's rank matches the dummy's rank — in particular that a lower-rank dummy (e.g. rank-2 `(:,:)`) is fed a matching slice inside a component loop, not the whole higher-rank state array. A deterministic gate on the CALL SITE is infeasible (Fortran is positional and the consumer uses its own local names), so this is an LLM check; Build's compiler is the deterministic backstop (an order or rank/shape mismatch fails Build and routes back to `Generate`). What IS deterministic since issue #153 is the other end: a `component` dependency's own published ABI is pinned §5.1 == its IR == its source, so the interface `<dependency_facts>` shows no longer moves between regenerations of one `spec_version` — the drift's CAUSE is gone, not the obligation to match what is shown. See the `verify` `SKILL`.

#### Severity of a finding (`issue_severity`)
`issue_severity` names the repair a finding calls for. The conductor acts on the value as `docs/workflow/WORKFLOW_CORE.md` states; the value does not grade the consequence the defect would have at `Validate`, and the size of the correction does not change it. One question selects the value: whether `Generate.generate`, re-run with the finding and the same `spec.ir.yaml` and `tests.md`, can resolve the finding.
- `minor`: the defect lies in the sources under review, and `last_fail_reason` names a correction that keeps them faithful to `spec.ir.yaml`. Every G1-G7 finding whose subject is the generated code takes this value — an unreachable `case`, a collapsed case-dependent input, a missing or added `algorithm` step, a constant or `case_id`-branched diagnostic, an ignored `impl_defaults` knob, a call outside `direct_deps`, a wrong argument order or rank.
- `major`: no re-run of `Generate.generate` from the same `spec.ir.yaml` and `tests.md` can resolve the finding. The subject is an input rather than the sources under review; that question decides the value, and these are the cases it usually takes: `spec.ir.yaml` drops or distorts a requirement that `controlled_spec.md` or `tests.md` carries (a requirement, not natural-language flavor); `spec.ir.yaml` lacks what a checklist item requires the code to reflect (a step with no lowered definition, a `case` input no `algorithm` step consumes, an `io_contract` output no `algorithm` output reaches); `spec.ir.yaml` contradicts the checks-module contract; or `controlled_spec.md` and `tests.md` contradict each other and `spec.ir.yaml` reproduces both. `last_fail_reason` names the input and the contradiction, and contains the literal `ir_inconsistency` when the input is `spec.ir.yaml`.
- `critical`: the sources under review cannot serve as the base of a repair: they are not this `node`'s, or the `model` implements a scheme other than the one `algorithm` describes as a whole rather than diverging in a step.
- A claim about what the host-rendered runner does with the RESULT a checks-module callback returns (an `ok` flag, a `found` flag, a `status`, a metric value) is dropped and takes no severity when the checks-module contract contradicts it. Where the contract is silent, the finding stands and takes the value its subject earns under the bullets above.
- When the reviewed documents do not settle whether the subject is the sources under review or an input, the value is `minor`. When they do not settle whether the sources under review can serve as the base of a repair, the value is `minor`: the repair the finding calls for is a producer re-run either way, and only a subject on the input side earns `major`.

## On-failure behavior
- A `Generate fail` retry defaults to an in-phase retry.
- When `Generate.verify` judges that "the IR itself has an error", record "ir_inconsistency" in `source_meta.json.last_fail_reason`, and the `orchestration agent` decides whether to go back to `Compile`. When `Compile` is already checkpointed `pass`, the return to `Compile` first runs `reopen-phase --from-phase compile --node-key <node_key> --trigger-agent-run-id <generate_verify_fail_substep_agent_run_id> --reason <reason_code>` to invalidate the stale `Compile` checkpoint / `step_result` and reset its `phase_state`, then re-runs `Compile` → `Generate`. Canonical: `docs/CLI_REFERENCE_RARE.md#reopen-phase`, `docs/RUNBOOK.md` §3-1.
