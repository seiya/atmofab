# Hook implementation policy

Repository-maintenance reference for the hook system (where hook validation and invocations are defined). Hooks act on agents transparently; this is not required reading for a workflow agent at runtime (for recovering from a hook block, see the "Repair cheat sheet on a hook block" section of `docs/RUNBOOK.md`).

- `tools/hooks/common.py` is the canonical source for backend-independent validation. Backend-specific invocation specifications are absorbed by the adapters under `tools/hooks/adapters/`.
- `.codex/hooks.json` is the canonical source for Codex hook invocation definitions; the `hooks` section of **`leaf_config/claude/settings.json`** is the canonical source for Claude Code (matcher/wiring details below). That file is the LEAF layer: since issue #63's final form a leaf loads it, and only it, as the `user` layer of a private `CLAUDE_CONFIG_DIR` the host prepares and SHA-256-pins. The repository's own `.claude/settings.json` is the DEV layer for an operator's interactive session; it is not read by any leaf, and `ClaudeLeafConfigSyncTests` requires the dev layer to carry every one of the leaf's hook commands — a SUPERSET, deliberately, so an operator's session enforces at least the policy a leaf does while still being free to add a convenience hook of its own. Edit the leaf file first — it is the owner.
- Codex `apply_patch` validation reads `tool_input.command` as the canonical patch program. `tool_input.patch` and `tool_input.patch_text` are compatibility fallbacks only. In workflow mode an absent, unparseable, or target-free patch program is denied.
- A Codex `PermissionRequest` response uses `hookSpecificOutput.hookEventName="PermissionRequest"` and an explicit `decision.behavior` of `allow` or `deny`. Other Codex command-hook allow responses remain empty.
- The Claude Code backend does not need a feature-flag probe, and the `hooks` requirement check is limited to the Codex backend. The common policy follows `evaluate_common_policy()` in `tools/hooks/common.py`.
- The `hooks` section of `leaf_config/claude/settings.json` (and its dev-layer twin) wires the 4 events `PreToolUse` / `PostToolUse` / `UserPromptSubmit` / `Stop`. Its `matcher` is a **regular expression matched in full** — measured on CLI 2.1.235: `Bash` and `Bash|Write` and `.*` all fire for `Bash`, while `Bas` does not, and an EMPTY or omitted `matcher` fires for every tool. (This bullet previously said "exact-match string (not a regular expression)"; that was false, and the leaf-config probe models it as `re.fullmatch`, which is what the CLI does.) Write the literal tool name (`"Bash"`) anyway: the repository's own configuration is a fixed list of tools, and a literal is what the coverage check reads. A tool with no entry is never sent to the hook at all — not because the match is "exact" (it is a full-match regex), but because this repository's own matchers are literal tool names — the entry list, not the CLI dispatch in `tools/hooks/cli.py`, is what decides which tools are validated.
- `PreToolUse` has **six** matchers, in this order: `Bash`, `Write`, `Edit`, `Read`, `Grep`, `Glob` (all invoking the same command). `Bash` must stay first; tests address the hook command as `PreToolUse[0]`.
- Read-boundary enforcement (`read_manifests/<agent_run_id>.json` `allowed_read_roots`, policy id `read_manifest_read_guard`) covers, in workflow mode:
  - `Read` — its `file_path`.
  - `Grep` / `Glob` — their `path`. An **absent `path` is validated as the repository root** and therefore blocks unless the manifest grants the root: a pathless search reads the whole checkout. A **`Glob`** `pattern` is validated too, since issue #71 (which put `Glob` in a leaf's hands for the first time on a CLI whose default roster omits it, making what had been an unreachable residue of issue #42 reachable): the pattern is authorized AT THE PLACE THE READ WOULD LAND: it is normalized, its literal prefix taken, and that prefix put through the same `validate_read_access` as `path`. An ordinary pattern normalizes to itself and resolves under `path`, so it rides the entry that authorized `path`; `../spec/*.md` and `docs/*/../../spec/*.md` are judged at `spec/` — allowed when `spec/` is granted, which is also what the Bash spelling of that read does; an absolute or `~` pattern is judged on its EXPANSION, since `~/.ssh/*` must not read as the in-repo literal `<repo>/~/.ssh`. A brace alternation is expanded first and every alternative judged, up to a bound past which the whole pattern is judged at the repository root: `{` is not in the shared glob metacharacter set (the Bash extractor resolves its targets against the filesystem, where a brace is not a wildcard), so `docs/{../secret,sub}/*` had the literal prefix `docs/{../secret,sub}` and read outside a granted `docs/` — measured, while the Bash spelling of the same read was refused. **What the Glob TOOL can reach is deliberately NOT part of this rule.** Two earlier versions of this check were narrowed and widened on a premise about the vendor's implementation, written as measured and false: bare `ripgrep` was measured rather than the tool, and driving the real tool returns files for `../x/*`, for `*/../../x/*`, through a symlinked directory and for a brace alternation. The landing place is computable from the pattern alone, so the rule holds whichever engine runs it and no vendor change can reopen it. `Grep`'s `pattern` is a content regex and names no path, so it is deliberately NOT path-validated — refusing a search for `\.\./config` would be an over-refusal; its unvalidated `glob` / `type` filters are recorded as narrowing the search within `path` — a sentence that predates the allowlist and has NOT been re-measured against the tool now that a leaf has `Grep`; `TODO.md` carries it, and carries why the neighbouring claim of the same shape turned out to be false.
  - `Bash` — the read targets `extract_bash_read_targets` (in `tools/hooks/common.py`) can extract from the command, filtered to those that exist on disk inside `repo_root`; blocks carry `"via": "bash"`. A wildcard target with more than two wildcard path components is not expanded — it is validated at the literal prefix before its first wildcard, since every match lies under it UNLESS a `..` follows a wildcard, which that path handles by validating at the repository root instead (`glob.glob` is unbounded and this hook runs on every tool call). That is a superset test, so such a block names the prefix directory rather than a file, and can fire even when every real match would have been in-manifest; narrowing the pattern is the fix. This runs **before** the read-only auto-approve, so a command the manifest rejects can never be auto-approved. A literal `cd` inside the same command anchors the targets that follow it. Extraction is best-effort by design, and what it can see is bounded by a **fixed set of reader commands** (`_BASH_READ_CMD_NAMES`) plus their grammars. Accepted residue, all yielding nothing: (a) **any command outside that set given a literal path** — including the contract-sanctioned scratch-script route `python3 workspace/tmp/<agent_run_id>/x.py` — the script is authored with the `Write` tool, which this extractor never sees at all, and a heredoc body attached to any command is deliberately blanked — so a path the script reads is invisible here; (b) targets that exist only at runtime — `xargs cat`, `find -exec`, command substitution, process substitution `<(…)`, `$VAR`; (c) a `cd` issued in an EARLIER Bash call (the hook sees one command at a time; leaves are told never to `cd`). An empty extraction therefore means "nothing to authorize", **not** "safe".
- **Layer boundary: which layer guards which path class.** For the tools that name a path they READ — `Read` and `Bash` — authorization is split by where the path lives, and each class has one owner. (`Glob`'s `pattern` was the standing exception here until issue #71 closed it: its literal prefix now goes through the in-repo class above, the same one its `path` does.)
  - **Inside `repo_root`** — the read manifest (`allowed_read_roots`), enforced per tool as above. The manifest is repo-relative, so it can only ever authorize this class.
  - **Outside `repo_root`, protected** — `~/.met-dsl` (operator-only dismiss-violation tokens, and since issue #64 the durable isolated backend homes at `~/.met-dsl/homes/<orchestration_id>/{claude,codex}` — see the isolated-homes paragraph of §"Layer boundary" below), and every backend credential home the bwrap profile rw-binds so the backend CLI can refresh its own auth (`~/.claude`, `~/.claude.json`, `~/.codex`, or its `CODEX_HOME` / `METDSL_HOME` relocation). These are **rejected fail-closed for Bash** by `evaluate_common_policy` in `tools/hooks/common.py` (policy ids `forbid_operator_secret_direct_read` / `forbid_backend_credential_direct_read`), on both backends and regardless of the reading command — the guard matches the path, not the argv0, so `od` / `xxd` / `read X < …` / `x=$(cat …)` / `..`-traversal / brace and glob spellings are covered, a relative wildcard being anchored exactly like a relative path (`cd ~ && cat .clau*e.json`). Containment is tested BOTH ways for a recursive reader: `grep -r … ~`, `ls -R ~`, `find ~ -exec cat {} +`, `tar cf - ~` name an ANCESTOR of a root and read it, with no expansion trick at all. Which flags make a command recursive is read PER COMMAND (`cp -a` is an archive copy, `ls -a` merely shows dotfiles), and the ancestor test applies only to real OPERANDS — not to the words the quote-collapsed copy of the command splits prose into (`echo "docs / runtime"` yields a bare `/`), and not to a `cd`'s own operand, excluded by INDEX rather than by spelling (`cd .. && grep -rn foo repo/docs` resolved `..` against the anchor that same `cd` produced; excluding the spelling instead let a prepended no-op `cd ~` disarm `grep -r … ~`). Each of those three fail-closed a real command from this repository's own logs; the quoted-but-real operand (`grep -r x '/'`) still blocks, because it is a token of its own. Because the shell resolves a path in ways `os.path.expandvars` does not, the guard tests **candidate spellings** of each token, not just its literal text: any `${HOME…}` parameter expansion — the value-TRANSFORMING operators (`/pat/rep`, `//pat/rep`, `^^`, `,,`, `^`, `,`, `#pfx`, `##pfx`, `%sfx`, `%%sfx`, `:off`, `:off:len`) are applied to the value, with their operand read as the GLOB bash reads it and with the shortest/longest distinction bash makes — matched by a bitset dynamic program rather than a translated regex, which backtracked catastrophically on `${V##*a*a*a*a*b}` — and the alternate-word operators (`:-`, `:=`, `:+`, `-`, `=`, `+`) are RESOLVED per expansion the way bash resolves them, from whether the variable is set and whether it is empty — with `+` inverting that test — rather than guessed as one all-or-nothing choice; a nested `${A:-${HOME}}` gets a second expansion pass, plus `${!V}` indirection, a variable assigned earlier in the SAME command including through another variable (`A=$HOME; B=$A; cat $B/…`), the bash-only tilde prefixes `expanduser` does not know (`~+`, `~-`, `~N`), the quoting constructs that hide a path from every literal match — ANSI-C (`$'\057etc'` IS `/etc`, a path containing no path characters) and locale (`$".claude.json"`), including the mid-token forms whose quotes shlex strips before this guard sees them, which survive as a bare `$` that is dropped when it precedes punctuation or a name defined NOWHERE (`~/.$'c'laude.json` arrives as `~/.$claude.json`; a `$` before a DEFINED name is a real expansion and is left to substitution), and every `cd` in the command — plus every `-C` / `--directory` / `--chdir` option OF A COMMAND THAT HAS ONE (`tar`, `git`, `make`, `env`, …, but not `rsync -C` / `scp -C` / `ls -C`, which mean something else), resolved against the segment's own argv0 — FOLDED in order so a relative walk lands where bash lands (`cd ..; cd ..`). The `cd` spellings covered are `cd ~`, a bare `cd` (which also goes to `$HOME`), `pushd`, `cd` with its own options, and a `cd` glued to a separator or wrapped in parentheses, including a separator glued to its target (`cd ~;cat x`). Candidates over-approximate deliberately: for a read guard, extra candidates can only block more. And where the emulation ENDS, the guard fails closed rather than falling through: a candidate still carrying `${`, or any command carrying `$(…)` / backticks, is one it could not resolve, and if a token also spells a protected root's own path component (`.claude.json`, `.codex`, `.met-dsl`, `.claude`) the read is treated as reaching it — which closes the class (nesting depth, arithmetic bases, POSIX classes, command substitution, whatever syntax comes next) instead of the instance. Two narrowings keep it from being blunt: a component that also exists INSIDE the checkout (`.claude/`, `.codex/` both do) only counts when the token reaches for HOME, starts with `~`, or the command has already left the repository through a `cd` or a `../..`, and an unresolved expansion naming nothing protected stays allowed. What it does not catch is a component SPLIT across a substitution (`.cod$(echo e)x`), where no token spells it.

    This hook is synchronous and every fan-out axis is attacker-chosen, so the candidate generation is bounded — but by RELEVANCE and WORK, never by a count of the things that could matter. That distinction is the whole design: a count cap is fail-OPEN to padding, because an evader writes N throwaway assignments (or `cd`s, or `${Z}` expansions) and puts the real one last. So: an assignment is kept when something in the command REFERENCES its name (with `${!V}` resolved through the assignment VALUES, since it names its target by value), and there is NO bound at all on how many assignments or how many bytes of them are carried — a count cap and then a byte budget were both shipped, and both fell to the same shape (pad until the bound is spent, then write the real assignment after it); the work is linear in the command's own length, which the OS already bounds; the assignment map is resolved to a fixpoint ONCE and each token then needs a single substitution pass, which is what takes the assignment count off the per-token cost; every `cd` fold step is kept as an anchor and every relative token is tried against all of them, because `.resolve()` follows symlinks and so even a `..`-free token can leave its base; expansions in a token are all substituted, the fan-out being two candidates regardless. What the work bounds can still drop, and therefore the residue they leave: a candidate that grows past `_CANDIDATE_MAX_LEN` while substituting (a cyclic chain such as `A=$B$B$B$B; B=$C$C$C$C; C=$A$A$A$A`, which multiplied the string per pass and made a 56-character command take over a minute); more than `_CD_FOLD_MAX` `cd`s in one command (the LAST ones are folded); a working directory deeper than `_CD_ANCHOR_MAX_DEPTH`; the tail of a `${X//pat/rep}` scan once (positions x pattern elements) exceeds `_GLOB_SUBSTITUTION_OPS_MAX`; and, only once (anchors x candidate tokens) exceeds `_RESOLVE_OPS_MAX` path checks, the anchors beyond the root-related ones and the two ends — a crafted command that pads BOTH ends and hides the decisive `cd` in the middle is the residue that leaves — a ceiling a plausible command does not reach, because each check is a lexical `normpath` with a syscall only where the path exists (a nonexistent path cannot be the symlink that would carry it out of its base, and leaks nothing either way). Uncapped, a ~13 KB command cost tens of seconds per tool call. Three accepted false positives, documented rather than carved out. (1) The raw-command marker match fires on a command that merely NAMES a protected path, so `grep -rn "~/.claude.json" docs/` blocks — this document and `TODO.md` both contain that string; the block message names the path, and searching for a different substring is the workaround. (2) An anchor applies to every relative token regardless of position, and `cd -` / `popd` / a subshell are not modelled as returning, so `cd ~ && cd work/<repo> && cat .claude/settings.json` blocks a read of the REPO's `.claude/` — use a repo-relative path without the `cd`. (3) The three audit skills that read a backend session transcript (`skills/workflow-audit-claude`, `skills/workflow-audit-codex`, `skills/workflow-timing-audit`) are operator-side procedures whose reads now block inside workflow mode; each carries a note saying so. Replaying 8046 real Bash commands from this repository's own hook logs (measured 2026-08-11), those transcript reads are the ONLY commands the guard newly blocks, and the auto-approve narrowing costs exactly one command (`echo "$PWD"`). That corpus is no longer reproducible: the retained `workspace/orchestrations/*/hooks/` logs hold 288 Bash `pre_command_execute` events over 29 orchestrations as of 2026-08-18, 280 distinct command strings, replayed as 283 (orchestration, command) pairs because a command shared by two orchestrations is validated against each one's own manifests. The corpus SIZE is reproducible and was reproduced independently; the classification SPLIT is not — three replays of these same 283 pairs disagreed (108 / 156 / 19 auto-approve / plain-allow / block against 114 / 149 / 20 from two independent implementations), and the one harness difference identified, whether the run binding is restored from the recorded session id (the claude adapter carries no session id, so an unrestored binding resolves to the orchestration agent), does not account for it: turning that restoration off moves the block count and leaves auto-approve at 108. A replay therefore has to publish its harness, not only its numbers; the per-orchestration verdict is what the hook is asked for, and a corpus-wide split is a property of the replay as much as of the hook. A later replay must state its own corpus size and date rather than carry this number forward. A CREDENTIAL root with any containment relationship to `repo_root` — above the checkout, or inside it (a misconfigured `CODEX_HOME` either way) — is dropped rather than enforced. `_resolve_backend_rw_binds` rejects both directions on the bind side, so nothing under such a root is bound writable, while enforcing it would fail-close every in-repo read. The OPERATOR-SECRET root is never dropped, and the reason for that changed with issue #64: it used to be "it is not an rw bind at all", which is now false, because the isolated backend homes ARE rw binds and they live at `~/.met-dsl/homes/`. What survives is that the root holds the dismiss-violation tokens, which are bound nowhere and whose entire purpose is to be unreachable by an agent, and that a checkout placed inside or around `~/.met-dsl` is a configuration nobody has a reason for — so it keeps failing closed there rather than losing the guard. The homes themselves are separate entries (`workflow_private_backend_homes`) and take the containment drop like any other rw bind; dropping one costs ATTRIBUTION, not enforcement, because this root still covers it. One carve-out, matching the Read tool's: `<projects-root>/<repo-slug>/<session>/tool-results/<id>.txt` is where the harness saves an oversized tool output and then tells the agent to read it, so that shape is exempt for Bash too (`_is_persisted_tool_result_shape`), in every spelling (`~`, `$HOME`, `${HOME}`, absolute, or a glob over the same directory) and after symlink RESOLUTION — for the glob form too, whose matches are re-resolved individually — and only for a file with one hard link — the projects root is an rw bind, so an exemption applied to the unresolved path is a place to plant a link. `<projects-root>` is `~/.claude/projects` for an operator session and `<private home>/projects` for a leaf, and the `~` / `$HOME` / `${HOME}` half of that list only ever applied to a root UNDER the home — which since issue #64 is both of them. The unresolved-expansion fallback resolved only the OPERATOR's root until then and so refused a leaf the reading of its own gate output when it spelled the path `${HOME}/…`; latent since issue #63, when the leaf's root moved into the private home, and reachable only through `$(…)` while that home was under `/tmp`. Shape-and-slug only, since the per-session check `_is_persisted_tool_result_read` makes needs an agent_run_id this layer does not have. The Read tool reaches none of the other paths by construction (an absolute home path cannot be in a repo-relative manifest). The rw-bind is what makes the Bash guard necessary: bwrap deliberately makes these paths writable, so their confinement cannot come from the sandbox.
  - **Outside `repo_root`, everything else** — the harness permission list. The hook neither authorizes nor blocks it: blocking would break benign commands while adding no confinement. It does, however, **withhold the read-only auto-approve**, because auto-approval bypasses that permission list and nothing else had a chance to authorize the path. Withheld when: an extracted read target resolves outside `repo_root` after `~` / `$VAR` expansion (existent or not, and an unexpandable `~-` / `~+` / `~N` counts as outside); a glob's literal prefix is outside, or its expanded matches escape the repository through a `..` after the wildcard or through a symlink (containment is decided on the resolved match, as for a literal target); the command carries a `~` word, which is outside the repository by definition and which the extractor does not model for non-reader commands like `ls`; or a word is an ABSOLUTE path outside the repository (`ls /etc` — the same class as the `~` word, and `ls` is not a reader the extractor models), or the command carries a shell expansion — `$NAME`, `${…}`, or a `$'…'` / `$"…"` quoting construct — decided by tracking QUOTE STATE over the raw command, since bash expands inside double quotes, `$'` opens a construct mid-word (`cat /etc/host$'name'`), and the `$` in `grep 'foo$'` is a literal only because it sits inside a single-quoted region — since `extract_bash_read_targets` declares `$VAR` operands as residue it cannot see and therefore proves nothing about where the read lands. A `$` that names nothing (`grep 'foo$'`, `$?`, `$$`) keeps its auto-approve. The cost of withholding is the fallback to the allowlist, not a block. That fallback is weaker than a refusal, measured on Claude Code 2.1.234 (2026-08-18) by launching the agentic leaf's own argv against a local Messages-API stand-in on `ANTHROPIC_BASE_URL` — turn 1 answers with a synthetic Bash `tool_use`, turn 2's request body carries the `tool_result`, so the permission layer's verdict is observed without a billed call — in a clean checkout carrying only the committed `.claude/settings.json`. The CLI applies its OWN read-only-command analysis ahead of that list: `sed -n '1,200p' <file>`, `find <root> -iname … 2>/dev/null`, `find . -path … -prune -o -name … -print 2>/dev/null`, `cat <file> 2>/dev/null | head -100` and pipes of them all execute although no committed entry matches, while `find . -delete` (refused by name, citing a `Bash(find:*)` prefix rule), `sed -i`, `rm` and `curl` are refused. Extending the auto-approve to those read shapes was therefore measured to change no outcome and was not implemented (issue #75); the 2026-08-07 log's own `post_command_execute` records show the same shapes executing under CLI 2.1.223 — 10 of the 11 commands the hook plain-allowed there carry one — which corroborates the shape class rather than the 2.1.234 verdict, for which the harness measurement is the only evidence. What that measurement DOES refuse is a Bash redirect to a file, in every position: as the whole command, and appended as a capture to a command an allow entry already permits. Both forms the documents taught — `... 2>workspace/tmp/<agent_run_id>/last_gate_stderr.txt` on the allowlisted run-gate command, and a stdout capture on the allowlisted `python3 workspace/tmp/*` route — answer `Output redirection to '<path>' was blocked. For security, Claude Code may only write to files in the allowed working directories for this session: '<repo root>'`, naming as allowed the very root the target sits under. The `2>`, `>` and `>>` spellings alike, new target and existing alike; `2>/dev/null` is unaffected, and both commands run once the redirect is dropped, so no `permissions.allow` entry is what fails. It executed on CLI 2.1.223 in the 2026-08-07 run (`post_command_execute` present), so this is a version regression; 2.1.223 was not re-run. **The premise that an appended capture rides its command's allow entry is therefore retired**: `docs/AGENT_CONTRACT.md`, `docs/CLI_REFERENCE.md`, `docs/RUNBOOK.md`, `docs/WORKSPACE_LAYOUT.md`, `docs/workflow/LAUNCH_PROMPT_REFERENCE.md` and the two `tools/orchestration_runtime.py` hints now state that a gate result is read from the command result, which carries stderr, and `test_instruction_surfaces_teach_no_redirect_into_the_tmp_root` admits no documented redirect into the tmp root at all rather than admitting the ones an allow entry covers. What is not restored is a gate result that outlives the tool call that produced it; that is issue #77.
  - The single canonical resolver for the protected out-of-repo set is `tools/hooks/common.py::protected_host_read_roots` / `backend_credential_home_paths`; `tools/orchestration_runtime.py::_backend_runtime_bind_paths` calls the same resolver for what it binds, so the bound set and the forbidden set cannot drift, and a test drives that profile function and asserts every rw path it returns is guarded. A new rw-bind must be added to the resolver, not spelled a second time. **That parity claim is about what the FUNCTION returns.** Since issue #63 a caller may pass `backend_rw_override`, which replaces that list wholesale, and both isolated backend homes do: an agentic claude leaf is bound `{<private home>, ~/.claude/.credentials.json}` and a codex leaf `{<private home>}`. The guarded set is therefore a SUPERSET of what such a leaf can write — never a subset, which is the direction that would matter — and the one credential file still writable stays inside the guarded `~/.claude`. The isolated homes are guarded too. That was **wrong in the first version of this change** and the correction is the point: both things the guard exists for are in those homes, and both arrive by a BIND, so inspecting the directory on the host shows neither. The operator's real credential file is bound over the home's placeholder (writably, for token refresh), so inside the sandbox `<home>/.credentials.json` IS the operator's secret — measured: `cat ~/.claude/.credentials.json` blocked while `cat <home>/.credentials.json` was ALLOWED, and a write through that bind reached the operator's file on the host. And ONE home serves every leaf of an orchestration, so `<home>/projects/<slug>/<arid>.jsonl` is every EARLIER leaf's full transcript — a `validate.judge` or `*.verify` leaf reading the producing leaf's transcript is the past-run state the workflow forbids, with no trace in any artifact. `tools/hooks/common.py::workflow_private_backend_homes` resolves the current orchestration's homes from host-authored `orchestration_meta.json`, keyed on the `METDSL_ORCHESTRATION_ID` the host set through the sandbox rather than on the hook payload's caller-influenced copy. **Residue:** the bound scope is the CURRENT orchestration's homes. A leaf does not need to learn another one's name to reach it — `Bash(python3 tools/audit_orchestration.py *)` is granted and that tool resolves any orchestration's home from `orchestration_meta.json`, so no path token reaches this guard; what it can surface is bounded by what the auditor prints (a dangling leaf's last tool name, an input preview, an interrupt excerpt, token counts), not the producing leaf's reasoning, and the same route existed against `~/.claude` before this change. Issue #64 has since moved the homes to `~/.met-dsl/homes/<orchestration_id>/<backend>`, and that CHANGES this residue rather than closing it. The homes are now under the operator-secret root, which is itself a protected root and is never dropped, so a Bash read of ANY orchestration's home fails closed — including the sibling homes this resolver does not name. What the resolver still decides for them is the block MESSAGE: `protected_host_read_roots` sorts longest-path-first, so the leaf's own home names itself while a sibling's is attributed to the HOMES ROOT `~/.met-dsl/homes` — which is a protected entry of its own since the relocation override was closed, and a longer path than the operator-secret root, so it wins the sort for everything beneath it. `~/.met-dsl` still names what sits directly under it (`operator_tokens/`, `start_claims/`). An earlier version of this sentence said a sibling was attributed to `~/.met-dsl`; that was measured before the homes root became an entry, and the test asserting it passed only because the suite redirects the homes root away from the home directory. That sort is load-bearing for attribution now in a way it was not when the homes lived outside the home directory. What does NOT change is the residue itself: the audit tool still resolves any orchestration's home from `orchestration_meta.json` and reads it in-process, so no path token reaches this guard either way.
  - Residue this boundary does NOT close, all in the "everything else" class and therefore owned by the permission list: a variable assigned in an EARLIER Bash call, a path assembled by command substitution (`cat "$(echo ~)/.claude.json"`), and a `cd` issued in an earlier call. The guard sees one command string at a time. Also unchanged and larger than all of these: an interpreter handed a script (`python3 workspace/tmp/<agent_run_id>/x.py`, which the agent contract sanctions and `permissions.allow` grants) reads the rw-bound credential home directly, with no Bash target for any of this to inspect. The Bash guard is an obstacle on one route, not a boundary around the paths.
  - **The host side of the same boundary, which no hook enforces and no check bounds.** The guards above constrain a LEAF. The workflow's own host-side code — the driver, the conductor, the failure diagnostician, the audit tools — is trusted and reads whatever it needs, including the operator's personal backend homes. What is recorded here is one decision and one residue, not a rule; two attempts to state it as a rule with an exhaustive exception list were both false, because nothing enumerates that set and prose cannot keep up with it. **The decision**: a design that would classify a leaf's failure, or account for its cost, by reading the operator's transcripts was proposed and REJECTED. Both now read what the host itself captured — `_classify_leaf_infra_error` decides a transport death from the `dialogs/leaf.{stdout,stderr}.log` capture taken at the spawn boundary, and since issue #47 each leaf's cost comes from its own result envelope (`tools/leaf_usage.py`) — because a record that lives only in a personal home is machine-local and volatile, so a judgment derived from it is not reproducible on another machine and leaves no trace in any artifact. **The residue**: several host-side paths do read those homes, and the set is not closed. Measured examples rather than an inventory — `resolve_claude_model_alias` reads the operator's `settings.json` for the model label a launch record carries; `_prepare_claude_workflow_home` and `_prepare_codex_workflow_home` resolve the credential to bind; `orchestration_diagnostics` reads `~/.claude/projects` for post-mortem launch-incident forensics and for the audit's legacy usage aggregation; `workflow_conductor._claude_session_resumable` reads it for a PURE leaf, which is required rather than merely allowed, since a pure leaf is given no private home and that is where its own transcript is written; and `_probe_codex_home_writable` writes a temporary file into `~/.codex`. Reading the homes the workflow AUTHORS — under `~/.met-dsl/homes/` since issue #64 — is not part of this at all. `docs/DEVELOPMENT.md` §Record placement is the general form of the decision.
  - The Read-tool half of the claim rests on the manifest WRITER, not on the hook: `_resolve_manifest_root` would honor an absolute `allowed_read_roots` entry, and what makes one impossible is `_write_read_access_manifest` normalizing every root through `_normalize_rel_posix` (which strips the leading `/`).
- Hook read decisions (allow and block, for `Read` / `Grep` / `Glob` / `Bash`) are appended to `workspace/orchestrations/<orchestration_id>/access_logs/<agent_run_id>.jsonl` with `"source": "hook"`, alongside the `run-gate --gate orchestration_read` lines that have no such key. The append is best-effort observability, never an authorization step: it never creates the directory (inside bwrap only the per-arid file is bound writable) and swallows every `OSError`, so the log is not an exhaustive record of reads.
- Tools the hook cannot validate are absent at leaf launch instead: since issue #71 an agentic claude leaf passes **`--tools` with an ALLOWLIST** (`orchestration_runtime.CLAUDE_LEAF_TOOLS`), and that value is DERIVED from this document's own `PreToolUse` matcher coverage — the leaf gets the tools a matcher can judge and nothing else, so putting a new built-in in a leaf's hands requires adding a matcher for it first (pure leaves pass `--tools ""` and get none). It replaces an enumerated denylist (`Task,WebFetch,WebSearch,NotebookEdit`) over a roster the VENDOR grows: measured on CLI 2.1.238, that argv left fifteen hook-unjudged built-ins in a leaf's hands, several of which defeated the denylist's own stated reasons — `Workflow` orchestrates subagents (why `Task` was denied), `Monitor` runs a long-lived script no matcher sees, `EnterWorktree` moves the working directory the read boundary is spelled against, `Cron*`/`ScheduleWakeup` outlive the run, and `DesignSync` reaches claude.ai through the operator's login. Under an allowlist a built-in the next CLI adds arrives OUTSIDE the leaf. That the installed CLI still offers exactly the allowed set is not assumed either: an unknown name is silently ignored rather than refused (measured), so the preflight check `claude_leaf_tool_roster_classified` captures the roster the leaf would actually come up with and fails on any difference in EITHER direction. **No MCP tool is covered by any of this**: `mcp__…` tools survive `--tools` (measured) and no matcher sees one. `mcp__build-runtime__*` is granted by `leaf_config/claude/settings.json` as a leaf-launch preflight requirement, and nothing validates what a leaf does with it. WHICH servers a leaf has is no longer an open set, though: since issue #63's final form an agentic claude leaf is launched with `CLAUDE_CONFIG_DIR=<private home> --setting-sources user --strict-mcp-config --mcp-config .mcp.json`, so its server set is the committed file and a server configured in the operator's `~/.claude` no longer reaches it — the same launch also stops that home's permission grants, skills, plugins and plugin hooks from reaching a leaf, and the bwrap profile no longer rw-binds that directory at all: an agentic leaf's writable backend paths are the private home plus the single file `~/.claude/.credentials.json`, bound so OAuth token refresh keeps working. The hooks in this document keep firing under it — measured twice, and the second measurement is the load-bearing one because the layer they live in CHANGED: first by launching that argv in workflow mode against an orchestration id with no manifest and watching the `PreToolUse` read guard block a `Read`; then, for the private home, by launching with `CLAUDE_CONFIG_DIR` set to a scratch home whose `user`-tier `settings.json` carried sentinel-writing `UserPromptSubmit` and `PreToolUse` hooks and observing both sentinels written (CLI 2.1.235, unbilled capture harness). Dropping the settings source would take the hooks with it, so this is what the whole relocation rested on. Measured on CLI 2.1.234 by launching that exact argv with `--debug-file` and asking the leaf to enumerate its own tools: `0` user skills, `0` plugins, `0` plugin hooks registered, and the only MCP tools in the roster are the six `mcp__build-runtime__*`. One residue the flags do NOT close: the CLI still fetches the account's claude.ai connector list from `api.anthropic.com` at startup (measured: `Fetched 4 servers`) — a network request the leaf's launch makes, though none of those servers enters its tool set. The closure above is about MCP SERVERS; the CLI's own built-in roster is a separate set, and it is closed by the `--tools` allowlist at the head of this bullet rather than by any of these flags. That closure is no longer interim: the hooks and the build-runtime grant now live in `leaf_config/claude/settings.json`, which the host copies into the private home under a SHA-256 pin and remounts read-only, so the repository's project layer is dropped entirely. The trust conditionality that applied to the project layer — an untrusted checkout dropping the committed grants with only a stderr warning while preflight stayed green (`docs/RUNBOOK.md` §0-2, issue #65) — does not apply to this launch shape: a user-tier grant in the private home was MEASURED to be honoured with no trust seed present (CLI 2.1.235, `tool_dispatch_end ... outcome=ok`), in a session where a control command was refused, so the permission layer was demonstrably alive during the measurement. A trust seed is written into the home anyway, since it was measured harmless and defends against a CLI that later does gate on trust. The unvalidated-MCP-call gap remains a live gap of the same class as issue #42, not something this enforcement covers. The build-runtime server's own capability gate is not one of them: a gated tool call that carries no `orchestration_id` is refused whenever the server runs under the workflow (`METDSL_ORCHESTRATION_ID` set, or `METDSL_WORKFLOW_MODE` set to a non-empty value other than `0`, in the server's environment — these reach the leaf, and the server the leaf spawns, because they are on the leaf's DECLARED environment and the bwrap profile `--setenv`s each one after `--clearenv`; bwrap no longer passes anything through), so a call through the registered server is either attributed to a capability or refused. Under the workflow `repo_root` must be the server's own checkout, so the capability the gate reads is the one the conductor wrote and not one the caller composed in its scratch directory. Outside a run the server is usable with no orchestration to attribute a call to. `detect_build_system` carries no capability — it executes nothing and no substep is granted it — and is refused outright under the workflow, since the marker files it reports on are a read the manifest boundary governs. Under an orchestration the caller-supplied inputs that decide what runs — `env`, `compile_project`'s `extra_args` and `target`, `run_syntax_check`'s `sources`, `project_dir` and `command_log_path` — are allowlists over what the workflow declares, not denylists over what has been noticed; `mcp_servers/README.md` is canonical for the rules and for the two constraints they place on where a checkout may live. **Residue**, two items. `run_program`'s `command` is caller-chosen argv by design and none of this covers it: the phase gate constrains its log placement and requires the joined command to mention `spec.ir.yaml`, so the `validate.execute` grant stays a general execution grant. And the workflow signal is the server process's own environment, so the refusal binds calls through the harness-registered server, not every invocation of the module — a leaf that can run a script can start `build_runtime_server.py` itself with the variables cleared, which is the pre-existing Bash/interpreter route recorded above.
- The Bash read guard is backend-independent: `.codex/hooks.json` routes Codex `Shell` calls through the same policy, so codex leaves get the same Bash and Read validation. The `Grep` / `Glob` matchers and the `--tools` allowlist are claude-specific. Since issue #71 a leaf holds `Glob` for the first time on a CLI whose default roster omits it, so its `pattern` — which names paths — is validated through the same read policy as its `path`, by the pattern's literal prefix; `Grep`'s `pattern` is a content regex and is deliberately not.
- `tools/hooks/lint_evidence.py` / `tools/hooks/syntax_evidence.py` are not event hooks but the host-authored, leaf-non-writable evidence certificates of the deterministic `Generate.gate` substep's lint and syntax checks (`<pipeline_root>/lint_evidence/<source_id>.json` / `<pipeline_root>/syntax_evidence/<source_id>.json`). The conductor writes them in-process (`workflow_conductor._gate_lint_check` / `_gate_syntax_check`, composed by `_gate_inproc`); `validate_pipeline_semantics --stage post_generate` certifies them; the write-attribution check in `tools/orchestration_runtime.py` exempts exactly those files scoped to the `gate` substep. See each module's docstring for the non-forgeability rationale. The same substep-granular scoping now also governs the bwrap `write_roots`: `compile.verify` / `generate.verify` / `validate.judge` are pinned to a single file (`ir_meta.json` / `source_meta.json` / `semantic_review.json`) rather than the step's whole directory, so the sandbox and the terminal FS-diff enforce the per-substep write scope structurally — a second layer beneath the pattern-based file-tool hook (canonical: `docs/ORCHESTRATION.md` §capability / write_root).
