# Hook implementation policy

Repository-maintenance reference for the hook system (where hook validation and invocations are defined). Hooks act on agents transparently; this is not required reading for a workflow agent at runtime (for recovering from a hook block, see the "Repair cheat sheet on a hook block" section of `docs/RUNBOOK.md`).

- `tools/hooks/common.py` is the canonical source for backend-independent validation. Backend-specific invocation specifications are absorbed by the adapters under `tools/hooks/adapters/`.
- `.codex/hooks.json` is the canonical source for Codex hook invocation definitions; the `hooks` section of `.claude/settings.json` is the canonical source for Claude Code (matcher/wiring details below).
- Codex `apply_patch` validation reads `tool_input.command` as the canonical patch program. `tool_input.patch` and `tool_input.patch_text` are compatibility fallbacks only. In workflow mode an absent, unparseable, or target-free patch program is denied.
- A Codex `PermissionRequest` response uses `hookSpecificOutput.hookEventName="PermissionRequest"` and an explicit `decision.behavior` of `allow` or `deny`. Other Codex command-hook allow responses remain empty.
- The Claude Code backend does not need a feature-flag probe, and the `hooks` requirement check is limited to the Codex backend. The common policy follows `evaluate_common_policy()` in `tools/hooks/common.py`.
- The `hooks` section of `.claude/settings.json` wires the 4 events `PreToolUse` / `PostToolUse` / `UserPromptSubmit` / `Stop`. Its `matcher` is an **exact-match string** (not a regular expression): write `"Bash"`, unlike `^Bash$` in `.codex/hooks.json`. Because the match is exact, a tool with no entry is never sent to the hook at all — the entry list, not the CLI dispatch in `tools/hooks/cli.py`, is what decides which tools are validated.
- `PreToolUse` has **six** matchers, in this order: `Bash`, `Write`, `Edit`, `Read`, `Grep`, `Glob` (all invoking the same command). `Bash` must stay first; tests address the hook command as `PreToolUse[0]`.
- Read-boundary enforcement (`read_manifests/<agent_run_id>.json` `allowed_read_roots`, policy id `read_manifest_read_guard`) covers, in workflow mode:
  - `Read` — its `file_path`.
  - `Grep` / `Glob` — their `path`. An **absent `path` is validated as the repository root** and therefore blocks unless the manifest grants the root: a pathless search reads the whole checkout. A **`Glob`** `pattern` is not validated, so one that walks out of the root — `../spec/*.md`, or an absolute pattern — still reaches past it (known residue; `**` only recurses within `path`). `Grep`'s `pattern` is a content regex and names no path; its unvalidated `glob` / `type` filters only narrow the search within `path`.
  - `Bash` — the read targets `extract_bash_read_targets` (in `tools/hooks/common.py`) can extract from the command, filtered to those that exist on disk inside `repo_root`; blocks carry `"via": "bash"`. A wildcard target with more than two wildcard path components is not expanded — it is validated at the literal prefix before its first wildcard, since every match lies under it (`glob.glob` is unbounded and this hook runs on every tool call). That is a superset test, so such a block names the prefix directory rather than a file, and can fire even when every real match would have been in-manifest; narrowing the pattern is the fix. This runs **before** the read-only auto-approve, so a command the manifest rejects can never be auto-approved. A literal `cd` inside the same command anchors the targets that follow it. Extraction is best-effort by design, and what it can see is bounded by a **fixed set of reader commands** (`_BASH_READ_CMD_NAMES`) plus their grammars. Accepted residue, all yielding nothing: (a) **any command outside that set given a literal path** — including the contract-sanctioned scratch-script route `python3 workspace/tmp/<agent_run_id>/x.py` — the script is authored with the `Write` tool, which this extractor never sees at all, and a heredoc body attached to any command is deliberately blanked — so a path the script reads is invisible here; (b) targets that exist only at runtime — `xargs cat`, `find -exec`, command substitution, process substitution `<(…)`, `$VAR`; (c) a `cd` issued in an EARLIER Bash call (the hook sees one command at a time; leaves are told never to `cd`). An empty extraction therefore means "nothing to authorize", **not** "safe".
- **Layer boundary: which layer guards which path class.** For the tools that name a path they READ — `Read` and `Bash` — authorization is split by where the path lives, and each class has one owner. (`Glob`'s `pattern` is the standing exception recorded above: it is validated through neither class, so enumeration outside `path` remains open residue.)
  - **Inside `repo_root`** — the read manifest (`allowed_read_roots`), enforced per tool as above. The manifest is repo-relative, so it can only ever authorize this class.
  - **Outside `repo_root`, protected** — `~/.met-dsl` (operator-only dismiss-violation tokens) and every backend credential home the bwrap profile rw-binds so the backend CLI can refresh its own auth (`~/.claude`, `~/.claude.json`, `~/.codex`, or its `CODEX_HOME` / `METDSL_HOME` relocation). These are **rejected fail-closed for Bash** by `evaluate_common_policy` in `tools/hooks/common.py` (policy ids `forbid_operator_secret_direct_read` / `forbid_backend_credential_direct_read`), on both backends and regardless of the reading command — the guard matches the path, not the argv0, so `od` / `xxd` / `read X < …` / `x=$(cat …)` / `..`-traversal / brace and glob spellings are covered, a relative wildcard being anchored exactly like a relative path (`cd ~ && cat .clau*e.json`). Containment is tested BOTH ways for a recursive reader: `grep -r … ~`, `ls -R ~`, `find ~ -exec cat {} +`, `tar cf - ~` name an ANCESTOR of a root and read it, with no expansion trick at all. Which flags make a command recursive is read PER COMMAND (`cp -a` is an archive copy, `ls -a` merely shows dotfiles), and the ancestor test applies only to real OPERANDS — not to the words the quote-collapsed copy of the command splits prose into (`echo "docs / runtime"` yields a bare `/`), and not to a `cd`'s own operand, excluded by INDEX rather than by spelling (`cd .. && grep -rn foo repo/docs` resolved `..` against the anchor that same `cd` produced; excluding the spelling instead let a prepended no-op `cd ~` disarm `grep -r … ~`). Each of those three fail-closed a real command from this repository's own logs; the quoted-but-real operand (`grep -r x '/'`) still blocks, because it is a token of its own. Because the shell resolves a path in ways `os.path.expandvars` does not, the guard tests **candidate spellings** of each token, not just its literal text: any `${HOME…}` parameter expansion — the value-TRANSFORMING operators (`/pat/rep`, `//pat/rep`, `^^`, `,,`, `^`, `,`, `#pfx`, `##pfx`, `%sfx`, `%%sfx`, `:off`, `:off:len`) are applied to the value, with their operand read as the GLOB bash reads it and with the shortest/longest distinction bash makes — matched by a bitset dynamic program rather than a translated regex, which backtracked catastrophically on `${V##*a*a*a*a*b}` — and the alternate-word operators (`:-`, `:=`, `:+`, `-`, `=`, `+`) are RESOLVED per expansion the way bash resolves them, from whether the variable is set and whether it is empty — with `+` inverting that test — rather than guessed as one all-or-nothing choice; a nested `${A:-${HOME}}` gets a second expansion pass, plus `${!V}` indirection, a variable assigned earlier in the SAME command including through another variable (`A=$HOME; B=$A; cat $B/…`), the bash-only tilde prefixes `expanduser` does not know (`~+`, `~-`, `~N`), the quoting constructs that hide a path from every literal match — ANSI-C (`$'\057etc'` IS `/etc`, a path containing no path characters) and locale (`$".claude.json"`), including the mid-token forms whose quotes shlex strips before this guard sees them, which survive as a bare `$` that is dropped when it precedes punctuation or a name defined NOWHERE (`~/.$'c'laude.json` arrives as `~/.$claude.json`; a `$` before a DEFINED name is a real expansion and is left to substitution), and every `cd` in the command — plus every `-C` / `--directory` / `--chdir` option OF A COMMAND THAT HAS ONE (`tar`, `git`, `make`, `env`, …, but not `rsync -C` / `scp -C` / `ls -C`, which mean something else), resolved against the segment's own argv0 — FOLDED in order so a relative walk lands where bash lands (`cd ..; cd ..`). The `cd` spellings covered are `cd ~`, a bare `cd` (which also goes to `$HOME`), `pushd`, `cd` with its own options, and a `cd` glued to a separator or wrapped in parentheses, including a separator glued to its target (`cd ~;cat x`). Candidates over-approximate deliberately: for a read guard, extra candidates can only block more. And where the emulation ENDS, the guard fails closed rather than falling through: a candidate still carrying `${`, or any command carrying `$(…)` / backticks, is one it could not resolve, and if a token also spells a protected root's own path component (`.claude.json`, `.codex`, `.met-dsl`, `.claude`) the read is treated as reaching it — which closes the class (nesting depth, arithmetic bases, POSIX classes, command substitution, whatever syntax comes next) instead of the instance. Two narrowings keep it from being blunt: a component that also exists INSIDE the checkout (`.claude/`, `.codex/` both do) only counts when the token reaches for HOME, starts with `~`, or the command has already left the repository through a `cd` or a `../..`, and an unresolved expansion naming nothing protected stays allowed. What it does not catch is a component SPLIT across a substitution (`.cod$(echo e)x`), where no token spells it.

    This hook is synchronous and every fan-out axis is attacker-chosen, so the candidate generation is bounded — but by RELEVANCE and WORK, never by a count of the things that could matter. That distinction is the whole design: a count cap is fail-OPEN to padding, because an evader writes N throwaway assignments (or `cd`s, or `${Z}` expansions) and puts the real one last. So: an assignment is kept when something in the command REFERENCES its name (with `${!V}` resolved through the assignment VALUES, since it names its target by value), and there is NO bound at all on how many assignments or how many bytes of them are carried — a count cap and then a byte budget were both shipped, and both fell to the same shape (pad until the bound is spent, then write the real assignment after it); the work is linear in the command's own length, which the OS already bounds; the assignment map is resolved to a fixpoint ONCE and each token then needs a single substitution pass, which is what takes the assignment count off the per-token cost; every `cd` fold step is kept as an anchor and every relative token is tried against all of them, because `.resolve()` follows symlinks and so even a `..`-free token can leave its base; expansions in a token are all substituted, the fan-out being two candidates regardless. What the work bounds can still drop, and therefore the residue they leave: a candidate that grows past `_CANDIDATE_MAX_LEN` while substituting (a cyclic chain such as `A=$B$B$B$B; B=$C$C$C$C; C=$A$A$A$A`, which multiplied the string per pass and made a 56-character command take over a minute); more than `_CD_FOLD_MAX` `cd`s in one command (the LAST ones are folded); a working directory deeper than `_CD_ANCHOR_MAX_DEPTH`; the tail of a `${X//pat/rep}` scan once (positions x pattern elements) exceeds `_GLOB_SUBSTITUTION_OPS_MAX`; and, only once (anchors x candidate tokens) exceeds `_RESOLVE_OPS_MAX` path checks, the anchors beyond the root-related ones and the two ends — a crafted command that pads BOTH ends and hides the decisive `cd` in the middle is the residue that leaves — a ceiling a plausible command does not reach, because each check is a lexical `normpath` with a syscall only where the path exists (a nonexistent path cannot be the symlink that would carry it out of its base, and leaks nothing either way). Uncapped, a ~13 KB command cost tens of seconds per tool call. Three accepted false positives, documented rather than carved out. (1) The raw-command marker match fires on a command that merely NAMES a protected path, so `grep -rn "~/.claude.json" docs/` blocks — this document and `TODO.md` both contain that string; the block message names the path, and searching for a different substring is the workaround. (2) An anchor applies to every relative token regardless of position, and `cd -` / `popd` / a subshell are not modelled as returning, so `cd ~ && cd work/<repo> && cat .claude/settings.json` blocks a read of the REPO's `.claude/` — use a repo-relative path without the `cd`. (3) The three audit skills that read a backend session transcript (`skills/workflow-audit-claude`, `skills/workflow-audit-codex`, `skills/workflow-timing-audit`) are operator-side procedures whose reads now block inside workflow mode; each carries a note saying so. Replaying 8046 real Bash commands from this repository's own hook logs (measured 2026-08-11), those transcript reads are the ONLY commands the guard newly blocks, and the auto-approve narrowing costs exactly one command (`echo "$PWD"`). That corpus is no longer reproducible: the retained `workspace/orchestrations/*/hooks/` logs hold 288 Bash `pre_command_execute` events over 29 orchestrations as of 2026-08-18, 280 distinct command strings, replayed as 283 (orchestration, command) pairs because a command shared by two orchestrations is validated against each one's own manifests, which today's hook classifies 108 auto-approve / 156 plain-allow / 19 block. A later replay must state its own corpus size and date rather than carry this number forward. A CREDENTIAL root with any containment relationship to `repo_root` — above the checkout, or inside it (a misconfigured `CODEX_HOME` either way) — is dropped rather than enforced. `_resolve_backend_rw_binds` rejects both directions on the bind side, so nothing under such a root is bound writable, while enforcing it would fail-close every in-repo read. The OPERATOR-SECRET root is never dropped: that justification does not apply to it, since it is not an rw bind at all, so a checkout placed inside or around `~/.met-dsl` keeps failing closed. One carve-out, matching the Read tool's: `~/.claude/projects/<repo-slug>/<session>/tool-results/<id>.txt` is where the harness saves an oversized tool output and then tells the agent to read it, so that shape is exempt for Bash too (`_is_persisted_tool_result_shape`), in every spelling (`~`, `$HOME`, `${HOME}`, absolute, or a glob over the same directory) and after symlink RESOLUTION — for the glob form too, whose matches are re-resolved individually — and only for a file with one hard link — `~/.claude` is an rw bind, so an exemption applied to the unresolved path is a place to plant a link. Shape-and-slug only, since the per-session check `_is_persisted_tool_result_read` makes needs an agent_run_id this layer does not have. The Read tool reaches none of the other paths by construction (an absolute home path cannot be in a repo-relative manifest). The rw-bind is what makes the Bash guard necessary: bwrap deliberately makes these paths writable, so their confinement cannot come from the sandbox.
  - **Outside `repo_root`, everything else** — the harness permission list. The hook neither authorizes nor blocks it: blocking would break benign commands while adding no confinement. It does, however, **withhold the read-only auto-approve**, because auto-approval bypasses that permission list and nothing else had a chance to authorize the path. Withheld when: an extracted read target resolves outside `repo_root` after `~` / `$VAR` expansion (existent or not, and an unexpandable `~-` / `~+` / `~N` counts as outside); a glob's literal prefix is outside, or its expanded matches escape the repository through a `..` after the wildcard or through a symlink (containment is decided on the resolved match, as for a literal target); the command carries a `~` word, which is outside the repository by definition and which the extractor does not model for non-reader commands like `ls`; or a word is an ABSOLUTE path outside the repository (`ls /etc` — the same class as the `~` word, and `ls` is not a reader the extractor models), or the command carries a shell expansion — `$NAME`, `${…}`, or a `$'…'` / `$"…"` quoting construct — decided by tracking QUOTE STATE over the raw command, since bash expands inside double quotes, `$'` opens a construct mid-word (`cat /etc/host$'name'`), and the `$` in `grep 'foo$'` is a literal only because it sits inside a single-quoted region — since `extract_bash_read_targets` declares `$VAR` operands as residue it cannot see and therefore proves nothing about where the read lands. A `$` that names nothing (`grep 'foo$'`, `$?`, `$$`) keeps its auto-approve. The cost of withholding is the fallback to the allowlist, not a block. That fallback is weaker than a refusal, measured on Claude Code 2.1.234 (2026-08-18) by launching the agentic leaf's own argv against a local Messages-API stand-in on `ANTHROPIC_BASE_URL` — turn 1 answers with a synthetic Bash `tool_use`, turn 2's request body carries the `tool_result`, so the permission layer's verdict is observed without a billed call — in a clean checkout carrying only the committed `.claude/settings.json`. The CLI applies its OWN read-only-command analysis ahead of that list: `sed -n '1,200p' <file>`, `find <root> -iname … 2>/dev/null`, `find . -path … -prune -o -name … -print 2>/dev/null`, `cat <file> 2>/dev/null | head -100` and pipes of them all execute although no committed entry matches, while `find . -delete` (refused by name, citing a `Bash(find:*)` prefix rule), `sed -i`, `rm` and `curl` are refused. Extending the auto-approve to those read shapes was therefore measured to change no outcome and was not implemented (issue #75); the 2026-08-07 log's own `post_command_execute` records corroborate it independently, since 10 of the 11 commands the hook plain-allowed there carry one and so executed. What that measurement DOES refuse is a Bash redirect to a file: `2>workspace/tmp/<agent_run_id>/last_gate_stderr.txt` — the capture form `docs/AGENT_CONTRACT.md`, `docs/CLI_REFERENCE.md`, `docs/RUNBOOK.md`, `docs/WORKSPACE_LAYOUT.md`, `docs/workflow/LAUNCH_PROMPT_REFERENCE.md` and two `tools/orchestration_runtime.py` hints all teach — is blocked as an output redirection even though its target is inside the session's own working directory, in the `2>`, `>` and `>>` spellings alike, to a new and to an existing file. `2>/dev/null` is unaffected. The gate's stderr still reaches the leaf in the tool result itself, so the taught form is a broken convenience rather than a lost diagnostic. It executed on CLI 2.1.223 in the 2026-08-07 run, so this is a version regression; it is recorded in `TODO.md` and is not closed here.
  - The single canonical resolver for the protected out-of-repo set is `tools/hooks/common.py::protected_host_read_roots` / `backend_credential_home_paths`; `tools/orchestration_runtime.py::_backend_runtime_bind_paths` calls the same resolver for what it binds, so the bound set and the forbidden set cannot drift, and a test drives that profile function and asserts every rw path it returns is guarded. A new rw-bind must be added to the resolver, not spelled a second time.
  - Residue this boundary does NOT close, all in the "everything else" class and therefore owned by the permission list: a variable assigned in an EARLIER Bash call, a path assembled by command substitution (`cat "$(echo ~)/.claude.json"`), and a `cd` issued in an earlier call. The guard sees one command string at a time. Also unchanged and larger than all of these: an interpreter handed a script (`python3 workspace/tmp/<agent_run_id>/x.py`, which the agent contract sanctions and `permissions.allow` grants) reads the rw-bound credential home directly, with no Bash target for any of this to inspect. The Bash guard is an obstacle on one route, not a boundary around the paths.
  - The Read-tool half of the claim rests on the manifest WRITER, not on the hook: `_resolve_manifest_root` would honor an absolute `allowed_read_roots` entry, and what makes one impossible is `_write_read_access_manifest` normalizing every root through `_normalize_rel_posix` (which strips the leading `/`).
- Hook read decisions (allow and block, for `Read` / `Grep` / `Glob` / `Bash`) are appended to `workspace/orchestrations/<orchestration_id>/access_logs/<agent_run_id>.jsonl` with `"source": "hook"`, alongside the `run-gate --gate orchestration_read` lines that have no such key. The append is best-effort observability, never an authorization step: it never creates the directory (inside bwrap only the per-arid file is bound writable) and swallows every `OSError`, so the log is not an exhaustive record of reads.
- Some tools the hook cannot validate are removed at leaf launch instead: `workflow_conductor.CLAUDE_LEAF_DISALLOWED_TOOLS` passes `--disallowedTools` on every agentic claude leaf (pure leaves already pass `--tools ""`). That list is an **enumerated denylist over a roster that varies with the CLI version**, so it is not a closed class — roughly twenty other built-ins ship unmatched by any hook. **No MCP tool is hooked or disallowed either**: `mcp__build-runtime__*` is granted by `.claude/settings.json` as a leaf-launch preflight requirement, and nothing validates what a leaf does with it. WHICH servers a leaf has is no longer an open set, though: since issue #63 step 1 an agentic claude leaf is launched with `--setting-sources project --strict-mcp-config --mcp-config .mcp.json`, so its server set is the committed file and a server configured in the operator's `~/.claude` no longer reaches it — the same launch also stops that home's permission grants, skills, plugins and plugin hooks from reaching a leaf, though the bwrap profile still rw-binds the directory itself (issue #63 step 2). The hooks in this document keep firing under it — measured by launching that argv in workflow mode against an orchestration id with no manifest and watching the `PreToolUse` read guard block a `Read`, which is the load-bearing check, since dropping the `project` source would take the hooks with it. Measured on CLI 2.1.234 by launching that exact argv with `--debug-file` and asking the leaf to enumerate its own tools: `0` user skills, `0` plugins, `0` plugin hooks registered, and the only MCP tools in the roster are the six `mcp__build-runtime__*`. Two residues the flags do NOT close. The CLI still fetches the account's claude.ai connector list from `api.anthropic.com` at startup (measured: `Fetched 4 servers`) — a network request the leaf's launch makes, though none of those servers enters its tool set. And the closure above is about MCP SERVERS: the CLI's own built-in roster is a separate set that the denylist has not kept pace with, and it now ships built-ins that defeat the denylist's own stated reasons — `Workflow` orchestrates subagents (why `Task` is denied), `Monitor` runs a long-lived script no `PreToolUse` matcher sees, `EnterWorktree` moves the session's working directory, `Cron*`/`ScheduleWakeup` outlive the run, and `DesignSync` reaches claude.ai through the operator's login. That is the version-varying roster this bullet already calls not a closed class; it is tracked separately as issue #71 rather than patched here, because changing what a leaf can do is not a configuration-surface change. That closure is **interim**: the hooks and the build-runtime permission grant live only in this repository's project layer today, so the project source cannot be dropped until they move to a leaf-only configuration directory copied into a private home. The project layer is itself conditional on workspace trust — in an untrusted checkout the committed grants are dropped with only a stderr warning while preflight stays green (`docs/RUNBOOK.md` §0-2). The unvalidated-MCP-call gap remains a live gap of the same class as issue #42, not something this enforcement covers. The build-runtime server's own capability gate is not one of them: a gated tool call that carries no `orchestration_id` is refused whenever the server runs under the workflow (`METDSL_ORCHESTRATION_ID` set, or `METDSL_WORKFLOW_MODE` set to a non-empty value other than `0`, in the server's environment, which bwrap passes through to the leaf and to the server the leaf spawns), so a call through the registered server is either attributed to a capability or refused. Under the workflow `repo_root` must be the server's own checkout, so the capability the gate reads is the one the conductor wrote and not one the caller composed in its scratch directory. Outside a run the server is usable with no orchestration to attribute a call to. `detect_build_system` carries no capability — it executes nothing and no substep is granted it — and is refused outright under the workflow, since the marker files it reports on are a read the manifest boundary governs. Under an orchestration the caller-supplied inputs that decide what runs — `env`, `compile_project`'s `extra_args` and `target`, `run_syntax_check`'s `sources`, `project_dir` and `command_log_path` — are allowlists over what the workflow declares, not denylists over what has been noticed; `mcp_servers/README.md` is canonical for the rules and for the two constraints they place on where a checkout may live. **Residue**, two items. `run_program`'s `command` is caller-chosen argv by design and none of this covers it: the phase gate constrains its log placement and requires the joined command to mention `spec.ir.yaml`, so the `validate.execute` grant stays a general execution grant. And the workflow signal is the server process's own environment, so the refusal binds calls through the harness-registered server, not every invocation of the module — a leaf that can run a script can start `build_runtime_server.py` itself with the variables cleared, which is the pre-existing Bash/interpreter route recorded above.
- The Bash read guard is backend-independent: `.codex/hooks.json` routes Codex `Shell` calls through the same policy, so codex leaves get the same Bash and Read validation. The `Grep` / `Glob` matchers and `--disallowedTools` are claude-specific.
- `tools/hooks/lint_evidence.py` / `tools/hooks/syntax_evidence.py` are not event hooks but the host-authored, leaf-non-writable evidence certificates of the deterministic `Generate.gate` substep's lint and syntax checks (`<pipeline_root>/lint_evidence/<source_id>.json` / `<pipeline_root>/syntax_evidence/<source_id>.json`). The conductor writes them in-process (`workflow_conductor._gate_lint_check` / `_gate_syntax_check`, composed by `_gate_inproc`); `validate_pipeline_semantics --stage post_generate` certifies them; the write-attribution check in `tools/orchestration_runtime.py` exempts exactly those files scoped to the `gate` substep. See each module's docstring for the non-forgeability rationale. The same substep-granular scoping now also governs the bwrap `write_roots`: `compile.verify` / `generate.verify` / `validate.judge` are pinned to a single file (`ir_meta.json` / `source_meta.json` / `semantic_review.json`) rather than the step's whole directory, so the sandbox and the terminal FS-diff enforce the per-substep write scope structurally — a second layer beneath the pattern-based file-tool hook (canonical: `docs/ORCHESTRATION.md` §capability / write_root).
