# Workflow Orchestration

This document defines the orchestration contract — the **conductor** (`tools/workflow_conductor.py`) that drives the whole `workflow` — and the independent-agent execution conventions for phases / substeps. It presumes the 5-phase structure `Spec -> Compile -> Generate -> Build -> Validate`.

## Related documents

- CLI reference of all subcommands: [`docs/CLI_REFERENCE.md`](CLI_REFERENCE.md)
- workspace artifact placement: [`docs/WORKSPACE_LAYOUT.md`](WORKSPACE_LAYOUT.md)
- workflow operation / startup (operator procedure): [`docs/RUNBOOK.md`](RUNBOOK.md)
- launch request templates (rendered by the conductor's `record-launch`): [`tools/prompt_templates/`](../tools/prompt_templates/)

## Purpose
- Hierarchize the workflow execution and separate phase responsibilities from audit responsibilities.
- Execute each `step` / each `substep` as an independent agent, and make the execution path traceable.

## Scope
- `Compile` / `Generate` / `Build` / `Validate`
- Per-`node workflow` phase execution, and the execution of in-phase `substep` (`generate` / `gate` / `static` / `verify` / `pre_judge` / `execute` / `judge` / `post_judge`; `gate` is the Generate deterministic checker substep, `static` the Compile one)

## term rules
- `phase` refers to the workflow's logical unit defined in the contract documents under `docs/workflow/WORKFLOW_CORE.md` and `docs/workflow/phases/`.
- `step` refers to the orchestration-level execution unit corresponding to one phase.
- `substep` refers to a lower execution unit decomposed from a `step`.
- `stage` is used only as existing field names such as `generated_by_stage`.
- The **conductor** (`tools/workflow_conductor.py`) is the orchestration actor: it drives the deterministic phase/substep loop, launches each `step` / `substep` as a leaf agent, and routes failures deterministically (escalating to a one-shot LLM diagnostician only on an unclassifiable failure). It is recorded in `agent_runs.jsonl` under an `orchestration_agent_run_id` with `agent_role=orchestration`.
- **Deterministic in-process execution.** The non-LLM substeps `Compile.static`, `Generate.gate`, `Build`, `Validate.pre_judge`, `Validate.execute` and `Validate.post_judge` are **always** run by the conductor **in-process** (no `claude -p` leaf, no `SKILL.md`) — it calls the build-runtime MCP handlers (`run_linter` / `run_syntax_check` / `compile_project` / `run_program` / `run_quality_checks`) or the static validators directly. `Compile.static` runs `validate_workspace_root.py` + `check_artifact_syntax.py` (on `spec.ir.yaml` + `ir_meta.json`) + `validate_pipeline_semantics --stage compile` (writing `compile_static_meta.json` under the IR dir) — the purely-static IR gates the verify leaf used to own — between `Compile.generate` and `Compile.verify`, and on a violation warm-resumes `Compile.generate` (a same-phase reopen), so the LLM `Compile.verify` is reached only on a deterministically-clean IR and launches no validator gate (it is a pure spec-cross-reference semantic pass). `Generate.gate` runs three checks in-process between `Generate.generate` and `Generate.verify` and writes ONE `gate_meta.json` (a `checkers` object with `lint` / `syntax` / `static` sub-sections, a `failure_categories` list in canonical order `syntax_error` → `lint_findings` → static-family, and a composed `failure_excerpt`). Its **lint check** runs `run_linter` over `source/<source_id>/src/` (always), writing a host-authored leaf-non-writable `lint_evidence/<source_id>.json` (certified by `post_generate`); a lint finding warm-resumes `Generate.generate` (a same-phase reopen) ONLY once it has been attributed to the leaf. A failing run is re-run over two isolated copies of `src/` — the host-authored basenames in one, everything else in the other — and the verdict is each copy's own exit status, never a read of the diagnostics. A finding on the host-authored side (`host_rendered_lint_findings`) or one neither half reproduces (`lint_finding_unattributed`) is TERMINAL on the first attempt: the leaf has no write authority over those files, so a warm retry re-authors the ones that were never the cause (issue #112). Its **syntax check** runs the `run_syntax_check` compiler front-end gate (mandatory gfortran `-fsyntax-only`, plus optional `METDSL_SYNTAX_COMPILERS` target-compiler stages) over the node + staged dependency-closure sources (always, independent of lint), writing a host-authored leaf-non-writable `syntax_evidence/<source_id>.json` (certified by `post_generate`); a compiler finding in the node's own source likewise warm-resumes `Generate.generate`. A failing syntax stage is first attributed by re-running the same compiler over two isolated source sets, never by reading the diagnostics text (a clean file still prints default-on warnings naming itself): a **canary** valid under every standard (if it fails, the invocation itself is unviable — typically an `impl_defaults.toolchain.standard` the compiler driver does not accept, which the leaf does not author), then the **staged dependency closure alone** (if it fails, the closure is at fault — either a dependency's certified source is defective, or this node's declared standard is narrower than the sound closure needs; the message names both causes and attaches the diagnostics, which say which). Each attribution terminalizes `fail_closed` (no `gate_meta.json` written) and dominates a co-occurring lint content failure, because the leaf authors neither the IR nor a dependency's certified source and no retry of this node could clear either. Every other compiler finding is the node's own and warm-resumes `Generate.generate`. Its **static check** runs `validate_workspace_root.py` + `validate_pipeline_semantics --stage post_generate` (the purely-static gates the verify leaf used to own) **only when the lint and syntax checks both pass** (otherwise its section records `status="skipped"` / `skipped_reason="lint_or_syntax_failed"`); a static violation likewise warm-resumes `Generate.generate`. A gate content failure carries route reason `gate_<cat1>+<cat2>+...`, so the LLM `Generate.verify` is reached only on a deterministically-clean source and launches no validator gate. The in-process bodies implement the in-source **Make** layout only (`build_system=make`; OBJDIR/BINDIR overrides, `make_test`); a non-Make `build_system` (cmake/meson/ninja) is rejected with a clear error rather than misplaced. A content failure (lint findings, compile/link error, post_build/post_execute violation, quality-check mismatch, runtime error) returns cleanly and routes via the Gate/Build/Validate decision tables (→ Generate etc.), exactly like the leaf era — EXCEPT for the three conditions the static validator answers with a dedicated exit code (3 `static_frontend_unavailable`, 4 `stale_dependency_ir`, 5 `host_authored_artifact_violation` — a violation whose SUBJECT is a file this repository authors, which the leaf has no write authority over, issue #112), which every gate reader that can receive them routes terminally on the CODE and never on the output text (the `post_build` and `--stage compile` readers do assign a failure_category, but neither code can reach them — see the comments at those two call sites), because a violation interpolates a path the leaf chose and any text scan of it was forgeable; a genuine conductor/MCP infra failure fail-closes as a transport error, as do the two `Generate.gate` syntax-check failures its attribution runs single out (an unviable compiler invocation; a defective staged dependency closure), neither of which any retry of this node could clear. They are the only substeps that are not leaf agents. The conductor still issues the `record-launch` → `record-child-return` → `finalize-child` bookkeeping so the executor is a normal `step` / `substep` `agent_run_id` with a capability and phase_state, but their launch prompt is a **minimal deterministic stub** (sentinel `Conductor-executed deterministic step` + core ids; no skill section), and the validator applies a reduced launch-prompt-marker set to it. `Validate.judge` is always a leaf (its independent LLM semantic check is essential), but the purely-structural `--stage pre_judge` gate it used to run is **hoisted to the conductor as two deterministic substeps wrapping the judge** (G4, mirroring `Compile.static` / `Generate.gate`). The `Validate.pre_judge` substep (index 0) runs a **dependency-DAG readiness** check before execute/judge (a `dependency_graph.json` sidecar `all_nodes` closure node not built+validated in its own pipeline authors `pre_judge_meta.json` `status=fail` and terminalizes `fail_closed`, reusing `validate_pipeline_semantics._closure_node_validated_in_own_pipeline`). The `Validate.post_judge` substep (index 3) runs the `--stage pre_judge` validator after the judge returns (scoped `--pipeline-root`/`--run-id`, with BOTH the post_judge substep's own arid AND the judge arid declared `--in-flight-agent-run-id`) and records the verdict + a severity `disposition` in `post_judge_meta.json` under the run-node dir. (Naming caution: the `post_judge` substep runs the validator stage literally named `pre_judge`.) `determine_substep_status` gates the post_judge substep on that verdict. Three **exit codes** are answered before the violations are classified at all, because they say the gate reached no verdict this run's judge could act on: 3 (`static_frontend_unavailable`), 4 (`stale_dependency_ir`) and 5 (`host_authored_artifact_violation`), all `fail_closed` — the severity rules below classify by artifact path, so left to them a bullet naming a run-node artifact would warm-resume a judge that cannot repair either condition. Otherwise: a **recoverable** violation (a judge-authored deliverable) warm-resumes the judge in place to re-author it; an orchestration-record/DAG **integrity** violation (or any `pre_judge` `fail`) is a **non-physics integrity blocker** the conductor terminalizes `fail_closed` (writing no routeable `fail` `step_result`, which the judge `pre_phase_complete` hook forbids atop a `pass` `semantic_review`); an **unknown** violation routes to the unified escalate LLM in prod, and terminalizes `fail_closed` in dev (G5). The judge leaf itself launches no validator gate (`ALLOWED_VALIDATE_PIPELINE_STAGES` is empty for all three validate substeps). See [`docs/workflow/phases/phase_03_build.md`](workflow/phases/phase_03_build.md) and [`phase_04_validate.md`](workflow/phases/phase_04_validate.md).

## phase / substep types

| phase | step type | substep |
|-------|-----------|---------|
| Compile | has substeps | `generate` / `static` / `verify` |
| Generate | has substeps | `generate` / `gate` (conductor-run deterministic; unions the lint / syntax / static checks) / `verify` |
| Build | single step | - |
| Validate | has substeps | `pre_judge` / `execute` / `judge` / `post_judge` |

## Requirements

### preflight and launch control
- Workflow execution runs exactly one conductor per `node` (started by `tools/run_workflow.py`).
- Before the workflow starts, the preflight of an execution platform that can launch the `step agent` and `substep agent` independently must be run. A failed preflight prevents workflow start.
- The `multi_agent` feature is advisory diagnostics for `backend=codex`; the conductor launches independent Codex CLI processes and does not use Codex subagents. Codex launchability requires headless JSON event streaming, thread-ID capture, enabled hooks, a writable `CODEX_HOME`, structured-output support, and the mandatory bwrap checks.
- The preflight of `backend=codex` must simultaneously satisfy `feature_states.hooks=true`, `checks.hooks_enabled.pass=true`, and `checks.codex_home_writable.pass=true`. `codex_home_writable` is CONSUMED here and has no producer anywhere in this repository (`git grep` finds the name only in this document, in the runtime's reader, and in tests), so what it inspects is not something this tree can be read to establish and is not asserted here. What IS checkable, and is the reason the question comes up: the isolated per-orchestration home is a different directory from the `CODEX_HOME` the auth file is read from — `_prepare_codex_workflow_home` resolves the latter from the environment and copies nothing out of it — so issue #64's move of the isolated home to `~/.met-dsl/homes/` changes nothing about whatever this check reads.
- A pre-existing `preflight.json` that contains `feature_states.codex_hooks=true` and `checks.codex_hooks_enabled.pass=true` is accepted only as a read-time compatibility input. A newly generated `preflight.json` must use `feature_states.hooks` and `checks.hooks_enabled`.
- The preflight must include `sandbox_runtime=bwrap` and `sandbox_enforced=true` as required conditions. When at least 1 of `checks.sandbox_bwrap_available.pass=true`, `checks.sandbox_bwrap_userns.pass=true`, or `checks.sandbox_bwrap_exec.pass=true` is not satisfied, the workflow must not start.
- The `hooks` feature decision is probed **host-side by the conductor** (`Conductor._ensure_codex_feature_cache`) once per `orchestration_id` and written to `workspace/orchestrations/<orchestration_id>/codex_feature_check.json` (the orchestration-dir ROOT, which is read-only inside the bwrap sandbox — NOT the leaf-writable `hooks/` dir, so a confined leaf cannot forge it). The in-sandbox native hook reads this cache read-only and fail-closes when it is missing/invalid.
- Making `preflight.json` `pass` by manual editing is forbidden.
- Just before launching a child `agent`, launchability must be re-checked by a live probe of the execution platform. On `fail`, `record-launch` and the child-`agent` launch are forbidden, and the workflow transitions to `fail`.
- Before starting each phase, run `workflow-launch-check`, and simultaneously check the required child-`agent`-type decision, execution-platform allowability, session-policy allowability, and dependency readiness.

### Leaf LLM configuration
- Which LLM runs a leaf is a property of the **`(phase, substep)`**, not of the run. `tools/llm_config.py` resolves a YAML file into one `ResolvedLeafEntry` per LLM leaf; the conductor asks that entry, never a run-wide backend name. `--llm-config <path>` selects the file; the default is `./llm.yaml`, resolved against `--repo-root`. That file is the OPERATOR's — gitignored, created by copying one of `docs/examples/llm_*.example.yaml` — because which model runs which leaf is a local decision, and a tracked default forces everyone who changes it to carry a permanent diff on a tree the run itself requires to be clean. There is no fallback when it is absent: a run resolved from a file nobody chose is a run nobody can reproduce, so startup fails with `llm_config_default_missing`, naming the path and the `cp` that creates it.
- The five LLM leaves are `compile.generate`, `compile.verify`, `generate.generate`, `generate.verify`, `validate.judge`. Every other `substep` is deterministic and in-process; naming one in a configuration is an error, not a no-op. `build` likewise has no LLM leaf and is rejected as a phase.
- **Resolution order** is `defaults` -> `phases.<phase>` -> `phases.<phase>.substeps.<substep>`, merged per field. A level that switches `provider` DROPS the inherited provider-scoped fields (`model`, `command`, `base_url`, `api_key_env`, `capabilities`): a model or wrapper command chosen for one transport does not name anything under another. The transport-neutral fields (`timeout_s`, `max_output_tokens`, `stream`) do inherit across a switch: they describe the endpoint's transport behaviour, not a provider's vocabulary, so two leaves pointed at the same gateway keep the same answer about it.
- **The samples spell out every phase, substep, provider, model and effort**, even though the resolution rules would let all five leaves inherit one `defaults` block. The file is the answer to "what runs where, and how hard does it think", and a sample should give a reader that answer by being read rather than by being re-derived from an inheritance chain. Omission remains legal and is the right choice once the copy is the operator's own. Four samples ship: `llm_claude.example.yaml` and `llm_codex.example.yaml` put every leaf on one CLI; `llm_openai_compatible.example.yaml` and `llm_anthropic_api.example.yaml` work through the HTTP providers on the two pure leaves, which is the whole surface those are admissible on. **Effort is uniform at `medium`, the current generation's own default** on both CLIs — and Codex lowered it from the `xhigh` its predecessor gpt-5.5 shipped, so the vendor moved the default down as the model improved. Overriding a vendor default needs evidence about the model that will actually run, and this repository's re-run measurements are NOT that evidence: they were recorded almost entirely on Opus 4.8, and a re-run rate is a property of the (model, effort, task) triple. Re-measure on the current model before tuning it. **The one economy is a model tier**, because that argument is structural rather than generational: re-runs were ~20% of every token spent and concentrated in the leaves that WRITE, and `generate.generate` (45% of tokens) was observed out to 7 attempts against a `MAX_ATTEMPTS_PER_PHASE` of 3, where crossing the cap fails the phase rather than costing one more attempt. So the writing leaves are the last to economise on any model, and `compile.verify` takes the cheaper tier: smallest leaf, re-ran in 3 of 93 nodes, reads an IR the deterministic `compile.static` gate already proved clean, and re-read downstream. `validate.judge` is left alone despite never being re-run, because nothing runs after it. Each config carries the measured table, and its caveat, in its own comments.
- `effort:` is the reasoning effort, in the PROVIDER's own vocabulary, and it reaches a different surface for each: `claude_cli` -> `claude --effort <level>` (`low` | `medium` | `high` | `xhigh` | `max`); `codex_cli` -> `codex --config model_reasoning_effort="<level>"` (`low` | `medium` | `high` | `xhigh` | `max` | `ultra`, read off the CLI's own `supported_reasoning_levels` and NOT the OpenAI API's `reasoning_effort` list, which differs in both directions; Codex has no `--effort` flag, and `--config` is the spelling `CODEX_EXEC_RESUME_REQUIRED_FLAGS` certifies by name); `openai_compatible` -> `reasoning_effort` in the request body (`minimal` | `low` | `medium` | `high`). It does not apply to `anthropic_api`, whose Messages API expresses the same idea as a thinking token budget rather than a level. A level the provider does not accept is rejected at load. An ABSENT effort says nothing and leaves the provider's own default in force — unlike `model`, there is no ambient alias the conductor is deliberately declining to pin, so a configured level is always passed.
- A `model:` NAMED IN THE FILE is pinned onto the launch (`claude --model <model>`; a `codex_cli` entry always pins one). When the file names none, no `--model` is passed and the choice is deliberately NOT pinned — which is the pre-existing rule and is what keeps a run without a declared model byte-identical to before. Since issue #63's final form an agentic claude leaf launches with `CLAUDE_CONFIG_DIR=<private home> --setting-sources user`, so what an unpinned launch resolves to is decided by the CLI itself rather than by the operator's `~/.claude`; the recorded `agent_model` for such a leaf is correspondingly a spec-side PREDICTION (`DEFAULT_CLAUDE_MODEL_ALIAS`), replaced after the run by the exact model the leaf's own result envelope reports. Declaring a model whose output ceiling is below `LEAF_MAX_OUTPUT_TOKENS` also requires setting `max_output_tokens:` on that entry, or every launch is rejected with the API's `max_tokens` error.
- A `command:` wrapper must forward BOTH channels. The leaf prompt arrives on the wrapper's **stdin** (a single argv element is capped at 128 KiB and a node's prompt exceeds it), while the host-side `/usage` probe still passes its prompt on **argv**. A wrapper that redirects `</dev/null`, or consumes stdin itself, launches the leaf with an empty prompt: `claude` refuses it with an explicit error, and `codex` — whose argv carries the `-` stdin sentinel — waits on an instruction set that never arrives.
- `defaults` also serves launches that carry no phase/`substep` — the failure diagnostician (`escalate`) — and must therefore be an agentic provider.
- **Capabilities are declared, never inferred.** `PROVIDER_CAPABILITIES` is the single authority; a configuration's own `capabilities:` list may only RESTRICT a provider's set, never extend it.

  | provider | backend token | `agentic` | `pure` | `warm_resume` | `mcp_tools` | `usage_probe` |
  | --- | --- | --- | --- | --- | --- | --- |
  | `claude_cli` | `claude` | yes | yes | yes | yes | yes |
  | `codex_cli` | `codex` | yes | yes | yes | yes | — |
  | `openai_compatible` | `openai_compatible` | — | yes | — | — | — |
  | `anthropic_api` | `anthropic_api` | — | yes | — | — | — |

- **HTTP providers are admissible only on the two `generate` leaves.** The rule is enforced as a capability comparison, not a provider-name test: the HTTP providers hold `pure` and not `agentic`, and each `substep` states what it requires (`compile.generate`, `compile.verify`, `validate.judge` require `agentic`; the two `generate` leaves accept either `agentic` or `pure`). A `claude_cli` entry restricted to `capabilities: [pure]` is refused on an agentic leaf under the same rule.
- Config load is fail-closed with NAMED rules (`LlmConfigError.rule`), which the startup envelope surfaces verbatim under `reason: invalid_startup_input`: `llm_config_unreadable`, `_not_a_mapping`, `_unknown_key`, `_unknown_phase`, `_unknown_substep`, `_unknown_provider`, `_missing_provider`, `_invalid_field`, `_field_not_applicable`, `_http_requires_base_url` / `_api_key_env` / `_model`, `_capability_exceeds_provider`, `_capability_insufficient_for_substep`, `_defaults_not_agentic`, and `llm_config_default_missing` when no `--llm-config` was passed and `./llm.yaml` does not exist. Run start additionally checks `llm_config_codex_cli_requires_model` — deliberately NOT a load check, so a configuration whose codex slug has been blanked stays loadable, diffable and testable while still failing before a run.
- Config validation cannot see node shape, so the pure-only rule has a **runtime half**: `_pure_leaf_substep` additionally requires the node's M3c form, and a node without a pure path (the `infrastructure` harness self-test — the other former shapes, a `c`/`cpp`/`mixed` toolchain and a physics node without exactly one infra dependency, are rejected upstream at spec-input / `Compile.static`) runs the shared agentic loop. An entry that lacks `agentic` on such a node fails the `substep` closed with `pure_only_provider_on_agentic_path` rather than launching into a loop it cannot run.
- **`base_url` conventions differ by provider and preflight cannot catch a mistake** (it validates only the URL shape, and any HTTP status counts as reachable). `openai_compatible` appends `/chat/completions`, so `base_url` MUST include the API version segment the endpoint expects (`http://localhost:8000/v1`). `anthropic_api` appends `/v1/messages`, so `base_url` must NOT (`https://api.anthropic.com`, which is also its default). A wrong convention passes preflight and then fails every leaf with `HTTP 404 from provider: ...` -> `pure_transport` -> `fail_closed`.
- **`max_output_tokens` applies to an HTTP entry and should usually be set.** Its default is `tools/llm_http_leaf.DEFAULT_MAX_OUTPUT_TOKENS` (32768) — deliberately NOT the CLI leaf's 128000 ceiling, which exceeds the whole context length of the local servers `openai_compatible` targets and is rejected as a client error, i.e. on the first attempt and without a retry. 32768 is sized on the artifact (the largest `CodegenBundle` in this repository is ~45 kB of JSON); a ceiling much below that turns every run into a truncation-repair loop instead. Size an override against the model's CONTEXT WINDOW rather than its documented maximum: the whole completion has to fit alongside the prompt, and streaming the answer does not change that arithmetic. The field does not apply to a `codex_cli` entry, and `timeout_s` does not apply to either CLI provider; declaring one there is rejected with `llm_config_field_not_applicable`, while a value INHERITED from a level on another provider is dropped rather than rejected.
- **Sizing `max_output_tokens` and `timeout_s` for an endpoint that bills reasoning against the output ceiling — the rule.** Sizing the ceiling against the artifact and the context window, as the bullet above requires, is necessary and NOT sufficient where the endpoint streams `reasoning_content`: there the ceiling is a COMBINED reasoning-plus-answer budget, and the reasoning has been the larger and the more variable half of it. Five consequences. (1) A ceiling below what the model spends thinking returns a ZERO-character answer, not a short one, so a value that is merely too small can produce no document at all. (2) A run that hit the ceiling tells you only a LOWER BOUND — that measurement is censored — while a run that finished tells you what that generation actually cost. (3) **Size against the largest COMPLETED consumption you have observed, and treat it as a bound that moves as runs accumulate, never as a requirement.** There is no arithmetic from artifact size to a safe ceiling, and a value derived from one closure has already been exceeded by the next one here (bullet after next). Recompute it over your own runs with `skills/workflow-timing-audit/scripts/leaf_token_report.py <orchestration_dir | orchestration_id>`, which reports what every leaf of a run actually spent. (4) The observed floor was specific to the model AND to the prompt, so treat a ceiling as non-transferable between entries; note that `max_output_tokens` INHERITS across a provider switch by the resolution-order rule at the head of this section, which makes an inherited ceiling on a second model the case to re-check first. (5) Move the ceiling and `timeout_s` together — raising the ceiling alone converts a truncation into a timeout — and check the deadline against the endpoint's LOADED throughput, not its idle one. **The configuration this repository runs**, as one worked pair rather than a formula: writer `max_output_tokens: 98304` with `timeout_s: 4200`, reviewer `32768` / `2400`. Measured against the corpus below that is ~20% over the largest completed writer draw and ~39% over the largest completed reviewer draw; at the slowest rate observed anywhere in it (17.6 tok/s) a full 98304-token draw would need ~5 585 s, more than the 4200 s the writer entry allows, so a large draw on a busy endpoint remains a `--resume` condition rather than a value to keep raising.
- **The measurements behind it.** Two closures of the same node on the same `openai_compatible` endpoint, `kimi-k3` writing and `glm-5.2` reviewing: `orch_20260806T115338Z_35903b8d` (2026-08-06, ceilings 65536 / 16384, failed) and `orch_20260807T002410Z_acf2b996` (2026-08-07, the worked pair above, passed) — 11 leaf requests in all. Every token, character, elapsed and throughput figure here is taken from those runs' own artifacts by `skills/workflow-timing-audit/scripts/leaf_token_report.py`; the runs are under `workspace/`, which is not tracked, so the figures survive here and the artifacts behind them are machine-local. **The failed closure.** Three writer attempts against 65536 reasoned 62 460 / 25 709 / 46 238 tokens for 65 536 / 35 923 / 58 080 output tokens at 28.3 / 29.3 / 36.9 tok/s; they are not three independent samples, since the second is a warm repair turn of the first (prompt 40 888 against 37 512) and the third follows a cold restart. The FIRST finished its reasoning at 62 460 and the ceiling then cut the answer after 3 076 tokens. Its reviewer, at 16384, produced 5 attempts that reasoned 16 315-16 431 against the ceiling and emitted a ZERO-character answer, every one `finish_reason: length`, on real substep prompts of 37 031-38 849 tokens; the zero is counted in CHARACTERS off the `delta.content` frames because at the ceiling the endpoint's token accounting does not close, `completion_tokens` minus `reasoning_tokens` landing between -47 and 69 on requests that wrote nothing. **The passed closure, which is what settles both sizes.** At 98304 the writer completed at 82 210 / 71 091 output tokens (68 830 / 59 486 reasoning) and at 32.8 / 37.5 tok/s; at 32768 the reviewer completed at 23 538 tokens — 23 438 of them reasoning, for an answer of 92 characters — at 59.8 tok/s. Those two `stop` results, not the truncations, are what the current ceilings have headroom over. **Cost and throughput.** A truncation is repairable, so a substep run spends its initial launch plus `MAX_BUNDLE_REPAIR_TURNS` repair turns — three launches at the current value of 2 — on documents that were never written; the exhausted category routes the REVIEWER's `generate` to a COLD restart (`GENERATE_VERDICT_FAILURE_ROUTING`), a fresh producer as well as a fresh reviewer, which is why the 5 truncations span two substep runs of three and two, while on the PRODUCER the same category routes to a warm `("generate", "reuse")` repair (`GENERATE_BUNDLE_FAILURE_ROUTING`). Two further reviewer launches of that substep produced no `usage` frame at all — one stream severed mid-flight, one an `HTTP 500` whose persisted body is the provider's error JSON rather than an event stream — and it was those two, classified `pure_transport`, that spent `TRANSIENT_RETRY_WALL_CLOCK_BUDGET_SECONDS` and terminated the phase; a truncation is a content category and is never charged to it. Rates across the two closures ran 17.6-59.8 tok/s on identical request shapes, halving within a single run (44.8 / 44.0 / 45.8 tok/s in the first reviewer substep run against 17.6 / 19.8 an hour later), and the longest single request took 2504 s. 65536 tokens inside `timeout_s: 2400` needs 27.3 tok/s sustained, and the truncating attempt above ran 2313.9 s — 86 seconds inside its deadline.
- **What was inferred about that endpoint and later retracted**, which is the reason to treat any of the numbers above as a floor under revision rather than a specification. Three retractions so far. Different models AND different prompts, which is why that pair is a warning and not a ratio.
- **An HTTP leaf STREAMS its answer by default, and the default is the fix.** Both HTTP shapes send `stream: true` (the `openai_compatible` one also sends `stream_options: {include_usage: true}`, without which an OpenAI-dialect stream reports no token usage at all) and read the reply as server-sent events. The reason is not latency: a non-streaming completion means the endpoint writes nothing until the whole answer exists, and any intermediary that bounds the interval between upstream READS cuts the connection long before the model is done. Measured, a `generate.generate` leaf on an nginx-fronted endpoint took `HTTP 504 Gateway Time-out` three times, on requests that ran 613.6 s / 612.3 s / 611.8 s, while the entry's own 2400 s `timeout_s` never fired — the gateway's ~600 s read timeout was what expired, and `timeout_s` is a client-side TOTAL that has nothing to say about it. A frame every few hundred milliseconds resets that timer. It moves the silence to the FRONT of the request rather than abolishing it — but only as far as the PREFILL: measured against one such endpoint, a reasoning model streams its thinking too, as `reasoning_content` deltas, so bytes flow from well before the answer begins. What remains silent is the queueing and prefill before the first token, and if that alone outlasts the intermediary's timeout the same 504 returns; the lever there is the entry's `effort` and prompt size, not `timeout_s`. `stream: false` is the per-entry escape hatch for an endpoint that cannot speak SSE; it restores byte-identical pre-streaming request bodies (there is no `"stream": false` on the wire — an escape hatch that adds a key is itself a new thing for a strict endpoint to reject), and it cannot be applied to a run already under way, because changing the file trips `llm_config_changed_since_launch`. The field does not apply to a CLI provider and is rejected there — including when written as `stream: false`, which is exactly the spelling an operator reaches for. **A stream that ends without its terminator is a TRANSPORT failure, never a short document.** Completion is `[DONE]` or a `finish_reason` for the OpenAI dialect (the union, because servers disagree about which they send) and `message_stop` for the Messages API, whose `error` event after a 200 outranks a `message_stop` that follows it. An `error` frame — the Messages API's `error` EVENT, or the OpenAI dialect's chunk carrying an `error` key — outranks any terminator that follows it, in both dialects. A severed connection produces none of these and is reported as `stream interrupted: ...` — wording chosen so the leaf-failure classifier tags it `llm_transport_flake` and retries it. A body that is not an event stream AT ALL (the endpoint ignored `stream: true`, decided on whether the body opens with an event-stream line) is reported as `response_not_an_event_stream: ...` instead and is deliberately NOT classifiable: it is a deterministic misconfiguration that reproduces on every launch, so it fails closed on the first attempt naming its own remedy rather than buying three re-launches. Passed through instead, a connection cut at 90% would reach the validators as a plausible-looking truncated document and spend bundle-repair turns blaming the model for a network fault. Whatever arrived is kept as `raw_response` even when the stream died, which is the only record of where it died. There is deliberately **no idle (inter-frame) bound** to go with the total one: a reasoning model can legitimately emit nothing for minutes before its first token, so an idle bound tight enough to be useful would kill the request streaming exists to save — and the total deadline already covers a stream that goes silent, because the socket timeout is narrowed to the remaining time on every receive.
- **An HTTP leaf is bounded by its entry's `timeout_s`, not by the leaf-timeout contract.** `METDSL_LEAF_TIMEOUT_SECONDS`, the process-group kill and the `leaf_timeout` event bound a CLI leaf, which is a process; an HTTP leaf is a request and none of them apply to it. Its bound is `timeout_s` (default `DEFAULT_HTTP_TIMEOUT_SECONDS` = 900 s), enforced as a WALL-CLOCK deadline over the response read — a socket timeout alone resets on every byte and never fires against an endpoint that trickles. A response body over 32 MiB is refused as transport, and the body is read one socket operation at a time so the deadline is checked between them (reading it in fixed-size chunks would not bound anything: a single `read(n)` loops internally until it has n bytes, with every inner receive resetting the socket timeout). The raw body is persisted as `launches/<agent_run_id>.http_response.txt`, with the API key's value redacted from it and from every transport-error string: the body is provider-supplied text, and a debug gateway or verbose proxy can echo the request headers back into it. Redaction applies to those DIAGNOSTIC copies only — never to the parsed document the run acts on, because a key that is a common substring (the placeholder keys local endpoints are configured with) would otherwise rewrite a valid reply. Redirects are refused outright: following one would forward the API key to the redirect target. A provider's HTTP status is reported as `HTTP <code> from provider: ...`, in the form the leaf-failure classifier reads, so the failure is TAGGED as `llm_rate_limit` / `llm_transport_flake` / `llm_overloaded` / `llm_client_error` rather than as an anonymous transport death. A transient tag (`llm_rate_limit` / `llm_transport_flake` / `llm_overloaded`) is re-launched in place by the bounded transient retry, on the pure substeps as well as the agentic ones — one 429 must not lose a run that has already paid for every earlier phase. Its budget is separate from the usage-limit waits and from the bundle repair turns, and none of the three can compound: a transient tag is never `llm_usage_limit`, and a transport death is never bundle-repairable. `llm_client_error` (a 4xx) is deliberately not transient and fails closed for an operator `--resume`, as does an exhausted retry budget. That budget is bounded in WALL-CLOCK as well as in launches: a retry is granted only while the already-dead attempts plus the one that just died stay within `TRANSIENT_RETRY_WALL_CLOCK_BUDGET_SECONDS` (600 s), because a failure that is a deterministic function of how long the request runs — the 504 above, which arrived within two seconds of the same duration every time — cannot be bounded by counting launches, and the count budget alone spent 33 minutes proving the third attempt was as doomed as the first. A cheap flake is untouched by it. A refusal emits `leaf_transient_retry_declined` (`reason`, `elapsed_seconds`, `spent_seconds`, `budget_seconds`) and then takes the same terminal path as an exhausted count. The error body is read through the same wall-clock deadline as a success body, under its own 64 KiB ceiling, so a gateway that trickles or floods its error page cannot outlive `timeout_s`.
- **A repair turn replays the conversation in memory.** An HTTP provider has no session to reopen, so `_run_http_leaf` re-sends the prior user prompt and assistant answer, and the repair turn renders the WARM (slim) prompt — it does NOT re-inline the closed context or `prior_document`, which the replay already carries. Input grows across the bounded repair turns of ONE substep run; the history does not survive the process, so a cross-restart reopen degrades to the cold path (full context, `prior_document`).
- Preflight is given the SHA-256 of the configuration snapshot its caller resolved and refuses to probe a file that has changed since: it runs in a subprocess and reloads the file, so without that check it could certify commands the conductor — which keeps the object it already loaded — will never launch.
- The `providers` map is re-probed in full whenever the live-preflight TTL expires, and the refreshed rows are persisted with the new `probed_at`. `probed_at` is the freshness claim for the whole document, so re-probing only `defaults` would leave a mixed configuration's other providers treated as fresh indefinitely — and `record-launch` would then create durable child state for a provider that has since become unavailable.
- An API key is never written to a configuration: an HTTP entry names the ENVIRONMENT VARIABLE (`api_key_env`), read at call time into a request header. Its value is never logged, recorded, or hashed, and it is redacted from every provider-supplied string the run persists or emits — including the model's own answer, which is redacted on the copy written to disk rather than in the value, because the validators parse that value and a key that is a common substring would corrupt a legitimate document.
- A `base_url` of plain `http://` to a NON-LOOPBACK host is rejected at load with `llm_config_insecure_base_url`: the key would go over it in cleartext, and the realistic cause is a typo or a LAN address. Loopback is allowed — that is where the local servers this provider exists for run — and `METDSL_ALLOW_INSECURE_LLM_BASE_URL=1` is the deliberate opt-in.
- A repeated mapping key is rejected with `llm_config_duplicate_key`. YAML keeps the last silently, and this file decides which model runs each substep and therefore what a run costs.
- **Data egress.** An HTTP leaf is answered from the conductor's own process over HTTPS to the operator-configured `base_url` — the host-assembled prompt (which inlines the node's specification, IR, and dependency surface) leaves the machine for that endpoint. There is no bwrap sandbox around it, and none is required: `bwrap` confines a leaf that runs model-directed tools against the filesystem, and an HTTP pure leaf runs none — its response is data passed to the same validators the CLI pure leaf's response reaches, and the empty-`write_roots` FS-diff still runs. The API key and the proxy settings are read from the CONDUCTOR's environment — the same one every spawned leaf receives — not from the process-global one, so a run's own credential and egress routing are what apply. `record-launch` marks such a launch `leaf_transport: "http"` with `sandbox_enforced: false`, so an audit can tell a skipped sandbox from a missing one.
- **Preflight** probes EVERY distinct provider a configuration can launch and records them under `preflight.json#providers`, keyed by backend token (the top-level fields keep describing `--backend`, i.e. `defaults`, so the payload is a back-compatible superset). `workflow-launch-check` tests MEMBERSHIP of that map — a launch naming a provider nobody probed is refused with `backend_not_probed` — and `record-launch` takes the launch's own token from its response payload rather than from the preflight's single `backend`. A payload without the map is a pre-adoption preflight, where membership and the former equality test coincide.
- An HTTP provider's probe checks three things, all fail-closed: the named environment variable is set and non-empty (its value is never recorded), `base_url` is a well-formed `http(s)` URL with a host, and the endpoint answers. The reachability request is UNAUTHENTICATED and any HTTP status counts as reachable (a `401` establishes that a server responds, which is the property under test); only DNS failure, connection refusal, or a timeout fail it. `METDSL_HTTP_PREFLIGHT_SKIP_REACHABILITY=1` drops only that third check.
- **Provenance.** The invocation record carries `llm_config_path`, `llm_config_sha256` (the bytes that were parsed, hashed from the same read), and `llm_leaf_map` (the resolved provider, model and command of every leaf — the command because two leaves can share a backend token and still run different executables), and each `agent_runs` row carries its own `agent_backend` / `agent_model`. A `--resume` re-hashes the recorded file and refuses a changed one with `llm_config_changed_since_launch` (see `docs/RUNBOOK.md` §3-1). The cold start also copies the configuration's BYTES — the ones it hashed and resolved, not a second read — to `workspace/orchestrations/<id>/llm_config_snapshot.yaml`, and never rewrites it on resume: the operator's own configuration file is not under version control, so without that copy a refusal naming an edited or deleted file would name something unrecoverable. The refusal points at the snapshot when there is one.
- **There is no run-wide override.** The `--llm` / `--agent-model` / `--llm-command` trio is removed: the file is the only thing that says what a leaf launches, and `llm` / `llm_command` — which the runtime's `init` / `preflight` surface still speaks — are DERIVED from `defaults`. An orchestration that recorded no configuration pin, or recorded the removed flags' literals, therefore cannot be resumed (`llm_config_legacy_flags_removed` / `llm_config_changed_since_launch`); there is nothing left that could reconstruct which model ran which leaf. `apply_defaults_overrides`, which applied a run-wide model/command onto `defaults` and everything that inherited it, survives for one caller: the preflight subprocess, which re-applies the resolved defaults onto the file it reloads. Codex transport flags (`--dangerously-bypass-hook-trust`, the pure output schema) are deliberately NOT a configuration surface: they stay code-level so the preflight's flag certification keeps covering exactly what is emitted.

### phase type and agent type
- Before starting each phase, explicitly judge by phase type whether the target phase requires a `step agent` or a `substep agent`. `Compile` / `Generate` / `Validate` require a `substep agent`, and `Build` requires a `step agent`.
- Phase-artifact generation, MCP execution, and verification-purpose provisional implementation are performed only by a launched child `agent`, never by the conductor before the child leaf launch completes.
- The phase-artifact roots of `workspace/ir/` and `workspace/pipelines/` can be materialized only by a child `agent` that satisfies the 3 conditions of `record-launch`, a capability token, and `phase_state=child_running`. Direct generation by the conductor is forbidden.
- When a root-path reservation is needed before launching a child `agent`, generate only the reservation artifact `workspace/orchestrations/<orchestration_id>/reservations/<node_key_safe>/<step>.json`, and the actual directories of `workspace/ir/` and `workspace/pipelines/` must not be created.
- The conductor is responsible only for the progress control of the whole workflow, and must not directly generate the phase-body artifacts (e.g. `spec.ir.yaml`, `diagnostics.json`).
- As a substitute for workflow execution, a script that batch-automates the progress of multiple phases and artifact generation must not be newly generated or executed.
- The `Build` step is a deterministic process that calls the MCP `compile_project` and requires no LLM inference. The `step agent` limits its responsibility to the MCP call and recording the result.
- The conductor directly launches each substep of `Compile` / `Generate` / `Validate` as a leaf (`record-launch` + a `claude -p` / `codex exec` subprocess). The rendered launch prompt is delivered on the leaf's **stdin**, never as an argv element: a single argv element is capped at 128 KiB and a node's prompt exceeds it (`execve` fails with `E2BIG` before the model starts). `Conductor.leaf_command` therefore takes no prompt argument at all. An **agentic claude leaf is launched with `--tools` carrying an ALLOWLIST (`orchestration_runtime.CLAUDE_LEAF_TOOLS`, derived from the `PreToolUse` matcher coverage: `Bash,Edit,Glob,Grep,Read,Write`)**: the read boundary is enforced by that hook, which can only judge a tool whose payload names what it touches, so a leaf is given the judged set and nothing else rather than having a named few discouraged in the prompt. It replaced a `--disallowedTools` denylist in issue #71, which by CLI 2.1.238 removed four names from a roster of twenty-three and left nineteen built-ins of which the matchers judge four; `docs/HOOKS.md` is canonical for what that left open, and the preflight check `claude_leaf_tool_roster_classified` fails before init if the installed CLI's roster stops matching the allowlist in either direction. An agentic claude leaf is also launched with **`--setting-sources user`, `--strict-mcp-config`, `--mcp-config .mcp.json` (`workflow_conductor.CLAUDE_LEAF_MCP_CONFIG`) and `--disable-slash-commands`**, against a private `CLAUDE_CONFIG_DIR` the host prepares per orchestration (issue #63 final form): the `user` layer of that home is a SHA-256-pinned copy of the committed `leaf_config/claude/settings.json`, and the HOME ITSELF is bound read-only with a measured allowlist of writable state paths (`CLAUDE_HOME_WRITABLE_RELPATHS`), so the leaf's ENTIRE settings surface is what this repository declares — neither the operator's `~/.claude` nor this checkout's dev-only `.claude/` is in reach — and its MCP server set is the committed `.mcp.json` read directly. Three consequences are deliberate — an untracked `.claude/settings.local.json` no longer reaches a leaf; user-level skills, plugins, plugin hooks and any claude.ai connector no longer reach one (measured on CLI 2.1.234; the connector LIST is still fetched at startup, but no connector server enters the leaf's tool set); and a leaf whose configuration entry declares no `model:` takes the CLI's own default rather than the operator's. A fourth consequence completes what the interim `project` layer could not: because this checkout's `.claude/` is no longer a settings source, **its `CLAUDE.md` and the `AGENTS.md` that file `@`-imports are no longer injected into a leaf's first message** — measured on CLI 2.1.235 by capturing the leaf's own request against a marker file, with `project` and the CLI default as controls (marker present, 96,852 B) versus `user` (marker absent, 96,430 B). The home is read-only for a second reason, measured rather than assumed: under `user` the config directory is a live instruction surface — `<home>/CLAUDE.md` is injected as the user's private global instructions and `<home>/agents/*.md` join the subagent roster — and ONE home serves every leaf of an orchestration, so a writable one would let a `generate` leaf plant instructions that the later `validate.judge` leaf reads, with no artifact trace. `CLAUDE_CODE_DISABLE_AUTO_MEMORY` remains load-bearing rather than redundant: `projects/` must stay writable for transcripts, so the memory path inside it can still be created. Since issue #64 the home is DURABLE — `~/.met-dsl/homes/<orchestration_id>/claude`, with the codex twin its sibling — because it holds the leaf's only conversation record and a `/tmp` home took that with the next host restart. A vanished home still ROTATES (`claude_workflow_home_generation` bumped, prior threads cold-only) rather than making `--resume` unlaunchable, but the trigger is now an operator prune or a lost filesystem, and the re-created home is at the SAME path. Retention is indefinite and manual: `docs/RUNBOOK.md` §"The operator-private root" is canonical for the layout, the cost of deleting one, and `tools/prune_workflow_homes.py`. **Which MCP servers a leaf has is therefore pinned by `.mcp.json`; what a leaf DOES with an MCP tool is still covered by neither mechanism** — no `PreToolUse` matcher sees an MCP call and an `mcp__…` tool survives `--tools` (measured), so the allowlist does not remove one; see `docs/HOOKS.md`. A pure leaf passes `--tools ""` and gets no tools at all. An agentic claude leaf also passes **`--output-format json`** (issue #47), the same result envelope the pure path selects: for a `claude` leaf it is the only in-boundary channel that reports what the leaf cost and which model actually ran, and without it every agentic row recorded `usage: {"status": "unavailable"}` — the workflow does not read `~/.claude`. The envelope is **unwrapped at the capture boundary** (`_unwrap_agentic_envelope`, in `spawn_leaf`): `ProcResult.stdout` is the `result` string, exactly the model text every consumer read before — or, for the CLI's error variants (`error_during_execution`, `error_max_turns`, `error_max_budget_usd`, `error_max_structured_output_retries`), which carry no `result` but an `errors` string array, the `subtype` on a line of its own followed by one error per line, because three of the classifier's patterns are start-anchored and a `<subtype>: ` prefix puts every one of them out of reach — the infra classifier, the failure summary, `escalate`'s directive parser and the usage-limit scrape are all line-oriented and stop working on a one-line JSON document — while the envelope's `usage` / `modelUsage` / `total_cost_usd` ride the `ProcResult` fields for them and the raw envelope is what gets persisted to `dialogs/leaf.stdout.log`. An envelope this reader cannot parse is left as it stands rather than blanked, so the diagnostic evidence survives at the cost of the line-oriented consumers; reaching that state needs a capture cut at `LEAF_RAW_STDOUT_CAPTURE_MAX_CHARS` or a kill inside the CLI's single terminal write, since a leaf killed at the per-leaf cap writes nothing at all under either output format. A **pure** leaf is deliberately not unwrapped: its loops parse the envelope themselves and read `is_error` / `parse_error` off it.

### capability / write_root
- The changes to phase artifacts permitted to a child `agent` must be limited to under the `write_root` permitted by the capability token.
  - `Compile.generate` / `Compile.static`: `workspace/ir/<node_key_safe>/<ir_id>/` (`Compile.static` writes `compile_static_meta.json`)
  - `Compile.verify`: **narrowed to the single file pin** `workspace/ir/<node_key_safe>/<ir_id>/ir_meta.json` — the verifier authors only `verification_status`, so the certified `spec.ir.yaml` (and the rest of the IR dir) is not RW-bound to it and cannot be mutated post-gate.
  - `Generate.generate`: `workspace/pipelines/<node_key_safe>/<pipeline_id>/source/<source_id>/` — **agentic (residual non-`M3c`) generate leaves only**. On an `M3c` pure-leaf node this substep writes nothing: its `write_roots` is `[]` and the host authors the deliverables after the leaf terminates (§pure-function leaf (`Z2` generate-executor)).
  - `Generate.verify`: **narrowed to the single file pin** `workspace/pipelines/<node_key_safe>/<pipeline_id>/source/<source_id>/source_meta.json` (agentic leaves only; a pure-leaf node writes `[]`) — the verifier re-authors only that meta and never rewrites the producer sources, which the deterministic `lint` / `syntax` / `static` gates already certified.
  - `Build`: `workspace/pipelines/<node_key_safe>/<pipeline_id>/binary/<binary_id>/`
  - `Validate.pre_judge` / `Validate.execute` / `Validate.post_judge`: `workspace/pipelines/<node_key_safe>/<pipeline_id>/runs/<run_id>/<node_key_safe>/` (the two gate substeps author `pre_judge_meta.json` / `post_judge_meta.json` there)
  - `Validate.judge`: **narrowed to the single file pin** `workspace/pipelines/<node_key_safe>/<pipeline_id>/runs/<run_id>/<node_key_safe>/semantic_review.json` — the judge is a pure semantic pass authoring only that file, so the same-dir host-authored `verdict.json` (the R2 verdict) / `diagnostics.json` are not RW-bound to it.
  - The three narrowed file pins above (`compile.verify` / `generate.verify` / `validate.judge`) are pre-created by `build_bwrap_profile` and `--bind`-mounted at file granularity, so `bwrap` and the terminal FS-diff enforce the same per-substep scope as `allowed_output_paths` — a structural second layer under the pattern-based file-tool hook. A missing/malformed `source_id` / `run_id` collapses the pin to `[]`, which the empty-`write_roots` invariant rejects at launch.
- Changes under `ir_ref` / `pipeline_ref` are limited to a direct `Edit` / `Write` to a path enumerated in `allowed_file_tool_paths` of `output_manifests/<agent_run_id>.json` — uniform across extensions (managed `.json` / `.txt` included; under `bwrap` confinement the write is authorized by `write_roots` containment, see "file write paths" below).
- `record-launch` must generate `workspace/orchestrations/<orchestration_id>/output_manifests/<agent_run_id>.json` per child `agent_run_id`, and finalize `allowed_output_paths`, `allowed_file_tool_paths`, and `allowed_tmp_root` (`workspace/tmp/<agent_run_id>`). **Exception — a pure launch (§pure-function leaf (`Z2` generate-executor)) writes no output manifest at all**: a no-write leaf has nothing to manifest, and the manifest's *absence* is itself a validated tripwire (its presence on a pure arid is a sweep violation, since it would mean the pure launch took the write-bearing branch).
- **Required file-pin auto-inject for Make builds**: when the step is `Generate` and `spec.ir.yaml.impl_defaults.toolchain.build_system=make` **and the Makefile is not conductor-authored** — i.e. a non-fortran make family (c/cpp/mixed) — `record-launch` auto-injects the in-source `Makefile` (`<pipeline_ref>/source/<source_id>/src/Makefile`) into `allowed_output_paths` and flows it into `allowed_file_tool_paths`. The conductor lists each source file explicitly (so it auto-derives into `allowed_file_tool_paths` and is written with `Edit` / `Write`), but the extension-less `Makefile` is intentionally excluded from the source-extension set of the directory allowlist (`tools/hooks/common.py`), so without the explicit pin it cannot be written via any path and the child fail-stops mid-run to avoid guessing. The conductor usually just omits `allowed_file_tool_paths` (auto-derive). For a `make` ∧ `fortran` node — **leaf OR with dependencies** — the conductor authors `src/Makefile` host-side (`_resolved_makefile_host_authored` mirrors `Conductor._conductor_authors_makefile`); the pin is then **suppressed** and the file dropped from the child's `allowed_output_paths` (the child must not write it). For a dependency node the authored Makefile also carries the closure object rules, with each `<dep>_model.f90` staged into `$(OBJDIR)` at Build (Model B; see `docs/design/deterministic_followups.md`). **Reachability since the non-(make, fortran) node path was removed**: the `Compile.static` toolchain gate (`_validate_toolchain_backend_supported`) rejects any non-`fortran` `language` on every non-`infrastructure` node, so no physics `spec` node reaches this branch any more — it survives as the fail-safe default of `record-launch` (which must not grant a write it cannot justify from the payload alone) and as the path an `infrastructure` node on another language would take.
- **launch-time provisioning verification**: when, in a Make-build Generate launch, the required `Makefile` pin is missing from the finalized `allowed_file_tool_paths` (e.g. the caller passed an explicit `allowed_file_tool_paths` and missed the pin), `record-launch` **fail-fasts with a `ValueError` before launching the child**. This converts an artifact-contaminating mid-run fail-stop into a cheap, recoverable launch-time error.
- `record-launch` must generate `workspace/orchestrations/<orchestration_id>/read_manifests/<agent_run_id>.json` per child `agent_run_id`, and finalize `allowed_read_roots` and `denied_read_roots`.
- `record-launch` must generate `workspace/orchestrations/<orchestration_id>/sandbox_profiles/<agent_run_id>.json` per child `agent_run_id` **that launches a child process**, and finalize the `read_roots`, `write_roots`, and runtime bind composition needed for `bwrap` execution. Such a child launch allows only `bwrap` execution using that profile. The read-only bind of the CLI's install directory is derived from the launch response's `backend_command` — the executable THIS leaf is launched through — falling back to `preflight.json#probe_command` (the run's `defaults`) for a launch that records none. A leaf whose provider is answered over HTTPS from the conductor's own process (`leaf_transport: "http"`; see "Leaf LLM configuration") launches no process, so no profile is generated and none may be referenced; the `--stage pre_judge` pure-launch audit applies the same exemption, on the same two response fields.

### file write paths
- When a `step agent` / `substep agent` changes a phase artifact, the canonical invocation — uniform across extensions (managed `.json` / `.txt`, `.yaml` / `.yml` / `.md`, source code) — is a direct `Edit` / `Write` to a path enumerated in `output_manifests/<agent_run_id>.json.allowed_file_tool_paths`. Under mandatory `bwrap` confinement the write is authorized by `write_roots`-containment of the FS-diff at terminalization, so no gate step is involved (`guarded-apply-patch` and the `apply_patch_writes` gate have been removed — see §"Patch application contract (removed in P2-7)"). The MCP-owned `command_log.jsonl` is excluded from `allowed_file_tool_paths` and is written only by the MCP server.
- `spec.ir.yaml` is in `.yaml` format, so write it with `Edit` / `Write`.
- The direct execution of normal `apply_patch`, shell redirection, `tee`, `sed -i`, `perl -0pi`, and file writes via `python` / `sh` / `bash` are forbidden.

### agent_run recording
- For a phase that has `substep`, the conductor must launch the required `substep` group, make the completion judgment, and then finalize `step_result.json`.
- The conductor must judge the launchability of a `step agent` or `substep agent` based on the dependencies reconstructed from `deps.yaml` and `spec_catalog.yaml` and the `dependency` section of `spec.ir.yaml`.
- Every `agent` execution has an `agent_run_id` and must record the input references, output references, and parent-child relationship.
- Each line of `agent_runs.jsonl` requires recording `started_at` and `status`, and when `status` is a terminal status (`pass` / `fail` / `blocked` / `timeout` / `cancel`), requires recording `finished_at`.
- `fail_closed` is used only as a terminal status of `orchestration_meta.status`.
- The `agent_runs.jsonl` of the `step` / `substep` roles requires recording `parent_agent_run_id`, `agent_backend`, `agent_model`, `context_id`, `context_isolated`, `agent_session_id`, `launch_request_ref`, `launch_response_ref`, `launch_prompt_ref`, `launch_reply_ref`, `agent_result_ref`, and `agent_summary_ref`.
- The `parent_agent_run_id` of a `substep agent` points to the `orchestration agent_run_id` that launched that `substep`.
- The child leaf's `agent_run_id` is recorded as its `agent_session_id`.
- **`agent_session_id` is a bookkeeping id; the claude backend ALSO pins a real session to it.** The conductor reuses the child's `agent_run_id` (UUID) as its `agent_session_id` / `context_id`. For orchestration bookkeeping these are identifiers only, and the **canonical** record of a child's work is `workspace/orchestrations/<orchestration_id>/agents/<agent_run_id>/dialogs/` (the launch prompt/request, and the final reply/summary). However, for the **claude backend** the leaf is launched with `--session-id <agent_run_id>`, so Claude Code **does** write a real transcript at `~/.claude/projects/.../<agent_run_id>.jsonl`. That host transcript is what `repair_strategy=reuse` warm-`--resume`s (see the reuse-repair rule below); it is NOT mirrored into the orchestration artifacts, so a warm resume leaves no trace in `agent_runs.jsonl` (which still records `context_isolated: true`) — to tell a warm resume from a cold start, inspect the host `~/.claude` transcript, not the orchestration dir.
- `record-launch` must update `workspace/orchestrations/<orchestration_id>/session_run_index.json` immediately after launching the child, and record `agent_run_id`, `agent_session_id`, `context_id`, `agent_role`, and `status`.
- The `edge` of `agent_graph.json` uses `orchestration -> step` or `orchestration -> substep` as the canonical source.
- `agent_runs.jsonl` and `agent_graph.json` must be generated by sequentially appending in-flight events. Post-generation is forbidden.
- The `agent_runs.jsonl` row of the conductor itself is appended **only once, immediately after launch** with `agent_role=orchestration`, `status=running`. The conductor itself has no path to update this row via `record-agent-run` (a double invoke is rejected with `ValueError: duplicate agent_run_id`). At termination, `set-status` rewrites this row in-place to a terminal status with runtime privilege and assigns `finished_at` (it is a rewrite, not an append, so it does not hit the duplicate guard), and on resume (terminal reset) it conversely returns it to `running`. This is to prevent the agent_runs-based audit / `validate_workspace_root` from mistaking the orchestration row as permanently `running`, and the canonical terminal state of the whole orchestration continues to be expressed on the `orchestration_meta.json` side via `set-status`. For details, [docs/CLI_REFERENCE.md#record-agent-run](CLI_REFERENCE.md#record-agent-run) and [docs/CLI_REFERENCE.md#set-status](CLI_REFERENCE.md#set-status) are the canonical source.
- `record-launch` saves the launch request/response and issues the capability/manifests; it runs as part of the leaf launch.
- For an agentic claude leaf, `record-launch` must additionally record `claude_setting_sources` (the value the argv's `--setting-sources` carries), `claude_tools` (every value the argv's `--tools` occurrences carry, in argv order — issue #71; the tool set a leaf came up with is written down nowhere else, and it is what a later audit of "could this leaf have done that" turns on) and `mcp_config` (one `{ref, sha256}` per `--mcp-config` value, hashed from the file's bytes at launch). All three are read the way the CLI resolves them, which differs per flag and matters because an entry's `command:` prefix may already carry any of them: `--setting-sources` OVERRIDES, so the LAST occurrence is recorded (the conductor appends its own after the prefix, so that is always the effective one), while `--mcp-config` ACCUMULATES, so EVERY occurrence's values are recorded in argv order and every one of them is covered by the fail-closed read. `--tools` UNIONS — measured on CLI 2.1.239, a prefix naming `Monitor` puts `Monitor` in the leaf's roster and the conductor's own flag does NOT win — which is why every occurrence is recorded and why the preflight roster check probes the configured command rather than the bare binary. All three are DERIVED from the argv the leaf is actually launched with, and none is recoverable elsewhere: the recorded `sandbox_command` renders the backend command alone, and `orchestration_meta.json#repo_revision` carries only `{commit, dirty}`, so on a dirty tree the configuration's bytes cannot be reconstructed. An agentic claude leaf additionally records `claude_workflow_home`, `claude_home_generation` and `claude_settings_sha256` — the private home it came up in, the rotation generation that decides whether a recorded session may be warm-resumed into it, and the hash of the settings file it actually loaded. That last field closes the step-2 item "the settings file is hashed nowhere": the hash now covers `leaf_config/claude/settings.json`, the only settings layer a leaf reads. The process ENVIRONMENT is no longer outside this record. It used to be: the conductor passed the operator's shell environment through, so `ANTHROPIC_BASE_URL` could redirect the leaf's traffic and `ANTHROPIC_MODEL` could decide the model of any launch that passes no `--model` (both measured on CLI 2.1.235). A leaf's environment is now RECONSTRUCTED by `workflow_conductor._child_env` from `orchestration_runtime.LEAF_ENV_ALLOWLIST` and DELIVERED by the bwrap profile, which `--clearenv`s and then emits one `--setenv` per declared name — so a name the allowlist does not carry is absent from the leaf. There is no separate env field in the launch response: the record IS `sandbox_profile_ref -> sandbox_profiles/<arid>.json#env`, which the same object also `#rendered_command`s, so the record and the delivery cannot disagree about a name the record declares with a non-empty value. (Two deliberate exceptions, both pinned by test: an empty value is DROPPED rather than delivered as an empty string, and `TMPDIR` is supplied by the renderer when the record omits it. Neither is reachable from a production caller today.) Three faces this deliberately does not cover, named rather than fixed. An HTTP leaf has no sandbox profile, so its environment — including the credential its entry's `api_key_env` names — is recorded nowhere. The failure diagnostician that `escalate` launches builds its profile IN-PROCESS (`workflow_conductor._readonly_sandbox_profile`) and never reaches `record-launch`, which is the sole writer of `sandbox_profiles/`, so its environment is delivered under the same `--clearenv` discipline but recorded nowhere either. And the proxy / TLS families, together with the claude credential variables, are excluded by name — see `LEAF_ENV_NAMED_EXCLUSIONS` for each decision and what it costs. An unreadable `--mcp-config` file fails the launch closed. What each other launch records follows from its own argv, not from a per-provider rule. A codex leaf names none of these flags and records none of these fields; an HTTP leaf and a deterministic substep have no argv at all — the first spawns no process, the second runs in-process — so they are recorded about nothing rather than about a launch that did not happen. A PURE claude leaf is the one that is not simply absent: it names `--tools` with the empty value, so it records `claude_tools: [""]`, which distinguishes "launched with no tools" from "not a claude CLI leaf at all". (This paragraph said all four record nothing, which stopped being true when `claude_tools` was added.)
- `record-launch` must record `sandbox_runtime=bwrap`, `sandbox_enforced=true`, and `sandbox_profile_ref` in the launch response of a child-process launch. For an HTTP leaf it must instead record `leaf_transport=http`, `sandbox_runtime=none`, `sandbox_enforced=false`, and no `sandbox_profile_ref`; `record-agent-run`'s terminal validation grants the corresponding exemption only when the response carries BOTH that transport marker and an HTTP provider token, so a child-process launch cannot claim it.

An instruction or implication to read the implementation under `tools/` and extract rules is forbidden.
- The prohibition on reading the implementation under `tools/` applies to workflow execution and child-`agent` rule derivation. Repository improvement, maintenance, testing, and refactoring may inspect `tools/*.py` directly.
- The validator invocation by the child `agent` defaults to `run-gate`, and the canonical invocation is `python3 tools/orchestration_runtime.py run-gate --gate <gate_name> --agent-run-id <agent_run_id> --capability-token <capability_token> --args-json '<json>'`.
- The direct execution of a validator script is permitted only as an exceptional operation. The permitted targets are limited to `validate_workspace_root.py` and `check_artifact_syntax.py`.

(Under mandatory `bwrap` a write outside `write_roots` is impossible by construction.) The canonical MCP audit logs are handled by their own placement check. ### repair / retry
- The conductor must evaluate the child `agent`'s returned result and judge `issue_severity` (`minor` / `major` / `critical`). A verify finding is never tolerated.
- The conductor routes a verify finding by `issue_severity` (`classify_verify_severity`): `minor` → `repair_strategy=reuse` **same-phase reopen** of the phase's producer substep (warm-resume + slim finding injection); `major` / `critical` → `dev`: `fail_closed`, `prod`: `escalate` to the diagnostician (which decides how far back to recover — `reuse`/`restart`/`reopen`/`fail_closed`, INCLUDING a `restart` of **this phase's own producer**, e.g. regenerate the IR from scratch). Any decision that targets the current phase with a `repair_strategy` (`reuse`→warm / `restart`→cold) re-runs that phase's producer (rotating its id); a same-phase decision with no `repair_strategy` terminalizes. For non-verify failures it chooses `repair_strategy` per the relevant decision table.
- **The retry budget is spent only on findings the failing party can act on.** A deterministic gate must attribute its finding to a file, and the file to an author, before it routes: a finding whose subject is a file THIS REPOSITORY authors — the build control file, or an `M3c` node's host-rendered runner glue, both written before the leaf runs and both removed from its `allowed_output_paths` — terminalizes the node on the first attempt with a reason naming the producer, instead of being re-presented to a leaf that has no honest means to change it. Re-presenting an unsatisfiable verdict is not merely wasted budget: it is the pressure that produces a `leaf shortcut` (`AGENTS.md` §Development premises). A finding a gate can attribute to NEITHER author fails closed for the same reason, because assuming the leaf is how such a loop stays invisible. Issue #112; the `Generate.gate` categories are in `phase_02_generate.md`.
- The conductor must not directly perform the repair of a phase artifact itself. When a repair is needed, it must re-delegate to the child `agent` of the target `step` or `substep`.
- `repair_strategy=reuse` may be chosen only when it can converge with a local fix without changing the input contract and expected output of the target `step` or `substep`.
- `repair_strategy=restart` is chosen when any of contract reinterpretation, design reconstruction, or wide-scope regeneration is needed.
- On re-submission, regardless of `repair_strategy`, a new `agent_run_id` and a new `context_id` are issued.
- With `repair_strategy=reuse`, the `agent_session_id` may be reused. With `repair_strategy=restart`, a new `agent_session_id` must be issued.
- **Warm-resume reuse (claude backend).** For the claude backend, a `reuse` repair whose target session transcript still exists is **always** warm-`--resume`d (forked) so the repair leaf inherits the producer's context instead of cold-starting, falling back to a cold launch if the transcript was GC'd. `restart` repairs stay cold (anchoring avoidance) — so the warm/cold choice is driven by the failure classification's `repair_strategy` (deterministic-gate findings route `reuse`→warm; LLM-verify-attributed `restart`→cold). When a warm resume fires AND a findings excerpt is present (the `Generate.gate`/`Compile.static` reopens), the conductor sends a **slim findings-only repair turn** (the resumed leaf already holds the SKILL/contract docs); a warm reuse without findings re-sends the full prompt. Both behaviours are always-on (no env gate). Canonical: [docs/design/deterministic_followups.md](design/deterministic_followups.md) "G1-slim".
- The `launches/<agent_run_id>.request.json` on re-submission requires recording `issue_severity`, `repair_strategy`, `repair_target_agent_run_id`, and `repair_reason`.
- With `repair_strategy=reuse`, a step/substep `pass` no longer requires `apply_patch_writes` gate evidence (`_validate_apply_patch_gate_coverage` early-returns for step/substep), so there is nothing to inherit: a reuse retry that writes nothing terminates `pass` on its own, and a reuse retry that re-writes a path does so directly with `Edit` / `Write`. (Same-identity `(node_key, step, substep)` is still verified runtime-side.) With `repair_strategy=restart`, the contract is reinterpreted and output is regenerated from scratch.
- **verify-family meta re-author (still required for a different reason):** a `compile.verify` / `generate.verify` substep must produce its declared meta output (`ir_meta.json` / `source_meta.json`) to terminate `pass` — an inspect-only verify that writes nothing cannot `pass` (it has no `output_refs`). When the inspection finds nothing to change, re-author the meta anyway (refresh an idempotent field such as `verify_attempts`) with `Edit` / `Write`. The verify launch prompt MUST instruct the meta re-author as mandatory (not optional) — see the verify-family line of the `substep agent` template in [tools/prompt_templates/substep_agent.txt](../tools/prompt_templates/substep_agent.txt). **This bullet is the agentic (residual) generate-leaf contract; a `pure` verify leaf inverts it — see §pure-function leaf (`Z2` generate-executor).**

### pure-function leaf (`Z2` generate-executor)
- Under the `pure` `generate-executor` — the only executor since `M-F` (`docs/GLOSSARY.md`) — the `(generate, generate)` and `(generate, verify)` substeps run as pure-function leaves on an `M3c` node: Claude uses a `claude -p` turn with tools disabled, and Codex uses a sandboxed structured-output approximation; both return exactly one JSON document and make no repository writes. (A residual non-`M3c` node runs the shared agentic leaves instead.) This is a distinct executor class from both a full agentic leaf and a deterministic in-process substep (the "Deterministic in-process execution" rule of §term rules above): the executor is a normal `substep` `agent_run_id` with a capability and phase_state, but its capability is `write_roots == []` (`mode: "pure_readonly"`) and its launch prompt reads no `SKILL` and no `skill_must_read_refs`.
- **Deliverable vouch by on-disk existence.** A pure leaf holds no write authority, so it cannot itself produce an `output_refs` deliverable. Its terminal `agent_run` row therefore carries `output_refs == []` — enforced **in both directions**: a pure terminal `pass` row with a non-empty `output_refs` is a violation (a no-write leaf must not claim a write). The phase's declared required outputs (`phase_required_outputs`: `<source_id>/src/<spec_id>_model.f90`, `<spec_id>_checks.f90` on an `M3c` node, and `<source_id>/source_meta.json`) are written by the **host** after the leaf terminates and are vouched by their **on-disk existence** at pass-evaluation time (a declared-but-unwritten deliverable still fails — the anti-mock-green invariant holds). `codegen_bundle.json` is host-written but is **not** a required output: it is certified separately by the `post_generate` gate (`_validate_post_generate_bundle`), which re-runs the full bundle acceptance contract against it. This inverts the agentic verify-family meta re-author bullet above: an agentic verify leaf re-authors its own meta, the `pure` verify leaf returns a verdict the host projects onto `source_meta.json`.
- **Verdict-category failure routing → cold generate restart.** A pure leaf's bounded in-conversation repair (schema-malformed bundle / verdict) is capped; on budget exhaustion the failure category, excerpt, and per-attempt model/usage are persisted (`bundle_meta.json` for the producer, `verdict_meta.json` for the reviewer) and no `source_meta.json` / verdict projection is written (proof-of-work: no schema-valid verdict, no meta). A pure `generate.verify` verdict category does **not** route `reuse` to the verify session: a cross-phase reopen structurally returns to the `generate.generate` producer, and the exhausted reviewer session has no reuse value, so it routes `restart` → **cold `generate.generate`**. (A `minor` verify finding on a schema-valid verdict still routes `reuse` → same-phase producer reopen per the `### repair / retry` table; only the schema-failure categories force the cold restart.)
- **Persona separation.** A pure `generate.verify` leaf never resumes the producer's session (the separate-persona hard rule). The guarantee is **structural, not a check**: `_run_pure_verify_substep` accepts no external resume seed at all — the only session it ever resumes is its own prior attempt's `agent_run_id`, assigned inside its repair loop — so a producer arid is unreachable rather than rejected. (The pure producer, by contrast, does accept an external reopen seed, which is why the two are not symmetric.) The producer and reviewer are always launched under fresh, distinct `--session-id`s.

### leaf transient retry
- A leaf that exits nonzero because of an LLM-infrastructure fault is classified from its captured output into an infra tag (`llm_usage_limit` / `llm_overloaded` / `llm_rate_limit` / `llm_client_error` / `llm_permission_probe_unavailable` / `llm_transport_flake`), plus the out-of-band `leaf_timeout` (the hard-timeout bullets below), which the conductor assigns from its own record of the kill and never from the captured output. `stderr` is authoritative and the most severe tag in it wins; `stdout` — which carries the leaf's own prose — decides only when `stderr` names nothing. The exception is the two **non-retryable** tags `llm_usage_limit` and `llm_client_error`: found on `stdout` (where the CLI reports both, as its result text) they override a `stderr` tag, which can only ever remove a re-launch, never add one. The conductor retries a **transient** tag in place instead of terminalizing the run.
- Retryable tags: `llm_transport_flake`, `llm_overloaded`, `llm_rate_limit`. Budget: at most 2 retries (3 launches of the same `substep`). Backoff before each re-launch is per tag (`llm_transport_flake`: 2s, 10s; `llm_overloaded`: 15s, 60s; `llm_rate_limit`: 30s, 90s).
- Non-retryable, terminal on the first occurrence: `llm_usage_limit` (a hard stop of hours; an immediate re-launch consumes budget and delays the operator's `--resume`), `llm_client_error` (a 4xx: the request itself is rejected, so every re-launch reproduces it byte-for-byte), `llm_permission_probe_unavailable`, and an **unclassifiable** nonzero exit (a crash, an out-of-memory kill, or a hook denial is deterministic; re-running it reproduces the same failure).
- **Hard per-leaf timeout (`leaf_timeout`).** Every leaf spawn is bounded by `METDSL_LEAF_TIMEOUT_SECONDS` (default 7200s = 2h), at all four spawn sites (`run_substep`, the pure producer, the pure reviewer, the failure diagnostician). A value that parses to `0` disables the cap: the leaf's exit is still what ends the wait (so a leaf that answers and exits while leaking a pipe-holder still returns, and the post-exit stream waits are still bounded by `LEAF_TERMINATE_GRACE_SECONDS`), but no deadline ever expires, restoring the previous unbounded wait on the leaf itself; anything the parser cannot make sense of — unset, non-numeric, or carrying a leading `-` — falls back to the default rather than to `0` (a negative is a typo or a spelling of "no limit", and must not silently remove the backstop); a value above `LEAF_TIMEOUT_MAX_SECONDS` (2 147 483s ≈ 24.8 days) is clamped — a sanity ceiling, pinned to the largest deadline the `select`-based waits in `subprocess` accept before raising `OverflowError` instead of waiting (both leaf paths hand the whole remaining cap to `Popen.wait`, which does not overflow; the ceiling is kept at the platform limit so that any future deadline on a selecting wait cannot be invalid).
- **How the bound is applied.** The cap is a deadline evaluated before every wait, rather than a timer that kills and then relies on the pipes closing: killing the leaf's process group does **not** guarantee its pipes close, because `bwrap --new-session` puts the sandboxed command in a session of its own, so a tool subprocess the CLI leaked survives the group signal while holding the write end. Both backends therefore separate the WAIT from the READ. Each leaf's `stdout` and `stderr` are drained concurrently by reader threads, and the leaf itself is waited on with `Popen.wait` against the cap's remaining time — a wait that ends at the leaf's **exit**, not at its streams' **EOF**, so a leaf that answers and exits while leaking a tool subprocess that keeps the pipe is not waited out to the cap and then reported as a wedge. `codex` additionally moves the JSONL records off its pipe through a bounded queue, so the parse in the main thread is likewise bounded by the cap. Once the leaf has exited (or been killed), every remaining stream wait is bounded by `LEAF_TERMINATE_GRACE_SECONDS` and then abandoned, never by the cap: at that point only a leaked descendant can still hold a pipe. The teardown takes at most two attempts (the second following the group signal) and, on the `claude` path, both readers share ONE grace per attempt rather than taking one each, so the teardown adds a small bounded multiple of the grace to the cap rather than one grace per stream per pass. On both backends the reads are **fixed-size blocks off the raw fd** (`LEAF_STREAM_READ_BLOCK_BYTES`), never lines, and the conductor decodes them itself with an incremental decoder in the codec `Popen(text=True)` would have selected (`_leaf_stream_encoding`), so a multi-byte character split across a block boundary decodes whole and a malformed byte is escaped rather than raised. The block is the unit of every bound below: a budget checked per delivered line does not run at all against a producer that writes megabytes without a newline terminator. Both captures are budgeted on both backends — `stderr` at `LEAF_STDERR_CAPTURE_MAX_CHARS` plus a retained tail of `LEAF_STDERR_CAPTURE_TAIL_CHARS`, and `stdout` (the `codex` JSONL stream, and the `claude` leaf's answer) at `LEAF_RAW_STDOUT_CAPTURE_MAX_CHARS`, with the `codex` structured terminal events spliced in after them bounded by `LEAF_FAILURE_EVENTS_MAX` — because a drain the conductor gave up on keeps running and an unbounded appender would grow the driver's heap for the rest of the run; each capture is bounded by its budget plus at most one decoded block (bounded in turn by `LEAF_STREAM_READ_BLOCK_BYTES`, times four in the worst case, since `backslashreplace` expands a malformed byte to four characters), and truncation is recorded in the stream as `[conductor] leaf_stderr_capture_truncated:` / `[conductor] leaf_stdout_capture_truncated:`. On the `claude` path the stdout notice fires only past 4 MB, where the envelope is already unusable. `stderr` keeps its TAIL as well as its head, marked `[conductor] leaf_stderr_capture_tail:`, because every consumer of that stream reads the END of it — the infra classifier takes the last matching line as the terminal cause and the failure summary takes the last 400 characters — so a head-only capture would spend the budget on a chatty leaf's progress log and discard the error it died of, terminalizing the run untagged. Reading continues past the budget: a reader that STOPS leaves nobody draining a pipe nothing will close, and the leaf's next write then blocks forever — the cap would become the cause of the hang it exists to stop. The `codex` pump additionally holds at most `LEAF_STREAM_QUEUE_MAX_CHARS` of unparsed stdout ahead of the reader, so a leaf emitting large records applies backpressure to its own pipe rather than accumulating in the driver; that same value caps a SINGLE record, since one JSONL record can be arbitrarily large and is otherwise reassembled whole before any budget applies to it. A record that exceeds it — newline-terminated or not — is clipped where it stands and returned BEHIND `[conductor] leaf_stdout_record_truncated:` on the same line, so that a prefix which happens to be valid JSON can never be parsed as a complete record (a clipped `thread.started` would otherwise bind a host identity from a record whose real content was never seen); the rest of that record is discarded to the next newline — the stream resynchronizes there, so a clipped record costs its own contents and not the rest of the turn. That marker is distinct from `leaf_stdout_capture_truncated:`, which reports the total budget spent. An abandoned stream appends `[conductor] leaf_stream_abandoned:` to the captured `stderr` so a truncated capture is not mistaken for a leaf that wrote nothing (it appears on a killed leaf and on a passing one alike — it reports a still-open pipe, not a failure), and a leaf that exited on its own keeps its exit status. An abandoned reader observes the stop signal within one block while its stream is still delivering; a reader parked on a stream that has gone silent stays parked, with its thread and the two pipe fds, until the driver exits. The read ends are never closed: `close()` waits on the same internal lock a blocked reader holds, which would trade a leaked fd for a hung driver. On expiry the conductor signals the leaf's **process group** (`SIGTERM`, then `SIGKILL` after `LEAF_TERMINATE_GRACE_SECONDS`), appends its own marker line `[conductor] leaf_timeout: leaf exceeded METDSL_LEAF_TIMEOUT_SECONDS=<n> (elapsed <s>s); process group killed` to the leaf's captured `stderr`, forces a nonzero exit code, and emits `leaf_timeout` (`node_key`, `step`, `substep`, `agent_run_id`, `backend`, `timeout_seconds`, `elapsed_seconds`, `leaf_exit`, `stdout_chars`, `stderr_chars`, and `raw_stdout_chars` for `codex`). Whatever had already reached the conductor's pipes, and was still readable at the kill, is retained and persisted under `agents/<agent_run_id>/dialogs/`; the marker is appended, never substituted. In practice that is mostly `stderr`: a `claude` leaf emits its result text only when the turn completes, and the `codex` timeout path returns an empty `stdout` (its evidence is the raw JSONL event stream in `dialogs/leaf.stdout.jsonl`). The tag is decided by the conductor's own record of the kill (`ProcResult.timed_out`), **not** by recognising the marker: it outranks every infra line in the leaf's own output — the kill is the terminal cause, not the quota or transport message the leaf was last retrying — and because no classifier pattern matches the marker, a leaf that writes the same line cannot claim the tag and cannot suppress a genuine `llm_usage_limit`. The kill is bounded, not guaranteed to be complete: a tool subprocess the leaf started runs in the sandbox's own session and can survive the group signal, so every post-kill wait is capped by `LEAF_TERMINATE_GRACE_SECONDS` and the streams are then abandoned rather than waited for.
- `leaf_timeout` is **non-retryable**: a re-launch spends another full cap of wall-clock on a leaf that has already demonstrated it can wedge, and the budget would allow three of them. In the three `substep` loops the attempt is terminalized **in band** by the ordinary `finalize-child` chain (the conductor synthesizes the reply, so a leaf that never answered still terminalizes with evidence instead of staying `running`), and the phase `fail_closed`s under the reused `leaf_transport_error:` prefix — so the tag inherits the `leaf_transport_error` `reason_code`, and `--resume` is `substep`-granular wherever item 51's preconditions hold (a `verify` death in `Compile` / `Generate` on an unmoved `repo_revision`); otherwise the resume re-runs the phase. The failure diagnostician (`escalate`) is the exception on the terminalization side: it has no child `agent_run_id` and no `finalize-child`, so a diagnostician killed at the cap emits `leaf_timeout` and then terminalizes as `<phase>_diagnose_unparsable` (an un-launchable or unreadable diagnosis is conservatively terminal by design), not as `leaf_transport_error`. Its partial output is **never** parsed as a routing directive: a leaf whose turn the conductor cut short does not get to spend a phase attempt on a directive it had half-written. A conductor that **died** leaves its leaf orphaned instead; that case is recovered by the crashed-driver liveness path (`docs/RUNBOOK.md` §3-1, §Incomplete launch recovery), and `record-timeout` remains the manual finalization procedure for a leaf the conductor did not finalize itself. A stream-idle watchdog, which would catch a wedge sooner than a hard cap, remains future work; it is now equally reachable on both backends, since both read through the same block-reader threads and either could take an idle deadline directly. The HTTP pure-leaf transport deliberately did NOT take one when it moved to server-sent events: a leaf process that has gone silent is a wedge, while an HTTP request that has sent no frame yet may simply be a reasoning model still thinking, so the two surfaces do not share the argument.
- **Opt-in `--wait-usage-reset` (default OFF)**: `llm_usage_limit` is still terminal by default, but with the flag set AND a **resolvable reset instant** — from the host-side `/usage` probe (the PRIMARY source, next bullet) or, failing that, from the dead leaf's terminal usage-limit line — the conductor instead **waits it out in place** and re-launches the same `substep` — a same-run, substep-granular resume instead of a next-day manual `--resume`. Two forms resolve, tried in order on the dead leaf's TERMINAL usage-limit line: (1) a **machine epoch** — a trailing `|<unix-epoch>` (`_parse_usage_reset_epoch`); (2) a **TZ-anchored human reset** — a wall-clock time-of-day plus a parenthesized IANA timezone, e.g. `resets 10:20pm (Asia/Tokyo)`, resolved by `_parse_usage_reset_human` to the occurrence nearest `now` (yesterday/today/tomorrow) within a 15-min grace so a minutes-stale message floors to a margin-only relaunch. The real CLI emits form (2), so (2) is what arms the wait in practice; (1) is kept first for backward-compat. A human reset **without** a parenthesized IANA timezone (`resets 6:10pm`) or without a time-of-day (`resets Monday`) is NOT resolved — the instant is never guessed from the conductor host's local timezone (that would make the wait depend on where the run executes and could wake into a still-shut window), so it declines. The terminal line is resolved **stderr-first, with a narrow stdout carve-out** (`_terminal_usage_limit_line` / `_sole_content_usage_limit_line`). This is **strictly narrower** than the classifier's cross-stream rule, not a mirror of it: `_CROSS_STREAM_PROMOTING_TAGS` lets a stdout match *outrank* a stderr one, whereas here a stderr usage-limit line always wins and stdout may only fill a stderr silence. The carve-out is required, not a relaxation: the real CLI reports a usage limit on **stdout** with an **empty stderr**, so a stderr-only rule made the flag inert in production — an opted-in E2E run still `fail_closed` with `leaf_usage_limit_wait_declined(no_reset_time)`. It arrives in **two** recorded shapes and both are admitted, the direction the code relies on being ``envelope ⇒ the CLI authored this stdout`` (true by construction — `allow_envelope` is passed only for a `claude_cli` **pure** launch; a codex or HTTP pure leaf writes its own answer to stdout, and an agentic claude leaf's envelope was already unwrapped at capture, so a JSON line in either is *model*-written and its keys prove nothing); the converse is not assumed, since a pure launch may still abort bare and the bare path accepts it. Every count in this bullet comes from ONE sweep of the recorded workspaces (2026-07-24, 711 leaf stdout logs) — read them as that snapshot, not as today's totals. In it an envelope appears *iff* the launch was pure: **bare** for every agentic launch (5 of the 6 incidents across all recorded workspaces — stdout is the ~59-char message) and **enveloped** for the single pure launch (the CLI put the message in `result`, alongside its own `is_error` / `api_error_status` / `terminal_reason`). Since issue #47 the CLI writes an envelope for an agentic launch too, but the capture boundary unwraps it (see "leaf launch" above), so what reaches this scrape is the bare shape either way — which is what keeps `--wait-usage-reset` armed for an agentic leaf. `_cli_abort_envelope_result` unwraps the enveloped shape before the shape clauses run **against the inner text**; it is reached only for a `claude_cli` **pure** launch (`allow_envelope`), is bounded by `_CLI_ABORT_ENVELOPE_MAX_CHARS` (a parse-cost guard only, deliberately far above every recorded envelope — sizing it to the one recorded abort envelope would decline the fatter ones the CLI's own accounting blocks produce), and is gated on those CLI-authored keys, so a *recovered* envelope (`is_error:false`, even when it reports an error status it retried past) and an ordinary completed envelope are never unwrapped, and model-authored `result` prose stays inert. Admitting only the bare shape left the flag inert for the two pure loops — where the expensive substeps live — i.e. the original bug one layer in. Because the wait ADDS a multi-hour sleep + relaunch (unlike the tag promotion, which only ever REMOVES a re-launch), stdout arms it only in the CLI's **abort shape** (the *tagging* pattern is deliberately one notch wider — it also matches the message at the head of an envelope's `result`, since a strictly line-anchored pattern cannot see it there and the fallback phrases cover only the `usage`/`session` windows): a *single* non-blank line, no longer than `_CLI_USAGE_ABORT_LINE_MAX_CHARS`, *opening* with the limit (`_CLI_USAGE_ABORT_LINE_RE`, anchored — deliberately narrower than the classifier's bare `usage limit` / `session limit` phrase match: either the observed lead-in `You've hit your <window> limit` plus a reset-instant cue, or the machine form `<window> limit reached|<epoch>`, which requires BOTH the `reached` wording and the epoch suffix — without them that alternative degenerates to "`<window> limit` at line start", which an agentic leaf's own one-line prose satisfies), and **not** a recovered retry banner. A fifth clause requires the line to match the classifier's usage pattern too; it is provably implied by the others (both abort alternatives are subsets of the classifier pattern, whitespace spelling included) and kept as a defensive invariant, with the implication itself asserted by a test. The weaker "every line matches the usage pattern" formulation would have been just as inert in the opposite direction: a pure leaf's entire stdout is ONE line (a JSON envelope with newlines escaped — 15 of the 46 stdout logs in the live workspace, 112 of 711 across all recorded workspaces, up to 47 kB), and an agentic leaf's result text can be one unbroken paragraph, so any model-authored text mentioning a limit would have satisfied a per-line test. A wording the anchored pattern does not recognise declines — degrading to today's `fail_closed`, the safe direction, and emitting `leaf_usage_limit_wait_declined` so the next unrecognised envelope is greppable rather than silent. It emits a `leaf_usage_limit_wait` event (`reset_epoch` / `wait_seconds` / `wait_attempt` / `dead_agent_run_id`), tombstones the dead attempt under the reason prefix `leaf_usage_limit_wait_orphan:` (same finalize-then-tombstone-outside-the-window ordering as a transient retry), then sleeps to the reset + a 120s margin. Every decline except the flag-off case emits `leaf_usage_limit_wait_declined` (`reason` `no_reset_time` / `over_6h_cap` / `budget_spent`, plus `dead_agent_run_id` and `evidence` — the line the decision was actually made from, so the operator can open the right `agents/<arid>/dialogs/` and see the wording that was not resolvable. That is the classifier's own tagged line, **except** when stdout was the consulted stream (stderr named no usage limit): there it is the shape-checked message `_sole_content_usage_limit_line` returned, because for an envelope the classifier's line is the raw JSON clipped at 160 chars and truncates mid-`result`) so a run that opted in but did not wait is greppable and diagnosable. The wait budget is **one per `substep`, independent of the transient-retry budget** (a usage limit is never a transient tag, so the two cannot compound), and a reset further out than 6h is treated as a weekly limit / misparse and falls back to `fail_closed`. The re-launch's `record-launch` re-runs the TTL-driven preflight live-probe, so a stale preflight self-heals; the residual is that waking before the reset actually lands makes that probe fail and the phase `fail_closed` (the 120s margin exists to avoid it). The flag is **not** auto-recovered on `--resume` (a per-invocation preference — re-pass it); it is recorded on `orchestration_meta.json#invocation` for provenance and **refreshed on resume** to the effective re-passed value so the record never reports the opposite of the resumed run's behavior. Wired into all three leaf loops (`run_substep`, the pure producer, the pure reviewer); a `substep`-terminal usage limit after the wait is spent reports the honest launch count in `[attempts=<n>]` exactly as a transient exhaustion does.
- **Reset source: the host-side `/usage` probe is PRIMARY, the stdout scrape is the fallback.** Before consulting the dead leaf's output at all, the conductor runs `<leaf argv base> --output-format json -p /usage` itself (`_run_usage_probe`) and reads the window rows out of the response's `result` (`_parse_usage_probe_rows`). The argv base is the failing leaf's own entry (its configured `command:` wrapper if it has one, else the bare backend binary), so the probe interrogates the executable that leaf actually uses; it runs only for a provider declaring the `usage_probe` capability (any other — `codex_cli`, either HTTP provider, or a `claude_cli` entry whose config withdrew it — reports `backend_unsupported` and spawns nothing), runs on the HOST without `bwrap` (the argv is a constant and carries no untrusted prompt — the same trust model as the preflight backend probes), is bounded by `USAGE_PROBE_TIMEOUT_SECONDS` (60s), and spends **0 tokens** (`/usage` is a local slash command answered at `num_turns: 0`). The `result` is trusted only when the envelope proves it is the BUILT-IN `/usage` command's output — `is_error` false, a string `result`, and `num_turns == 0` (no model turn consumed); a binary that ran `/usage` as an ordinary prompt would reply with model-authored text at `num_turns >= 1`, which is rejected (reported `probe_unparseable`) so it is never parsed into trusted rows. Because the trusted response is host-authored, **none** of the anti-forgery apparatus the scrape requires (`allow_envelope`, `_cli_abort_envelope_result`, the abort-shape clauses) applies to it, and none is duplicated. A probe row is `Current <window>: <n>% used · resets <Mon> <D>, <h>[:<mm>]<am|pm> (<IANA TZ>)`, parsed per LINE so an unrecognised wording costs only the rows it touches; the IANA timezone is required exactly as in the scrape, and the missing year is resolved to the parse timezone's current year, rolled forward by one when that lands further than the 15-min grace in the past. The probe supplies what the scrape structurally cannot: an explicit **date** (so no yesterday/today/tomorrow inference) and an explicit **window name**.
- **Two gates govern whether a probe row may arm the wait** (`_probe_reset_for_evidence`). (1) **Window agreement is required.** The window family named by the line the wait was decided from — `session` or `week`/`weekly` — must match a probe row's family. The classifier's remaining windows (`usage`, `hourly`, `<n>-hour`) have no corresponding row, a line naming both families is not resolved, and a family whose rows disagree on the instant (the response's two `week` rows can reset a minute apart) is not resolved; each declines to the scrape. This excludes structurally the failure of waking on the wrong window — a weekly stop matched to the session row would sleep a couple of hours and then fail the re-launch preflight against a window still shut. (2) **The matched window must be FULLY exhausted**: the highest `used_pct` of the matched family must be at least `USAGE_PROBE_EXHAUSTED_MIN_PCT` (100). This gate is load-bearing, not a sanity check: the `llm_usage_limit` tag that reaches the wait may have been promoted out of the leaf's own stdout prose (`_CROSS_STREAM_PROMOTING_TAGS`), a session row always exists, and the probe path does not run the abort-shape clauses that catch that case — so the server-observed percentage replaces them. The probe's job is to CORROBORATE that the named window is out of quota; a window with headroom (95..99%) has demonstrably not been reached, so it cannot be the cause of the death and declines to the scrape (whose abort-shape clauses still decide). `/usage`'s percentage is explicitly approximate and local-only, so a genuine exhaustion may read under 100 on the host — that only ever costs a decline-to-scrape (the safe direction), and the observed percentage is recorded on `leaf_usage_limit_probe` so a real incident is the evidence that would justify lowering the floor, never a guess.
- **Probe visibility and the unverified case.** Every probe attempt emits `leaf_usage_limit_probe` (`outcome` ∈ `resolved` / `probe_timeout` / `probe_error` / `probe_unparseable` / `backend_unsupported` / `window_unmatched` / `window_ambiguous` / `window_not_exhausted`, plus `windows` — the parsed rows — `matched_window`, `reset_epoch`, `duration_ms`, `excerpt`, `dead_agent_run_id`). No probe runs, and no event is emitted, when the flag is off or the per-`substep` wait budget is already spent. Whether `/usage` still answers once the quota is actually exhausted is **not verified** — that state cannot be reproduced on demand — which is why the probe is primary-with-fallback rather than a replacement: every probe failure lands on the scrape, i.e. on exactly the pre-probe behavior. The `excerpt` retains the raw response (bounded at `_USAGE_PROBE_EXCERPT_MAX_CHARS`) precisely for the unparseable case, so the next real incident answers the question from the event stream. `leaf_usage_limit_wait` and `leaf_usage_limit_wait_declined` carry `reset_source` (`probe` / `scrape_machine` / `scrape_human`) and `window` (the probe's matched window, `null` for a scraped instant); the 6h cap applies to both sources unchanged.

- The retry loop is closed inside the `substep` execution: the phase's outcome list stays one entry per `substep` of `SUBSTEPS[phase]`, and a retried `substep` contributes exactly one outcome (its surviving attempt).
- Each attempt is a new `agent_run_id` with its own `record-launch`, its own `launches/<agent_run_id>.request.json`, its own `agents/<agent_run_id>/dialogs/` (the dead attempt's leaf output is retained as failure evidence), and its own launch instant (the freshness bound of `determine_substep_status`, so an artifact left half-written by a dead attempt cannot satisfy the retry).
- The warm-resume target is invariant across attempts: a retry re-forks the same producer session and re-sends the same slim findings-only repair turn. A retry must not fall back to a cold launch (the slim prompt, hence the findings excerpt, is conditional on warm resume).
- A dead attempt is `finalize-child`ed and then tombstoned with `add-superseded-runs` (reason prefix `leaf_transient_retry_orphan:`), both **before** the next `record-launch`: it is never vouched by a `step_result.json` (`substep_agent_run_ids` records only the surviving attempt), and an un-vouched terminal `agent_run_id` is rejected by `_validate_orchestration_completion_for_pass`. The order is load-bearing in both directions. `finalize-child` must come **first** because it closes the child's write window: `record-agent-run` diffs the live workspace against the baseline `record-launch` took, and `<orch_root>/reopen/` — where the tombstone writes — is not runtime-ignored, so tombstoning inside the window would charge the conductor's own writes to the dying leaf as an unauthorized write and the retry would never launch. It must also **precede the next `record-launch`** (the runtime rejects a launch while a child of the same parent is active). The residual is a host crash between the two writes, which leaves a terminal, un-vouched, un-tombstoned `agent_run_id` that a `--resume` cannot repair on its own (recovery: a manual `add-superseded-runs`); this is the same window the other tombstone call sites carry.
- A transient retry is an **infra** retry, not a content retry: `retry_decisions` stays `null`, no `issue_severity` / `repair_strategy` is assigned, and a recovered `phase` writes its `step_result.json` exactly as an unretried one does.
- Deterministic in-process `substep`s (`Build`, `Validate.{pre_judge,execute,post_judge}`, `Generate.gate`, `Compile.static`) are out of scope: they spawn no leaf, so they have no transport to fail.
- On budget exhaustion the phase terminalizes exactly as before: `fail_closed` with reason `leaf_transport_error: leaf_exit=<rc> (tag: <tag>; <evidence>) [attempts=<n>]`, and the final attempt's `agent_run_id` is tombstoned by the phase-level transport branch. The `tag` is the cause of the **last** attempt and `attempts` is the launch count — a run may mix tags (a retried transport flake that then hits a usage limit terminalizes as `llm_usage_limit` with `attempts=2`), so recovery is decided by the tag, not by the presence of the suffix. Every `agent_run_id` the loop issues is therefore tombstoned (the dead retries by the retry loop, the last attempt by the transport branch).

### baseline diff contract on re-submission
- The child baseline diff in a retry after a `record-agent-run` reject walks the live workspace each time and compares it with the baseline (`_compute_changed_paths_against_baseline`). This keeps any filesystem modification after deactivate within the scope of terminal write validation.
- To prevent retry brick-cascade, `<orch_root>/agent_runs_invalid.jsonl` (and the lock sidecar) is narrowly excluded from the live diff as a runtime-owned single file. It is not the only such exclusion — `orchestration_runtime._should_ignore_runtime_snapshot_path` is canonical for the set, which also covers the runtime's own bookkeeping (`agent_graph.json`, `agent_runs.jsonl`), the host driver's `run_logs/` and `llm_config_snapshot.yaml`, and the `failure_analysis.runtime.<uuid12>.json` sidecar — but it is the one this rule exists for. This is the file that causes the previous `record-agent-run` failure to contaminate the next retry's diff, and `record-agent-run` itself is confirmed to be the writer. Other control-plane paths such as `<orch_root>/audit/`, `<orch_root>/violations/`, and `<orch_root>/failure_analysis.json` are **not** blanket-exempt — a hook-bypass write by the child remains as a backstop for terminal validation (`tools/orchestration_runtime.py::_should_ignore_runtime_snapshot_path` is the canonical source).
- Per-arid runtime-managed prefixes such as `<orch_root>/launches/...`, `<orch_root>/violations/...`, and `<orch_root>/agents/...` are also excluded from the diff (originally runtime-only directories). The parent scratch under `workspace/tmp/<parent_arid>/` is excluded by the `parent_tmp_root` exclusion of `_validate_actual_write_paths`.
- `deactivate-child` saves the child-authored path set in `<orch_root>/agents/<agent_run_id>/deactivate_snapshot.json` for audit. This snapshot is for manual audit and future debug use only, and is not referenced in the `record-agent-run` validation path (the live diff is always run).

- The feedback direction from a failed phase is fixed per phase:
  - `Compile` failure → only an in-Compile retry (no automatic retry because upstream is the manual Spec).
  - `Generate` failure → an in-Generate retry. When a verify failure of `source_meta.json` is judged `attribution=ir`, go back to `Compile`.
  - `Build` failure → go back to Generate. Because Build itself is a deterministic process, it does not involve an LLM, and forwards to Generate, as `repair_reason`, one of `compile_error` / `link_error` / `make_error` recorded in `build_log` (for details, the retry-trigger section of `docs/workflow/phases/phase_03_build.md`).
  - `Validate` failure → deterministically decide whether to go back to Generate / Compile / Spec by the combination of the `judge`'s `semantic_review.json#findings[*].attribution` and `verdict.json#failure_class` (the canonical decision table is the "Decision criteria for retry on failure" section of `docs/workflow/phases/phase_04_validate.md`).

## Design Policy
- Single responsibility: one `agent` has only one responsibility.
- Hierarchical delegation: control via the 2 systems `conductor -> step agent` and `conductor -> substep agent`.
- Contract-driven: when launching a child `agent`, fix the input contract and output contract, and forbid reads/writes outside the contract.
- Traceability: save all launch / termination events chronologically, and make the same judgment reproducible on re-execution.

## Orchestration instruction contract
### Common required items
- The conductor must record, in the launch request to a child `agent`, `orchestration_id`, `agent_run_id`, `parent_agent_run_id`, `node_key`, `step`, `substep` (when it exists), `ir_ref`, `pipeline_ref`, and `dependency_ref` as required.
- The launch prompt to a child `agent` is based on the corresponding template in `tools/prompt_templates/`, with the in-template placeholders substituted by the actual values of the target `agent_run`. `record-launch` performs this rendering; the conductor supplies the request parameters rather than the rendered prompt.
- The launch request to a child `agent` records `execution input`, `verification input`, `expected output`, `write_root`, and `read_roots` as required.
- `execution input` is limited to the input that the relevant `agent` may directly reference to generate the artifact.
- `verification input` is made explicit as input that the relevant `agent` may use only for pass/fail judgment, consistency confirmation, and dependency confirmation.
- `expected output` is made explicit including the file name, storage location, and update responsibility.
- The parent `agent` must not instruct guessed completion on an input shortage. When there is an input shortage, it instructs a `fail-fast` stop.
- The launch request to a child `agent` records `skill_name`, `skill_ref`, and `skill_must_read_refs` as required.

### Conventions for `ir_ref` / `pipeline_ref` / `dependency_ref`
- `ir_ref` is only `workspace/ir/<node_key_safe>/<ir_id>`, and an additional path segment must not be appended. `<ir_id>` is in the canonical `<slug>_<YYYYMMDD>_<seq3>` form (regex `^[a-z0-9]+(?:-[a-z0-9]+)*_[0-9]{8}_[0-9]{3}$`, canonical source: `docs/workflow/WORKFLOW_CORE.md` and `_SLUG_DATE_SEQ3_PATTERN` of `tools/orchestration_runtime.py`). Place `<node_key_safe>` as the parent directory of `<ir_id>`, and do not prepend it as a prefix to `<ir_id>` itself (because `node_key_safe` contains `__` / `_`, it violates the slug regex).
- `pipeline_ref` is only `workspace/pipelines/<node_key_safe>/<pipeline_id>`, and an additional path segment (including `source/` or `source_meta.json`) must not be appended.
- `dependency_ref` fixes the canonical path per phase. `Compile` records `spec/.../deps.yaml`, and from `Generate` onward records the phase root of `workspace/...` (`ir_ref` or `pipeline_ref`), forbidding a direct `spec` reference.
- In the launch request of `Generate verify`, `source_id` must be recorded as required.
- When a `step agent` / `substep agent` ends with `pass`, each path of `output_refs` must be included under the `ir_ref` or `pipeline_ref` directory recorded in the corresponding launch request.

### `Compile` launch request
- The `skill_must_read_refs` of `Compile.generate` includes `controlled_spec.md`, `tests.md`, `deps.yaml`, and `spec/registry/spec_catalog.yaml`.
- The `skill_must_read_refs` of `Compile.verify` includes the `spec.ir.yaml` generated by `Compile.generate`, `controlled_spec.md`, `tests.md`, and `deps.yaml`.

In addition, when `impl_defaults.toolchain.language` / `impl_defaults.toolchain.standard` / `impl_defaults.toolchain.build_system` / `impl_defaults.target.architecture` are undefined, it is a `fail` (canonical source: `docs/IMPL_PLAN_SPEC.md` "Required items").

### `Generate` launch request
- The `skill_must_read_refs` of `Generate.generate` includes `spec.ir.yaml`. It must not read `controlled_spec.md` directly.
- The `skill_must_read_refs` of `Generate.verify` includes `spec.ir.yaml`, `controlled_spec.md` (verify-only requirement-fidelity cross-check; `Generate.generate` does not read it), and `tests.md`, plus — as relative paths based on `pipeline_ref` — `lineage.json` and `source/<source_id>/source_meta.json`.

- The `skill_must_read_refs` of `Validate.judge` includes `spec.ir.yaml`, `tests.md`, the `raw/` / `diagnostics.json` / `perf.json` / `quality_check.json` / `trial_meta.json` under the same `run_id`, and `pipeline_ref/source/<source_id>/`. The judge's launch request does not require `source_id` / `source_binary_id` (the runtime enforces only `run_id`); instead the judge reads `trial_meta.json` under the same `run_id` and resolves `trial_meta.json.source_source_id` as `<source_id>` (because trial_meta is written by Validate.execute and the runtime has verified its match with `binary_meta.json.source_source_id`, there is no path for the judge to read the wrong source even in a pipeline where multiple sources coexist due to retries).
- `Validate.judge` must recompute the judgment metrics from `raw/` via an independent path, and confirm consistency with `diagnostics.json`. It must execute an `LLM` semantic check.

## Operations Rules
1. At workflow start, issue an `orchestration_id` and create `workspace/orchestrations/<orchestration_id>/orchestration_meta.json`. Alongside `orchestration_id` / `status` / `started_at` (and, when supplied, `spec_ref` / `source_dependency_ref`), record `repo_revision` — the git version of the repository resolved at run time so a run's artifacts can be traced back to the exact source that produced them. `repo_revision` is `{ "commit": "<HEAD sha>", "dirty": <bool> }` (`dirty` reflects `git status --porcelain`; `workspace/` is gitignored so orchestration artifacts do not flip it). The SHA is resolved at run time, not pinned to a constant, mirroring the model-alias convention, and is captured **once at the initial start** and preserved across re-init / `--resume` (so it stays the source that produced the run rather than being overwritten by a later `HEAD`). When the run directory is not a git checkout (or git is unavailable), `repo_revision` is omitted so an absent revision stays distinguishable from a clean/dirty one; if `HEAD` resolves but the dirty state cannot be determined (or the repository has no commits yet), `repo_revision` is either omitted or carries `dirty: null`. Also record `driver` — the identity of the `workflow driver` process (`pid`, `pid_start_ticks`, `boot_id`, `hostname`, `pid_ns`, `uid`, `recorded_at`), which is what lets a later run classify a non-terminal orchestration as a live concurrent run or as the corpse of a driver that died without terminalizing (`driver liveness`; operations rules in `docs/RUNBOOK.md` §3-1). Unlike `repo_revision` it is NOT preserved: it must always describe the process that currently drives the run, so a cold init that supplies no identity drops any recorded block and a `--resume` replaces it with the resuming process's. When the identity cannot be captured (a host without a readable `/proc`), it is omitted, and every liveness verdict for that orchestration degrades to `unknown` — there is no block to compare against.
2. Before the workflow starts, record the preflight result in `workspace/orchestrations/<orchestration_id>/preflight.json`, and when `can_launch_step_agents=true`, `can_launch_substep_agents=true`, and `sandbox_enforced=true` are not simultaneously satisfied, stop with `fail`.
3. Before starting each phase, confirm the phase type, and finalize the launch target as a `substep agent` for `Compile` / `Generate` / `Validate` and a `step agent` for `Build`.
4. The conductor saves `launches/<agent_run_id>.request.json`, `launches/<agent_run_id>.response.json`, `launches/<agent_run_id>.prompt.txt`, and `launches/<agent_run_id>.reply.txt` per launch request of a `step agent` or `substep agent`.
   Before each of those two calls it also saves the payload it passes, as `launches/<agent_run_id>.request.input.json` (`record-launch`) and `launches/<agent_run_id>.agent_run.input.json` (`finalize-child`). A payload travels as a file because a single argv element is capped at 128 KiB. Both are kept permanently as the evidence of what was sent, including when the call they feed fails. The full inventory is `docs/WORKSPACE_LAYOUT.md`.
5. The `response.json` and `child.response.json` saved by `record-launch` are a complete save of the leaf launch response, and must not drop the child-`agent` identifier.
6. On completion of each `step agent` and each `substep agent`, save `agents/<agent_run_id>/dialogs/agent.result.json` and `agents/<agent_run_id>/dialogs/agent.summary.txt`.
7. `agent.summary.txt` includes at least the final `status` and the failure cause or main-artifact reference.
8. `launches/<agent_run_id>.prompt.txt` is the body that concretizes the corresponding template in `tools/prompt_templates/`.
9. The conductor reconciles `deps.yaml`, `spec_catalog.yaml`, and the `dependency` section of `spec.ir.yaml`, and finalizes the execution queue based on the `spec` dependencies. **Scope clarification:** a single orchestration targets exactly **one `node`** (one `spec_ref`); items 9/28 describe the dependency-order reconciliation and the phase/substep queue **within that node**, not the automatic execution of dependency nodes' own workflows. By default a missing dependency is fail-closed (`workflow-launch-check` → `dependency_not_ready`; the operator runs each dependency node first). The entrypoint `tools/run_workflow.py --with-deps` opts into running the target's transitive dependency closure bottom-up (one orchestration per node) before the target; without it the default single-node, fail-closed behavior is unchanged.
10. The conductor issues a `step agent` or `substep agent` per launch target, and passes `node_key`, `step`, `ir_ref`, `pipeline_ref`, and `dependency_ref` as input.
11. Before launching the `Compile` of an upper `node`, the conductor reconciles the `ir_ref` and `ir_meta.json.verification_status` per immediate dependency `node`, and must not launch when `direct dependency ir readiness` is not satisfied.
12. Before launching `Generate` onward of an upper `node`, the conductor reconciles the `ir_ref`, `pipeline_ref`, and latest `aggregate_verdict` per immediate dependency `node`, and must not launch when `direct dependency execution readiness` is not satisfied.
13. When `direct dependency ir readiness` or `direct dependency execution readiness` is not satisfied, the conductor records the relevant `node` as `blocked` or `fail`.
13a. **Dependency-freshness readiness (R6-lite).** Both readiness levels additionally require each dependency's *certified* dependency resolution to still be the one the registry derives today. A certified node records the closure it was built against in its `dependency_graph.json` sidecar (each `all_nodes[]` entry a `kind/spec_id@version` node_key); readiness re-derives that closure from the current `deps.yaml` + `spec_catalog.yaml` with the same pure builder (`tools/dependency_graph.py`) and compares. A mismatch means **stale**, not unbuilt: the node is not ready. This is the mechanism behind "when a dependency `spec` is updated, its dependents are regenerated" — bumping a shared node's catalog version makes every dependent stale, and `run_workflow.py --with-deps` re-certifies the closure bottom-up in one run; no content-free version bump of the dependents is required. On a single-node run the launch check names the drifted node and points at `--with-deps`. A node whose derived closure is only itself (a leaf) can never go stale. The scope is **version granularity**: a content change within one `spec_version` is not detected, which the respec discipline (content change ⇒ `spec_version` bump) makes sufficient; content-hash chaining is R6 proper.
14. The conductor makes explicit the `execution input`, `verification input`, and `expected output` of the target `step`.
15. For a phase that has `substep`, the conductor launches each `substep agent` sequentially.
16. The `substep agent` generates its own artifact and the corresponding phase's metadata, and returns `agent_output_ref` to the conductor.
17. The conductor evaluates the child `agent`'s returned result, and finalizes `issue_severity` and whether re-submission is needed.
18. When re-submission is needed and `repair_strategy=reuse`, the conductor may permit continuation repair of the same `agent_session_id`. It issues a new `agent_run_id` and adds a `record-launch` record with `relation_type` of `reuse`.
19. When re-submission is needed and `repair_strategy=restart`, the conductor relaunches a `substep agent` with a new `agent_session_id` and adds a `record-launch` record with `relation_type` of `restart`.
20. For a phase that has `substep`, the conductor verifies the required artifacts of all `substep`, and outputs `step_result.json` to `workspace/orchestrations/<orchestration_id>/steps/<node_key_safe>/<step>/<agent_run_id>/step_result.json`. This `agent_run_id` is the `orchestration agent_run_id` (for the no-substep `Build` phase it is the `step agent_run_id`). `write-step-result` enforces this fail-fast: a wrong-role `--agent-run-id` whose role is resolvable in `agent_runs.jsonl` is rejected at write time (before the file is written and before the phase transitions, so the step stays `child_finished` for retry), rather than only at the Validate `pre_judge` gate. The `substep_agent_run_ids` of `step_result.json` enumerates, without omission, the `agent_run_id` of **all** `substep` launched in that `step` and recorded in `agent_runs.jsonl`.
21. `step_result.json` holds a `retry_decisions` array when re-submission was performed, and records `issue_severity`, `repair_strategy`, `repair_target_agent_run_id`, `new_agent_run_id`, and `repair_reason` in each element. In the `retry_decisions` recorded in a `write-step-result` with `status=pass`, each `new_agent_run_id` is limited to a `pass` run finally adopted into the `effective pass substep` set.
22. A re-submission triggered by a `noncanonical_phase_write_attempt` requires `repair_strategy=restart`.
23. The `status=pass` judgment in the `step_result.json` of a phase that has `substep` is made over the `effective pass substep` set.
24. In a `step_result` with `status=pass`, each run included in the `effective pass substep` set must have terminated with `pass`.
25. The `required_outputs` coverage judgment in a `step_result` with `status=pass` is made over only the `output_refs` of the `effective pass substep` set.
26. The `step agent` verifies its own artifact in a phase that has no standard `substep` (`Build`), and outputs `step_result.json`.
27. The conductor receives `step_result.json` and judges the launchability of the next `step`.
28. `node` execution proceeds sequentially in the dependency order reconstructed from `deps.yaml`, `spec_catalog.yaml`, and `spec.ir.yaml.dependency`. It does not perform parallel execution unless explicitly instructed. When the closure spans multiple `node` (only under `tools/run_workflow.py --with-deps`), the nodes are run bottom-up (dependencies before dependents), one orchestration per node, also sequentially; on the first dependency-node failure the run stops before the dependent/target node.
29. When a `step agent` or `substep agent` is `fail` / `timeout` / `cancel`, the relevant `step` of the relevant `node` is `fail`, and downstream `step` launch is forbidden.
30. The conductor appends each `agent` execution event to `workspace/orchestrations/<orchestration_id>/agent_runs.jsonl`.
31. The conductor saves the parent-child relationship in `workspace/orchestrations/<orchestration_id>/agent_graph.json`, and requires recording `parent_agent_run_id`, `child_agent_run_id`, and `relation_type`.
32. All `agent` of the core workflow must not write outside of `workspace/`.
33. When the actual processing of a `step` / `substep` is proxied by a script during workflow execution, it is a `fail`, and the relevant trial is discarded.
34. On re-submission, issue a new `agent_run_id`, and do not overwrite existing `launch` evidence or `agent_runs` rows.
35. `status` and `can_launch_*` must not be changed by manual editing or post-editing of `preflight.json`.
36. When the live probe just before launching a child `agent` is `fail`, `record-launch` must not be run.
37. The live probe that `record-launch` runs is skipped when a probe that succeeded within the TTL set by `METDSL_PREFLIGHT_TTL_SECONDS` (default 30 minutes) exists. It is disabled when `METDSL_ORCHESTRATION_ENFORCE_LIVE_PREFLIGHT=1` is explicitly set.
38. The execution result of a native hook is appended to `workspace/orchestrations/<orchestration_id>/hooks/native_hook_events.jsonl`. A hook that cannot name its orchestration is refused by §39, and the refusal is recorded under `_global/` — the only thing that reaches that name — on every backend and whether or not `METDSL_WORKFLOW_MODE` is set. **The record is BEST EFFORT and the refusal is not**: the write is skipped when no `repo_root` resolves (there is no tree to write into) and when the tree refuses it, which under `bwrap` is the ordinary case, because a leaf's only writable tree is its own `workspace/orchestrations/<orchestration_id>/` and `_global/` is not among its write roots. An audit that cannot be written must never change a decision; the decision is delivered either way. `_global/` is a reserved name and not a run: `tools/validate_pipeline_semantics.py` skips it when it sweeps `workspace/orchestrations/`.
39. `tools/hooks/cli.py` is the LEAF hook entrypoint, and it fails closed when the payload cannot resolve an `orchestration_id` (neither the payload nor `METDSL_ORCHESTRATION_ID` supplies one). There is no fallback and no policy variable. The guards past that point are keyed on the id — the write manifest, the read manifest, the codex feature certificate, the protected-root resolver — and each resolves nothing without one, so a call evaluated as `_global` is authorized by none of them; what it retains is only the checks that read the command alone, measured at `7560edc`: a credential read and a leaf-issued redirect were still refused there. The refusal is therefore about the guards that go silent, not about everything going silent. A leaf always has the id: `tools/orchestration_runtime.py::_profile_child_env` carries both per-launch ids into every sandbox profile on both of its paths, filling an absence rather than tolerating it, over the environment `WorkflowConductor._child_env` authored. An operator's own interactive session does NOT reach this entrypoint; since issue #102 it runs `tools/hooks/dev_cli.py`, registered by `.claude/settings.json` and `.codex/hooks.json`, which applies `tools/hooks/operator_safety.py` (shared with the LEAF path — the operator's checkout) and `tools/hooks/dev_session_hygiene.py` (DEV-only — the session's process table), and nothing else. `docs/HOOKS.md` is canonical for the module split and the `dev_` naming convention; this section is canonical for both halves; cite it rather than restating them.
40. When about to deviate into a contract-violating shortcut in a child-`agent`-required phase, the conductor makes explicit that the relevant phase requires a child-`agent` launch, and returns to the legitimate launch procedure.
41. After `write-step-result` completes with `status=pass`, `orchestration_checkpoint.json` is auto-updated by `tools/orchestration_runtime.py`.
42. In an orchestration with `resume_enabled=true`, the conductor runs `check-step-completed` before launching each `step`, and permits skipping the relevant `step` only when `completed=true` and `integrity=ok`.
43. A `step` skipped by checkpoint is recorded in `agent_runs.jsonl` as `agent_role=skipped_by_checkpoint`.
44. In an orchestration with `resume_enabled=false`, a `step` must not be skipped by trusting `orchestration_checkpoint.json`.
45. When the `status` of `write-step-result` is terminal (`pass` / `fail` / `blocked` / `timeout` / `cancel`), `validation_stage` is required in the `step_result.json` of `Compile` / `Generate` / `Build` / `Validate`. The allowed values are `Compile: compile|full`, `Generate: post_generate|full`, `Build: post_build|full`, `Validate: post_execute|pre_judge|full` (runtime canonical: `STEP_REQUIRED_VALIDATION_STAGES` of `tools/orchestration_runtime.py`). The runtime rejects with `ValueError` for anything other than the per-step allowed values, or on omission.
46. `codex_feature_check.json` is authored host-side by the conductor (orchestration-dir root, leaf-unwritable). The probe runs the leaf's configured command prefix (its entry's `command:` wrapper, else the bare backend), so it certifies the executable the leaf actually runs; it is memoized per launch command, so a configuration launching codex through two different commands certifies each. When the hooks feature is NOT certified (disabled / probe error) and the requirement is on (`METDSL_REQUIRE_CODEX_HOOKS_FEATURE` ≠ `0`/`false`/`no`), the conductor **fails closed before launching the codex leaf** (`SandboxEnforcementError` → `sandbox_enforcement_violation`) — a leaf whose hooks would not fire must not run, since the in-sandbox fail-closed read only happens if the hook runs. The in-sandbox hook itself reads the cache read-only and never re-probes; a missing/invalid/disabled cache fail-closes the hook gate too (defence in depth). The host re-probes on the next orchestration run / `--resume`.
47. `workspace/tmp/<agent_run_id>/` can be used as each agent's temporary working area. The agent writes there with the `Write` tool, directly specifying that literal path (`output_manifest_write_guard` judges only the write-target path and does not reference the `$TMPDIR` env; `docs/AGENT_CONTRACT.md` is canonical for the route). `record-agent-run` auto-deletes `workspace/tmp/<agent_run_id>/` after recording that `agent_run`. `tools/run_workflow.py` sets the environment variable `TMPDIR` to `workspace/tmp/<orchestration_agent_run_id>/` after `init` succeeds, but this is an insurance for subprocess inherit, and `export TMPDIR=...` on the agent side is unnecessary and forbidden (the Claude Code session sandbox's approval request would stop the workflow).
48. Because `Build` is a step-only phase (one child == one `step_result.json`), the conductor must write the `step agent`'s `step_result.json` — including a **`fail` / `timeout` / `cancel`** outcome — before launching the next `Build` child. `record-launch` enforces this: launching a `Build` child while a **prior terminal `Build` step agent for the node still lacks its `step_result.json`** is rejected fail-closed (the check is against the actual `step_result` files, not the `child_finished` phase-state proxy, so a crash that interrupts the phase transition after the result was already written does not wedge recovery). This runs before any durable launch/session/graph write, so a blocked relaunch leaves no dangling `agent_graph` edge. It prevents the original gap where a failed `Build` was folded into another build's `retry_decisions` and left without its own `step_result`, which later deadlocked `_validate_orchestration_completion_for_pass`.
49. Recovery-only: a `step agent` left **stranded without a `step_result`** (e.g. its `child_finished` authority lost when a checkpoint resume reset the `Build` phase) is remediated with `write-step-result --backfill`, which writes the missing `step_result` directly without consuming a fresh `child_finished` and without advancing the phase state. It is gap-fill only (refuses to overwrite), requires the agent to be a terminal `step` agent in `agent_runs.jsonl` for the same `node_key` / `step`, and requires the `--result-json` `status` to match the recorded run status (the anti-fabrication guard — a recorded `pass` is backfillable, since otherwise a build that recorded `pass` but lost its `child_finished` before the result was written would have no recovery path). Canonical: `docs/CLI_REFERENCE.md#write-step-result`.
50. Cross-phase retry of an already-passed phase (`reopen-phase`): when the decision table (`docs/workflow/phases/phase_04_validate.md`, `docs/workflow/phases/phase_02_generate.md`) routes a `Validate` / `Generate` failure back to a `Compile` that is already checkpointed `pass`, the conductor must run `reopen-phase --from-phase compile --node-key <node_key> --trigger-agent-run-id <failed_downstream_arid> --reason <reason_code>` before re-launching `Compile`. The re-point cannot otherwise be expressed in place: `check-step-completed` reads the stale IR as `integrity=ok`, the phase sits at `step_result_written` (not the `child_finished` the `write-step-result` path requires), and `retry_decisions` only models a within-step substep retry. `reopen-phase` invalidates the `from_phase` and all downstream phases — snapshotting the prior attempt's step/substep runs as **superseded** (`reopen/superseded_runs.json`, exempt from the `_validate_orchestration_completion_for_pass` vouch), archiving their `step_result.json` aside, dropping the affected `completed_steps` checkpoint entries, and resetting the affected `phase_state` to `not_started` — so `Compile` → `Generate` → `Build` → `Validate` re-run against the corrected IR. `--trigger-agent-run-id` must be a terminal non-pass step/substep strictly downstream of `--from-phase` (the anti-abuse gate). On `--resume`, `orchestration_meta.resume_directive` supplies the arguments. Canonical: `docs/CLI_REFERENCE_RARE.md#reopen-phase`, `docs/RUNBOOK.md` §3-1.
51. **Transport-substep resume (default-on, pure optimization).** The per-STEP skip granularity of items 42-44 has one forward exception: a `Compile` / `Generate` phase that terminalized `fail_closed` with reason_code `leaf_transport_error` **whose `verify` substep is the substep that died** resumes at `verify` with the surviving producer artifact reused, instead of re-running the whole phase from its billed LLM producer. It is structurally safe because a transport death can only strike an LLM substep, and the only LLM substeps of `Compile`/`Generate` are the producer (index 0) and `verify` (last) — a `verify` death therefore proves the whole substep prefix passed. On `--resume`, `_derive_leaf_transport_resume_directive` records the surviving producer (`orchestration_meta.resume_directive`, `source: leaf_transport_substep_resume`) after a revision-equality gate (`orchestration_meta.repo_revision` frozen at start must equal the current `HEAD`+dirty — else the artifact is not the source it was produced from), and `run_phase` preseats it as `outcomes[0]` and relaunches only the deterministic mids + `verify` (the mids re-run in ~30s, re-validating the artifact and supplying the completion rule's fresh non-superseded rows). It emits `transport_substep_resume` / `substep_resumed`, and every precondition miss (revision moved, dead substep not `verify`, `Validate`/`Build`, producer artifact gone) emits `transport_resume_declined` and falls back to today's **full-phase re-run** — a decline is exactly the prior behavior, so no new failure mode. No flag, and — because nothing is persisted at death time — the deriver is not gated on anything the failed run recorded, so it fires for any `leaf_transport_error` orchestration **resumed on the same checkout it failed on**; the revision-equality gate still requires the repo revision to be unchanged, so a resume on a newer checkout (e.g. after obtaining this very code) declines to a full re-run. Complements the opt-in in-run `--wait-usage-reset` wait (which covers the run-still-alive case); this covers the manual `--resume` fallback (flag off / unknown epoch / cap exceeded / `llm_client_error` / any transport tag). Canonical: `docs/RUNBOOK.md` §3-1, `docs/design/deterministic_followups.md`.

## Decision Criteria
- Per workflow, an `orchestration_id` is issued and `orchestration_meta.json` exists.
- Each `step` or each `substep` has an independent `agent_run_id`.
- The `context_id` of `step` and `substep` do not duplicate, and `context_isolated=true` is recorded for all.
- The `agent_runs.jsonl` of `step` and `substep` records `agent_session_id` and the various references, and the referenced entities exist.
- `launches/<agent_run_id>.response.json` and `agents/<agent_run_id>/dialogs/child.response.json` hold the same content of the leaf launch response.
- `agent_runs.jsonl.agent_session_id` matches the child-`agent` identifier of the corresponding `launch response`.
- `preflight.json` exists and satisfies `can_launch_step_agents=true` and `can_launch_substep_agents=true`.
- `sandbox_runtime=bwrap` and `sandbox_enforced=true` are recorded in the preflight.
- From the execution record of each phase, it can be traced that `Compile` / `Generate` / `Validate` used a `substep agent` and `Build` used a `step agent`.
- The parent-child relationship `orchestration -> step` or `orchestration -> substep` can be traced in `agent_graph.json`.
- The `executor_agent_run_id` of `step_result.json` matches the relevant directory name, and `substep_agent_run_ids` is consistent with the parent-child relationship. For a phase with no standard `substep` (`Build`), `substep_agent_run_ids=[]` is allowed.
- For a `step` that has `substep`, the `agent_run_id` of all `substep` of that `step` recorded in `agent_runs.jsonl` is included in the `substep_agent_run_ids` of some `step_result.json`. A `substep` / `step` recorded in `reopen/superseded_runs.json` is exempt from this vouch requirement. The invariant is that a terminal `agent_run_id` no `step_result.json` can vouch for is ALWAYS tombstoned, by whichever writer replaced or discarded it: a `reopen-phase` cross-phase retry (its `step_result.json` was archived to `step_result.superseded.<seq>.json`); a phase that terminalized without writing a `step_result.json` at all (`leaf_transport_error_orphan:` / `validate_gate_fail_orphan:` / the escalate-terminal orphans); an attempt replaced by a warm resume (`validate_post_judge_warm_resume_orphan` / `<phase>_verify_meta_schema_warm_resume_orphan`); and a dead attempt of a **leaf transient retry**, superseded by the surviving attempt of the same `substep` (`leaf_transient_retry_orphan:`). A reopened `(node, phase)` (every `(node_key, step)` carried by a superseded run) must nonetheless regain at least one fresh non-superseded terminal run before `pass`; otherwise `_validate_orchestration_completion_for_pass` rejects the `pass`, so a `reopen-phase` that archived the only evidence cannot be marked `pass` until the replacement attempt runs. A recovered transient retry satisfies this by construction (its surviving attempt is a fresh non-superseded terminal run of the same `(node_key, step)`). A **transport-substep resume** (item 51) intentionally re-vouches a **superseded** producer arid: the resumed `step_result.json` lists the reused run-1 producer (which stays superseded, tombstoned by the transport branch) alongside the fresh re-run `substep`s. This is permitted, not a drift — superseded rows are vouch-**exempt**, never vouch-**forbidden** (`_validate_orchestration_completion_for_pass` `continue`s a superseded row before the vouch check), and the reopened `(node, compile|generate)` regains its required fresh non-superseded row from the re-run mids/verify. (Load-bearing: a future validator tightening must not reclassify a vouched-superseded arid as an error.)
- The `required_outputs` of `step_result.json` match the phase contract of `docs/workflow/WORKFLOW_CORE.md` and the corresponding `docs/workflow/phases/phase_*.md`.
- When `step_result.json` holds `retry_decisions`, the `effective pass substep` set can be uniquely restored.
- For `Compile` / `Generate` / `Build` / `Validate` where `step_result.json` has a terminal status, `validation_stage` matches the per-phase allowed values (item 45).

| `node_key` | string | `<spec_kind>/<spec_id>@<spec_version>` |
| `step` | string | `"compile"\|"generate"\|"build"\|"validate"` |
| `substep` | string (optional) | the substep token, present for substep agents; scopes the per-substep `write_root` file pins (`compile.verify`→`ir_meta.json`, `generate.verify`→`source_meta.json`, `validate.judge`→`semantic_review.json`) |
| `write_roots` | array of strings | the list of write roots the capability permits (a directory root, trailing `/`, or a single-file pin) |
| `mcp_permissions` | array of strings | the gated build-runtime MCP tools this capability permits, granted per-substep least-privilege: `build`→`["compile_project"]`, `generate.gate`→`["run_linter", "run_syntax_check"]`, `validate.execute`→`["run_program", "run_quality_checks"]` (the three conductor in-process bodies that call a gated tool). **Every other `(step, substep)` fails closed to `[]`** — all LLM leaves (`compile`/`generate`.`generate`/`verify`, `validate.judge`, forbidden by SKILL from calling any MCP tool) and every other deterministic in-process validator (`compile.static`, `validate.pre_judge`/`post_judge`). |
| `expires_at` | ISO8601 | the capability expiry |

**Invariant:** a capability whose `agent_role` is `"step"` or `"substep"` must not have an empty array for `write_roots`. **The single exception is a `pure-function leaf`** (§pure-function leaf (`Z2` generate-executor)), whose capability declares `mode: "pure_readonly"` with `write_roots: []` and `mcp_permissions: []` by construction — it holds no write authority. The builder relaxes the empty-`write_roots` rejection only for that mode; every other `step` / `substep` capability still fails closed on an empty array. An empty `write_roots` is enforced as deny-all (never fail-open): any change inside a pure leaf's window is an unauthorized write.

### Required fields of `output_manifests/<agent_run_id>.json`

| field | type | description |
|---|---|---|
| `allowed_output_paths` | array of strings | the permitted path set for `.json`/`.txt` output |
| `allowed_file_tool_paths` | array of strings | the permitted path set for direct `Edit`/`Write` |
| `allowed_tmp_root` | string | the temporary-file permission root (`workspace/tmp/<agent_run_id>`) |

**Usage:** the agent writes by directly specifying the literal path of `allowed_tmp_root` (`workspace/tmp/<agent_run_id>/...`). Because `output_manifest_write_guard` judges only the write-target path and does not reference the `$TMPDIR` env, bootstrap Bash such as `export TMPDIR=...` / `jq -er ...` is unnecessary and forbidden (the Claude Code session sandbox's approval request would stop the workflow; for details see the tmp-area rules in `docs/AGENT_CONTRACT.md`).

### Required fields of `read_manifests/<agent_run_id>.json`

| field | type | description |
|---|---|---|
| `allowed_read_roots` | array of strings | the list of root paths that are permitted to read |
| `denied_read_roots` | array of strings | the list of root paths that are explicitly denied |

`output_manifests/<agent_run_id>.json` and `read_manifests/<agent_run_id>.json` may be read directly with the `Read` tool (`run-gate` not needed).

**Enforcement surface.** `allowed_read_roots` is enforced by the `PreToolUse` hook (policy `read_manifest_read_guard`) for `Read` (`file_path`), `Grep` / `Glob` (`path`; an absent `path` is validated as the repository root and therefore blocks — and since issue #71 a `Glob` `pattern` too, when it begins with `/` or `~` — `/` is the one shape measured to reach outside `path`, `~` is inert and refused anyway; no relative spelling is refused), and the read targets extractable from a `Bash` command (blocks carry `"via": "bash"`, and the check runs before the read-only auto-approve; a wildcard target with more than two wildcard components is validated at its literal prefix rather than expanded, so such a block names a directory). Bash extraction is **best-effort** and bounded by a fixed set of reader commands: any OTHER command handed a literal path is unvalidated — including the contract-sanctioned `python3 workspace/tmp/<agent_run_id>/x.py` scratch-script route, which `permissions.allow` grants; the script itself is authored with the `Write` tool, which the extractor never sees, and any heredoc body it does see is blanked. Also residue: `xargs cat`, `find -exec`, command and process substitution, `$VAR`, and a `cd` issued in an earlier Bash call (a `cd` within the same command IS followed). Also outside it: **every MCP tool**, which no `PreToolUse` matcher sees and which the `--tools` allowlist does not remove (an `mcp__…` tool is in the roster whatever that value says — measured). WHICH servers exist is no longer ambient for an agentic leaf — since issue #63 it is launched with `--strict-mcp-config --mcp-config .mcp.json`, so the committed file is the whole set (`mcp__build-runtime__*`) and a server configured in the operator's `~/.claude` does not reach it — and since that issue's final form the bwrap profile no longer rw-binds that home either, only the private `CLAUDE_CONFIG_DIR` and the single credential file `~/.claude/.credentials.json`. What a leaf DOES with the tools in that set remains unvalidated by the hook. This concerns the read boundary; the build-runtime server enforces its own capability gate on every gated tool, and under the workflow a call that omits `orchestration_id` is refused (`mcp_servers/README.md` is canonical). Closing these classes is what the bwrap read confinement below is for. `allowed_read_roots` governs only paths INSIDE the repository; out-of-repo Bash reads are split by a separate rule — the protected roots (`~/.met-dsl` plus the backend credential homes the bwrap profile rw-binds) are rejected fail-closed regardless of the reading command, and any other out-of-repo target merely withholds the read-only auto-approve so the harness permission list stays in charge. `docs/HOOKS.md` §"Layer boundary" is canonical for that split. The remaining structural fix — confining reads with a tmpfs over the repo instead of the current whole-repo `ro-bind` — is **not implemented**: it is gap 3 of issue #42, deliberately left out of that issue's fix as a much larger change, and no separate issue tracks it yet. Hook read decisions are appended to `access_logs/<agent_run_id>.jsonl` with `"source": "hook"` (best-effort, not an exhaustive record).
