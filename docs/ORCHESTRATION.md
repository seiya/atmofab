# Workflow Orchestration

This document defines the orchestration contract — the **conductor** (`tools/workflow_conductor.py`) that drives the whole `workflow` — and the independent-agent execution conventions for phases / substeps. It presumes the 5-phase structure `Spec -> Compile -> Generate -> Build -> Validate`.

## Related documents

- CLI reference of all subcommands: [`docs/CLI_REFERENCE.md`](CLI_REFERENCE.md)
- workspace artifact placement: [`docs/WORKSPACE_LAYOUT.md`](WORKSPACE_LAYOUT.md)
- workflow operation / startup (operator procedure): [`docs/RUNBOOK.md`](RUNBOOK.md)
- launch request templates (rendered by the conductor's `record-launch`): [`tools/prompt_templates/`](../tools/prompt_templates/)

## Purpose
- Hierarchize the workflow execution and separate phase responsibilities from audit responsibilities.
- Execute each `step` / each `substep` as an independent agent, and make the execution path traceable.

## Scope
- `Compile` / `Generate` / `Build` / `Validate`
- Per-`node workflow` phase execution, and the execution of in-phase `substep` (`generate` / `gate` / `static` / `verify` / `pre_judge` / `execute` / `judge` / `post_judge`; `gate` is the Generate deterministic checker substep, `static` the Compile one)

## term rules
- `phase` refers to the workflow's logical unit defined in the contract documents under `docs/workflow/WORKFLOW_CORE.md` and `docs/workflow/phases/`.
- `step` refers to the orchestration-level execution unit corresponding to one phase.
- `substep` refers to a lower execution unit decomposed from a `step`.
- `stage` is used only as existing field names such as `generated_by_stage`.
- The **conductor** (`tools/workflow_conductor.py`) is the orchestration actor: it drives the deterministic phase/substep loop, launches each `step` / `substep` as a leaf agent, and routes failures deterministically (escalating to a one-shot LLM diagnostician only on an unclassifiable failure). It is recorded in `agent_runs.jsonl` under an `orchestration_agent_run_id` with `agent_role=orchestration`.
- **Deterministic in-process execution.** The non-LLM substeps `Compile.static`, `Generate.gate`, `Build`, `Validate.pre_judge`, `Validate.execute` and `Validate.post_judge` are **always** run by the conductor **in-process** (no `claude -p` leaf, no `SKILL.md`) — it calls the build-runtime MCP handlers (`run_linter` / `run_syntax_check` / `compile_project` / `run_program` / `run_quality_checks`) or the static validators directly. `Compile.static` runs `validate_workspace_root.py` + `validate_pipeline_semantics --stage compile` (writing `compile_static_meta.json` under the IR dir; the `--stage compile` validator reports the well-formedness of `spec.ir.yaml` / `ir_meta.json` itself, so no separate syntax gate precedes it) — the purely-static IR gates the verify leaf used to own — between `Compile.generate` and `Compile.verify`, and on a violation warm-resumes `Compile.generate` (a same-phase reopen), so the LLM `Compile.verify` is reached only on a deterministically-clean IR and launches no validator gate (it is a pure spec-cross-reference semantic pass). `Generate.gate` runs three checks in-process between `Generate.generate` and `Generate.verify` and writes ONE `gate_meta.json` (a `checkers` object with `lint` / `syntax` / `static` sub-sections, a `failure_categories` list in canonical order `syntax_error` → `lint_findings` → static-family, and a composed `failure_excerpt`). Its **lint check** runs `run_linter` over `source/<source_id>/src/` (always), writing a host-authored leaf-non-writable `lint_evidence/<source_id>.json` (certified by `post_generate`); a lint finding warm-resumes `Generate.generate` (a same-phase reopen) ONLY once it has been attributed to the leaf. A failing run is re-run over two isolated copies of `src/` — the host-authored basenames in one, everything else in the other — and the verdict is each copy's own exit status, never a read of the diagnostics. A finding on the host-authored side (`host_rendered_lint_findings`) or one neither half reproduces (`lint_finding_unattributed`) is TERMINAL on the first attempt: the leaf has no write authority over those files, so a warm retry re-authors the ones that were never the cause (issue #112). Its **syntax check** runs the `run_syntax_check` compiler front-end gate (mandatory gfortran `-fsyntax-only`, plus optional `ATMOFAB_SYNTAX_COMPILERS` target-compiler stages) over the node + staged dependency-closure sources (always, independent of lint), writing a host-authored leaf-non-writable `syntax_evidence/<source_id>.json` (certified by `post_generate`); a compiler finding in the node's own source likewise warm-resumes `Generate.generate`. A failing syntax stage is first attributed by re-running the same compiler over two isolated source sets, never by reading the diagnostics text (a clean file still prints default-on warnings naming itself): a **canary** valid under every standard (if it fails, the invocation itself is unviable — typically an `impl_defaults.toolchain.standard` the compiler driver does not accept, which the leaf does not author), then the **staged dependency closure alone** (if it fails, the closure is at fault — either a dependency's certified source is defective, or this node's declared standard is narrower than the sound closure needs; the message names both causes and attaches the diagnostics, which say which). Each attribution terminalizes `fail_closed` (no `gate_meta.json` written) and dominates a co-occurring lint content failure, because the leaf authors neither the IR nor a dependency's certified source and no retry of this node could clear either. Every other compiler finding is the node's own and warm-resumes `Generate.generate`. Its **static check** runs `validate_workspace_root.py` + `validate_pipeline_semantics --stage post_generate` (the purely-static gates the verify leaf used to own) **only when the lint and syntax checks both pass** (otherwise its section records `status="skipped"` / `skipped_reason="lint_or_syntax_failed"`); a static violation likewise warm-resumes `Generate.generate`. A gate content failure carries route reason `gate_<cat1>+<cat2>+...`, so the LLM `Generate.verify` is reached only on a deterministically-clean source and launches no validator gate. The in-process bodies implement the in-source **Make** layout only (`build_system=make`; OBJDIR/BINDIR overrides, `make_test`); a non-Make `build_system` (cmake/meson/ninja) is rejected with a clear error rather than misplaced. A content failure (lint findings, compile/link error, post_build/post_execute violation, quality-check mismatch, runtime error) returns cleanly and routes via the Gate/Build/Validate decision tables (→ Generate etc.), exactly like the leaf era — EXCEPT for the three conditions the static validator answers with a dedicated exit code (3 `static_frontend_unavailable`; 4 `stale_dependency_ir` — a violation whose subject is the node's OWN certified IR, predating the current contract, from either of two emit sites, the §5.1 surface guard and, since issue #238, the io_contract reader at `--stage post_generate`, neither about a dependency's IR despite the name; 5 `host_authored_artifact_violation` — a violation whose SUBJECT is a file this repository authors, which the leaf has no write authority over, issue #112), which every gate reader that can receive them routes terminally on the CODE and never on the output text (the `post_build` and `--stage compile` readers do assign a failure_category, but neither code can reach them — see the comments at those two call sites), because a violation interpolates a path the leaf chose and any text scan of it was forgeable; a genuine conductor/MCP infra failure fail-closes as a transport error, as do the two `Generate.gate` syntax-check failures its attribution runs single out (an unviable compiler invocation; a defective staged dependency closure), neither of which any retry of this node could clear. They are the only substeps that are not leaf agents. The conductor still issues the `record-launch` → `record-child-return` → `finalize-child` bookkeeping so the executor is a normal `step` / `substep` `agent_run_id` with a launch record and phase_state, but their launch prompt is a **minimal deterministic stub** (sentinel `Conductor-executed deterministic step` + core ids; no skill section), and the validator applies a reduced launch-prompt-marker set to it. `Validate.judge` is always a leaf (its independent LLM semantic check is essential), but the purely-structural `--stage pre_judge` gate it used to run is **hoisted to the conductor as two deterministic substeps wrapping the judge** (G4, mirroring `Compile.static` / `Generate.gate`). The `Validate.pre_judge` substep (index 0) runs a **dependency-DAG readiness** check before execute/judge (a `dependency_graph.json` sidecar `all_nodes` closure node not built+validated in its own pipeline authors `pre_judge_meta.json` `status=fail` and terminalizes `fail_closed`, reusing `validate_pipeline_semantics._closure_node_validated_in_own_pipeline`). The `Validate.post_judge` substep (index 3) runs the `--stage pre_judge` validator after the judge returns (scoped `--pipeline-root`/`--run-id`, with BOTH the post_judge substep's own arid AND the judge arid declared `--in-flight-agent-run-id`) and records the verdict + a severity `disposition` in `post_judge_meta.json` under the run-node dir. (Naming caution: the `post_judge` substep runs the validator stage literally named `pre_judge`.) `determine_substep_status` gates the post_judge substep on that verdict. Three **exit codes** are answered before the violations are classified at all, because they say the gate reached no verdict this run's judge could act on: 3 (`static_frontend_unavailable`), 4 (`stale_dependency_ir`) and 5 (`host_authored_artifact_violation`), all `fail_closed` — the severity rules below classify by artifact path, so left to them a bullet naming a run-node artifact would warm-resume a judge that cannot repair either condition. Otherwise: a **recoverable** violation (a judge-authored deliverable) warm-resumes the judge in place to re-author it — which since Z3 (issue #169) applied to a residual AGENTIC judge only, and since Z4 (issue #171) to no launch at all, because the pure judge's `semantic_review.json` is host-authored and a violation in it is the host's defect, reclassified to `unrecoverable` before the disposition is chosen; an orchestration-record/DAG **integrity** violation (or any `pre_judge` `fail`) is a **non-physics integrity blocker** the conductor terminalizes `fail_closed` (writing no routeable `fail` `step_result`, which the judge `pre_phase_complete` hook forbids atop a `pass` `semantic_review`); an **unknown** violation routes to the unified escalate LLM in prod, and terminalizes `fail_closed` in dev (G5). The judge leaf itself launches no validator gate — it holds no shell to launch one with. (Until Z4, issue #171, that was enforced by `ALLOWED_VALIDATE_PIPELINE_STAGES` being empty for all three validate substeps; the map is deleted with the agentic prompt it constrained.) See [`docs/workflow/phases/phase_03_build.md`](workflow/phases/phase_03_build.md) and [`phase_04_validate.md`](workflow/phases/phase_04_validate.md).

## phase / substep types

| phase | step type | substep |
|-------|-----------|---------|
| Compile | has substeps | `generate` / `static` / `verify` |
| Generate | has substeps | `generate` / `gate` (conductor-run deterministic; unions the lint / syntax / static checks) / `verify` |
| Build | single step | - |
| Validate | has substeps | `pre_judge` / `execute` / `judge` / `post_judge` |

## Requirements

### preflight and launch control
- Workflow execution runs exactly one conductor per `node` (started by `tools/run_workflow.py`).
- Before the workflow starts, the preflight of an execution platform that can launch the `step agent` and `substep agent` independently must be run. A failed preflight prevents workflow start.
- The `multi_agent` feature is advisory diagnostics for `backend=codex`; the conductor launches independent Codex CLI processes and does not use Codex subagents. Codex launchability requires headless JSON event streaming and thread-ID capture.
- The preflight of `backend=codex` requires `checks.codex_home_writable.pass=true`. `codex_home_writable` is CONSUMED here and has no producer anywhere in this repository — an operator's own `preflight.json` supplies it. The `hooks` feature requirement (`feature_states.hooks`, `checks.hooks_enabled`, `checks.codex_hooks_enabled`, and the host-side `codex_feature_check.json` probe behind them) went with the leaf hook layer in Z4 ([issue #171](https://github.com/seiya/atmofab/issues/171)): a `pure-function leaf` makes no tool call, so there is no hook to enable and no reason to refuse a host that cannot run one.
- The preflight must include `sandbox_runtime=bwrap` and `sandbox_enforced=true` as required conditions. When at least 1 of `checks.sandbox_bwrap_available.pass=true`, `checks.sandbox_bwrap_userns.pass=true`, or `checks.sandbox_bwrap_exec.pass=true` is not satisfied, the workflow must not start.
- Making `preflight.json` `pass` by manual editing is forbidden.
- Just before launching a child `agent`, launchability must be re-checked by a live probe of the execution platform. On `fail`, `record-launch` and the child-`agent` launch are forbidden, and the workflow transitions to `fail`.
- Before starting each phase, run `workflow-launch-check`, and simultaneously check the required child-`agent`-type decision, execution-platform allowability, session-policy allowability, and dependency readiness.

### Leaf LLM configuration
- Which LLM runs a leaf is a property of the **`(phase, substep)`**, not of the run. `tools/llm_config.py` resolves a YAML file into one `ResolvedLeafEntry` per LLM leaf; the conductor asks that entry, never a run-wide backend name. `--llm-config <path>` selects the file; the default is `./llm.yaml`, resolved against `--repo-root`. That file is the OPERATOR's — gitignored, created by copying one of `docs/examples/llm_*.example.yaml` — because which model runs which leaf is a local decision, and a tracked default forces everyone who changes it to carry a permanent diff on a tree the run itself requires to be clean. There is no fallback when it is absent: a run resolved from a file nobody chose is a run nobody can reproduce, so startup fails with `llm_config_default_missing`, naming the path and the `cp` that creates it.
- The five LLM leaves are `compile.generate`, `compile.verify`, `generate.generate`, `generate.verify`, `validate.judge`. Every other `substep` is deterministic and in-process; naming one in a configuration is an error, not a no-op. `build` likewise has no LLM leaf and is rejected as a phase.
- **Resolution order** is `defaults` -> `phases.<phase>` -> `phases.<phase>.substeps.<substep>`, merged per field. A level that switches `provider` DROPS the inherited provider-scoped fields (`model`, `command`, `base_url`, `api_key_env`, `capabilities`): a model or wrapper command chosen for one transport does not name anything under another. The transport-neutral fields (`timeout_s`, `max_output_tokens`, `stream`) do inherit across a switch: they describe the endpoint's transport behaviour, not a provider's vocabulary, so two leaves pointed at the same gateway keep the same answer about it.
- **The samples spell out every phase, substep, provider, model and effort**, even though the resolution rules would let all five leaves inherit one `defaults` block. The file is the answer to "what runs where, and how hard does it think", and a sample should give a reader that answer by being read rather than by being re-derived from an inheritance chain. Omission remains legal and is the right choice once the copy is the operator's own. Four samples ship: `llm_claude.example.yaml` and `llm_codex.example.yaml` put every leaf on one CLI; `llm_openai_compatible.example.yaml` and `llm_anthropic_api.example.yaml` work through the HTTP providers on EVERY LLM leaf, which since Z3 (issue #169) is the whole surface those are admissible on. **Effort is uniform at `medium`, the current generation's own default** on both CLIs — and Codex lowered it from the `xhigh` its predecessor gpt-5.5 shipped, so the vendor moved the default down as the model improved. Overriding a vendor default needs evidence about the model that will actually run, and this repository's re-run measurements are NOT that evidence: they were recorded almost entirely on Opus 4.8, and a re-run rate is a property of the (model, effort, task) triple. Re-measure on the current model before tuning it. **The one economy is a model tier**, because that argument is structural rather than generational: re-runs were ~20% of every token spent and concentrated in the leaves that WRITE, and `generate.generate` (45% of tokens) was observed out to 7 attempts against a `MAX_ATTEMPTS_PER_PHASE` of 3, where crossing the cap fails the phase rather than costing one more attempt. So the writing leaves are the last to economise on any model, and `compile.verify` takes the cheaper tier: smallest leaf, re-ran in 3 of 93 nodes, reads an IR the deterministic `compile.static` gate already proved clean, and re-read downstream. `validate.judge` is left alone despite never being re-run, because nothing runs after it. Each config carries the measured table, and its caveat, in its own comments.
- `effort:` is the reasoning effort, in the PROVIDER's own vocabulary, and it reaches a different surface for each: `claude_cli` -> `claude --effort <level>` (`low` | `medium` | `high` | `xhigh` | `max`); `codex_cli` -> `codex --config model_reasoning_effort="<level>"` (`low` | `medium` | `high` | `xhigh` | `max` | `ultra`, read off the CLI's own `supported_reasoning_levels` and NOT the OpenAI API's `reasoning_effort` list, which differs in both directions; Codex has no `--effort` flag, and `--config` is the spelling `CODEX_EXEC_RESUME_REQUIRED_FLAGS` certifies by name); `openai_compatible` -> `reasoning_effort` in the request body (`minimal` | `low` | `medium` | `high`). It does not apply to `anthropic_api`, whose Messages API expresses the same idea as a thinking token budget rather than a level. A level the provider does not accept is rejected at load. An ABSENT effort says nothing and leaves the provider's own default in force — unlike `model`, there is no ambient alias the conductor is deliberately declining to pin, so a configured level is always passed.
- A `model:` NAMED IN THE FILE is pinned onto the launch (`claude --model <model>`; a `codex_cli` entry always pins one). When the file names none, no `--model` is passed and the choice is deliberately NOT pinned — which is the pre-existing rule and is what keeps a run without a declared model byte-identical to before. Until Z4 (issue #171) an agentic claude leaf launched with `CLAUDE_CONFIG_DIR=<private home> --setting-sources user`, so what an unpinned launch resolved to was decided by the CLI itself rather than by the operator's `~/.claude`; a pure claude leaf carries no `--setting-sources`, so there the operator's configuration decides (`TODO.md` records this as the unmeasured half of `--safe-mode`); the recorded `agent_model` for such a leaf is correspondingly a spec-side PREDICTION (`DEFAULT_CLAUDE_MODEL_ALIAS`), replaced after the run by the exact model the leaf's own result envelope reports. Declaring a model whose output ceiling is below `LEAF_MAX_OUTPUT_TOKENS` also requires setting `max_output_tokens:` on that entry, or every launch is rejected with the API's `max_tokens` error.
- A `command:` wrapper must forward BOTH channels. The leaf prompt arrives on the wrapper's **stdin** (a single argv element is capped at 128 KiB and a node's prompt exceeds it). A wrapper that redirects `</dev/null`, or consumes stdin itself, launches the leaf with an empty prompt: `claude` refuses it with an explicit error, and `codex` — whose argv carries the `-` stdin sentinel — waits on an instruction set that never arrives.
- `defaults` also serves the one launch that carries no phase/`substep` — the failure diagnostician (`escalate`) — and must therefore support the `pure` capability. It is a pure leaf like every other `LLM` leaf (issue #169), so an entry restricted to `capabilities: [agentic]` is refused there. An `HTTP` provider is admissible as `defaults`, which the agentic requirement used to close by accident. `init` and the preflight still take ONE backend token whose parser is `choices={claude, codex}`, so it is resolved by `LlmConfig.cli_launch_identity()` from what the configuration can actually LAUNCH — `defaults` when it is a CLI provider, else the CLI entry the file does name (the preflight probes every provider through `--llm-config` regardless; that token is only its top-level description). A configuration in which nothing launches a process is refused by name, `llm_config_no_cli_backend`. Z3 (issue #169) removed the OTHER thing standing between a configuration and an all-HTTP run — `validate.judge` was the last leaf requiring `agentic` — so that refusal is now the single remaining floor, and lifting it is a separate question about `init` and the preflight rather than about the leaves.
- **Capabilities are declared, never inferred.** `PROVIDER_CAPABILITIES` is the single authority; a configuration's own `capabilities:` list may only RESTRICT a provider's set, never extend it.

- **HTTP providers are admissible on every LLM leaf** — `compile.generate`, `compile.verify`, `generate.generate`, `generate.verify` and, since Z3 (issue #169), `validate.judge`. The rule is unchanged and is still enforced as a capability comparison rather than a provider-name test: the HTTP providers hold `pure` and not `agentic`, and each `substep` states what it requires (a pure-capable leaf accepts either `agentic` or `pure`). What changed is the SUBJECT set, which is now empty: no LLM leaf requires `agentic`, so the refusal has no reachable subject through the configuration surface and is kept as the backstop for the next leaf that cannot be expressed purely. A `claude_cli` entry restricted until it holds NEITHER transport is refused everywhere under the same rule.
- Config load is fail-closed with NAMED rules (`LlmConfigError.rule`), which the startup envelope surfaces verbatim under `reason: invalid_startup_input`: `llm_config_unreadable`, `_not_a_mapping`, `_unknown_key`, `_unknown_phase`, `_unknown_substep`, `_unknown_provider`, `_missing_provider`, `_invalid_field`, `_field_not_applicable`, `_http_requires_base_url` / `_api_key_env` / `_model`, `_capability_exceeds_provider`, `_capability_insufficient_for_substep`, `_defaults_not_pure`, and `llm_config_default_missing` when no `--llm-config` was passed and `./llm.yaml` does not exist. Run start additionally checks `llm_config_codex_cli_requires_model` and `llm_config_no_cli_backend` — deliberately NOT load checks, so a configuration whose codex slug has been blanked, or which names no CLI provider at all, stays loadable, diffable and testable while still failing before a run. Both are raised from `LlmConfig.validate_runnable()`, never from `load_llm_config`.
- Config validation cannot see node shape, so the pure-only rule has a **runtime half for the two `generate` leaves**: `_pure_leaf_substep` additionally requires the node to have a CodegenBundle SHAPE (`_bundle_shape`, which answers `m3c` for a physics node whose runner the host renders and `harness` for an `infrastructure` self-test, issue #169). The two `compile` leaves carry no shape condition — the Compile contract does not depend on the node kind, and at `compile.generate` time no IR exists to read a shape from. **No node in the spec catalog answers None**, so every leaf of every in-tree node runs pure; the remaining None answers (a `c`/`cpp`/`mixed` toolchain, a physics node without exactly one infra dependency) are rejected upstream at spec-input / `Compile.static`, so the fall-through has nowhere to go: the shared agentic loop it named is DELETED (Z4), and `_render_launch_prompt_template` refuses a request that is neither deterministic nor pure, so a hand-crafted IR that reached it would be refused at `record-launch` rather than run under a second leaf model. (Until Z4, [issue #171](https://github.com/seiya/atmofab/issues/171), an entry that lacked `agentic` on such a node failed the `substep` closed with `pure_only_provider_on_agentic_path`. Neither that rule name nor the `agentic` capability exists: `agentic` is refused at `capabilities:` parse time, so a configuration still naming it fails at load with `llm_config_invalid_field`.)
- **`base_url` conventions differ by provider and preflight cannot catch a mistake** (it validates only the URL shape, and any HTTP status counts as reachable). `openai_compatible` appends `/chat/completions`, so `base_url` MUST include the API version segment the endpoint expects (`http://localhost:8000/v1`). `anthropic_api` appends `/v1/messages`, so `base_url` must NOT (`https://api.anthropic.com`, which is also its default). A wrong convention passes preflight and then fails every leaf with `HTTP 404 from provider: ...` -> `pure_transport` -> `fail_closed`.
- **`max_output_tokens` applies to an HTTP entry and should usually be set.** Its default is `tools/llm_http_leaf.DEFAULT_MAX_OUTPUT_TOKENS` (32768) — deliberately NOT the CLI leaf's 128000 ceiling, which exceeds the whole context length of the local servers `openai_compatible` targets and is rejected as a client error, i.e. on the first attempt and without a retry. 32768 is sized on the artifact (the largest `CodegenBundle` in this repository is ~45 kB of JSON); a ceiling much below that turns every run into a truncation-repair loop instead. Size an override against the model's CONTEXT WINDOW rather than its documented maximum: the whole completion has to fit alongside the prompt, and streaming the answer does not change that arithmetic. The field does not apply to a `codex_cli` entry, and `timeout_s` does not apply to either CLI provider; declaring one there is rejected with `llm_config_field_not_applicable`, while a value INHERITED from a level on another provider is dropped rather than rejected.
- **Sizing `max_output_tokens` and `timeout_s` for an endpoint that bills reasoning against the output ceiling — the rule.** Sizing the ceiling against the artifact and the context window, as the bullet above requires, is necessary and NOT sufficient where the endpoint streams `reasoning_content`: there the ceiling is a COMBINED reasoning-plus-answer budget, and the reasoning has been the larger and the more variable half of it. Five consequences. (1) A ceiling below what the model spends thinking returns a ZERO-character answer, not a short one, so a value that is merely too small can produce no document at all. (2) A run that hit the ceiling tells you only a LOWER BOUND — that measurement is censored — while a run that finished tells you what that generation actually cost. (3) **Size against the largest COMPLETED consumption you have observed, and treat it as a bound that moves as runs accumulate, never as a requirement.** There is no arithmetic from artifact size to a safe ceiling, and a value derived from one closure has already been exceeded by the next one here (bullet after next). Recompute it over your own runs with `skills/workflow-timing-audit/scripts/leaf_token_report.py <orchestration_dir | orchestration_id>`, which reports what every leaf of a run actually spent. (4) The observed floor was specific to the model AND to the prompt, so treat a ceiling as non-transferable between entries; note that `max_output_tokens` INHERITS across a provider switch by the resolution-order rule at the head of this section, which makes an inherited ceiling on a second model the case to re-check first. (5) Move the ceiling and `timeout_s` together — raising the ceiling alone converts a truncation into a timeout — and check the deadline against the endpoint's LOADED throughput, not its idle one. **The configuration this repository runs**, as one worked pair rather than a formula: writer `max_output_tokens: 98304` with `timeout_s: 4200`, reviewer `32768` / `2400`. Measured against the corpus below that is ~20% over the largest completed writer draw and ~39% over the largest completed reviewer draw; at the slowest rate observed anywhere in it (17.6 tok/s) a full 98304-token draw would need ~5 585 s, more than the 4200 s the writer entry allows, so a large draw on a busy endpoint remains a `--resume` condition rather than a value to keep raising.

- **An HTTP leaf STREAMS its answer by default, and the default is the fix.** Both HTTP shapes send `stream: true` (the `openai_compatible` one also sends `stream_options: {include_usage: true}`, without which an OpenAI-dialect stream reports no token usage at all) and read the reply as server-sent events. The reason is not latency: a non-streaming completion means the endpoint writes nothing until the whole answer exists, and any intermediary that bounds the interval between upstream READS cuts the connection long before the model is done. Measured, a `generate.generate` leaf on an nginx-fronted endpoint took `HTTP 504 Gateway Time-out` three times, on requests that ran 613.6 s / 612.3 s / 611.8 s, while the entry's own 2400 s `timeout_s` never fired — the gateway's ~600 s read timeout was what expired, and `timeout_s` is a client-side TOTAL that has nothing to say about it. A frame every few hundred milliseconds resets that timer. It moves the silence to the FRONT of the request rather than abolishing it — but only as far as the PREFILL: measured against one such endpoint, a reasoning model streams its thinking too, as `reasoning_content` deltas, so bytes flow from well before the answer begins. What remains silent is the queueing and prefill before the first token, and if that alone outlasts the intermediary's timeout the same 504 returns; the lever there is the entry's `effort` and prompt size, not `timeout_s`. `stream: false` is the per-entry escape hatch for an endpoint that cannot speak SSE; it restores byte-identical pre-streaming request bodies (there is no `"stream": false` on the wire — an escape hatch that adds a key is itself a new thing for a strict endpoint to reject), and it cannot be applied to a run already under way, because changing the file trips `llm_config_changed_since_launch`. The field does not apply to a CLI provider and is rejected there — including when written as `stream: false`, which is exactly the spelling an operator reaches for. **A stream that ends without its terminator is a TRANSPORT failure, never a short document.** Completion is `[DONE]` or a `finish_reason` for the OpenAI dialect (the union, because servers disagree about which they send) and `message_stop` for the Messages API, whose `error` event after a 200 outranks a `message_stop` that follows it. An `error` frame — the Messages API's `error` EVENT, or the OpenAI dialect's chunk carrying an `error` key — outranks any terminator that follows it, in both dialects. A severed connection produces none of these and is reported as `stream interrupted: ...` — wording chosen so the leaf-failure classifier tags it `llm_transport_flake` and retries it. A body that is not an event stream AT ALL (the endpoint ignored `stream: true`, decided on whether the body opens with an event-stream line) is reported as `response_not_an_event_stream: ...` instead and is deliberately NOT classifiable: it is a deterministic misconfiguration that reproduces on every launch, so it fails closed on the first attempt naming its own remedy rather than buying three re-launches. Passed through instead, a connection cut at 90% would reach the validators as a plausible-looking truncated document and spend bundle-repair turns blaming the model for a network fault. Whatever arrived is kept as `raw_response` even when the stream died, which is the only record of where it died. There is deliberately **no idle (inter-frame) bound** to go with the total one: a reasoning model can legitimately emit nothing for minutes before its first token, so an idle bound tight enough to be useful would kill the request streaming exists to save — and the total deadline already covers a stream that goes silent, because the socket timeout is narrowed to the remaining time on every receive.
- **An HTTP leaf is bounded by its entry's `timeout_s`, not by the leaf-timeout contract.** `ATMOFAB_LEAF_TIMEOUT_SECONDS`, the process-group kill and the `leaf_timeout` event bound a CLI leaf, which is a process; an HTTP leaf is a request and none of them apply to it. Its bound is `timeout_s` (default `DEFAULT_HTTP_TIMEOUT_SECONDS` = 900 s), enforced as a WALL-CLOCK deadline over the response read — a socket timeout alone resets on every byte and never fires against an endpoint that trickles. A response body over 32 MiB is refused as transport, and the body is read one socket operation at a time so the deadline is checked between them (reading it in fixed-size chunks would not bound anything: a single `read(n)` loops internally until it has n bytes, with every inner receive resetting the socket timeout). The raw body is persisted as `launches/<agent_run_id>.http_response.txt`, with the API key's value redacted from it and from every transport-error string: the body is provider-supplied text, and a debug gateway or verbose proxy can echo the request headers back into it. Redaction applies to those DIAGNOSTIC copies only — never to the parsed document the run acts on, because a key that is a common substring (the placeholder keys local endpoints are configured with) would otherwise rewrite a valid reply. Redirects are refused outright: following one would forward the API key to the redirect target. A provider's HTTP status is reported as `HTTP <code> from provider: ...`, in the form the leaf-failure classifier reads, so the failure is TAGGED as `llm_rate_limit` / `llm_transport_flake` / `llm_overloaded` / `llm_client_error` rather than as an anonymous transport death. A transient tag (`llm_rate_limit` / `llm_transport_flake` / `llm_overloaded`) is re-launched in place by the bounded transient retry, on every substep — one 429 must not lose a run that has already paid for every earlier phase. Its budget is separate from the usage-limit waits and from the bundle repair turns, and none of the three can compound: a transient tag is never `llm_usage_limit`, and a transport death is never bundle-repairable. `llm_client_error` (a 4xx) is deliberately not transient and fails closed for an operator `--resume`, as does an exhausted retry budget. That budget is bounded in WALL-CLOCK as well as in launches: a retry is granted only while the already-dead attempts plus the one that just died stay within `TRANSIENT_RETRY_WALL_CLOCK_BUDGET_SECONDS` (600 s), because a failure that is a deterministic function of how long the request runs — the 504 above, which arrived within two seconds of the same duration every time — cannot be bounded by counting launches, and the count budget alone spent 33 minutes proving the third attempt was as doomed as the first. A cheap flake is untouched by it. A refusal emits `leaf_transient_retry_declined` (`reason`, `elapsed_seconds`, `spent_seconds`, `budget_seconds`) and then takes the same terminal path as an exhausted count. The error body is read through the same wall-clock deadline as a success body, under its own 64 KiB ceiling, so a gateway that trickles or floods its error page cannot outlive `timeout_s`.
- **A repair turn replays the conversation in memory.** An HTTP provider has no session to reopen, so `_run_http_leaf` re-sends the prior user prompt and assistant answer, and the repair turn renders the WARM (slim) prompt — it does NOT re-inline the closed context or `prior_document`, which the replay already carries. Input grows across the bounded repair turns of ONE substep run; the history does not survive the process, so a cross-restart reopen degrades to the cold path (full context, `prior_document`).
- Preflight is given the SHA-256 of the configuration snapshot its caller resolved and refuses to probe a file that has changed since: it runs in a subprocess and reloads the file, so without that check it could certify commands the conductor — which keeps the object it already loaded — will never launch.
- The `providers` map is re-probed in full whenever the live-preflight TTL expires, and the refreshed rows are persisted with the new `probed_at`. `probed_at` is the freshness claim for the whole document, so re-probing only `defaults` would leave a mixed configuration's other providers treated as fresh indefinitely — and `record-launch` would then create durable child state for a provider that has since become unavailable.
- An API key is never written to a configuration: an HTTP entry names the ENVIRONMENT VARIABLE (`api_key_env`), read at call time into a request header. Its value is never logged, recorded, or hashed, and it is redacted from every provider-supplied string the run persists or emits — including the model's own answer, which is redacted on the copy written to disk rather than in the value, because the validators parse that value and a key that is a common substring would corrupt a legitimate document.
- A `base_url` of plain `http://` to a NON-LOOPBACK host is rejected at load with `llm_config_insecure_base_url`: the key would go over it in cleartext, and the realistic cause is a typo or a LAN address. Loopback is allowed — that is where the local servers this provider exists for run — and `ATMOFAB_ALLOW_INSECURE_LLM_BASE_URL=1` is the deliberate opt-in.
- A repeated mapping key is rejected with `llm_config_duplicate_key`. YAML keeps the last silently, and this file decides which model runs each substep and therefore what a run costs.
- **Data egress.** An HTTP leaf is answered from the conductor's own process over HTTPS to the operator-configured `base_url` — the host-assembled prompt (which inlines the node's specification, IR, and dependency surface) leaves the machine for that endpoint. There is no bwrap sandbox around it, and none is required: `bwrap` confines a leaf that runs model-directed tools against the filesystem, and an HTTP pure leaf runs none — its response is data passed to the same validators the CLI pure leaf's response reaches. The API key and the proxy settings are read from the CONDUCTOR's environment — the same one every spawned leaf receives — not from the process-global one, so a run's own credential and egress routing are what apply. `record-launch` marks such a launch `leaf_transport: "http"` with `sandbox_enforced: false`, so an audit can tell a skipped sandbox from a missing one.
- **Preflight** probes EVERY distinct provider a configuration can launch and records them under `preflight.json#providers`, keyed by backend token (the top-level fields keep describing `--backend`, i.e. `defaults`, so the payload is a back-compatible superset). `workflow-launch-check` tests MEMBERSHIP of that map — a launch naming a provider nobody probed is refused with `backend_not_probed` — and `record-launch` takes the launch's own token from its response payload rather than from the preflight's single `backend`. A payload without the map is a pre-adoption preflight, where membership and the former equality test coincide.
- An HTTP provider's probe checks three things, all fail-closed: the named environment variable is set and non-empty (its value is never recorded), `base_url` is a well-formed `http(s)` URL with a host, and the endpoint answers. The reachability request is UNAUTHENTICATED and any HTTP status counts as reachable (a `401` establishes that a server responds, which is the property under test); only DNS failure, connection refusal, or a timeout fail it. `ATMOFAB_HTTP_PREFLIGHT_SKIP_REACHABILITY=1` drops only that third check.
- **Provenance.** The invocation record carries `llm_config_path`, `llm_config_sha256` (the bytes that were parsed, hashed from the same read), and `llm_leaf_map` (the resolved provider, model and command of every leaf — the command because two leaves can share a backend token and still run different executables), and each `agent_runs` row carries its own `agent_backend` / `agent_model`. A `--resume` re-hashes the recorded file and refuses a changed one with `llm_config_changed_since_launch` (see `docs/RUNBOOK.md` §3-1). The cold start also copies the configuration's BYTES — the ones it hashed and resolved, not a second read — to `workspace/orchestrations/<id>/llm_config_snapshot.yaml`, and never rewrites it on resume: the operator's own configuration file is not under version control, so without that copy a refusal naming an edited or deleted file would name something unrecoverable. The refusal points at the snapshot when there is one.
- **There is no run-wide override.** The `--llm` / `--agent-model` / `--llm-command` trio is removed: the file is the only thing that says what a leaf launches, and `llm` / `llm_command` — which the runtime's `init` / `preflight` surface still speaks — are DERIVED from `defaults`. An orchestration that recorded no configuration pin, or recorded the removed flags' literals, therefore cannot be resumed (`llm_config_legacy_flags_removed` / `llm_config_changed_since_launch`); there is nothing left that could reconstruct which model ran which leaf. `apply_defaults_overrides`, which applied a run-wide model/command onto `defaults` and everything that inherited it, survives for one caller: the preflight subprocess, which re-applies the resolved defaults onto the file it reloads. Codex transport flags (`--sandbox read-only`, `--skip-git-repo-check`, …) are deliberately NOT a configuration surface: they stay code-level so the preflight's flag certification can cover what is emitted (the `exec resume` argv is pinned against `CODEX_EXEC_RESUME_REQUIRED_FLAGS` by equality; the `exec` argv is certified by hand-listed substrings and is not — `TODO.md`).

### phase type and agent type
- Before starting each phase, explicitly judge by phase type whether the target phase requires a `step agent` or a `substep agent`. `Compile` / `Generate` / `Validate` require a `substep agent`, and `Build` requires a `step agent`.
- Phase-artifact generation, MCP execution, and verification-purpose provisional implementation are performed only by a launched child `agent`, never by the conductor before the child leaf launch completes.
- The phase-artifact roots of `workspace/ir/` and `workspace/pipelines/` are materialized inside a recorded phase: `record-launch` has run for the substep that produces them and `phase_state` is `child_running`. Until PR-2 of [issue #171](https://github.com/seiya/atmofab/issues/171) a capability token was the third condition and the writer was the child itself; the conductor is the writer now (§phase artifact authorship), so the rule is about WHEN, not about who.
- When a root-path reservation is needed before launching a child `agent`, generate only the reservation artifact `workspace/orchestrations/<orchestration_id>/reservations/<node_key_safe>/<step>.json`, and the actual directories of `workspace/ir/` and `workspace/pipelines/` must not be created.
- The conductor is responsible only for the progress control of the whole workflow, and must not directly generate the phase-body artifacts (e.g. `spec.ir.yaml`, `diagnostics.json`).
- As a substitute for workflow execution, a script that batch-automates the progress of multiple phases and artifact generation must not be newly generated or executed.
- The `Build` step is a deterministic process that calls the MCP `compile_project` and requires no LLM inference. The `step agent` limits its responsibility to the MCP call and recording the result.
- The conductor directly launches each substep of `Compile` / `Generate` / `Validate` as a leaf (`record-launch` + a `claude -p` / `codex exec` subprocess). ### phase artifact authorship
> **This section stated a leaf's WRITE AUTHORITY until PR-2 of [issue #171](https://github.com/seiya/atmofab/issues/171).** It listed a per-substep `write_root` for each launch, and the capability document, output manifest, read manifest and terminal FS-diff that bounded and audited it. None of those documents is written any more: a `pure-function leaf` returns one JSON document and the HOST writes every artifact after the child window, so there was no authority left to bound. What replaces the section is a statement of who AUTHORS each phase artifact — which is what the rest of this document, the phase docs and `determine_substep_status` actually read.

- Each phase artifact has exactly one author, and it is the conductor's own process:
  - `Compile`: `<ir_ref>/spec.ir.yaml` and `<ir_ref>/ir_meta.json` from the pure producer's and reviewer's returned documents; `<ir_ref>/compile_static_meta.json` from the deterministic `Compile.static` substep.
  - `Generate`: `<pipeline_ref>/source/<source_id>/…` from the accepted `CodegenBundle` (the declared source files, the assembled runner and Makefile, `codegen_bundle.json`, `bundle_meta.json`, `verdict_meta.json`), and `source_meta.json` from the reviewer's verdict; `gate_meta.json` and the `lint_evidence/` / `syntax_evidence/` certificates from the deterministic `Generate.gate` substep.
  - `Build`: `<pipeline_ref>/binary/<binary_id>/…`, written by `_build_inproc`.
  - `Validate`: `<pipeline_ref>/runs/<run_id>/<node_key_safe>/…` — the evidence tree and `verdict.json` from `_execute_inproc`, `semantic_review.json` from the pure judge's returned document, `pre_judge_meta.json` / `post_judge_meta.json` from the two deterministic gate substeps.
  - The pipeline root's `lineage.json` is host-authored by the conductor (`_write_lineage`) at the start of each phase.
- A LEAF authors nothing. Its terminal `agent_run` row therefore carries `output_refs == []`, enforced in both directions (§pure-function leaf), and the deliverables are vouched by their on-disk existence at pass-evaluation time.
- What a launch still DECLARES is `allowed_output_paths` on the launch request — the paths a DETERMINISTIC substep is contracted to produce, validated against the phase contract by `_allowed_output_paths_for_launch` and read back by `determine_substep_status` and `_validate_pass_output_refs_against_launch`. It is a contract, not an authority: nothing enforces it against the conductor's own process.
- `record-launch` writes `workspace/orchestrations/<orchestration_id>/sandbox_profiles/<agent_run_id>.json` for every launch that starts a CHILD PROCESS, and that profile is the one document about a launch that still decides something — `bwrap` enforces it, read-only, with `write_roots: []`. A launch that starts no process writes none and may reference none: an HTTP pure leaf answered from the conductor's own process (`leaf_transport: "http"`) and a deterministic substep (`leaf_transport: "in_process"`) are both exempt, and the `--stage pre_judge` audit applies the same exemption on the same response fields.

### file write paths
- Every phase artifact is written by the conductor's own process, so there is no leaf-facing write protocol to state. The rules that stood here — the `Edit` / `Write` path list, the ban on shell redirects, `tee`, `sed -i` and `python`-mediated writes — governed an AGENTIC leaf holding tools, and Z4 ([issue #171](https://github.com/seiya/atmofab/issues/171)) deleted that leaf.
- The MCP-owned `command_log.jsonl` is still written only by the build-runtime server, at the canonical placements `docs/workflow/MCP_COMMAND_LOG_PLACEMENT.md` names.

### LLM context
- The `step agent` and `substep agent` must not share the same `LLM` context. Each `agent_run_id` has a unique `context_id` and requires recording `context_isolated=true`.
- `Compile.generate` and `Compile.verify` are launched in independent contexts. The same applies to `Generate.generate` and `Generate.verify`, and `Validate.execute` and `Validate.judge`.

### agent_run recording
- For a phase that has `substep`, the conductor must launch the required `substep` group, make the completion judgment, and then finalize `step_result.json`.
- The conductor must judge the launchability of a `step agent` or `substep agent` based on the dependencies reconstructed from `deps.yaml` and `spec_catalog.yaml` and the `dependency` section of `spec.ir.yaml`.
- Every `agent` execution has an `agent_run_id` and must record the input references, output references, and parent-child relationship.
- Each line of `agent_runs.jsonl` requires recording `started_at` and `status`, and when `status` is a terminal status (`pass` / `fail` / `blocked` / `timeout` / `cancel`), requires recording `finished_at`.
- `fail_closed` is used only as a terminal status of `orchestration_meta.status`.
- The `agent_runs.jsonl` of the `step` / `substep` roles requires recording `parent_agent_run_id`, `agent_backend`, `agent_model`, `context_id`, `context_isolated`, `agent_session_id`, `launch_request_ref`, `launch_response_ref`, `launch_prompt_ref`, `launch_reply_ref`, `agent_result_ref`, and `agent_summary_ref`.
- The `parent_agent_run_id` of a `substep agent` points to the `orchestration agent_run_id` that launched that `substep`.
- The child leaf's `agent_run_id` is recorded as its `agent_session_id`.
- **`agent_session_id` is a bookkeeping id; the claude backend ALSO pins a real session to it.** The conductor reuses the child's `agent_run_id` (UUID) as its `agent_session_id` / `context_id`. For orchestration bookkeeping these are identifiers only, and the **canonical** record of a child's work is `workspace/orchestrations/<orchestration_id>/agents/<agent_run_id>/dialogs/` (the launch prompt/request, and the final reply/summary). However, for the **claude backend** the leaf is launched with `--session-id <agent_run_id>`, so Claude Code **does** write a real transcript at `~/.claude/projects/.../<agent_run_id>.jsonl`. That host transcript is what `repair_strategy=reuse` warm-`--resume`s (see the reuse-repair rule below); it is NOT mirrored into the orchestration artifacts, so a warm resume leaves no trace in `agent_runs.jsonl` (which still records `context_isolated: true`) — to tell a warm resume from a cold start, inspect the host `~/.claude` transcript, not the orchestration dir.
- `record-launch` must update `workspace/orchestrations/<orchestration_id>/session_run_index.json` immediately after launching the child, and record `agent_run_id`, `agent_session_id`, `context_id`, `agent_role`, and `status`.
- The `edge` of `agent_graph.json` uses `orchestration -> step` or `orchestration -> substep` as the canonical source.
- `agent_runs.jsonl` and `agent_graph.json` must be generated by sequentially appending in-flight events. Post-generation is forbidden.
- The `agent_runs.jsonl` row of the conductor itself is appended **only once, immediately after launch** with `agent_role=orchestration`, `status=running`. The conductor itself has no path to update this row via `record-agent-run` (a double invoke is rejected with `ValueError: duplicate agent_run_id`). At termination, `set-status` rewrites this row in-place to a terminal status with runtime privilege and assigns `finished_at` (it is a rewrite, not an append, so it does not hit the duplicate guard), and on resume (terminal reset) it conversely returns it to `running`. This is to prevent the agent_runs-based audit / `validate_workspace_root` from mistaking the orchestration row as permanently `running`, and the canonical terminal state of the whole orchestration continues to be expressed on the `orchestration_meta.json` side via `set-status`. For details, [docs/CLI_REFERENCE.md#record-agent-run](CLI_REFERENCE.md#record-agent-run) and [docs/CLI_REFERENCE.md#set-status](CLI_REFERENCE.md#set-status) are the canonical source.
- `record-launch` saves the launch request/response and builds the read-only sandbox profile; it runs as part of the leaf launch.
- For a claude leaf, `record-launch` must record `claude_tools` — every value the argv's `--tools` occurrences carry, in argv order (issue #71). The tool set a leaf came up with is written down nowhere else, and it is what a later audit of "could this leaf have done that" turns on; on a pure launch the recorded value is the empty allowlist, which is the audit's evidence that it was. `--tools` UNIONS — measured on CLI 2.1.239: a `command:` prefix naming `Monitor` puts `Monitor` in the leaf's roster and the conductor's own flag does NOT win — which is why EVERY occurrence is recorded rather than the last, and why the value is DERIVED from the argv the leaf is actually launched with rather than from the configuration that produced it.

  Three fields were recorded beside it and went with the agentic leaf in Z4 ([issue #171](https://github.com/seiya/atmofab/issues/171)): `claude_setting_sources` (the `--setting-sources` value, OVERRIDE semantics, so the last occurrence was the one recorded), `mcp_config` (one `{ref, sha256}` per `--mcp-config` value, ACCUMULATE semantics, each hashed from the file's bytes at launch and fail-closed on an unreadable one), and the private-home trio `claude_workflow_home` / `claude_home_generation` / `claude_settings_sha256`. A pure launch passes neither flag — `--safe-mode` refuses every settings layer, and there is no server set because the leaf holds no tool to call one with — and prepares no private home, so all five have nothing to describe.

  What each other launch records follows from its own argv. A codex leaf names none of these flags and records none of these fields; an HTTP leaf and a deterministic substep have no argv at all — the first spawns no process, the second runs in-process — so they are recorded about nothing rather than about a launch that did not happen. An HTTP leaf also has no sandbox profile, so its environment, including the credential its entry's `api_key_env` names, is recorded nowhere; the proxy / TLS families and the claude credential variables are excluded by name, and `LEAF_ENV_NAMED_EXCLUSIONS` carries each decision and what it costs. A PURE claude leaf is the one that is not simply absent: it names `--tools` with the empty value, so it records `claude_tools: [""]`, which distinguishes "launched with no tools" from "not a claude CLI leaf at all".
- `record-launch` must record `sandbox_runtime=bwrap`, `sandbox_enforced=true`, and `sandbox_profile_ref` in the launch response of a child-process launch. For an HTTP leaf it must instead record `leaf_transport=http`, `sandbox_runtime=none`, `sandbox_enforced=false`, and no `sandbox_profile_ref`; `record-agent-run`'s terminal validation grants the corresponding exemption only when the response carries BOTH that transport marker and an HTTP provider token, so a child-process launch cannot claim it.

### child agent launch request
- When launching a child `agent`, the conductor must, using `docs/workflow/WORKFLOW_CORE.md` and the `docs/workflow/phases/phase_*.md` corresponding to the target `step` as the canonical source, make explicit the `execution input`, `verification input`, and `expected output` of the target `step` or `substep`.
- The conductor must make explicit, in the child-`agent` launch request, that the canonical source for the requirement definition and judgment rules is `docs/`, `spec/`, and the relevant trial's artifacts. An instruction or implication to read the implementation under `tools/` and extract rules is forbidden.
- The prohibition on reading the implementation under `tools/` applies to workflow execution and child-`agent` rule derivation. Repository improvement, maintenance, testing, and refactoring may inspect `tools/*.py` directly.
- Every validator gate is invoked by the CONDUCTOR, directly, in its own deterministic substeps (`Compile.static`, `Generate.gate`, `Validate.pre_judge` / `post_judge`). The `run-gate` subcommand existed so a leaf could invoke one through a capability check; it is deleted with the capability (issue #171 PR-2), and no leaf invokes anything.
- The direct execution of a validator script is permitted only as an exceptional operation. The permitted target is limited to `validate_workspace_root.py`.
- `guarded-apply-patch` and the `apply_patch_writes` gate have been **removed** (P2-7), and so has the FS-diff that replaced them (issue #171 PR-2). No leaf writes an artifact; see §phase artifact authorship.
- `record-agent-run` no longer audits the filesystem. It validated a step/substep child's writes by `write_roots`-containment of the paths that changed during its window, with hand-maintained exemptions for the host's own writes inside it (the `Generate.gate` lint / syntax certificates above all); PR-2 of [issue #171](https://github.com/seiya/atmofab/issues/171) deleted it with the write baseline it diffed against. What it still checks on a `pass` is the declared `output_refs` against the LAUNCH's own `allowed_output_paths`, and — for a pure leaf — that `output_refs` is exactly `[]`.
- **runtime placeholder restoration: removed (P2-7).** The `created_file_pin_stubs` 0-byte placeholder restoration is gone, and so is the file-pin system it served: no launch declares a `write_root` of any kind since PR-2 of issue #171, so there is no pin to pre-touch and no bind-mounted file inside a sandbox. `lineage.json` stays host-authored at the pipeline root, as does every other phase artifact (§phase artifact authorship).
- The child-`agent` launch prompt must be rendered from the corresponding template in `tools/prompt_templates/`; a free-form prompt that does not use the template is forbidden. The conductor supplies the launch-request parameters; `record-launch` renders the prompt (the canonical render path) and returns the rendered `launch_prompt_text`, which the conductor passes to the leaf subprocess.
- `ir_ref`, `pipeline_ref`, and `dependency_ref` must be finalized to canonical paths before launching the child `agent`. A placeholder must not be recorded in the launch request.

### repair / retry
- The conductor must evaluate the child `agent`'s returned result and judge `issue_severity` (`minor` / `major` / `critical`). A verify finding is never tolerated.
- The conductor routes a verify finding by `issue_severity` (`classify_verify_severity`): `minor` → `repair_strategy=reuse` **same-phase reopen** of the phase's producer substep (warm-resume + slim finding injection); `major` / `critical` → `dev`: `fail_closed`, `prod`: `escalate` to the diagnostician (which decides how far back to recover — `reuse`/`restart`/`reopen`/`fail_closed`, INCLUDING a `restart` of **this phase's own producer**, e.g. regenerate the IR from scratch). `resolve_severity_directive` is the single source of the reuse-vs-discard mapping and it applies to a directive that NAMES a `target_phase`; a directive with a null target has its `repair_strategy` CLEARED and terminalizes instead of repairing, whatever the leaf spelled — otherwise a null target, which `conduct` resolves to the current phase, would fire the producer reopen with the severity forcing skipped. Any decision that targets the current phase with a `repair_strategy` (`reuse`→warm / `restart`→cold) re-runs that phase's producer (rotating its id); a same-phase decision with no `repair_strategy` terminalizes. Which value a finding takes is defined by the phase contract (`Compile.verify`: `docs/workflow/phases/phase_01_compile.md` §1-2 §Severity of a finding; `Generate.verify`: `docs/workflow/phases/phase_02_generate.md` §2-2 §Severity of a finding). For non-verify failures it chooses `repair_strategy` per the relevant decision table.
- **The retry budget is spent only on findings the failing party can act on.** A deterministic gate must attribute its finding to a file, and the file to an author, before it routes: a finding whose subject is a file THIS REPOSITORY authors — the build control file, or an `M3c` node's host-rendered runner glue, both written before the leaf runs and both removed from its `allowed_output_paths` — terminalizes the node on the first attempt with a reason naming the producer, instead of being re-presented to a leaf that has no honest means to change it. Re-presenting an unsatisfiable verdict is not merely wasted budget: it is the pressure that produces a `leaf shortcut` (`AGENTS.md` §Development premises). A finding a gate can attribute to NEITHER author fails closed for the same reason, because assuming the leaf is how such a loop stays invisible. Issue #112; the `Generate.gate` categories are in `phase_02_generate.md`.
- The conductor must not directly perform the repair of a phase artifact itself. When a repair is needed, it must re-delegate to the child `agent` of the target `step` or `substep`.
- `repair_strategy=reuse` may be chosen only when it can converge with a local fix without changing the input contract and expected output of the target `step` or `substep`.
- `repair_strategy=restart` is chosen when any of contract reinterpretation, design reconstruction, or wide-scope regeneration is needed.
- On re-submission, regardless of `repair_strategy`, a new `agent_run_id` and a new `context_id` are issued.
- With `repair_strategy=reuse`, the `agent_session_id` may be reused. With `repair_strategy=restart`, a new `agent_session_id` must be issued.
- **Warm-resume reuse (claude backend).** For the claude backend, a `reuse` repair whose target session transcript still exists is **always** warm-`--resume`d (forked) so the repair leaf inherits the producer's context instead of cold-starting, falling back to a cold launch if the transcript was GC'd. `restart` repairs stay cold (anchoring avoidance) — so the warm/cold choice is driven by the failure classification's `repair_strategy` (deterministic-gate findings route `reuse`→warm; LLM-verify-attributed `restart`→cold). When a warm resume fires AND a findings excerpt is present (the `Generate.gate`/`Compile.static` reopens), the conductor sends a **slim findings-only repair turn** (the resumed leaf already holds the SKILL/contract docs); a warm reuse without findings re-sends the full prompt. Both behaviours are always-on (no env gate). Canonical: [docs/design/deterministic_followups.md](design/deterministic_followups.md) "G1-slim".
- The `launches/<agent_run_id>.request.json` on re-submission requires recording `issue_severity`, `repair_strategy`, `repair_target_agent_run_id`, and `repair_reason`.
- With `repair_strategy=reuse`, a step/substep `pass` no longer requires `apply_patch_writes` gate evidence (`_validate_apply_patch_gate_coverage` early-returns for step/substep), so there is nothing to inherit: a reuse retry that writes nothing terminates `pass` on its own, and a reuse retry that re-writes a path does so directly with `Edit` / `Write`. (Same-identity `(node_key, step, substep)` is still verified runtime-side.) With `repair_strategy=restart`, the contract is reinterpreted and output is regenerated from scratch.
- **verify-family meta re-author (HISTORICAL — the agentic path, deleted in Z4, issue #171):** an agentic `compile.verify` / `generate.verify` substep had to produce its declared meta output (`ir_meta.json` / `source_meta.json`) to terminate `pass` — an inspect-only verify that writes nothing cannot `pass` (it has no `output_refs`). When the inspection finds nothing to change, re-author the meta anyway (refresh an idempotent field such as `verify_attempts`) with `Edit` / `Write`. The verify launch prompt MUST instruct the meta re-author as mandatory (not optional) — the `substep agent` template's verify-family line carried it, and both the template and that leaf are deleted (Z4, issue #171). **This bullet is the agentic (residual) generate-leaf contract; a `pure` verify leaf inverts it — see §pure-function leaf (`Z2` generate-executor, `Z1` compile pair).**

### pure-function leaf (the only leaf model)
- **Since Z4 ([issue #171](https://github.com/seiya/atmofab/issues/171)) there are exactly two launch shapes, and this is one of them.** Every LLM `substep` — `(compile, generate)`, `(compile, verify)`, `(generate, generate)`, `(generate, verify)`, `(validate, judge)` and the `escalate` diagnostician — runs as a pure-function leaf on every node and every declared provider; the other shape is a DETERMINISTIC substep the conductor runs in its own process. A request that is neither is refused rather than rendered. A `generate` pair on a node with no `CodegenBundle` shape used to fall back to the agentic leaf; it now fails closed (`node_has_no_bundle_shape`).
- The history the rest of this section was written against: four `substep`s ran as pure-function leaves first — `(compile, generate)` and `(compile, verify)` on every node (`Z1`, [issue #168](https://github.com/seiya/atmofab/issues/168)), and — under the `pure` `generate-executor`, the only executor since `M-F` (`docs/GLOSSARY.md`) — `(generate, generate)` and `(generate, verify)` on any node with a `CodegenBundle` shape — `m3c`, or `harness` since [issue #169](https://github.com/seiya/atmofab/issues/169): Claude uses a `claude -p` turn with tools disabled, and Codex runs inside a read-only sandbox; both return exactly one JSON document and make no repository writes. (Until Z4 — issue #171 — a node with no bundle shape ran the shared agentic `generate` leaves instead, as did any leaf whose configured entry narrowed its `capabilities:` to drop `pure`; both now fail closed, `node_has_no_bundle_shape` and `llm_config_capability_insufficient_for_substep`, and the catalog holds no such node.) This is a distinct executor class from both the deleted agentic leaf and a deterministic in-process substep (the "Deterministic in-process execution" rule of §term rules above): the executor is a normal `substep` `agent_run_id` with a launch record and phase_state, but it holds no repository write authority and its launch prompt reads no `SKILL` and no `skill_must_read_refs`. (It held a CAPABILITY document declaring `write_roots: []` / `mode: "pure_readonly"` until PR-2 of issue #171; the document is gone, the property is structural.)
- **Deliverable vouch by on-disk existence.** A pure leaf holds no write authority, so it cannot itself produce an `output_refs` deliverable. Its terminal `agent_run` row therefore carries `output_refs == []` — enforced **in both directions**: a pure terminal `pass` row with a non-empty `output_refs` is a violation (a no-write leaf must not claim a write). The phase's declared required outputs (`phase_required_outputs`: `<source_id>/src/<spec_id>_model.f90`, `<spec_id>_checks.f90` on an `M3c` node, the host-rendered runner, every other file of the accepted bundle, the build control file, and `<source_id>/source_meta.json` — the runner, the bundle's other files and the control file since [issue #250](https://github.com/seiya/atmofab/issues/250)) are written by the **host** after the leaf terminates and are vouched by their **on-disk existence** at pass-evaluation time (a declared-but-unwritten deliverable still fails — the anti-mock-green invariant holds). `codegen_bundle.json` is host-written but is **not** a required output: it is certified separately by the `post_generate` gate (`_validate_post_generate_bundle`), which re-runs the full bundle acceptance contract against it. This inverts the agentic verify-family meta re-author bullet above: an agentic verify leaf re-authors its own meta, the `pure` verify leaf returns a verdict the host projects onto `source_meta.json`.
- **Verdict-category failure routing → cold generate restart.** A pure leaf's bounded in-conversation repair (schema-malformed bundle / verdict) is capped; on budget exhaustion the failure category, excerpt, and per-attempt model/usage are persisted (`bundle_meta.json` for the producer, `verdict_meta.json` for the reviewer) and no `source_meta.json` / verdict projection is written (proof-of-work: no schema-valid verdict, no meta). A pure `generate.verify` verdict category does **not** route `reuse` to the verify session: a cross-phase reopen structurally returns to the `generate.generate` producer, and the exhausted reviewer session has no reuse value, so it routes `restart` → **cold `generate.generate`**. (A `minor` verify finding on a schema-valid verdict still routes `reuse` → same-phase producer reopen per the `### repair / retry` table; only the schema-failure categories force the cold restart.)
- **The `compile` pair's documents and host writes (`Z1`).** The pure `compile.generate` producer returns one JSON object with exactly the keys `ir` (the IR's own top-level sections) and `last_fail_reason` (`null`, or a non-empty string DECLARING that the phase cannot be completed from its inputs). The host validates that SHAPE only — the two-key envelope, the declaration's type, the presence of the top-level sections, and that the object survives its own serialize/parse round trip — then writes `<ir_ref>/spec.ir.yaml` and `<ir_ref>/ir_meta.json` itself. The MEANING of the IR is judged by the existing deterministic `Compile.static` gate, whose `compile_static_violation` already reopens `(compile, reuse)`; nothing in the pure loop re-runs `--stage compile`. The producer's `ir_meta.json` carries `verification_status: "pending"` (a non-empty string the meta contract requires, and deliberately not `"pass"`, which is what every dependency-certification reader compares against); the pure `compile.verify` reviewer returns the same verdict document the `generate.verify` reviewer returns and the host re-authors `ir_meta.json` from it. Per-attempt records are `<ir_ref>/compile_generate_meta.json` and `<ir_ref>/compile_verify_meta.json`, the twins of `bundle_meta.json` / `verdict_meta.json`.
- **The judge's document and the host write (`Z3`).** The pure `validate.judge` reviewer returns one JSON object with exactly the keys `decision` (`"pass"` / `"fail"`), `findings` (empty on a pass, non-empty on a fail; each entry `{attribution, evidence_refs, confidence, description}` with closed keys), and an optional `notes` string. The host validates that shape in the reviewer loop — including that every `evidence_refs` entry names one of the documents it INLINED — and then writes `<run_node_dir>/semantic_review.json` itself: the `review_method` literal the `--stage pre_judge` gate requires, the `scope.model_ref` / `scope.runner_ref` / `scope.raw_refs` it checks for existence, the run identity, and the `raw_excerpt_policy_version` the review was made under. Everything in that list is a fact about the workspace a closed-context leaf cannot know and must not guess. Each citation is resolved from the document key back to the path the host inlined it from, which keeps `evidence_refs` a path list without the leaf ever naming a workspace location. The per-attempt record is `<run_node_dir>/judge_meta.json`, the twin of `bundle_meta.json` / `verdict_meta.json`. **The consequence downstream** is that `semantic_review.json` is now a HOST-authored artifact: a `recoverable` `--stage pre_judge` violation naming it cannot be repaired by re-running the leaf, which would produce the identical file. `_post_judge_inproc` used to reclassify it as `unrecoverable` for that reason; issue #176 made both graded classes write `fail_closed`, so the reclassification became a no-op and went with the mini-loop. **On budget exhaustion** the host writes no `semantic_review.json` at all, so `_judge_semantic_decision` reads nothing and the existing `validate_judge_conformance_violation` branch fires — deliberately not a second routing table.
- **What the judge is shown of `raw/` (`Z3`).** `raw/` is 13 MB of float arrays on `shallow_water2d` and cannot be inlined, so the host computes a bounded, versioned EXCERPT of it and inlines that: the expected-vs-produced (`test_id`, `case_id`) coverage matrix (derived by the same function the `--stage post_execute` gate uses, so the two cannot disagree), and per-array summaries — shape, extent, non-finite counts, all-zero — with no numeric array at any size. `docs/workflow/phases/phase_04_validate.md` §4-2-1 is canonical for its contents and for what it deliberately omits.
- **The producer's THIRD exit, and where it lands.** A non-null `last_fail_reason` is neither a pass nor a repairable document defect. The host writes `ir_meta.json` with `verification_status: "fail"`, that reason, and `issue_severity: "major"` (the phase rubric's grade for a finding whose subject is an INPUT), writes NO `spec.ir.yaml`, and records the off-table category `compile_declared_fail`. `classify_failure` recognizes the token, declines the document routing table, and falls through to the verify-severity gate — `dev` fail_closed, `prod` escalate — which is exactly where the agentic leaf's own `Compile fail` declaration landed before Z4 (issue #171).
- **How the `compile` pair recovers, warm and cold.** Because `Compile.static` is the single semantic gate of the pair, a `compile_static_violation` reaches the producer as an outer `(compile, reuse)` reopen carrying `compile_static_meta.json#failure_excerpt`. Where the session can be resumed (`claude_cli`'s transcript, `codex_cli`'s thread id) that first attempt is a WARM repair: the findings alone, on the session that already holds the context. Where it cannot — a provider without `warm_resume` (`openai_compatible` / `anthropic_api`), a GC'd claude transcript, a pruned codex lineage home — it is a COLD repair on the SAME repair template, carrying `<findings>`, `<prior_document>` (the failed attempt's own artifact, read back from the directory that attempt's launch record names; absent on the routes that reopen without an accepted artifact), `<output_contract>`, `<authoring_rules>`, `<dependency_facts>` and a re-inlined `<pure_context>`. A reopen renders the full launch prompt in two cases, and only those two: it carries no findings excerpt, or its `repair_target_agent_run_id` is unnamed (`"none"` — the payload-absent spelling, which the launch validator refuses as a repair target). The second is the one residue: findings the run holds and cannot deliver. The run log names the path taken at the SEED — `resume_session_unavailable` then `pure_reopen_cold` (`findings_carried` / `prior_document_carried`). A codex lineage home found missing later — at the launch itself (`record_launch`'s `codex_lineage_home_missing`, under the metadata lock), or by the thread's row naming no lineage at all (a run recorded before issue #245) — turns an already warm turn cold through the loop's own fallback instead, and records only `resume_session_unavailable` with `reason=codex_lineage_home_missing`; both carriers ride that turn too. The `generate` pair takes the same two paths. Closed by [issue #209](https://github.com/seiya/atmofab/issues/209) (split out of [issue #168](https://github.com/seiya/atmofab/issues/168)).
- **Persona separation.** A pure `generate.verify` leaf never resumes the producer's session (the separate-persona hard rule). The guarantee is **structural, not a check**: `_run_pure_verify_substep` accepts no external resume seed at all — the only session it ever resumes is its own prior attempt's `agent_run_id`, assigned inside its repair loop — so a producer arid is unreachable rather than rejected. (The pure producer, by contrast, does accept an external reopen seed, which is why the two are not symmetric.) The producer and reviewer are always launched under fresh, distinct `--session-id`s.

### leaf transient retry
- A leaf that exits nonzero because of an LLM-infrastructure fault is classified from its captured output into an infra tag (`llm_usage_limit` / `llm_overloaded` / `llm_rate_limit` / `llm_client_error` / `llm_permission_probe_unavailable` / `llm_transport_flake`), plus the out-of-band `leaf_timeout` (the hard-timeout bullets below), which the conductor assigns from its own record of the kill and never from the captured output. `stderr` is authoritative and the most severe tag in it wins; `stdout` — which carries the leaf's own prose — decides only when `stderr` names nothing. The exception is the two **non-retryable** tags `llm_usage_limit` and `llm_client_error`: found on `stdout` (where the CLI reports both, as its result text) they override a `stderr` tag, which can only ever remove a re-launch, never add one. The conductor retries a **transient** tag in place instead of terminalizing the run.
- Retryable tags: `llm_transport_flake`, `llm_overloaded`, `llm_rate_limit`. Budget: at most 2 retries (3 launches of the same `substep`). Backoff before each re-launch is per tag (`llm_transport_flake`: 2s, 10s; `llm_overloaded`: 15s, 60s; `llm_rate_limit`: 30s, 90s).
- Non-retryable, terminal on the first occurrence: `llm_usage_limit` (a hard stop of hours; an immediate re-launch consumes budget and delays the operator's `--resume` — terminal by default; the opt-in `--wait-usage-reset` below waits it out on a fixed schedule), `llm_client_error` (a 4xx: the request itself is rejected, so every re-launch reproduces it byte-for-byte), `llm_permission_probe_unavailable`, and an **unclassifiable** nonzero exit (a crash, an out-of-memory kill, or a hook denial is deterministic; re-running it reproduces the same failure).
- **Hard per-leaf timeout (`leaf_timeout`).** Every leaf spawn is bounded by `ATMOFAB_LEAF_TIMEOUT_SECONDS` (default 7200s = 2h), at every spawn site (`_spawn_pure_turn`, the one spawn site left since Z4 — the pure producer, the pure reviewer and the failure diagnostician all go through it). A value that parses to `0` disables the cap: the leaf's exit is still what ends the wait (so a leaf that answers and exits while leaking a pipe-holder still returns, and the post-exit stream waits are still bounded by `LEAF_TERMINATE_GRACE_SECONDS`), but no deadline ever expires, restoring the previous unbounded wait on the leaf itself; anything the parser cannot make sense of — unset, non-numeric, or carrying a leading `-` — falls back to the default rather than to `0` (a negative is a typo or a spelling of "no limit", and must not silently remove the backstop); a value above `LEAF_TIMEOUT_MAX_SECONDS` (2 147 483s ≈ 24.8 days) is clamped — a sanity ceiling, pinned to the largest deadline the `select`-based waits in `subprocess` accept before raising `OverflowError` instead of waiting (both leaf paths hand the whole remaining cap to `Popen.wait`, which does not overflow; the ceiling is kept at the platform limit so that any future deadline on a selecting wait cannot be invalid).
- **How the bound is applied.** The cap is a deadline evaluated before every wait, rather than a timer that kills and then relies on the pipes closing: killing the leaf's process group does **not** guarantee its pipes close, because `bwrap --new-session` puts the sandboxed command in a session of its own, so a tool subprocess the CLI leaked survives the group signal while holding the write end. Both backends therefore separate the WAIT from the READ. Each leaf's `stdout` and `stderr` are drained concurrently by reader threads, and the leaf itself is waited on with `Popen.wait` against the cap's remaining time — a wait that ends at the leaf's **exit**, not at its streams' **EOF**, so a leaf that answers and exits while leaking a tool subprocess that keeps the pipe is not waited out to the cap and then reported as a wedge. `codex` additionally moves the JSONL records off its pipe through a bounded queue, so the parse in the main thread is likewise bounded by the cap. Once the leaf has exited (or been killed), every remaining stream wait is bounded by `LEAF_TERMINATE_GRACE_SECONDS` and then abandoned, never by the cap: at that point only a leaked descendant can still hold a pipe. The teardown takes at most two attempts (the second following the group signal) and, on the `claude` path, both readers share ONE grace per attempt rather than taking one each, so the teardown adds a small bounded multiple of the grace to the cap rather than one grace per stream per pass. On both backends the reads are **fixed-size blocks off the raw fd** (`LEAF_STREAM_READ_BLOCK_BYTES`), never lines, and the conductor decodes them itself with an incremental decoder in the codec `Popen(text=True)` would have selected (`_leaf_stream_encoding`), so a multi-byte character split across a block boundary decodes whole and a malformed byte is escaped rather than raised. The block is the unit of every bound below: a budget checked per delivered line does not run at all against a producer that writes megabytes without a newline terminator. Both captures are budgeted on both backends — `stderr` at `LEAF_STDERR_CAPTURE_MAX_CHARS` plus a retained tail of `LEAF_STDERR_CAPTURE_TAIL_CHARS`, and `stdout` (the `codex` JSONL stream, and the `claude` leaf's answer) at `LEAF_RAW_STDOUT_CAPTURE_MAX_CHARS`, with the `codex` structured terminal events spliced in after them bounded by `LEAF_FAILURE_EVENTS_MAX` — because a drain the conductor gave up on keeps running and an unbounded appender would grow the driver's heap for the rest of the run; each capture is bounded by its budget plus at most one decoded block (bounded in turn by `LEAF_STREAM_READ_BLOCK_BYTES`, times four in the worst case, since `backslashreplace` expands a malformed byte to four characters), and truncation is recorded in the stream as `[conductor] leaf_stderr_capture_truncated:` / `[conductor] leaf_stdout_capture_truncated:`. On the `claude` path the stdout notice fires only past 4 MB, where the envelope is already unusable. `stderr` keeps its TAIL as well as its head, marked `[conductor] leaf_stderr_capture_tail:`, because every consumer of that stream reads the END of it — the infra classifier takes the last matching line as the terminal cause and the failure summary takes the last 400 characters — so a head-only capture would spend the budget on a chatty leaf's progress log and discard the error it died of, terminalizing the run untagged. Reading continues past the budget: a reader that STOPS leaves nobody draining a pipe nothing will close, and the leaf's next write then blocks forever — the cap would become the cause of the hang it exists to stop. The `codex` pump additionally holds at most `LEAF_STREAM_QUEUE_MAX_CHARS` of unparsed stdout ahead of the reader, so a leaf emitting large records applies backpressure to its own pipe rather than accumulating in the driver; that same value caps a SINGLE record, since one JSONL record can be arbitrarily large and is otherwise reassembled whole before any budget applies to it. A record that exceeds it — newline-terminated or not — is clipped where it stands and returned BEHIND `[conductor] leaf_stdout_record_truncated:` on the same line, so that a prefix which happens to be valid JSON can never be parsed as a complete record (a clipped `thread.started` would otherwise bind a host identity from a record whose real content was never seen); the rest of that record is discarded to the next newline — the stream resynchronizes there, so a clipped record costs its own contents and not the rest of the turn. That marker is distinct from `leaf_stdout_capture_truncated:`, which reports the total budget spent. An abandoned stream appends `[conductor] leaf_stream_abandoned:` to the captured `stderr` so a truncated capture is not mistaken for a leaf that wrote nothing (it appears on a killed leaf and on a passing one alike — it reports a still-open pipe, not a failure), and a leaf that exited on its own keeps its exit status. An abandoned reader observes the stop signal within one block while its stream is still delivering; a reader parked on a stream that has gone silent stays parked, with its thread and the two pipe fds, until the driver exits. The read ends are never closed: `close()` waits on the same internal lock a blocked reader holds, which would trade a leaked fd for a hung driver. On expiry the conductor signals the leaf's **process group** (`SIGTERM`, then `SIGKILL` after `LEAF_TERMINATE_GRACE_SECONDS`), appends its own marker line `[conductor] leaf_timeout: leaf exceeded ATMOFAB_LEAF_TIMEOUT_SECONDS=<n> (elapsed <s>s); process group killed` to the leaf's captured `stderr`, forces a nonzero exit code, and emits `leaf_timeout` (`node_key`, `step`, `substep`, `agent_run_id`, `backend`, `timeout_seconds`, `elapsed_seconds`, `leaf_exit`, `stdout_chars`, `stderr_chars`, and `raw_stdout_chars` for `codex`). Whatever had already reached the conductor's pipes, and was still readable at the kill, is retained and persisted under `agents/<agent_run_id>/dialogs/`; the marker is appended, never substituted. In practice that is mostly `stderr`: a `claude` leaf emits its result text only when the turn completes, and the `codex` timeout path returns an empty `stdout` (its evidence is the raw JSONL event stream in `dialogs/leaf.stdout.jsonl`). The tag is decided by the conductor's own record of the kill (`ProcResult.timed_out`), **not** by recognising the marker: it outranks every infra line in the leaf's own output — the kill is the terminal cause, not the quota or transport message the leaf was last retrying — and because no classifier pattern matches the marker, a leaf that writes the same line cannot claim the tag and cannot suppress a genuine `llm_usage_limit`. The kill is bounded, not guaranteed to be complete: a tool subprocess the leaf started runs in the sandbox's own session and can survive the group signal, so every post-kill wait is capped by `LEAF_TERMINATE_GRACE_SECONDS` and the streams are then abandoned rather than waited for.
- `leaf_timeout` is **non-retryable**: a re-launch spends another full cap of wall-clock on a leaf that has already demonstrated it can wedge, and the budget would allow three of them. In the three `substep` loops the attempt is terminalized **in band** by the ordinary `finalize-child` chain (the conductor synthesizes the reply, so a leaf that never answered still terminalizes with evidence instead of staying `running`), and the phase `fail_closed`s under the reused `leaf_transport_error:` prefix — so the tag inherits the `leaf_transport_error` `reason_code`, and `--resume` re-runs the phase. The failure diagnostician (`escalate`) is the exception on the ROUTING side: it has a child `agent_run_id` and a `finalize-child` of its own since issue #169, so a diagnostician killed at the cap emits `leaf_timeout`, finalizes its row `fail`, and then terminalizes the PHASE as `<phase>_diagnose_unparsable` (an un-launchable or unreadable diagnosis is conservatively terminal by design), not as `leaf_transport_error`. Its partial output is **never** parsed as a routing directive: a leaf whose turn the conductor cut short does not get to spend a phase attempt on a directive it had half-written. A conductor that **died** leaves its leaf orphaned instead; that case is recovered by the ordinary `--resume` (`docs/RUNBOOK.md` §3-1, §Incomplete launch recovery), which a free exclusive claim admits whatever the recorded status says, and `record-timeout` remains the manual finalization procedure for a leaf the conductor did not finalize itself. A stream-idle watchdog, which would catch a wedge sooner than a hard cap, remains future work; it is now equally reachable on both backends, since both read through the same block-reader threads and either could take an idle deadline directly. The HTTP pure-leaf transport deliberately did NOT take one when it moved to server-sent events: a leaf process that has gone silent is a wedge, while an HTTP request that has sent no frame yet may simply be a reasoning model still thinking, so the two surfaces do not share the argument.
- **Opt-in `--wait-usage-reset` (default OFF)**: `llm_usage_limit` is still terminal by default; with the flag set the conductor instead **waits it out in place** and re-launches the same `substep` — a same-run, substep-granular resume instead of a next-day manual `--resume`. The decision is the classifier's **tag alone**: no reset instant is read from the dead leaf's output and no provider is asked for one, so the wait is the same for every declared provider (`AGENTS.md` §Development premises, no vendor lock-in — the issue #170 form; the reset-instant scrape and the host-side `/usage` probe it replaced are described in `docs/design/deterministic_followups.md` L5 as history). The wait is a **fixed schedule**, `USAGE_LIMIT_WAIT_SCHEDULE_SECONDS` in `tools/workflow_conductor.py`: 15 min, then 1 h, then 4 h (5 h 15 min in total), indexed by how many usage-limit deaths this `substep` has already waited out, so the budget is `MAX_USAGE_LIMIT_WAITS` = 3 waits per `substep` and the fourth death is terminal. That budget is **independent of the transient-retry budget** (a usage limit is never a transient tag, so the two cannot compound), and a wait is **not a repair turn**: `attempt` and the repair carriers are unchanged, so the re-launch is the SAME turn again with the same repair carriers — a first attempt re-launches cold (`repair_strategy: none`), and an interrupted repair turn re-runs as the same `reuse` repair with the same findings: warm against the session it was already repairing where the provider can resume one (`warm_resume`), else as the cold-fallback repair carrying `prior_document` — never against the dead attempt. Two events: `leaf_usage_limit_wait` (`node_key` / `step` / `substep` / `tag` / `wait_seconds` / `wait_attempt` / `max_waits` / `dead_agent_run_id` / `evidence` — the classifier's own tagged line, clipped as `leaf_transient_retry`'s is) before each sleep, and `leaf_usage_limit_wait_declined` (`node_key` / `step` / `substep` / `tag` / `reason` / `wait_attempt` / `dead_agent_run_id` / `evidence`) when the budget is spent — `budget_spent` is the only `reason`, so a run that opted in and still `fail_closed` on a usage limit is greppable; with the flag off nothing is emitted and the death is terminal as before. The re-launch's `record-launch` re-runs the TTL-driven preflight live-probe, so a stale preflight self-heals; the residual is that a wait shorter than the provider's actual window makes that probe or the re-launched leaf fail again, which spends the next schedule entry. The flag is **not** auto-recovered on `--resume` (a per-invocation preference — re-pass it); it is recorded on `orchestration_meta.json#invocation.wait_usage_reset` for provenance and **refreshed on resume** to the effective re-passed value so the record never reports the opposite of the resumed run's behavior. Wired into both pure loops (the producer and the reviewer); a `substep`-terminal usage limit after the budget is spent reports the honest launch count in `[attempts=<n>]` exactly as a transient exhaustion does.

- The retry loop is closed inside the `substep` execution: the phase's outcome list stays one entry per `substep` of `SUBSTEPS[phase]`, and a retried `substep` contributes exactly one outcome (its surviving attempt).
- Each attempt is a new `agent_run_id` with its own `record-launch`, its own `launches/<agent_run_id>.request.json`, its own `agents/<agent_run_id>/dialogs/` (the dead attempt's leaf output is retained as failure evidence), and its own launch instant (the freshness bound of `determine_substep_status`, so an artifact left half-written by a dead attempt cannot satisfy the retry). That instant is a FILESYSTEM stamp, not a `time.time()` reading — `agents/<agent_run_id>/launch_instant.probe.json`'s mtime, which is also the record of it — because the two sides of the comparison have to come from one clock: the kernel stamps an inode from a coarse clock that lags `time.time()`, and a deterministic in-process substep can write its deliverable inside that lag and fail its own gate having done everything right (issue #113). `Conductor._launch_instant` is the one producer, and it returns the tick after its own probe, so the dead-attempt property above survives the move. It waits for that next tick, bounded by `LAUNCH_INSTANT_TICK_WAIT_SECONDS` (2.0 s); a filesystem whose stamps advance more slowly THAN THE BOUND makes it give up and emit **`launch_instant_tick_wait_timeout`** (`agent_run_id`, `waited_seconds`, `instant`) — the run continues, having lost only the strict half of the property (a file written in the previous tick can then share the instant), never the lag half. No recorded run has emitted it; the tick is ~4 ms on this host's `workspace/` (one xfs mount). A granularity BETWEEN the tick and the bound emits nothing and is not loud at all — the wait succeeds after spinning that long, without sleeping, on every launch.
- The warm-resume target is invariant across attempts: a retry re-forks the same producer session and re-sends the same slim findings-only repair turn. A retry must not fall back to a cold launch (the slim prompt, hence the findings excerpt, is conditional on warm resume — the AGENTIC leaf; a pure producer's cold repair carries the excerpt too, §pure-function leaf).
- A dead attempt is `finalize-child`ed before the next `record-launch`: it is never vouched by a `step_result.json` (`substep_agent_run_ids` records only the surviving attempt), and since issue #177 that is all a failed attempt is — the completion vouch reads the artifact chain and the LATEST attempt's result, so no tombstone is owed. `finalize-child` must still come FIRST, because it closes the child's write window: `record-agent-run` diffs the live workspace against the baseline `record-launch` took, so a host write inside the window is charged to the dying leaf. It must also precede the next `record-launch` (the runtime rejects a launch while a child of the same parent is active). The residual a tombstone used to cover — a host crash between the two writes — is now nothing: the terminal, un-vouched `agent_run_id` it leaves needs no repair.
- A transient retry is an **infra** retry, not a content retry: `retry_decisions` stays `null`, no `issue_severity` / `repair_strategy` is assigned, and a recovered `phase` writes its `step_result.json` exactly as an unretried one does.
- Deterministic in-process `substep`s (`Build`, `Validate.{pre_judge,execute,post_judge}`, `Generate.gate`, `Compile.static`) are out of scope: they spawn no leaf, so they have no transport to fail.
- On budget exhaustion the phase terminalizes exactly as before: `fail_closed` with reason `leaf_transport_error: leaf_exit=<rc> (tag: <tag>; <evidence>) [attempts=<n>]`, and the final attempt's `agent_run_id` is tombstoned by the phase-level transport branch. The `tag` is the cause of the **last** attempt and `attempts` is the launch count — a run may mix tags (a retried transport flake that then hits a usage limit terminalizes as `llm_usage_limit` with `attempts=2`), so recovery is decided by the tag, not by the presence of the suffix. Every `agent_run_id` the loop issues is therefore tombstoned (the dead retries by the retry loop, the last attempt by the transport branch).

### baseline diff contract on re-submission (removed in issue #171 PR-2)
- There is no baseline and no diff. `record-agent-run` walked the live workspace at every terminalization and compared it against a per-agent write baseline, requiring every changed path to fall inside the capability's `write_roots`; a retry after a reject re-walked it, which is what this section's exclusion list existed for (`agent_runs_invalid.jsonl` above all, the file that carried the previous failure into the next retry's diff).
- What it measured was the HOST's own writes. A pure leaf holds no write authority — it runs read-only under `bwrap` and the host writes every artifact after the child window — so the audit ran the conductor's writes against a grant the conductor is not bound by, and `_should_ignore_runtime_snapshot_path`'s exemption list was the accumulated record of that mismatch.
- `deactivate-child` no longer captures a `deactivate_snapshot.json` either; it existed to freeze the child-authored path set before a later host write could contaminate the same diff.

- The feedback direction from a failed phase is fixed per phase:
  - `Compile` failure → only an in-Compile retry (no automatic retry because upstream is the manual Spec).
  - `Generate` failure → an in-Generate retry. When a verify failure of `source_meta.json` is judged `attribution=ir`, go back to `Compile`.
  - `Build` failure → go back to Generate. Because Build itself is a deterministic process, it does not involve an LLM, and forwards to Generate, as `repair_reason`, one of `compile_error` / `link_error` / `make_error` recorded in `build_log` (for details, the retry-trigger section of `docs/workflow/phases/phase_03_build.md`).
  - `Validate` failure → deterministically decide whether to go back to Generate / Compile / Spec by the combination of the `judge`'s `semantic_review.json#findings[*].attribution` and `verdict.json#failure_class` (the canonical decision table is the "Decision criteria for retry on failure" section of `docs/workflow/phases/phase_04_validate.md`).

## Design Policy
- Single responsibility: one `agent` has only one responsibility.
- Hierarchical delegation: control via the 2 systems `conductor -> step agent` and `conductor -> substep agent`.
- Contract-driven: when launching a child `agent`, fix the input contract and output contract, and forbid reads/writes outside the contract.
- Traceability: save all launch / termination events chronologically, and make the same judgment reproducible on re-execution.

## Orchestration instruction contract
### Common required items
- The conductor must record, in the launch request to a child `agent`, `orchestration_id`, `agent_run_id`, `parent_agent_run_id`, `node_key`, `step`, `substep` (when it exists), `ir_ref`, `pipeline_ref`, and `dependency_ref` as required.
- The launch prompt to a child `agent` is based on the corresponding template in `tools/prompt_templates/`, with the in-template placeholders substituted by the actual values of the target `agent_run`. `record-launch` performs this rendering; the conductor supplies the request parameters rather than the rendered prompt.
- The launch request to a child `agent` records `execution input`, `verification input` and `expected output` as required. It recorded a `write_root` and `read_roots` until PR-2 of issue #171; a leaf holds neither.
- `execution input` is limited to the input that the relevant `agent` may directly reference to generate the artifact.
- `verification input` is made explicit as input that the relevant `agent` may use only for pass/fail judgment, consistency confirmation, and dependency confirmation.
- `expected output` is made explicit including the file name, storage location, and update responsibility.
- The parent `agent` must not instruct guessed completion on an input shortage. When there is an input shortage, it instructs a `fail-fast` stop.
- The launch request to a child `agent` carries `skill_name`, `skill_ref` and `skill_must_read_refs` EMPTY. No leaf reads a `SKILL` since Z4 ([issue #171](https://github.com/seiya/atmofab/issues/171)) — its whole contract is the rendered prompt — and a pure launch request carrying a non-empty one is refused by name (`tools/orchestration_runtime.py`, `_validate_launch_request_payload`). They were REQUIRED fields until that change.

### Conventions for `ir_ref` / `pipeline_ref` / `dependency_ref`
- `ir_ref` is only `workspace/ir/<node_key_safe>/<ir_id>`, and an additional path segment must not be appended. `<ir_id>` is in the canonical `<slug>_<YYYYMMDD>_<seq3>` form (regex `^[a-z0-9]+(?:-[a-z0-9]+)*_[0-9]{8}_[0-9]{3}$`, canonical source: `docs/workflow/WORKFLOW_CORE.md` and `_SLUG_DATE_SEQ3_PATTERN` of `tools/orchestration_runtime.py`). Place `<node_key_safe>` as the parent directory of `<ir_id>`, and do not prepend it as a prefix to `<ir_id>` itself (because `node_key_safe` contains `__` / `_`, it violates the slug regex).
- `pipeline_ref` is only `workspace/pipelines/<node_key_safe>/<pipeline_id>`, and an additional path segment (including `source/` or `source_meta.json`) must not be appended.
- `dependency_ref` fixes the canonical path per phase. `Compile` records `spec/.../deps.yaml`, and from `Generate` onward records the phase root of `workspace/...` (`ir_ref` or `pipeline_ref`), forbidding a direct `spec` reference.
- In the launch request of `Generate verify`, `source_id` must be recorded as required.
- When a `step agent` / `substep agent` ends with `pass`, each path of `output_refs` must be included under the `ir_ref` or `pipeline_ref` directory recorded in the corresponding launch request.

## Operations Rules
1. At workflow start, issue an `orchestration_id` and create `workspace/orchestrations/<orchestration_id>/orchestration_meta.json`. Alongside `orchestration_id` / `status` / `started_at` (and, when supplied, `spec_ref` / `source_dependency_ref`), record `repo_revision` — the git version of the repository resolved at run time so a run's artifacts can be traced back to the exact source that produced them. `repo_revision` is `{ "commit": "<HEAD sha>", "dirty": <bool> }` (`dirty` reflects `git status --porcelain`; `workspace/` is gitignored so orchestration artifacts do not flip it). The SHA is resolved at run time, not pinned to a constant, mirroring the model-alias convention, and is captured **once at the initial start** and preserved across re-init / `--resume` (so it stays the source that produced the run rather than being overwritten by a later `HEAD`). When the run directory is not a git checkout (or git is unavailable), `repo_revision` is omitted so an absent revision stays distinguishable from a clean/dirty one; if `HEAD` resolves but the dirty state cannot be determined (or the repository has no commits yet), `repo_revision` is either omitted or carries `dirty: null`. No `driver` identity is recorded: issue #177 deleted the liveness probe that read it, and concurrency is decided by an exclusive `flock` claim under `~/.atmofab/start_claims/` instead — held for the life of the driver process, released by the OS when it dies, so a claim that is free proves the driver is gone without a record that can go stale (operations rules in `docs/RUNBOOK.md` §3-1).
2. Before the workflow starts, record the preflight result in `workspace/orchestrations/<orchestration_id>/preflight.json`, and when `can_launch_step_agents=true`, `can_launch_substep_agents=true`, and `sandbox_enforced=true` are not simultaneously satisfied, stop with `fail`.
3. Before starting each phase, confirm the phase type, and finalize the launch target as a `substep agent` for `Compile` / `Generate` / `Validate` and a `step agent` for `Build`.
4. The conductor saves `launches/<agent_run_id>.request.json`, `launches/<agent_run_id>.response.json`, `launches/<agent_run_id>.prompt.txt`, and `launches/<agent_run_id>.reply.txt` per launch request of a `step agent` or `substep agent`.
   Before each of those two calls it also saves the payload it passes, as `launches/<agent_run_id>.request.input.json` (`record-launch`) and `launches/<agent_run_id>.agent_run.input.json` (`finalize-child`). A payload travels as a file because a single argv element is capped at 128 KiB. Both are kept permanently as the evidence of what was sent, including when the call they feed fails. The full inventory is `docs/WORKSPACE_LAYOUT.md`.
5. The `response.json` and `child.response.json` saved by `record-launch` are a complete save of the leaf launch response, and must not drop the child-`agent` identifier.
6. On completion of each `step agent` and each `substep agent`, save `agents/<agent_run_id>/dialogs/agent.result.json` and `agents/<agent_run_id>/dialogs/agent.summary.txt`.
7. `agent.summary.txt` includes at least the final `status` and the failure cause or main-artifact reference.
8. `launches/<agent_run_id>.prompt.txt` is the body that concretizes the corresponding template in `tools/prompt_templates/`.
9. The conductor reconciles `deps.yaml`, `spec_catalog.yaml`, and the `dependency` section of `spec.ir.yaml`, and finalizes the execution queue based on the `spec` dependencies. **Scope clarification:** a single orchestration targets exactly **one `node`** (one `spec_ref`); items 9/28 describe the dependency-order reconciliation and the phase/substep queue **within that node**, not the automatic execution of dependency nodes' own workflows. By default a missing dependency is fail-closed (`workflow-launch-check` → `dependency_not_ready`; the operator runs each dependency node first). The entrypoint `tools/run_workflow.py --with-deps` opts into running the target's transitive dependency closure bottom-up (one orchestration per node) before the target; without it the default single-node, fail-closed behavior is unchanged. A `profile` dependency is NOT a node of that closure: the host resolves it as data at closure-resolution time, expanding it into the `component` it selects (`orchestration_runtime.expand_profile_dependencies`), so no `profile` leaf is ever launched and a `profile` target is refused at launch (issue #175).
10. The conductor issues a `step agent` or `substep agent` per launch target, and passes `node_key`, `step`, `ir_ref`, `pipeline_ref`, and `dependency_ref` as input.
11. Before launching the `Compile` of an upper `node`, the conductor reconciles the `ir_ref` and `ir_meta.json.verification_status` per immediate dependency `node`, and must not launch when `direct dependency ir readiness` is not satisfied.
12. Before launching `Generate` onward of an upper `node`, the conductor reconciles the `ir_ref`, `pipeline_ref`, and latest `aggregate_verdict` per immediate dependency `node`, and must not launch when `direct dependency execution readiness` is not satisfied.
13. When `direct dependency ir readiness` or `direct dependency execution readiness` is not satisfied, the conductor records the relevant `node` as `blocked` or `fail`.
13a. **Derivation-key certification ([issue #250](https://github.com/seiya/atmofab/issues/250), Z5 PR-2).** Both readiness levels, and `check-phase-certified` for the node's own phases, are ONE question: does the phase have a certified output whose stamped `derivation key` (`docs/GLOSSARY.md`) equals the key recomputed NOW over the phase's contract inputs? An output is `eligible` when its certifying stage meta records `verification_status: pass`, is not revoked, still hashes to what the certifying run stamped (`artifact_hashes`), and carries that key; among the eligible outputs of one key the `selection policy` (v1: the latest attempt, `tools/derivation.py#select_eligible`) chooses ONE, and every consumer binds to that output's `output_hash` — the node's own next phase and every dependent node alike. A pipeline is one chain: the build key binds the source's output hash, not its pipeline, so a byte-identical source reproduced in a fresh pipeline (a `--rederive` whose Generate ran into the pipeline `prepare_node` minted, or an IR re-derived to different bytes whose Generate came out the same) carries the same build key as the old pipeline's build — and that build IS selected, but only together with the old pipeline's byte-identical TWINS of the upstream chain (a certified source with the selected source's output hash; for a verdict, a certified binary with the selected binary's), to which the selection re-points, so that the refs a run adopts name one pipeline; a build whose own pipeline no longer holds such twins is not a candidate (`binary_not_found`, and Build re-derives), because adopting it would put a `pipeline_ref` from one pipeline beside a `source_id` that exists only in the other. The inputs each phase hashes are listed at `tools/orchestration_runtime.py` §derivation keys and in 13d; because the compile key hashes the registry-derived closure signature and every closure member's selected IR output hash, the generate and build keys the members' selected source output hashes, and every key the transformation version, this ONE comparison carries what the two it replaced compared beside the status — the recorded dependency resolution (the former 13a, "R6-lite": the `dependency_graph.json` sidecar's node set against the registry, version granularity) and the staged closure sources (the former 13b, "R6 proper": `binary_meta.dependency_check.closure_bindings[].model_source_sha256` against the staged selection, content granularity) — and what neither could see: the spec text under an unchanged `spec_version`, the IR content, the target profile and toolchain, the compiler version, the prompt contract. The comparison is over content, not identity: a dependency re-derived to byte-identical output (the output hash is stage-relative) invalidates nobody, and a `--rederive` whose attempt reproduces the phase's output leaves every downstream phase certified. A refusal names the first clause that failed: `<step>_not_found` (no output was ever produced), `derivation_key_missing` (an output stamped before PR-1 of the issue — the legacy corpus, which re-derives once; no backfill is written, by decision), `derivation_key_mismatch:<first differing input>` (the stamped `derivation_inputs` diffed against the recomputation, e.g. `spec.controlled_spec`, `closure[0].source`, `dependency_graph`, `transformation`), `derivation_inputs_unresolvable: …` (the key cannot be computed — a dependency with no certified output, a closure that does not build, a spec file that cannot be read), or the stage meta's own reason (`revoked`, `verification_status_not_pass`, `artifact_hash_mismatch:<ref>`) when an output of the matching key is not eligible. A revocation SHADOWS every older eligible output of the same key: `revoke-artifact` is a decision that the derivation must run again, taken on findings no input carries, and an older output produced under the same inputs is not an answer to it — so after a `--rederive` has left two eligible outputs, revoking the newer one refuses the phase (`revoked`, with the repair seed) rather than falling through to the older one; a newer FAILED attempt shadows nothing — at the node's own phases and at a dependency's readiness alike, a failed attempt is a record and the standing output stays selected and ready (this REVERSES the pre-key rule that the latest directory's status decided, under which a newer failing attempt un-readied a dependency; a revocation is the decision that un-readies it) — and the re-derivation the revocation asked for is selected once it passes. Two scope lines of this rule, both measured (security round 1 of PR-2): (i) a consumer binds a dependency's OUTPUT, so revoking a dependency's Build or Validate — a decision about that dependency's verdict, carried by no output — moves no consumer key: a consumer whose four phases are certified skips them on a cold single-node run without asking readiness, while `--with-deps` and any phase that RUNS meet the readiness refusal (`revoked`); re-derive the dependency (`run_workflow.py <dependency>`), and its new output, if different, moves every consumer. (ii) Shadowing orders outputs by canonical id, pipeline first, not by production time: a revoked output in a NEWER pipeline shadows an eligible output produced LATER in an OLDER pipeline (two populated pipelines of one node arise when a `--rederive` Generate ran into the pipeline `prepare_node` minted under `--rederive compile`, or when an IR re-derived to different bytes produced the same source); the phase answers `revoked` until a cold run mints into the newer pipeline. Accepted as a residual: rare, an over-refusal rather than a false certification, and self-healing. Readiness asks the same question of a dependency's chain (`_verify_dep_stage_detail`: `ir_ref` — its Compile has an eligible output; `pipeline_ref` — its Build has; `aggregate_verdict` — its Validate has), through ONE `DerivationResolver` per evaluation, which memoises every selection it makes (a closure member reached through two dependencies is selected once). A dependency whose IR was re-derived under an unchanged `spec_version` therefore re-derives its consumers' Compile; a publish of a new catalog version re-resolves the closure; a `profile` bump moves the adopter's compile key through the closure signature and `profiles[]` — the mechanism behind "when a dependency `spec` is updated, its dependents are regenerated" (`run_workflow.py --with-deps` re-certifies the closure bottom-up; on a single-node run the launch check names the node, the stage and the input that moved and points at `--with-deps`). The id chain that used to bind a phase to the one above it (`source_ir_id`, `source_source_id`, `trial_meta.source_binary_id`) and the "latest artifact under the root" selection are RECORDS now, read by nothing that certifies; `ir_not_latest` and `pipeline_not_latest` are gone with them, and a cold run adopts the SELECTED IR and pipeline (`prepare_node`) while a skipped phase adopts the selected ids and re-reserves the roots (`_adopt_certified_refs`). The `spec`/IR and target-profile halves of R6 land with this rule (`docs/design/workflow_scaling_redesign.md` R6).

13b. *(replaced by 13a in PR-2 of [issue #250](https://github.com/seiya/atmofab/issues/250); the number is kept so 13c / 13d keep their names.)* The closure-binding comparison lived here: `binary_meta.dependency_check.closure_bindings[]` re-resolved through the staging selection and compared by `sha256`. The build key's `closure[].source` is that comparison; `closure_bindings` is still WRITTEN by Build as the durable record of what it linked, and read by nothing that certifies.
13c. **Validator-rule freshness of the node's own IR (issue #238).** The compile clause of `check-phase-certified` (`orchestration_runtime._ir_certification`) certifies an IR only while the CURRENT `validate_pipeline_semantics --stage compile` accepts it — the same function `Compile.static` runs at the gate, called in-process after the selection under the key (13a), so that a rule added to the validator after the IR was certified refuses the skip (`ir_rejected_by_current_validator:<n>:<first finding>`) and `Compile` re-derives it, on a resume and on a cold run alike (the adoption path `_certified_ir_candidate` asks the same clause, so a cold run mints a fresh `ir_id` instead of adopting a stale one; the re-derived IR carries the SAME key, and the selection policy then prefers the newer attempt). A validator exception is a refusal too (`ir_validator_raised:<type>`), never a raise. `Generate.gate` keeps the terminal rc 4 as the backstop for a rule change landing between the skip decision and the gate of one run. This is NOT the `spec`/IR half of R6: it compares the certified IR against today's RULES, not against a hash of today's inputs — the key does that, and the two are complementary (a rule change moves no input; a `spec` edit moves the key whether or not any rule reads it). **A DEPENDENCY's IR is not covered.** Rule 11's `ir_ref` readiness (`_verify_dep_stage_detail`, the key lookup alone) runs no validator, and the `--with-deps` closure driver (`run_workflow._dependency_node_readiness`) skips a ready member without launching a conductor, so this clause never runs on it: a dependency whose certified IR the current validator rejects stays `ready`. That is a deliberate scope line for issue #238 (nothing a consumer reads from a dependency's IR depends on an io_contract rule), recorded here so no remedy sends an operator to `--with-deps` for it.
13d. **What each phase's derivation key hashes ([issue #250](https://github.com/seiya/atmofab/issues/250), Z5).** At the start of every phase attempt the conductor computes the phase's `derivation key`: a content hash over the phase's contract inputs as they are at that moment — the spec files, the adopted profiles, the derived closure signature, the closure members' selected IR output hashes, the resolved published-operation surface of the component direct dependencies and the admissible-toolchain document for Compile; the selected IR's output hash, the spec, the harness manifest and the closure's selected IR + source output hashes for Generate; the selected source's output hash, the staged closure sources and the toolchain identity (compiler `--version` included) for Build; the selected binary's and IR's output hashes, the tests and the execution policy for Validate — plus the transformation version (`PURE_PROMPT_CONTRACT_VERSION`, the compile-inlined-documents version, and the deterministic stages' versions, `tools/derivation.py`). The key is stamped on every launch row of the attempt (`agent_runs.jsonl#derivation_key`), on its terminal `step_result.json#derivation`, and — on a pass — into the certifying stage meta beside `artifact_hashes` and `output_hash` (rule 41), which is what 13a reads back. A dependency's output binds by the `output_hash` of its SELECTED certified output and by nothing else: a dependency with no eligible output under its own key makes the consumer's key unresolvable (a transport `fail_closed`, `derivation_inputs_unresolvable`, when the conductor meets it at phase start; a readiness refusal when the driver or the launch gate meets it), never a labelled stand-in — the `unstamped:` / `unverified:` / `uncertified:<stage_id>` bindings of PR-1 are gone with the decision they deferred. The model and the execution environment are recorded per attempt and stay out of the key by decision (the plan on the issue, §2). The closure sources Build and the `Generate.gate` syntax probe STAGE are the ones the key bound: their bindings are resolved at phase start by the resolver that computed the key (`Conductor._phase_derivation` → `_bind_closure_sources`), and `_stage_dependency_sources` copies from those bindings alone, re-hashing each copy (PR-3) — a member re-certified between the key and the copy changes what a later key will bind, never what this attempt compiles.
14. The conductor makes explicit the `execution input`, `verification input`, and `expected output` of the target `step`.
15. For a phase that has `substep`, the conductor launches each `substep agent` sequentially.
16. The `substep agent` generates its own artifact and the corresponding phase's metadata, and returns `agent_output_ref` to the conductor.
17. The conductor evaluates the child `agent`'s returned result, and finalizes `issue_severity` and whether re-submission is needed.
18. When re-submission is needed and `repair_strategy=reuse`, the conductor may permit continuation repair of the same `agent_session_id`. It issues a new `agent_run_id` and adds a `record-launch` record with `relation_type` of `reuse`.
19. When re-submission is needed and `repair_strategy=restart`, the conductor relaunches a `substep agent` with a new `agent_session_id` and adds a `record-launch` record with `relation_type` of `restart`.
20. For a phase that has `substep`, the conductor verifies the required artifacts of all `substep`, and outputs `step_result.json` to `workspace/orchestrations/<orchestration_id>/steps/<node_key_safe>/<step>/<agent_run_id>/step_result.json`. This `agent_run_id` is the `orchestration agent_run_id` (for the no-substep `Build` phase it is the `step agent_run_id`). `write-step-result` enforces this fail-fast: a wrong-role `--agent-run-id` whose role is resolvable in `agent_runs.jsonl` is rejected at write time (before the file is written and before the phase transitions, so the step stays `child_finished` for retry), rather than only at the Validate `pre_judge` gate. The `substep_agent_run_ids` of `step_result.json` enumerates, without omission, the `agent_run_id` of **all** `substep` launched in that `step` and recorded in `agent_runs.jsonl`.
21. `step_result.json` holds a `retry_decisions` array when re-submission was performed, and records `issue_severity`, `repair_strategy`, `repair_target_agent_run_id`, `new_agent_run_id`, and `repair_reason` in each element. In the `retry_decisions` recorded in a `write-step-result` with `status=pass`, each `new_agent_run_id` is limited to a `pass` run finally adopted into the `effective pass substep` set.
22. A re-submission triggered by a `noncanonical_phase_write_attempt` requires `repair_strategy=restart`.
23. The `status=pass` judgment in the `step_result.json` of a phase that has `substep` is made over the `effective pass substep` set.
24. In a `step_result` with `status=pass`, each run included in the `effective pass substep` set must have terminated with `pass`.
25. The `required_outputs` coverage judgment in a `step_result` with `status=pass` is made over only the `output_refs` of the `effective pass substep` set.
26. The `step agent` verifies its own artifact in a phase that has no standard `substep` (`Build`), and outputs `step_result.json`.
27. The conductor receives `step_result.json` and judges the launchability of the next `step`.
28. `node` execution proceeds sequentially in the dependency order reconstructed from `deps.yaml`, `spec_catalog.yaml`, and `spec.ir.yaml.dependency`. It does not perform parallel execution unless explicitly instructed. When the closure spans multiple `node` (only under `tools/run_workflow.py --with-deps`), the nodes are run bottom-up (dependencies before dependents), one orchestration per node, also sequentially; on the first dependency-node failure the run stops before the dependent/target node. **The explicit instruction is `--jobs N` with N > 1** ([issue #250](https://github.com/seiya/atmofab/issues/250) Z5 PR-3; `docs/workflow/WORKFLOW_CORE.md` rule 36): the driver becomes a ready-set scheduler over the closure — a member whose direct dependencies (the edges `_resolve_dependency_closure` records as `direct_deps`) have all finished ready is launchable, up to N run at once, each as a child `tools/run_workflow.py … --closure-member <closure_id>` process with its own orchestration, and the target runs in the driver's process after every member. Read for a parallel closure, "stops on the first failure" means: no further member is launched, the members already running are waited for (an orchestration is never killed mid-run; their records land in `dependency_runs`), and the closure stops with `dependency_node_failed` naming the FIRST failure; the target is not launched. An interrupted driver (Ctrl-C, SIGTERM) sends its running members SIGTERM and waits for them — each terminalizes its own orchestration, resumable — before propagating the interrupt; the members run in their own session so the terminal's signal reaches only the driver. A member takes its start claim WAITING rather than refusing (`start_claim_waiting`), and once it holds the claim asks its readiness again: a member another closure certified meanwhile skips (`closure_member_skipped`, exit 0) — the duplicate-work suppression the concurrency needs — so two closures that share a dependency derive it once and both record having stood on it. The driver asks readiness before launching (a ready member is skipped without a child) and re-verifies after the child exits, exactly as the sequential loop does. `concurrent_orchestration_running` stays the answer of the sequential paths (a cold single-node run, `--jobs 1`), where no explicit parallel instruction was given.
29. When a `step agent` or `substep agent` is `fail` / `timeout` / `cancel`, the relevant `step` of the relevant `node` is `fail`, and downstream `step` launch is forbidden.
30. The conductor appends each `agent` execution event to `workspace/orchestrations/<orchestration_id>/agent_runs.jsonl`.
31. The conductor saves the parent-child relationship in `workspace/orchestrations/<orchestration_id>/agent_graph.json`, and requires recording `parent_agent_run_id`, `child_agent_run_id`, and `relation_type`.
32. All `agent` of the core workflow must not write outside of `workspace/`.
33. When the actual processing of a `step` / `substep` is proxied by a script during workflow execution, it is a `fail`, and the relevant trial is discarded.
34. On re-submission, issue a new `agent_run_id`, and do not overwrite existing `launch` evidence or `agent_runs` rows.
35. `status` and `can_launch_*` must not be changed by manual editing or post-editing of `preflight.json`.
36. When the live probe just before launching a child `agent` is `fail`, `record-launch` must not be run.
37. The live probe that `record-launch` runs is skipped when a probe that succeeded within the TTL set by `ATMOFAB_PREFLIGHT_TTL_SECONDS` (default 30 minutes) exists. It is disabled when `ATMOFAB_ORCHESTRATION_ENFORCE_LIVE_PREFLIGHT=1` is explicitly set.
38. *(retired in Z4, [issue #171](https://github.com/seiya/atmofab/issues/171); the number is kept so the items after it keep their names.)* A native hook's execution result was appended to `workspace/orchestrations/<orchestration_id>/hooks/native_hook_events.jsonl`, and a hook that could not name its orchestration was refused by the leaf entrypoint and recorded under the `_global/` sink. A `pure-function leaf` issues no tool call, so no hook fires on its behalf and the leaf entrypoint is deleted. The `_global/` sink is still EXCLUDED from the orchestration sweep, for the runs that already hold one.
39. *(retired with §38; the manifest half went in PR-2 of the same issue.)* `tools/hooks/cli.py` was the LEAF hook entrypoint and failed closed when the payload could not resolve an `orchestration_id`. Nothing replaces it: the guards it keyed on that id — the write manifest, the read manifest, the protected-root resolver — all guarded a leaf's tool call, a pure leaf makes none, and the two manifests themselves are no longer written.
40. When about to deviate into a contract-violating shortcut in a child-`agent`-required phase, the conductor makes explicit that the relevant phase requires a child-`agent` launch, and returns to the legitimate launch procedure.
41. On `write-step-result` with `status=pass`, the runtime stamps the phase's certification into its stage meta before writing the result: `artifact_hashes` (the sha256 of each `required_outputs` entry except the meta itself and the audit-log basenames), `output_hash` and the derivation record (`derivation_key` / `derivation_inputs` / `derivation_transformation`, [issue #250](https://github.com/seiya/atmofab/issues/250)) and, for `generate` and `build`, `source_ir_id` from the `compile` reservation. Every phase certifies a meta — Validate's is `validate_meta.json` since issue #250. Failure to stamp is fail-closed, a pass without a derivation record included. A NON-pass write strips every stamp key instead — between the two, the keys exist only where a passing `write-step-result` put them. Canonical: `docs/CLI_REFERENCE.md#write-step-result`.
42. Before launching each `step`, on EVERY run — cold or resumed — the conductor runs `check-phase-certified` and skips the `step` only when it answers `certified=true`. The answer is a property of the ARTIFACTS (`docs/GLOSSARY.md` `certified (phase)`), not of a ledger entry recording that a run completed, so the same call decides both cases and a cold re-run over an already certified node skips every phase.
43. A skipped `step` is recorded in `phase_state.json` as `skipped_certified` (event `skip_certified`, carrying the adopted artifact as its `reason`). It launches no agent, so it appends no `agent_runs.jsonl` row and writes no `step_result.json`; the validator's `pre_judge` step-result census reads that state and demands none for it (issue #250 PR-2 — measured on a `--rederive build` run, whose Compile and Generate stood certified while Validate ran), as the completion vouch (49) already did.
44. A `step` must not be skipped by trusting a ledger of what ran. Issue #177 deleted `orchestration_checkpoint.json` and `check-step-completed` with it: a ledger records that a run completed, cannot see an edit made to the artifact afterwards, and is absent entirely on a cold run over a node another run certified.
45. When the `status` of `write-step-result` is terminal (`pass` / `fail` / `blocked` / `timeout` / `cancel`), `validation_stage` is required in the `step_result.json` of `Compile` / `Generate` / `Build` / `Validate`. The allowed values are `Compile: compile|full`, `Generate: post_generate|full`, `Build: post_build|full`, `Validate: post_execute|pre_judge|full` (runtime canonical: `STEP_REQUIRED_VALIDATION_STAGES` of `tools/orchestration_runtime.py`). The runtime rejects with `ValueError` for anything other than the per-step allowed values, or on omission.
46. *(retired in Z4, [issue #171](https://github.com/seiya/atmofab/issues/171); the number is kept so the items after it keep their names.)* `codex_feature_check.json` was authored host-side by the conductor, certifying the `hooks` feature of the exact executable the leaf would run, and the conductor failed CLOSED before launching a codex leaf whose hooks would not fire (`ATMOFAB_REQUIRE_CODEX_HOOKS_FEATURE`). Both the certificate and the requirement went with the leaf hook layer: a `pure-function leaf` makes no tool call, so no hook fires on its behalf and there is nothing to certify. The file, the env var and `_ensure_codex_feature_cache` no longer exist.
47. `workspace/tmp/<agent_run_id>/` is the scratch root of one agent run. NO LEAF writes there since Z4 ([issue #171](https://github.com/seiya/atmofab/issues/171)) — a pure leaf writes no file at all and its sandbox does not bind the root writable; what uses it is the conductor's own deterministic substeps (`OBJDIR` for the build, `RUNDIR` for the run and quality-check trees). `record-agent-run` auto-deletes it after recording that `agent_run`. `tools/run_workflow.py` still sets `TMPDIR` to `workspace/tmp/<orchestration_agent_run_id>/` after `init` succeeds, as insurance for subprocess inheritance. Canonical: `docs/WORKSPACE_LAYOUT.md` §tmp / TMPDIR.
48. Because `Build` is a step-only phase (one child == one `step_result.json`), the conductor writes the `step agent`'s `step_result.json` — including a **`fail` / `timeout` / `cancel`** outcome — before launching the next `Build` child. This is no longer ENFORCED at `record-launch`: the guard that refused a relaunch while a prior terminal build agent lacked a step_result existed for the completion vouch's per-arid rule, which item 49 replaced, and with that rule gone it refused a relaunch for a condition that blocks nothing.
49. The pass-completion vouch reads the ARTIFACTS and the LATEST attempt, not an arid census. It requires: an orchestration row; every `step` / `substep` run terminal with resolvable launch refs; (an outstanding `violations/<agent_run_id>.unauthorized_write_violation.json` was a fourth requirement until PR-2 of [issue #171](https://github.com/seiya/atmofab/issues/171); the terminal write audit that wrote that marker is deleted with the write baseline it diffed against, and a leaf reaches the filesystem only through a read-only `bwrap` profile, so the class it refused cannot occur from a child window); every `agent_graph.json` edge's parent and child recorded in `agent_runs.jsonl` or `agent_runs_invalid.jsonl` (a child in NEITHER is a corrupt edge; the invalid log is tolerated here because `record-agent-run` diverts on every terminal-payload rejection, most of which leave no bytes behind); at least one node reservation, with every reserved node `certified` through `orchestration_meta.invocation.until_phase_high_water` — the furthest end-phase this orchestration has ever been driven to, which only ever rises. The CURRENT `until_phase` may be lowered (a `--with-deps` closure legitimately drives a dependency to an earlier end-phase than a previous run did); what cannot be lowered is what must have been certified, because that is the vouch's own bar being moved by the thing it judges — a run started for `validate`, re-recorded as `compile`, would otherwise report `pass` with three phases never run. The high water is DERIVED from the record, never accepted from a caller's `--invocation-json`; an `edges` list, non-empty whenever any step/substep run is recorded; and, for each `(node, phase)` this orchestration wrote a step_result for, that the LATEST attempt — ordered by the executor's position in `agent_runs.jsonl`, never mtime — passed with its `required_outputs` on disk. A phase recorded `skipped_certified` is exempt from that last clause: it did not run here. What an attempt that ended WITHOUT a step_result gets a leaf: nothing — it certifies nothing, and the latest attempt is not something a leaf can make itself be.
50. Re-derivation of an already-certified phase: when the decision table (`docs/workflow/phases/phase_04_validate.md`, `docs/workflow/phases/phase_02_generate.md`) routes a failure back to a phase that is `certified`, the conductor runs `revoke-artifact --step <phase> --node-key <node_key> --trigger-agent-run-id <failed_arid> --reason <reason_code>` and then `reset-phase --from-phase <phase>`. The REVOCATION is the load-bearing half: it rewrites that phase's stage meta to `verification_status: revoked` with the finding as `last_fail_reason`, which is what `check-phase-certified` reads — so the decision reaches every later run, a cold one included. The reset is the record. Downstream phases need neither: each binds, in its derivation key, to the output hash of the phase above it, so a re-derived upstream that changes the output moves every downstream key (rule 13a). In `dev` a cross-phase rollback still fail_closes on the first occurrence (F1), but it revokes BEFORE terminalizing, so the operator's `--resume` re-derives with the finding rather than re-running the identical artifact. Canonical: `docs/CLI_REFERENCE_RARE.md#revoke-artifact`, `docs/RUNBOOK.md` §3-1.

## Decision Criteria
- Per workflow, an `orchestration_id` is issued and `orchestration_meta.json` exists.
- Each `step` or each `substep` has an independent `agent_run_id`.
- The `context_id` of `step` and `substep` do not duplicate, and `context_isolated=true` is recorded for all.
- The `agent_runs.jsonl` of `step` and `substep` records `agent_session_id` and the various references, and the referenced entities exist.
- `launches/<agent_run_id>.response.json` and `agents/<agent_run_id>/dialogs/child.response.json` hold the same content of the leaf launch response.
- `agent_runs.jsonl.agent_session_id` matches the child-`agent` identifier of the corresponding `launch response`.
- `preflight.json` exists and satisfies `can_launch_step_agents=true` and `can_launch_substep_agents=true`.
- `sandbox_runtime=bwrap` and `sandbox_enforced=true` are recorded in the preflight.
- From the execution record of each phase, it can be traced that `Compile` / `Generate` / `Validate` used a `substep agent` and `Build` used a `step agent`.
- The parent-child relationship `orchestration -> step` or `orchestration -> substep` can be traced in `agent_graph.json` for every edge the run recorded. An orchestration with NO edge is accepted since issue #177 — a re-run over a node whose every `phase` is already `certified` launches nothing. What carries the edgeless case is the ARTIFACTS: the orchestration must have reserved at least one node (`reservations/<node_key_safe>/compile.json`, which `prepare_node` writes before the first phase runs, skipped or not), and each reserved node must be `certified` through `orchestration_meta.invocation.until_phase`. A reservation proves preparation, not completion, so it is not sufficient on its own.
- The `executor_agent_run_id` of `step_result.json` matches the relevant directory name, and `substep_agent_run_ids` is consistent with the parent-child relationship. For a phase with no standard `substep` (`Build`), `substep_agent_run_ids=[]` is allowed.
- For each `(node, phase)` this orchestration wrote a `step_result.json` for, the LATEST attempt passed and its `required_outputs` are on disk — "latest" by the executor's position in `agent_runs.jsonl`, never mtime, which a copy or a restore forges. An executor with no recorded run cannot be ordered and is refused. A phase recorded `skipped_certified` is exempt: it did not run here, so an earlier attempt's `fail` is not this run's account of it. What is NOT required, since issue #177, is that every terminal `agent_run_id` be vouched by a `step_result.json` — that rule is what made 17 tombstone call sites necessary, and an attempt that ended without a step_result is simply a failed attempt.
- The `required_outputs` of `step_result.json` match the phase contract of `docs/workflow/WORKFLOW_CORE.md` and the corresponding `docs/workflow/phases/phase_*.md`.
- When `step_result.json` holds `retry_decisions`, the `effective pass substep` set can be uniquely restored.
- For `Compile` / `Generate` / `Build` / `Validate` where `step_result.json` has a terminal status, `validation_stage` matches the per-phase allowed values (item 45).

## Capability / Manifest contract (removed in issue #171 PR-2)

`record-launch` issued three documents per child — `capabilities/<arid>.json`, `output_manifests/<arid>.json` and `read_manifests/<arid>.json` — and this section stated their required fields. Each answered a question about what a LEAF was allowed to do: which roots it might read, which paths it might write, which MCP tools it might call, and the secret it would present to prove all three. **None of them is written any more.**

They were enforced by the in-sandbox leaf hook, which Z4 deleted with the leaf that held tools; for one PR after that they were records checked only against themselves. The two launch shapes that remain are a PURE leaf — no tools, no MCP configuration, a read-only `bwrap` profile and `write_roots: []` by construction — and a DETERMINISTIC substep, which is the conductor's own process and is bound by nothing it writes about itself.

What survives, and where it is stated: the read-only sandbox profile (§phase artifact authorship, and the `--stage pre_judge` audit that re-checks `readonly` / `write_roots == []` on a persisted record); the launch request's `allowed_output_paths` as a CONTRACT (same section); and the pure leaf's `output_refs == []` (§pure-function leaf).

**The read boundary, closed for both backends.** A **claude** pure leaf launches with `--tools ""`: it can make no read at all, and the boundary is structural. A **codex** pure leaf is `codex exec --sandbox read-only`, which is tool-BEARING; its writes are closed by the read-only profile, and since [issue #227](https://github.com/seiya/atmofab/issues/227) its reads are closed by the mount set: **the checkout is not bound at all**. `render_bwrap_command` puts an empty tmpfs at `repo_root` (the path is kept — the cwd and the private `CODEX_HOME`'s `[projects."<repo>"]` trust key are unchanged), and what the sandbox holds is the system directories, the backend CLI's install root (issue #226), the backend's credential home outside the checkout, and the leaf's own two scratch roots (rw): `workspace/tmp/<arid>` and the profile's `tmp_dir`, `sandboxes/<arid>/tmp` under the orchestration. Neither the artifact trees (`workspace/`, the `workspace_*/` archives, `releases/`) nor the source trees (`tools/`, `docs/`, `spec/`, `.git/`) are in the sandbox; `build_readonly_bwrap_profile`'s docstring is canonical for the bound set. The history: the implementation plan (issue #171's 2026-09-12 comment, §6.6) had accepted the read boundary as out of scope on the ground that the gate RULES are already quoted verbatim into the prompt; PR-1's review REVERSED that, and `docs/design/z4_enforcement_retirement.md` §Decisions item 4 records the reversal — the prompt gives the leaf the rules, the checkout gives it the CHECKER, and a leaf that can read the gate's implementation can satisfy a presence floor's exact signal without doing the work the floor stands for. PR-1 hid the artifact trees with per-tree overlays over a whole-checkout ro-bind and left the source trees readable; issue #227 replaced the overlays with the one tmpfs. One consequence for the codex launch: the sandbox cwd is an empty non-git directory, which `codex exec` refuses before any API call unless `--skip-git-repo-check` is passed (measured on codex-cli 0.154.0: `Not inside a trusted directory and --skip-git-repo-check was not specified.`, rc 1), so `leaf_command` passes it on both `exec` and `exec resume`, `CODEX_EXEC_RESUME_REQUIRED_FLAGS` and the `codex_exec_pure_isolation_flags` preflight check certify it, and the claude launch — which takes the same profile — needs nothing. **The codex home is per THREAD LINEAGE, not per orchestration** ([issue #245](https://github.com/seiya/atmofab/issues/245), closing what issue #227's round-1 security review found and measured under real `bwrap` with the real CLI): codex-cli 0.154.0 writes each launch's whole rollout — the prompt and every response item — under `$CODEX_HOME/sessions/` and into the sqlite state at the home's root (`state_*.sqlite-wal`, `thread_history_*.sqlite-wal`; measured, the marker prompt in all three), so while one home served every codex leaf of an orchestration, a later leaf (the VERIFY leaf, for the producer it reviews; a repair turn, for the previous verdict) could read it through its own shell tool, inside this profile and inside codex's own read-only sandbox alike — the `dialogs/` gain under a second name. The home has to stay writable and shared across the attempts of one THREAD (warm `exec resume` reads the resumed thread's rollout from `sessions/`; measured, a resume from any other home fails before its first request), so `orchestration_meta.json#codex_workflow_home` is now a CONTAINER, `~/.atmofab/homes/<oid>/codex/`, bound into nothing, and the `CODEX_HOME` a leaf is bound rw is the lineage home `<container>/<codex_lineage_id>/` beneath it — created exclusively by the cold launch whose `agent_run_id` names it, reused by every warm resume of that thread (the id rides the thread's `session_run_index.json` row and `record-launch --codex-lineage-id`), and simply not mounted for any other thread's leaf. `_prepare_codex_workflow_home` is canonical for the two levels; `docs/RUNBOOK.md` §"The operator-private root" for the layout an operator sees. Pinned under real `bwrap` by `tools/tests/test_bwrap_simulation.py`: `test_a_second_codex_leaf_cannot_read_the_first_leafs_rollout_anywhere_under_its_home` (the whole container is walked on the host — everything the CLI wrote, and every file holding the marker, lies under the launching lineage; a sibling lineage's probe finds no marker under its own home and gets ENOENT on the first leaf's rollout), `test_a_warm_exec_resume_reaches_the_api_from_its_own_lineage_home` (the second attempt of a thread, prepared against the first attempt's lineage, reaches the API; the same resume from another lineage's home does not), `test_readonly_profile_hides_workspace_from_the_leaf` (each artifact tree and each source tree HIDDEN, `workspace/tmp/<arid>` writable as the control), `test_readonly_profile_hides_the_checkout_and_keeps_own_tmp_writable` (the cwd's whole listing is the one mountpoint), and the two unbilled loopback rows `test_codex_pure_launch_reaches_the_api_from_the_empty_cwd` / `test_claude_pure_launch_reaches_the_api_from_the_empty_cwd` (the real CLI, with the production argv, reaches its first API request from the empty cwd; the codex row's control shows the flag is what gets it there).
