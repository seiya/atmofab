# Requirements and format of tests (canonical source)

## Purpose
`tests.md` is the canonical source for the verification input and judgment conditions of a `spec`. It is commonly used for the `spec_kind` `problem` / `component` / `infrastructure`. A `profile` has none: it is a compile-time selection policy the host resolves, nothing is generated or executed for it, and there is therefore nothing for a test to be about (`docs/SPEC.md` requirement 5, issue #175).
The evaluation result of `tests.md` is mapped to the relevant `node`'s `self_verdict` in `verdict.json`, and the aggregated judgment including dependencies is handled in `aggregate_verdict.json`.

## Scope
- `spec/problem/<domain>/<family>/<spec_id>/tests.md`
- `spec/component/<domain>/<family>/<spec_id>/tests.md`
- `spec/infrastructure/<domain>/<family>/<spec_id>/tests.md`

## Requirements
1. The canonical source format is `Markdown`.
2. State `test_profile_id`, `test_profile_version`, `status`, and `spec_ref` at the top of the document as required. The two `test_profile_*` values are `provenance input`s (`docs/GLOSSARY.md`): a `tests.md` sentence asking that they be recorded in `trial_meta.json` is met by the host at `Validate.execute`, not by generated code.
3. `spec_ref` requires `spec_kind`, `spec_id`, `spec_version`, and `controlled_spec_path`.
4. Each `spec` defines at least 1 `L0` test.
5. Define `L1` / `L2` / `L3` according to the verification purpose. They are not forbidden by `spec_kind`.
6. No fixed lower bound on the number of tests is set. Sufficiency is judged by the requirement-coverage rule.
7. Treat an undefined item as an error without completion.
8. The judgment condition must be evaluable per `node_key`. It must not implicitly reference the state of a dependency `node`.
9. A judged quantity is defined in §5 as an expression over the captured state, the captured time and the case inputs, and that expression reads captured state: a test is judged by the host's predicates over the captures alone ([issue #582](https://github.com/seiya/atmofab/issues/582)). A quantity the inputs alone fix is refused, because nothing of the run enters it; the time variable and the step count do not count as a read (`docs/workflow/phases/phase_01_compile.md`, the `predicates` rule of the schema block), except in gate (l)'s zero-step closure, which that rule exempts under the quantity `run.n_step` only; nor does a logical `out` state (a flag the operation returns, a `drive` entry's `result:` or not), except in its flag predicate, which that rule exempts under the flag's own name only (review round 5 of [issue #589](https://github.com/seiya/atmofab/issues/589), R5-2). So a `pass` test of a `problem` or `component` node without a time loop lists the result's name in its `quantities` line (the Compile gate requires the flag there; a harness has no `drive`, and its line is not asked), any test judges any flag under that flag's name, a flag values a test's cases only on an `xfail` test and with `value: 0`, the refusal (another read values each case of a `pass` test), and a flag under any other quantity reads nothing. A quantity that no captured state variable enters — the definition fixes it from the case inputs, the constants and the time alone (a CFL number over a prescribed speed, a step count the inputs fix; a variable that only echoes a value the inputs fix, such as a time step, is not captured state here) — therefore carries, in §5, its **primary-evidence statement** ([issue #340](https://github.com/seiya/atmofab/issues/340)): the expression the host evaluates over the captured state and the declared inputs for that judgment, and the state fact it rests on (a bound an invariant of the `Controlled Spec` gives). For each `xfail` test that judges the quantity, the statement says whether the guard leaves a state fact at all. A quantity that a captured state variable enters needs none, however much of it the inputs fix (a CFL number over a wave speed the state carries): its definition is its statement. Neither does the `xfail_condition` of a guard test over the inputs (`nx < 2`, `dt <= 0`): what that test judges is the kernel's refusal, stated by the predicates in the failure direction, not a quantity. Nor does `run.n_step`, the driver's committed step count against the count the loop runs by: its entry is that closure, and the step count it reads needs no state term. Nor does a flag's name: its entry is that flag predicate. A run-wide quantity (an extremum over the integration path, a stability index over the committed states) is defined over the host's `series` and `history` captures of a time-marching node (`docs/workflow/phases/phase_01_compile.md`, grammar 6), never as a value the operation returns ([issue #589](https://github.com/seiya/atmofab/issues/589)); a reference field the judgment compares against is a closed form in §5 the host evaluates, never a value generated code computes. Without the statement, the Compile contract has no faithful expression to transcribe and `Compile` fails (the same rule of the schema block, and V3). The two Compile leaves apply the statement's rule; no deterministic gate does, so a certified IR is not evidence that its spec carried a statement.

## Coverage rules per `spec_kind`
- `problem`
  - Define execution control, case expansion, judgment expressions, and pass/fail aggregation rules.
  - When there is a non-applicable item in the validity judgment, define `N/A` and the reason.

- `component`
  - For each published `operation`, define at least one normal case and one guard case (`fail` or `xfail`) each.
  - Add `L1`-and-above accuracy / conservation / equivalence tests as needed.

- `infrastructure` (R1 harness)
  - For each published harness operation, define at least one normal case and one guard case (`fail` / `xfail`) each — e.g. numeric round-trip (negative / min / max), boolean-literal emission, case fan-out → per-case snapshot naming, and a missing-`--cases` guard (`xfail`).
  - The harness's own runner (a self-test driver) exercises these; the existing `post_execute` gate group provides additional oracles.

## Description format
0. Meta information
1. Test purpose
2. Input-defaulting rules
3. Execution-control rules
4. Case-expansion rules
5. Judged quantities
6. Test definitions
7. Pass/fail aggregation rules
8. Traceability

When there is an unnecessary section depending on the `spec_kind`, state `N/A` and the reason rather than omitting it.

Each test definition in §6 carries exactly one `quantities` line, opening with the key and listing the judgments the test makes by name, and nothing else on the line: `` - `quantities`: `cfl_max`, `mass_drift` `` or `quantities: cfl_max, mass_drift`. The Compile leaf copies it into `io_contract.tests[].quantities`, and the Compile gate refuses a definition with no such line, with two, or with an entry that is not a name (`[a-z][a-z0-9_.]*`), and an IR whose `quantities`, or whose predicates' `quantity` set, differs from the line (a cross-target judgment is outside it, below). No gate reads the line against the prose: `Compile.verify` V3 (i) and `skills/spec-input-check` do. A threshold stays in the definition's prose, which no gate parses.

Each test definition in §6 also carries exactly one `expected_outcome` line, `` - `expected_outcome`: `pass` `` or `` `xfail` ``. The Compile gate refuses a definition with no such line, with two, or with another value, and an IR whose `io_contract.tests[].expected_outcome` differs from it: the outcome decides what the gate asks of the test and what its flags value, so it is the definition's and not a label the IR chooses.

A `tests.md` whose node runs a time loop (its IR's `drive.loop`, `docs/workflow/phases/phase_01_compile.md`) carries ONE `history` line, in §3, naming the input that sets how many committed steps lie between two state samples and its value: `history: every = <N> (<input name>)`, or, when the value differs per case, `history: every = (<input name>) <case_id> = <M>, ...` listing every case. The value is a number, an integer of at least `0`; `0` takes no sample. The Compile gate refuses a time-marching node's IR whose `drive.history.every` names another input, or whose case input differs from the line's number, and refuses a `history` line on a node without a time loop. A judgment over a committed state between two samples is exposed to the stride, so a suite whose judgment needs every step sampled sets `every = 1`. Every `pass` test of such a node also lists `run.n_step` in its `quantities` line: the Compile gate requires its zero-step closure (the driver's committed step count against the count the loop runs by, `docs/workflow/phases/phase_01_compile.md` gate (l)) under that quantity and no other, because the closure reads no captured state, and the read rule of requirement 9 exempts it under that name only. When `init` plans the loop (`drive.loop.n_step` is a scalar `init` writes) every `pass` test also lists the init result's name: a refused `init` planning no step satisfies the closure, so the Compile gate requires that flag too.

A `reported` line (a test's list of run-wide reductions the operation returned) is refused by the Compile gate: the class it named is retired ([issue #589](https://github.com/seiya/atmofab/issues/589)), and the run-wide quantity is the host's reduction over the `series` and `history` captures (requirement 9).

## Cross-target judgment
A `problem` or `component` node generated for more than one target is also judged variant against variant ([issue #324](https://github.com/seiya/atmofab/issues/324)): in each target case, a state variable this target's run captured after the run is compared with the same variable, in the same case, of every other target's eligible variant of the node (the `comparand`, `docs/GLOSSARY.md`). A test applies it with a judgment that contains the exact words "The cross-target judgment is applied" inside its own definition (a `problem` writes "The cross-target judgment is applied. The evaluation expression is `cross_target_state_agreement` over `<variables>`, and the threshold is $\le v$"; a `component` appends "The cross-target judgment is applied: `cross_target_state_agreement` over `<variables>` is `<= v`" to its `judgment` line), naming each state variable it compares; §5 of the same `tests.md` defines the quantity. The Compile gate keys on those words (`validate_pipeline_semantics.CROSS_TARGET_JUDGMENT_PHRASE`): every test whose definition contains them must carry a cross-target predicate and no other test may. A `pass` test of a `problem` or `component` applies it, whatever the number of declared targets; with no other eligible variant, the variants have nothing to compare and the predicates still compare execution shapes (below). A `pass` test whose target cases define no common variable is split so that each resulting test names a variable every one of its target cases defines. A test whose `expected_outcome` is `xfail` or `fail` does not apply it (below), and may say "The cross-target judgment is not applied"; the gate reads neither the presence nor the absence of that sentence. No gate reads which outcome applies it; the framework's test suite pins that over the `spec` nodes of this repository (`test_cross_target_judged_ids_of_the_real_corpus`), `skills/spec-input-check` checks it on request, and nothing else enforces it for a `spec` outside this repository. The default definition is, for one variable $q$ and one other variant $q^{ref}$,
$$
\mathrm{cross\_target\_state\_agreement}=\frac{\max_i |q_i-q^{ref}_i|}{\max(\max_i|q_i|,\ \max_i|q^{ref}_i|,\ 1)}
$$
over every element $i$ of the variable. The denominator is symmetric in the two variants, so which of them is the comparand does not decide the agreement, and its floor of `1` makes the bound an absolute one for a variable of magnitude below `1`. A `tests.md` states another normaliser in its §5 when a variable's own maximum is not the scale of its rounding — a velocity or momentum component that is a small residue of the flow is normalised by the largest maximum over all the components of that vector in both variants — and keeps it symmetric in the two variants.
- The host evaluates it from the captures, against each other variant separately, and it is not listed in the test's `quantities`: the generated code of one target never sees another target's state.
- It is not part of any run's verdict: the host compares the variants when it asks whether a node is ready or a run may pass (the `cross-target agreement`, `docs/GLOSSARY.md`). With no other eligible variant there is nothing to compare; with one, a disagreement stops every target of the node, because it does not say which of the two is wrong.
- Name only variables whose value after the run the `Controlled Spec` defines in every target case of the test. Do not apply it to an `xfail` or `fail` guard test: the state a refused or unstable case leaves is not a result two variants must agree on.
- The threshold states how far two correct variants may drift apart (a contracted multiply-add, another summation order, a device math library); it is not an accuracy bound.
- The same predicates compare, within one run, the state of every execution shape the binary ran in (another rank count or process grid, another thread count, another thread-block size) with the quality check's one-process, one-thread serial reference (`docs/workflow/phases/phase_04_validate.md` §4-2, [issue #512](https://github.com/seiya/atmofab/issues/512)); so the threshold also bounds how far one correct kernel may drift under another decomposition.
- An `infrastructure` harness node does not carry it: each target has its own harness `spec`.

## Refinement judgment
A `problem` suite that judges the error against a reference under refinement (a `refinement` family of `tests.md` §4, [issue #513](https://github.com/seiya/atmofab/issues/513)) judges it in three norms per judged level, `l1_rel`, `l2_rel` and `linf_rel`, and the order of each norm per pair of adjacent levels, over every state variable the `Controlled Spec` defines after the run: a momentum or velocity component is not left to the depth alone. A family judges at least three levels with a ratio of 2.
- **Normaliser.** A variable whose reference is not identically zero is normalised by the same norm of its reference. A component whose reference is zero, or a small residue of the flow, is normalised by the largest of that norm over the components of the vector it belongs to (for momentum in the `linf` norm, $\max(\max_i|hu^{ref}_i|,\ \max_i|hv^{ref}_i|)$).
- **Reference.** The reference is the analytic or exact solution where the spec gives one. Otherwise it is the `restricted reference`: the finest level of the family restricted to each coarser grid by the conservative block mean over the $f^k$ cells it covers ($f = N/n$ for a level $n$ and the finest level $N$ in $k$ dimensions; the grammar function `coarsen`, `docs/workflow/phases/phase_01_compile.md`), or by the spec's own restriction where it states one. The finest level then judges no error of its own, so the family carries one level more than the levels it judges. Over a topography sampled per grid, the compared depth variable is the free surface.
- **Order against a restricted reference.** An order judged against a restricted reference includes the reference's own error: for a scheme of order $p$, the pair $(n, 2n)$ against the level $N$ reads about
$$
p + \log_2\frac{1-(n/N)^p}{1-(2n/N)^p},
$$
so its bound is the calibrated value, not the asymptotic order.
- **Expected order.** The expected order of each norm comes from the scheme. A norm whose order is lower for a known reason (a limiter at an extremum, an $O(\Delta y)$ term at a wall) states that reason beside its bound.
- **Carrying case.** A judged quantity that reads another case is a predicate scoped `case: <case_id>` at the case that sorts last among the cases it reads, reading the others through `at('<case_id>')` (`docs/workflow/phases/phase_01_compile.md`). Against a `restricted reference` that case is the finest level: it carries the error of every coarser level and every order.
- **Calibration.** Every band and bound is calibrated against an independent reference implementation of the `Controlled Spec` scheme ([issue #265](https://github.com/seiya/atmofab/issues/265)'s procedure). An error is judged by a two-sided band, as two judged quantities (an upper and a lower bound; 5-5 of the `shallow_water2d` and `shallow_water2d_channel` `tests.md` states why), and an order by a lower bound.

## Symmetry pairs
A `problem` or `component` suite adds a `symmetry pair` for every transformation its equations admit ([issue #513](https://github.com/seiya/atmofab/issues/513)): translation, the **axis exchange** $(q, u, v)(x, y) \to (q, v, u)(y, x)$ with the grid and the lengths exchanged, and the **mirrors** $x \to L_x - x$ with $u \to -u$, and $y \to L_y - y$ with $v \to -v$. Each transformation reverses every parameter that is odd under it: a rotation rate or a Coriolis parameter changes sign under a reflection and under the exchange, the phase of a wave moves, and a translation direction reverses. A linear equation also admits the sign reversal $q \to -q$, so a mirror pair whose initial condition is odd under the mirror may keep the base's initial condition and judge $q' = -q$ mirrored (the mirror of `advdiff1d_linear`: $a \to -a$, $u'(x) = -u(L - x)$).
- **The spec admits the transformed case.** Where the transformed case is not an input of the `Controlled Spec` as it stands (a boundary condition or a forcing fixed to one axis, a constant fixed to one sign, a depth constant referred to one wall, a topography centred by a fixed rule), the spec is changed to admit it: the orientation, the sign, the constant or the centre becomes an input whose default is the current value, and the components the problem composes take the same input.
- **The transformed case carries the metric.** Its `case_id` sorts after its base's (§Refinement judgment, carrying case). It reads the base case's final state through `at('<base>')`, applies the transformation with `roll`, `transpose` and `flip` (on a stacked `[ncomp, nx, ny]` state ordered `[q, u, v]`: `roll(flip(transpose(a, 1, 2), 0), 1, 0, 0)` for the axis exchange, which exchanges the spatial axes and the components `u`, `v`; the sign of one component under a mirror by a coordinate declared on the component axis, `docs/workflow/phases/phase_01_compile.md` `coordinates`), and judges every state variable in the `l2` norm, normalised by the `l2` norm of the base's variable (a momentum or velocity component by the largest `l2` norm over the base's components of that vector), to a round-off bound the suite states with its reason (`2.0e-11` on the two-dimensional shallow-water `problem` suites; on a `component` suite a bound of the order of its cross-target bound, whose normaliser differs). The residual of a conforming kernel is round-off, not zero: a contracted multiply-add or a vector remainder loop changes the last bit under a reordering.
- **The transformed case runs the transformed code path.** A kernel that maps the input back to the base orientation or sign internally and transforms the result compares a path with itself. The `Controlled Spec` of a suite that carries a pair forbids that mapping in its prohibitions section (§7 of a `problem`, §6 of a `component`, `docs/CONTROLLED_SPEC.md`).
- **A transformation the equations do not admit judges nothing.** The suite's `tests.md` §1 states it with the reason (a one-dimensional problem has no axis exchange).

## Operations Rules
- When a `Controlled Spec` change affects the judgment conditions, update `tests.md` in the same change.
- For `xfail`, define `xfail_condition` and the judgment in the failure direction simultaneously.
- When changing a threshold, state the affected `test_id`.
- Judge pass/fail including dependencies not in `tests.md` but in the `dependency` section of `spec.ir.yaml` and `aggregate_verdict.json`.

## Decision Criteria
- The test input and pass/fail judgment can be restored from the document alone.
- The correspondence between `spec_ref` and `controlled_spec.md` is unique.
- An `L0` test exists.
- The requirement-coverage rule is satisfied.
- The judgment result can be reproduced as a per-`node_key` `self_verdict`.
