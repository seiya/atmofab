# Generate rules — the Fortran binding

> **Audience: the maintainer of the Fortran `Generate` prompts and gates.** No leaf reads this
> document from disk; the rules it states reach a pure `generate.generate` leaf through the
> Fortran prompt fragments (`tools/prompt_templates/backends/language/fortran/`) and, for the
> gate-guard subset, through `docs/backends/language/fortran/CHECKS_ABI.md` §5. It is the
> canonical checklist behind them: the idioms that make a Fortran source pass the
> `Generate.gate` lint check and syntax check on the first attempt
> (`docs/workflow/phases/phase_02_generate.md` §2-1 states the language-neutral rules and points
> here).

## 1. Lint and syntax idioms

- **fortitude rule idioms (write Fortran source that passes `static lint` on the first attempt — this is the canonical checklist; a finding reopens `Generate.generate` and costs a regenerate cycle):** the conductor's `Generate.gate` lint check runs `fortitude check` under a rule set this repository DECLARES (`tools/backends/linter/fortitude/lint.py`, `RULE_CODES`), not under whatever the installed build enables by default, so a rule absent from that set cannot fail a node however the host is configured. The rules below are the subset a generated source most often trips; satisfy them up front:
  - **S001 (line length < 100 columns — 99 is the longest that passes on EVERY supported linter build):** the comparison itself differs across the supported range — `>=` on 0.8.x, so a line of exactly 100 already fails there (`line length of 100, exceeds maximum 100`, despite the message's wording), and `>` from 0.9.0, where the same line passes. Write under 100 and the difference cannot reach you. Split long `subroutine` signatures and `write` statements at a `&` continuation (break between arguments or `//`-concatenated pieces, never inside a string literal).
  - **C121 (`use` must have `only:`):** every `use` names the imported entities, e.g. `use <dep>_model, only: dp, <dep>__<op>`.
  - **C122 (intrinsic module `use` needs the `intrinsic` modifier):** import from an intrinsic module as `use, intrinsic :: iso_fortran_env, only: error_unit, int64` (the `, intrinsic ::` form), not a bare `use iso_fortran_env, only: ...`.
  - **PORT011 (no number-literal integer kind):** declare kind-qualified integers with a named kind (it fires for any literal kind, e.g. `integer(4)` too), `integer(int64) :: clock0` — never `integer(8)`. `int64` comes from `iso_fortran_env`, so importing it pairs with **C122**: write `use, intrinsic :: iso_fortran_env, only: int64`. (Fixing PORT011 by adding a bare `use iso_fortran_env` is the common cascade that introduces a fresh C122 finding on the next attempt — add the `intrinsic` modifier in the same edit.)
  - **C011 (`select case` needs a default):** every `select case` block ends with a `case default` arm (even if it only guards an unreachable value).
  - **C131 (module needs a default accessibility statement) — write BOTH halves, they fail different gates:** give every module a bare `private` in the specification part AND a `public :: <name>` line for every name it must expose. A `public :: <names>` list is NOT a default accessibility statement, so the list alone still fails lint with `module '<spec_id>_model' missing default accessibility statement`; the bare `private` alone publishes nothing, so it silences C131 and then fails the `Generate.gate` syntax check when a consumer cannot resolve the symbol.
  - **C072 (assumed-length character dummy must be `intent(in)`):** a `character(len=*)` dummy declared `intent(out)` / `intent(inout)` is rejected — give it an explicit length (in `checks_compute(case_id, check_id, status)` the `intent(out)` `status` must be `character(len=4)`, never `character(len=*)`).
  - **No suppression directive, and none is needed:** the rule set the gate applies is imposed with `--ignore-allow-comments`, so an `! allow(...)` comment suppresses nothing. Write no allow directive. Do not expect to be told when one is inert: a code the gate does not run earns `FORT005`, a code it does run earns `FORT002` on otherwise clean source, and on source that actually violates that code you simply get the finding you tried to suppress. This replaces the former workaround — an allow directive naming **C003**, written above every `implicit none` — which existed because that rule wants the F2018 spec-list `implicit none (type, external)` while `impl_defaults.toolchain.standard=f2008` (Makefile `FFLAGS=-std=f2008`) makes that form a `compile_error` (`Error: Fortran 2018: IMPLICIT NONE with spec list`). **C003 is no longer in the declared set**, so plain `implicit none` — no spec list, no directive above it — is correct and passes. ❌ `implicit none (external)` or `implicit none (type, external)` remain build-breaking `compile_error`s under `-std=f2008` that the deterministic `Generate.gate` syntax check (real `gfortran -fsyntax-only -std=f2008`) rejects, reopening `Generate.generate`. ❌ an allow directive of any kind, naming any rule, is no longer a fix — it changes no verdict, and the finding it was meant to silence is reported anyway.
- **Write standard-conforming f2008 — the `Generate.gate` syntax check compiles your source.** The conductor's deterministic `Generate.gate` syntax check runs the REAL compiler front-end (`gfortran -fsyntax-only -std=f2008`, with the dependency closure staged) over `source/<source_id>/src/*.f90` before the `Generate.gate` static check, so **every** syntax / standard-conformance `compile_error` — not a curated subset — is caught there and reopens `Generate.generate` (this replaced the former `post_generate` text heuristics). Known instances that used to slip through to Build and are now caught at the gate: an identifier over the 63-char f2008 name limit (keep generated names within the limit; if `<spec_id>_model` / `<spec_id>__<op>` itself would exceed it, that is a spec-level problem — do not abbreviate); a non-constant `STOP` / `ERROR STOP` code (❌ `error stop 'unknown case_id: '//cid` — under `-std=f2008` the code must be a scalar CHARACTER/INTEGER **constant** expression; ✅ use a fixed literal, or `print`/`write` the run-time value first and then `error stop <integer>`); the `implicit none (...)` spec-list form above. The gate additionally promotes `-Werror=unused-dummy-argument -Werror=unused-variable -Werror=ampersand` over the whole staged set, so a dummy argument the interface fixes but the body never consumes (an inert input the algorithm defines as unused; an ABI-fixed `name` / `case_id`) is a `compile_error` — ✅ keep it a live `intent(in)` dummy and bind it immediately after the declarations with `associate (unused_<name> => <name>)` / `end associate`; ❌ an arithmetic no-op (`0*<name>`); ❌ `! allow(...)` — not because of which rule it names, but because the lint gate runs `--ignore-allow-comments`, so no directive suppresses anything (and this class is a compiler error, which a lint directive could never have reached). An unused local variable is deleted, not bound. Canonical: [CHECKS_ABI.md](CHECKS_ABI.md) §5. The third promoted class is the continuation of a character literal: a wrapped literal must resume with a leading `&` — ✅ `'a message that is &` / `      &continued'`; ❌ the same wrap with the resume line's `&` omitted, which gfortran accepts as an extension and this gate rejects. Getting these right up front avoids a regenerate cycle, exactly as with the fortitude idioms.
  - **Fortran identifiers are case-insensitive.** A pair of names differing only in case (a dummy `g` and an output `G`; a dummy `U_L` and a local `u_l`) is one identifier in the same scope, so it is a `compile_error` — a duplicate declaration, or an `intent` conflict on the dummy. When an IR-derived name collides this way, rename the **local / dummy** side; the IR-derived name stays verbatim.

## 2. The syntax stage

The mandatory syntax stage for `fortran` is `gfortran -fsyntax-only -std=<toolchain.standard> -Werror=unused-dummy-argument -Werror=unused-variable -Werror=ampersand` (plus `-fopenmp` when the target profile's `parallel.backend` is `openmp`), over the node's `src/*.f90` staged with the certified dependency-closure `<dep>_model.f90`, with module files written to an isolated `.mods` scratch directory. The adapter is `tools/backends/compiler/gfortran/syntax.py`; the suffixes, the module/use source order and the promoted classes are `tools/backends/language/fortran/syntax.py`.

Three warning classes are promoted to errors over the whole staged set. An unreferenced dummy argument or an unused local variable is a gate failure, so a dummy the interface fixes but the algorithm defines as inert stays a live dummy bound by the `associate (unused_<name> => <name>); end associate` idiom (canonical: [CHECKS_ABI.md](CHECKS_ABI.md) §5). The third is `-Werror=ampersand` (issue #25): gfortran EXTENDS the standard by accepting a continued character literal whose resume line carries no leading `&`, and that shape let a counted-`do` spelling written inside a string reach a physical line start, where the `!$omp` presence floor (`docs/workflow/phases/phase_02_generate.md` §2-1) counted it — a false reject on a source this gate had passed. Rejecting the shape here is what lets the floor stay line-anchored and stateless; a conforming `&`-led resume is unaffected.

## 3. Model naming and dependency use

Moved from `docs/workflow/phases/phase_02_generate.md` §2-1 (issue #289, R4-b PR-3), which states the neutral rule and points here. The names are the ones `bundle.py` gives the host's files (`model_basename`, `checks_basename`, `runner_basename`) and the ones the `post_generate` gates read through `source.py`.

- The node's own `module` name must be the **literal** `<spec_id>_model` (the `spec_id` is prefixed verbatim; an abbreviation or derived short form is **not** permitted), and the published `subroutine` names must use the literal prefix `<spec_id>__<op>`. The literal `spec_id` is load-bearing, not merely a collision-avoidance device: a depending node is required to `use <spec_id>_model` / `call <spec_id>__*`, so an abbreviated module name breaks dependency resolution. The deterministic `post_generate` validator accepts only this exact name and rejects any other (it reports the required `<spec_id>_model.f90`, and when a model source was emitted under a different name it names the offending file and instructs a rename). If a `spec_id` is long enough that `<spec_id>_model` or `<spec_id>__<op>` would exceed the f2008 63-char identifier limit, do **not** abbreviate at `Generate`'s discretion — treat it as a `spec`-level problem (the `spec_id` is too long) and stop, rather than emitting a name the validator will reject.
- The source file name requires `<module_name>.f90` matching the defined `module` name (i.e. `<spec_id>_model.f90`).
- The `model` of a `node` that has a dependency `component` requires `use <spec_id>_model` and `call <spec_id>__*` per dependency `spec_id`, and forbids redefining `subroutine <spec_id>__*`. Each `call <dep>__<op>(...)` must pass arguments in the **exact positional order** of the dependency's published interface — never guessed. The conductor injects that order into the launch prompt's `<dependency_facts>` ("Published dependency operations"), resolved from the dependency's certified source (the exact source Build links); use it verbatim. Normally the injected set is exactly the dependency's IR `operations`; should a certified IR reach Generate with an empty `operations` (an authoring wobble the `Compile` gate `_validate_component_dep_operations` now pins going forward), the conductor falls back to injecting every `<dep_spec_id>__`-prefixed public subroutine of the certified source, so `<dependency_facts>` still names the surface the mandatory `call <dep>__*` builds against. Under each op's header the block also lists **each dummy argument's declared type, intent, and rank/shape**; the actual argument you pass must **match the dummy's rank and shape**, not only the order. When a dummy is lower-rank than your full state array (e.g. a rank-2 `(:,:)` field dummy vs. your rank-3 `(ncomp,:,:)` state), **loop over the extra component/dimension and pass lower-rank slices** (`call <dep>__<op>(u(c,:,:), ...)`) — never pass the whole higher-rank array. Fortran is positional and rank-checked: a wrong order **or** a rank/shape mismatch fails Build. See the `generate` `SKILL`.

## 4. How the presence floor reads a Fortran source

The parallel presence floor (`docs/workflow/phases/phase_02_generate.md` §2-1) asks this language backend to count a model source's loops (`source.counted_loops`) and the parallel backend for its directive (`tools/backends/parallel/openmp/directives.py`). Detection is line-anchored: a `do` opener and an `!$omp` sentinel count only at the start of a physical line. That is the free-form language rule (a comment line begins with `!`, a continued character literal resumes with `&`), and it is what puts a mention inside a comment, or inside a literal, structurally out of reach. That covers every literal that reaches this floor because the syntax check above rejects the one shape it would not — gfortran's extension of resuming a literal with no `&`, which does put a counted-`do` spelling at a line start (measured as an accepted residual by issue #23, closed by issue #25). The cost is three further fail-opens, all recorded in the checker: a `do` reached only through a `;` or a joined continuation is not counted, and a `do` header that WRAPS before it can be classified takes the whole file out of scope — it might be a `do concurrent`, and a false reject costs more than a miss.
