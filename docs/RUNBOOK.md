# Runbook (minimal procedure for running trials)

This document defines the "minimal operational procedure for running trials". The core workflow is a 5-phase structure `Spec → Compile → Generate → Build → Validate`. Update it as operational knowledge accrues.

## 0. Purpose
- From a `spec`'s `Controlled Spec` (physics definition) and `tests` (verification profile), perform execution and judgment, and evaluate physical validity and performance.
- Isolate where a failure's cause lies among **Spec / Compile / Generate / Build / Validate**. The optional flows `Tune` / `Promote` are handled outside the core workflow.

## 0-1. Host prerequisites

This is the canonical list of what the HOST that runs a workflow must have. `README.md` points
here rather than restating it: the two used to be separate lists, and the shorter of them was the
one an operator setting up a machine reads (issue #109).

Everything in the first three tables is refused at the point `tools/run_workflow.py` starts,
before any `LLM` leaf is launched, with the reason code named in each table's heading. The last
table is checked later, by `preflight`, still before the first leaf.

### Refused at startup — `missing_required_cli_tools`

| tool | purpose |
|---|---|
| `python3` | the workflow runtime (`tools/orchestration_runtime.py` etc.) |
| `jq` | extracting shell variables from JSON such as output_manifest (`python3 -c` is blocked by `forbid_python_inline_write`, so it cannot be substituted) |
| `git` | `write_scope_baseline` (FS-diff for terminal write authorization) / status check |

### Refused at startup — `missing_required_python_modules`

The host interpreter needs these packages, which this repository does not install for you:

```
pip install PyYAML tree-sitter tree-sitter-fortran
```

| package | purpose |
|---|---|
| `PyYAML` | every host-side reader of `spec.ir.yaml` and of the leaf-`LLM` configuration |
| `tree-sitter` | the parser runtime behind `tools/backends/language/fortran/structure.py` |
| `tree-sitter-fortran` | the Fortran grammar the three `problem` model gates read structure through (written against 0.6.0) |

They are needed by the HOST that runs the conductor, because `Generate.gate`'s static check runs
`python3 tools/validate_pipeline_semantics.py` there; no leaf needs them. Without them that gate
cannot read a Fortran source at all and fails closed — correctly, but only after lint and syntax
have passed, i.e. part-way into a billed run — so their absence is checked at launch instead.

(`PyYAML` is listed here because a run needs it, but it is not a member of
`REQUIRED_PYTHON_MODULES` and its absence does not carry this reason code: `tools/workflow_conductor.py`
imports it at module top, and `tools/orchestration_runtime._require_yaml` raises its own
"install PyYAML" message. Both are already launch-time and legible, which is the property the
reason codes exist to give the other two families.)

### Refused at startup — `missing_required_host_tools`

The executables the run's own toolchain implies. They are **not** named in the check: it reads
argv[0] out of the tables that will actually run them, so what it looks for cannot drift from
what a gate later launches (`tools/host_prerequisites.py`). For the Fortran nodes in this tree
the set resolves to:

| tool | purpose | when its absence used to surface |
|---|---|---|
| `fortitude` | the `static lint` tool the `Generate.gate` lint check runs via MCP `run_linter`. Supported versions: `>=0.8,<0.10` — see the version check below | `Generate.gate`, after `Compile` and `Generate.generate` had been billed |
| `make` | the build system `Build` drives via MCP `compile_project` | `Build` — one phase later still |
| `gfortran` | the compiler — both the mandatory `Generate.gate` syntax-only stage and the `FC` the build control file pins | `Generate.gate`, same as above: `run_syntax_check` reports a missing compiler as `skipped`, and the conductor turns a skipped MANDATORY stage into a fail_closed |

Install them with the platform's own package manager, e.g. on Debian/Ubuntu:

```
sudo apt-get install gfortran make      # the toolchain
pipx install 'fortitude-lint>=0.8,<0.10'   # or: pip install 'fortitude-lint>=0.8,<0.10'
```

### Refused at startup — `unsupported_required_host_tool_versions`

The same executables, checked a second way: PRESENT but of a version this repository has not
measured its gates against. Checked after the missing-tool arm, because an absent program has no
version to read.

Every `static lint` tool carries a range, and the probe evaluates the range of whichever one the
run's own axis selection resolves to — for the Fortran nodes in this tree, `fortitude` alone, the
row in the table above. The `Generate.gate` lint check applies a rule set this repository declares
rather than the linter's own default, and each set is measured against its own range. Neither the
tool name, the range, nor the probe argv is written in the launch check — all three come from the
backend package that owns the tool, so the check cannot look for a build the gate never runs.

| linter | supported versions | declaration and measurement |
|---|---|---|
| `fortitude` | `>=0.8,<0.10` | [docs/backends/linter/fortitude/RULES.md](backends/linter/fortitude/RULES.md) |
| `ruff` | `>=0.14,<0.17` | [docs/backends/linter/ruff/RULES.md](backends/linter/ruff/RULES.md) |
| `cppcheck` | `>=2.7,<2.18` | [docs/backends/linter/cppcheck/RULES.md](backends/linter/cppcheck/RULES.md) |

Which of them a run selects follows from its own `toolchain.language`, and that mapping is stated
once, in [docs/workflow/phases/phase_02_generate.md](workflow/phases/phase_02_generate.md) §2-1 —
not restated here, because what an operator meeting this refusal needs is the RANGE.

Only the first row is reachable today: no `spec` node can select a non-`fortran` language on a
non-`infrastructure` node, so an operator setting up a machine installs `fortitude` and neither of
the other two. The other rows are here because the ranges are refused by the same launch arm the
moment one of them is selected. The `missing_required_host_tools` table above deliberately does
not grow the same rows: it renders one RESOLVED selection, not a catalogue, and adding a program
no run installs would make the install line above wrong.

Without this arm the failure surfaces at the first `Generate.gate` and consumes the whole
`Generate` retry budget on findings no leaf can act on: the linter's vendor enabled 18 additional
rules by default in 0.9.0, and on this tree every finding they produce lands in the host-rendered
runner (issue #110). The refusal names the installed version and the supported range; the remedy
is to install a version inside the range, or to re-measure and widen it per that document's
Operations Rules.

### Refused at `preflight`, still before the first leaf

| requirement | where it is checked |
|---|---|
| the agent CLI the leaf-`LLM` configuration names, its MCP registration, its tool permission, and its tool roster | §0-2 (Claude) / §0-3 (Codex) |
| the CLI or API credentials of every provider that configuration names | `preflight.json#providers` |
| the sandbox runtime `bwrap` | `docs/BWRAP_ENABLEMENT.md` |


## 0-2. Claude backend preflight requirements (operator setup)

When any leaf runs on the `claude_cli` provider (the copied `llm_claude.example.yaml`; preflight `--backend claude`):
- The `preflight` of the Claude backend requires that the **`.claude/settings.json` committed to the repository** include `build-runtime` in `enabledMcpjsonServers` (or that `enableAllProjectMcpServers=true` and `.mcp.json` define `build-runtime`) (providing `run_linter` / `run_syntax_check` / `compile_project` / `run_program` / `run_quality_checks`; the server also exposes `detect_build_system`, which is refused under the workflow). The decision is made over the set `(.claude/settings.json: enabledMcpjsonServers ∪ enableAll expansion) − (.claude/settings.json: disabledMcpjsonServers) − (.claude/settings.local.json: disabledMcpjsonServers)`. **`~/.claude.json` (per-user / per-machine trust history) is intentionally not referenced** — because it would cause preflight results to vary per machine, enablement is declared via repo commit to ensure reproducibility (only the disable in `.claude/settings.local.json` is subtracted as a personal opt-out; since disables via `~/.claude.json` are not seen, this is a deliberate trade-off that can false-pass). Because `claude mcp list` skips the workspace trust dialog and spawns the stdio server, even a `✓ Connected` does not guarantee that the session exposes the tool (a false-positive source), so it is not used for the preflight gate and is kept as advisory display only. When not enabled, `claude_mcp_build_runtime_registered` in `preflight.json#checks` becomes `pass=false` and stops with `status=fail`. Remediation is to add `"enabledMcpjsonServers": ["build-runtime"]` at the top level of the committed `.claude/settings.json`, and confirm there is no disable of `build-runtime` in `.claude/settings.local.json`. **The leaf itself no longer goes through this enablement path.** Since issue #63 an agentic claude leaf is launched with `--strict-mcp-config --mcp-config .mcp.json`, so it reads the committed file directly and the enablement/disablement set above does not decide what it has — in particular a `disabledMcpjsonServers` entry in `.claude/settings.local.json` no longer subtracts anything from a leaf. The gate PREDICATE is unchanged and still reads that set: it certifies the operator's own checkout as a place where the server is registered, which is the property this section is about.
- The `preflight` of the Claude backend also requires that, **in addition to server registration, the MCP tool be permission-granted to the child `Agent` session**. Even if registered (enabled), without tool-invocation permission the child agent cannot call `run_linter` etc. and gets blocked with `Claude requested permissions … but you haven't granted it yet.` (stopping Generate/Build/Validate entirely). The decision is made by `claude_mcp_build_runtime_permission_granted` in `preflight.json#checks`, and its **AND** with `claude_mcp_build_runtime_registered` becomes the launch gate (`can_launch_*` / `status`). The granted condition is read from the committed **`leaf_config/claude/settings.json`** — the LEAF configuration, which since issue #63's final form is the only settings layer a leaf loads (copied into a private `CLAUDE_CONFIG_DIR` and read as the `user` layer) — and is one of: (a) its `permissions.allow` has the server-level grant `mcp__build-runtime` (and not in deny), (b) the required 5 tools `mcp__build-runtime__run_linter` / `__run_syntax_check` / `__compile_project` / `__run_program` / `__run_quality_checks` are individually allowed (and none in deny), (c) `permissions.defaultMode == "bypassPermissions"`. **Neither `.claude/settings.json` nor `.claude/settings.local.json` is consulted for this check** (issue #63): a leaf launches with `--setting-sources user` against a private home holding only the leaf configuration, so the gate reads the file the leaf reads. The repository's `.claude/settings.json` is the DEV layer for an operator's own session and reaches no leaf. It used to combine that file's `permissions.allow` and take `defaultMode` from it, which after the launch change made the gate wrong in BOTH directions — a grant living only in the untracked file kept the gate green while the leaf came up without it and died at its first `mcp__build-runtime__*` call, and a `deny` there refused a run whose leaves would have worked. Only the committed file grants or denies now. (The registration bullet above still subtracts that file's `disabledMcpjsonServers`: that is a deliberate opt-out that stops the RUN at the gate, a different question from what a leaf loads.) **Claude Code's permission rule does not interpret a wildcard in the MCP tool name part (`mcp__build-runtime__*`)**, so to allow all tools use the server-level `mcp__build-runtime`. Remediation is to add `"mcp__build-runtime"` to the `permissions.allow` of the committed `leaf_config/claude/settings.json`. A restart of the Claude Code session may be required for the permission to take effect in an OPERATOR's session; a leaf reads a freshly prepared home on every launch, so nothing is cached across runs. Whether the CLI honours the grant is no longer a matter of workspace trust for a leaf: a user-tier grant in the private home was measured (CLI 2.1.235, 2026-08-19) to be honoured with no trust seed present, in a session where a control command was refused — the trust conditionality below applied to the PROJECT layer, which no leaf now uses.
- **The committed `permissions.allow` is conditional on WORKSPACE TRUST, and preflight cannot see the difference** (issue #65; measured on CLI 2.1.232). **This bullet is about the PROJECT layer, which a workflow leaf no longer uses** (issue #63 moved a leaf onto the `user` layer of a private `CLAUDE_CONFIG_DIR`; measured on CLI 2.1.235, a user-tier grant there is honoured with NO trust seed present, in a session where a control command was refused — and the host seeds trust into that home anyway). What follows therefore applies to an OPERATOR's own interactive session in this checkout, and to any launch that still reads the project layer. In a checkout the CLI does not treat as trusted, the project layer's permission grants are dropped with only a warning on stderr — the run then fails at the leaf's first `mcp__build-runtime__*` call, while `claude_mcp_build_runtime_permission_granted` stayed `pass=true` because it reads the committed file, which is present and correct either way. This is the ordinary state of a FRESH checkout (a new clone, a CI workspace, a worktree), not an exotic one. The non-interactive remedy is to seed trust in the configuration directory's `.claude.json`: set `projects["<absolute MAIN repository root>"].hasTrustDialogAccepted` to `true` before starting the run. **The key is the main repository root, NOT the run's `repo_root`** — measured on 2.1.234, a run whose cwd is a git worktree is still keyed on the main checkout, so seeding the worktree path silently does nothing and leaves exactly the failure this bullet describes. Get it with `dirname $(git rev-parse --path-format=absolute --git-common-dir)`, which returns the checkout itself outside a worktree and the main root inside one. Hooks are NOT affected — they fire in an untrusted checkout too (measured), so the read/write guards stay in force while the MCP grants are gone, which is why the symptom is a blocked tool call rather than an unguarded leaf.
- **The CLI's own tool roster must match the leaf allowlist, and a CLI upgrade is what breaks it** (issue #71). `checks.claude_leaf_tool_roster_classified` LAUNCHES the leaf argv once against a loopback stand-in for the Messages endpoint, reads the `tools` array the CLI itself sends, and requires every name in it to be classified: a built-in must be exactly `orchestration_runtime.CLAUDE_LEAF_REQUIRED_TOOLS` (the set `--tools` declares, derived from the `PreToolUse` matcher coverage, minus anything recorded in `CLAUDE_LEAF_TOOLS_ABSENT_ON_CLI` — empty today), and an `mcp__<server>__<tool>` must come from a server the committed `.mcp.json` declares. It is **unbilled and modelless** — the stand-in answers `400` before any model turn — and costs ONE CLI START per probe, 2.0-6.1 s wall measured on one machine idle-to-lightly-loaded (a higher series exists and is most likely a suspend artefact — `tools/orchestration_runtime.py` carries that measurement), and that one start produces two captures, not one each. A preflight pays it once per provider surface it probes — the `defaults` entry plus each distinct configured command — and again once per TTL window, so a long orchestration can hit it MID-RUN: a CLI upgraded underneath a running workflow fails the check in flight, with the same detail and the same remedies as at launch. It GATES: a failure sets `status=fail` and both `can_launch_*` to false, and unlike the leaf-configuration check there is no launch-time backstop, because only the endpoint can see a roster.
  - **Why it will fail one day even though nothing in this repository changed**: the roster is the vendor's, and the flag is not a promise. A release can add a built-in, reinstate one, rename one — the CLI ignores an unknown `--tools` name *silently*, measured — or stop honouring the flag altogether. That is the check working. It replaced a denylist whose failure mode was the opposite and worse: it stayed green while the roster grew, and by CLI 2.1.238 fifteen built-ins no `PreToolUse` matcher validates were reaching a leaf.
  - **Remedy — classify the change on purpose; do not widen the check.** Read the `detail`, which names each unclassified or missing tool and records the whole measured roster and the CLI version. For a tool a leaf may legitimately keep, TWO things are needed and a matcher is only the first: add the `PreToolUse` matcher to `leaf_config/claude/settings.json` AND a dispatch branch that judges it in `tools/hooks/cli.py` (`docs/HOOKS.md` is canonical). A matcher makes the hook FIRE; it does not make the hook JUDGE — `_evaluate_pre_command_file_access_policy` returns "no opinion", which the caller treats as allow, for any tool name it has no branch for. Adding only the matcher would pass every preflight row while handing a leaf an unjudged tool; `test_every_tool_the_leaf_is_launched_with_is_actually_judged` is what stops it, and the failure it produces is the reminder. For a tool a leaf must not have, nothing is needed: it is already outside the launch, and the check is telling you the CLI put it back. For a declared tool the CLI did not offer, **check `leaf_config/claude/settings.json` for a `permissions.deny` naming it before concluding the vendor dropped it**: the probe seeds its scratch home with that committed file (see the bullet below on what the roster is measured UNDER), a `deny` there removes the tool from the roster, and a local edit to that file is therefore the most reachable cause of a `missing` row. Only when the CLI itself stopped offering it, record it in `CLAUDE_LEAF_TOOLS_ABSENT_ON_CLI` with the version that dropped it — that seam SUBTRACTS from the required set and never adds to it, so using it to absorb a configuration mistake would permanently give up a tool the leaf needs and turn the check green by widening it rather than by fixing anything. **The check also gates on the MCP half, and neither of those failures has a remedy above**: "servers .mcp.json declares that put NO tool in the roster" means the server did not start (check its `command` and run it by hand — `mcp_servers/README.md`), and "MCP tools from servers .mcp.json does not declare" means the `--strict-mcp-config` closure did not hold, so a leaf's server set is not the committed file. The detail now prints only the remedy for the failure that occurred; it used to append the built-in ones to every failure, including these two. Re-measure by hand with the argv `orchestration_runtime.claude_leaf_roster_probe_argv` builds. **One caveat before you classify anything as a vendor change**: two reviewers measured a LARGER built-in roster than this repository records, on the same CLI version and the same host (27/23 with a `Task*` family, and 24/20 with `Skill`), and it has not reproduced in any re-taking under the leaf's own argv since. So an unfamiliar built-in in a failure detail may be roster nondeterminism rather than a release adding a tool. Re-measure two or three times before editing anything; `TODO.md` carries the unreconciled measurement.
  - **A failure attributable to the environment rather than the repository**: a spawn error, a timeout, or a run that produced no roster request at all also fails, because an unmeasured roster is the state the check refuses. Check that the `claude` on `PATH` is the one the configuration names and that nothing on the machine blocks a loopback listener — preflight now depends on both. There is no opt-out AT FIRST LAUNCH; a `preflight.json` written by code older than this check carries no roster row at all, and a resume reads it back — re-probing under the default TTL mode, but NOT when `ATMOFAB_ORCHESTRATION_ENFORCE_LIVE_PREFLIGHT` disables the live probe. `TODO.md` carries that gap and the measurement of why the obvious fix (a required-check-name set for claude, mirroring the codex one) was written and backed out.
  - **What the check does NOT cover, beyond the settings layer below.** It probes the AGENTIC argv only. A PURE leaf is launched with `--tools ""` (`tools/pure_leaf.py`), and that declaration is unmeasured by the same argument this check makes for the agentic side. It holds today — measured on 2.1.239, the pure argv sends two requests each carrying an EMPTY `tools` array, which is the positive evidence that no tool is offered — and nothing would notice if it stopped. (An earlier version of this bullet said the pure argv "sends no request carrying tools at all". That was this probe's view rather than the wire's: its capture rule records only a NON-EMPTY array, so an empty one reads as no capture. The declaration is measurable by exactly this probe; it is simply not measured, because the check probes the agentic argv.) Each probe also leaves an MCP log under `$HOME/.cache/claude-cli-nodejs/<mangled-cwd>/mcp-logs-build-runtime/`, one per probe, which accumulate at 1+N per preflight plus one per TTL window.
  - **What the check measures the roster UNDER.** The probe seeds its scratch `CLAUDE_CONFIG_DIR` with the committed `leaf_config/claude/settings.json` — the same file a leaf loads as its `user` layer — because that layer decides the roster: a `permissions.deny` naming `Grep` and `Glob` in it removes both from what the CLI sends (measured on 2.1.238 and 2.1.239). An earlier version of this bullet said the real layer could not be measured this way, on the claim that its `UserPromptSubmit` hook blocks the probe prompt. That claim was false when written, and **issue #102 made it true**: the leaf entrypoint fails closed when it cannot name an orchestration, and this probe removes `ATMOFAB_ORCHESTRATION_ID` from the launch on purpose, so seeding the hooks made every claude launch unlaunchable (`can_launch_agents` ANDs this check). The seeded copy therefore carries the file **minus its `hooks` key** since #102. The fail-open the old claim justified — a deny stripping every leaf while this check reported pass — stays CLOSED, and it is `permissions` that closes it: measured by construction, `deny: ["Glob"]` added to a worktree's copy makes this check fail naming Glob. **Consequence for an operator**: the probe runs NO hook chain, so a "no request carrying a tool roster" failure here is about the CLI or the environment rather than about a hook — the detail prints both streams and names the seeding. The MCP half is unaffected either way, because `--strict-mcp-config` makes `.mcp.json` the whole server set regardless of the settings layer.

## 0-3. Codex backend preflight requirements (operator setup)

When any leaf runs on the `codex_cli` provider (preflight `--backend codex`), the launch gate is the conjunction of every check named in `CODEX_REQUIRED_LAUNCH_CHECKS` (`tools/orchestration_runtime.py`), which already includes the sandbox members; only `multi_agent_enabled` is advisory, and a check added later gates by default rather than silently becoming advisory. Reading a recorded `preflight.json` back applies more than that set — `status`, both `can_launch_*` fields, `sandbox_enforced`, the `hooks` feature state and every provider's launchability are ANDed by `_preflight_allows_agent_launch`. **This section covers the members of that set an operator configures**, plus one requirement that is enforced at launch instead. The CLI-capability members (`codex_version_available`, `codex_features_list_available`, `codex_exec_*`) are properties of the installed build rather than of the operator's configuration, and the sandbox members belong to `docs/BWRAP_ENABLEMENT.md`; read the set in the code for the whole list. The section exists because the repository can commit the hook source and the launch flags, and cannot commit the operator's own CLI state.

- **The CLI's `hooks` feature must be enabled.** `checks.hooks_enabled.pass` is read from `codex features list`, which reports one line per feature; the gate requires the `hooks` line to read `true`. Enable it in the operator's own `~/.codex/config.toml`:

  ```toml
  [features]
  hooks = true
  ```

  When it is `false` the run stops at preflight. That matters because the hook source is the whole enforcement boundary for a Codex leaf — the read guard, the write guard, and the capability gate all arrive through it — so the check is fail-closed by design and must not be worked around.

  **What the check does NOT establish**, measured 2026-08-21 on codex-cli 0.147.0: it reads `codex features list` under the OPERATOR's `CODEX_HOME`, while a leaf runs under the isolated home, whose host-authored `config.toml` carries only a `[projects.…] trust_level` and **no `[features]` table at all**. The two are different configurations. Today they agree because the CLI's own default for `hooks` is `true` — measured against an empty home and against a copy of the isolated home's `config.toml`, both reporting `true` — so the gate is currently sound by coincidence rather than by construction. `TODO.md` carries this; a CLI whose default flips would leave the gate green while the leaf came up without a policy layer.

- **The credential must exist — and NOTHING CHECKS IT AT PREFLIGHT.** `~/.codex/auth.json` (or the `CODEX_HOME` relocation of it) is bound read-only into the per-orchestration isolated home. Its absence is refused by `_prepare_codex_workflow_home`, which runs when the FIRST codex leaf is prepared, so a missing credential terminalizes part-way into a billed run rather than at the gate. There is no `auth`-named entry in the check set. Run the CLI's own login once before the first run; the failure it prevents is the one the rest of this section is gated to avoid.

- **The state home must be writable.** `checks.codex_home_writable.pass` resolves `CODEX_HOME`, else the deprecated `ATMOFAB_HOME`, else `~/.codex`, and requires the directory (or its parent, when it does not exist yet) to be writable. `CODEX_HOME` and `ATMOFAB_HOME` set to different paths is a refusal rather than a precedence rule.

- **The committed hook source must validate.** `checks.codex_project_hooks_validated.pass` reads `leaf_config/codex/hooks.json` from the repository (the LEAF-owned source since issue #102; the repository's `.codex/hooks.json` is the DEV layer and is not what a leaf validates) and requires every required event to be covered by an entry whose command is exactly the canonical repository wrapper. This one is committed, so it is the only item in this section an operator does not configure; it is listed because a failure here is reported alongside the machine-local ones. Its sibling `codex_project_hook_trust_bypass` gates too, and is a property of the installed build.

- **The prompt-on-stdin contract must hold.** `checks.codex_prompt_stdin.pass` requires `codex exec --help` and `codex exec resume --help` to document the `-` stdin sentinel. A failure means the installed build no longer accepts a prompt on stdin; install one that does, and do not move the prompt back onto argv — see §1-3.

**Hook trust is separate from the feature flag, and it applies to an operator's own interactive session rather than to a leaf.** The CLI records a trusted digest per hook entry in `~/.codex/config.toml` under `[hooks.state."<absolute path to .codex/hooks.json>:<event>:<index>:<index>"]`, and prompts for it the first time an entry is seen. Editing `.codex/hooks.json` changes the digest and re-prompts. A workflow leaf never takes that path: the host prepares an isolated home containing a SHA-256-verified copy of the committed LEAF hook source (`leaf_config/codex/hooks.json` since issue #102 — the file the operator's session trusts is a different one, and applies only the two DEV rule modules `docs/HOOKS.md` names), marks the repository project `untrusted` in that home's `config.toml` so the project hook layer is not loaded a second time, and launches with `--dangerously-bypass-hook-trust`, which therefore applies only to the verified copy. `docs/BWRAP_ENABLEMENT.md` is canonical for that isolation; the durable location of the home is `docs/RUNBOOK.md` §"The operator-private root" (issue #64).

## 1. Input and artifacts (minimal)
- Input: `controlled_spec.md` (physics / algorithm definition) / `tests.md` (case expansion / execution conditions / judgment thresholds) / `deps.yaml` (dependency declaration)
- Generated (Compile): `spec.ir.yaml` (**a single structural IR**: integrating the case / algorithm / impl_defaults / io_contract / dependency sections)
- Generated (Generate): the source of `model` (physics computation) and `runner` (execution / judgment coordination)
- Generated (Build): the binary (`binary/<binary_id>/bin/`)
- Output (Validate): `diagnostics.json` / `perf.json` / `verdict.json` / `aggregate_verdict.json` / `summary.json` / `semantic_review.json`
- Forbidden: `dummy` output, `dummy` data, `dummy` computation, artificial artifact generation for the purpose of advancing the workflow

## 1-1. artifact layout (operationally required)
- `Compile` saves `spec.ir.yaml` and `ir_meta.json` in `workspace/ir/<node_key_safe>/<ir_id>/`.
- `Generate` / `Build` / `Validate` save in `workspace/pipelines/<node_key_safe>/<pipeline_id>/`.
- Each `pipeline` requires placing `lineage.json`.
- The `source` artifact is saved in `workspace/pipelines/<node_key_safe>/<pipeline_id>/source/<source_id>/`.
- The `binary` artifact is saved in `workspace/pipelines/<node_key_safe>/<pipeline_id>/binary/<binary_id>/`.
- The `Validate` artifact is saved in `workspace/pipelines/<node_key_safe>/<pipeline_id>/runs/<run_id>/<node_key_safe>/`.

## 1-2. Deviation-prevention gates (operationally required)
- `docs/workflow/WORKFLOW_CORE.md` is the canonical source for the workflow common invariants (anti-fraud, the ban on referencing past artifacts, verification-contract derivation, the `workspace/` root constraint, the `quality check` judgment axis).
- `SPEC.md` is the canonical source for the overall policy and `spec` management requirements (`spec_kind` / registry / naming rules).
- Workflow execution runs each phase (`Compile` / `Generate` / `Validate`) with the `LLM`. `Build` is a deterministic process and is run by an MCP `compile_project` call.
- As a substitute for workflow execution, a script that batch-proxies the processing of multiple phases and artifact generation must not be newly generated or executed.
- Before each phase starts, capture `write_scope_baseline`, and before each phase completes, mandatorily run the `write_scope` check that detects diffs outside of `workspace/`.
- When `python` execution is used in the workflow path, limit `__pycache__` to under `workspace/`. Mandatorily apply `PYTHONDONTWRITEBYTECODE=1` or `PYTHONPYCACHEPREFIX=workspace/.pycache/<pipeline_id>/`.
- When the `write_scope` check detects a diff outside of `workspace/`, the relevant phase is `fail`, and `write_scope_violation.json` is recorded under `workspace/`.
- `spec.ir.yaml.io_contract.semantic_dependency.required_sources` is the canonical source for the data-dependency judgment of `Generate.verify`.
- `spec.ir.yaml.io_contract.outputs` is the canonical source for the output-contract judgment of `Generate.verify`, and the consistency of `evidence_ref` and `shape_expr` is mandatorily checked.
- The requirement definition for the output format, input/output contract, and judgment conditions is obtained from `controlled_spec.md`, `tests.md`, `deps.yaml`, `spec.ir.yaml`, and the `docs/` canonical source, and the verification scripts under `tools/` must not be used as input for the requirement definition.
- The canonical implementation of the procedure that finalizes a mechanical pass/fail is the procedure of running the `validate_pipeline_semantics.py`-equivalent invocation via `python3 tools/orchestration_runtime.py run-gate --gate validate_pipeline_semantics --agent-run-id <agent_run_id> --capability-token <capability_token> --args-json '<json>'`. The agent completes that `run-gate` execution to `exit code 0`.
- The validator invocation defaults to `run-gate`. When direct execution is permitted, it is limited to a read-only check and a gate-independent check, and the permitted targets are only `validate_workspace_root.py` and `check_artifact_syntax.py`.
- A shortage of the requirement definition must not be back-derived from the verification implementation. On shortage, the relevant phase is `fail`.
- `Validate.judge`, in addition to the fixed-script check, mandatorily executes an `LLM` semantic check, and includes `decision=pass` of `semantic_review.json` as a start condition.
- Before `Validate.judge` starts, verify that the `run_program` execution record, `diagnostics.json`, `perf.json`, and the `raw` execution evidence are present under the same `run_id` of the target `node_key`. When not met, it is a `Validate.judge fail`.
- `Compile.verify` launches **no** validator gate. The `--stage compile` gate (`--ir-ref workspace/ir/<node_key_safe>/<ir_id>/`), `check_artifact_syntax.py`, and `validate_workspace_root.py` now run in the conductor's deterministic `Compile.static` substep (`Conductor._compile_static_inproc`) **before** `Compile.verify`; a violation warm-resumes `Compile.generate` so verify is reached only on a deterministically-clean IR. `ALLOWED_VALIDATE_PIPELINE_STAGES[("compile","verify")]` is empty, so a verify leaf that issues `--stage compile` is rejected by the gate allowlist.
- `Generate.verify` launches **no** validator gate. The `post_generate` gate (`--stage post_generate --pipeline-root workspace/pipelines/<node_key_safe>/<pipeline_id>/ --source-id <source_id>`) and `validate_workspace_root.py` now run in the conductor's deterministic `Generate.gate` static check (`Conductor._gate_static_check`) **before** `Generate.verify`; a violation warm-resumes `Generate.generate` so verify is reached only on a deterministically-clean source. `ALLOWED_VALIDATE_PIPELINE_STAGES[("generate","verify")]` is empty, so a verify leaf that issues `--stage post_generate` is rejected by the gate allowlist.
- Before `Build` completes, run `validate_pipeline_semantics` via `run-gate` with arguments equivalent to `--stage post_build --pipeline-root workspace/pipelines/<node_key_safe>/<pipeline_id>/`.
- Before `Validate.execute` completes, run `validate_pipeline_semantics` via `run-gate` with arguments equivalent to `--stage post_execute`. `--pipeline-root` can be specified repeatedly, and in a trial where the `dependency_graph.json` sidecar's `all_nodes` holds multiple `node`, expand all `pipeline_root` corresponding to `all_nodes` into `--pipeline-root` to run. Pass this trial's `run_id` into the `run_id` of `args_json` (→ `--run-id`) to scope the verification to that run (to avoid permanent fail on a broken sibling run of a past retry that remains in the `append-only` pipeline). On `fail`, `Validate.execute` is `fail`, and `Validate.judge` must not start.
- The `--stage pre_judge` gate is run by the **conductor** as two deterministic substeps wrapping the `Validate.judge` leaf (G4), not by the judge leaf. The `pre_judge` substep (index 0) is a dependency-DAG readiness check (a `dependency_graph.json` sidecar `all_nodes` closure node not built+validated in its own pipeline authors `pre_judge_meta.json` `status=fail` and terminalizes `fail_closed` before execute/judge). The `post_judge` substep (index 3) runs `validate_pipeline_semantics --stage pre_judge` after the judge returns — answering its three dedicated exit codes (3 `static_frontend_unavailable`, 4 `stale_dependency_ir`, 5 `host_authored_artifact_violation`) as `fail_closed` BEFORE the violations are classified at all, since none of the three is repairable by a re-authored `semantic_review.json` — scoped to this run (`--pipeline-root`/`--run-id`, with both the post_judge substep's own arid AND the judge arid as `--in-flight-agent-run-id`, never `--allow-missing-orchestration` / `--allow-missing-llm-review`), recording the verdict + a severity `disposition` in `post_judge_meta.json`. (Naming caution: the `post_judge` substep runs the validator stage literally named `pre_judge`.) A recoverable (judge-authored) violation warm-resumes the judge to re-author its artifact; an orchestration-record/DAG **integrity** violation (and any `pre_judge` `fail`) is a non-physics integrity blocker terminalized `fail_closed`; an **unknown** violation routes to the unified escalate LLM in prod, and terminalizes `fail_closed` in dev (G5). Operators do not invoke `pre_judge` by hand during a normal run.
- `trial_meta.json` requires recording `generated_by_stage`, `source_source_id`, `source_binary_id`, `source_command_ref`, and `source_artifact_hash`, and on omission or inconsistency it is a `fail` (because `run_id` is encoded by the `runs/<run_id>/` directory path itself where the trial_meta is placed, a separate `source_run_id` field is not recorded).
- A trial that violates the verification of this section stops at the relevant phase, and artificial artifact generation for the purpose of satisfying a downstream phase's start condition is forbidden.

## 1-3. Agent launch conventions (operationally required)
- Workflow execution starts from the `orchestration agent` and requires issuing an `orchestration_id`.
- Before the workflow starts, run the `preflight` that verifies the independent launchability of a `step agent` and a `substep agent`, and when it is not `pass` do not start.
- The preflight of `backend=codex` must simultaneously satisfy `checks.hooks_enabled.pass=true` and `checks.codex_home_writable.pass=true`.
- Both backends must satisfy `checks.<backend>_prompt_stdin.pass=true`. The leaf prompt is delivered on the CLI's stdin, never as an argv element (a single one is capped at 128 KiB and a node's prompt exceeds it). The codex check requires `codex exec --help` and `codex exec resume --help` to document the `-` stdin sentinel; the claude check requires `claude -p` on empty input to exit non-zero with `through stdin` in its message. A failure means the installed CLI no longer accepts a prompt on stdin: install a build that does. Do not work around it by putting the prompt back on argv — that is the `E2BIG` failure this check exists to prevent.
- The `preflight` includes `sandbox_runtime=bwrap` and `sandbox_enforced=true` as required conditions.
- Before the first run, create the leaf-LLM configuration: `cp docs/examples/llm_claude.example.yaml llm.yaml`, then edit it. It is gitignored, so it stays yours and the tree stays clean.
- The canonical entrypoint for starting the workflow is `python3 tools/run_workflow.py <spec_ref> <until_phase> [--llm-config <path>]`. `<until_phase>` specifies one of `compile` / `generate` / `build` / `validate`. `--llm-config` names the leaf-LLM configuration file (default `./llm.yaml`, resolved against `--repo-root`), which selects the provider, model and reasoning effort of each phase / `substep` — the samples write all five leaves out explicitly, so what runs where is read rather than derived; see [docs/ORCHESTRATION.md](ORCHESTRATION.md) "Leaf LLM configuration". A missing default is not filled in from anywhere: the run stops with `invalid_startup_input` / `llm_config_default_missing` before launching, naming the path and the command that creates it. A `codex_cli` entry additionally requires an explicit `model:`; the generic `codex` alias is rejected so each leaf has authoritative model provenance. There is no run-wide flag that overrides the file: the removed `--llm` / `--agent-model` / `--llm-command` trio has no replacement on the command line, because what each leaf launches belongs in the configuration.
- The `Build` step has no standard `substep` and launches no `agent`: it is deterministic and runs in the conductor's own process (`Conductor._build_inproc`), which issues the MCP `compile_project` call and the `post_build` gate. It is recorded as one `step` whose `substep_agent_run_ids` is an empty array (§1-2 and the `Build` item of §2 state the same thing).
- Each phase of `Compile` / `Generate` / `Validate` runs with the `orchestration agent` launching each `substep`'s `substep agent` independently.
- The actual processing of each `step` / `substep` must not be proxied by a script.
- The `step agent` and `substep agent` have a unique `context_id` per `agent_run_id` and require recording `context_isolated=true`.
- `record-launch` generates `workspace/orchestrations/<orchestration_id>/output_manifests/<agent_run_id>.json` / `read_manifests/<agent_run_id>.json` / `sandbox_profiles/<agent_run_id>.json`.
- On completion of each `step` / `substep`, save `agent.result.json` and `agent.summary.txt`.
- The `orchestration agent` sequentially decides the launch order based on the `topo_level` of the `dependency_graph.json` sidecar and the dependency-satisfaction state.
- The `orchestration` execution record is saved in `workspace/orchestrations/<orchestration_id>/`, and `orchestration_meta.json`, `agent_graph.json`, and `agent_runs.jsonl` are required.
- `step_result.json` requires recording `executor_agent_run_id` and `substep_agent_run_ids`. The `substep_agent_run_ids` of `Build` (a phase with no standard substep) may be an empty array.

## 2. Minimal loop
1. **Spec update**: fix `controlled_spec.md` / `tests.md` / `deps.yaml`, and resolve ambiguity and omissions.
2. **Compile**: take `controlled_spec.md` + `tests.md` + `deps.yaml` + `spec/registry/spec_catalog.yaml` as input and generate `spec.ir.yaml`.
   - The `Compile.generate` substep generates a single IR that integrates and holds the 5 sections `case` / `algorithm` / `impl_defaults` / `io_contract` / `dependency`.
   - The `Compile.verify` substep self-checks the structural invariants (case coverage / algorithm completeness / io_contract consistency / dependency consistency / impl_defaults consistency).
   - Because it is an `LLM`-using phase, apply the "Handling of the `LLM`" of `SPEC.md`.
3. **Fix the hierarchical execution order**: fix the execution order in ascending `dependency_graph.json` sidecar `topo_level`. The `Compile` of a parent `node` must not start until the immediate dependency `node` satisfies `direct dependency ir readiness`. `Generate` onward of a parent `node` must not start until the immediate dependency `node` satisfies `direct dependency execution readiness`. Independent `node` of the same `topo_level` are also executed sequentially one at a time.
4. **Per-`node` workflow issuance**: the `orchestration agent` issues an individual `ir_id` and an individual `pipeline_id` per `node_key`.
5. **Generate**: per target `node`, generate `model` and `runner` separately with the `LLM`.
   - `Generate.generate` must not take `controlled_spec.md` as direct input, and uses `spec.ir.yaml` as the canonical source.
   - `Generate.verify` performs the G1–G7 verification items (see `phase_02_generate.md`) against each section of `spec.ir.yaml`, and additionally reads `controlled_spec.md` as a secondary requirement-fidelity cross-check (`spec.ir.yaml` stays primary).
   - A `node` that has dependencies requires an implementation that calls the published `operation` of the dependency `node` resolved by `spec.ir.yaml.dependency.direct_deps`, and forbids re-implementing an equivalent function.
6. **Build**: per target `node`, run the standard build tool that can handle dependencies via the `MCP` server's `compile_project`.
   - A `Build` failure **always becomes a retry feedback to `Generate`** (because it is a deterministic process, there is no room for fixing other than the code).
   - `Build` must not internally retry itself.
7. **Validate**: per target `node`, the deterministic `Validate.pre_judge` substep checks dependency-DAG readiness, the `Validate.execute` substep runs the binary and generates primary evidence, the `Validate.judge` substep recomputes the judgment metrics and finalizes the `verdict`, and the deterministic `Validate.post_judge` substep runs the `--stage pre_judge` gate and classifies violation severity.
   - `Validate.execute` runs the `runner` with `MCP run_program`, and always includes `spec.ir.yaml.case` in the `run_program` execution command.
   - `Validate.execute` saves the primary evidence for judgment recomputation into `runs/<run_id>/<node_key_safe>/raw/`. The required condition of the `raw` composition uses `spec.ir.yaml.io_contract.raw_requirements.required_evidence` as the canonical source.
   - `Validate.judge` recomputes the judgment metrics with only the `raw` primary evidence as input, and when it does not match `diagnostics`, it is a `Validate.judge fail`. In addition to the fixed-script check, it performs an `LLM` semantic check, and makes `decision=pass` of `semantic_review.json` a required condition.
   - The judgment including dependencies is output to `aggregate_verdict.json`. When an immediate dependency `node` is `fail` or `blocked`, the upper `node` ends as `blocked`.
8. **Forced stop**: when the relevant phase cannot proceed due to an input shortage or a preceding-stage artifact shortage, stop the relevant phase with `fail`. It must not proceed with estimated completion or artificial file generation.
9. **Recording**: save `spec_version` / `test_profile_version` / `case_hash` / `git_sha`.
   - Save `ir_id` / `pipeline_id` / `source_id` / `binary_id` / `run_id`.
   - Save `node_key` / `topo_level` (from the `dependency_graph.json` sidecar) / `dependency_ref`.
   - `dependency_ref` saves the per-phase canonical path. `Compile` records `spec/.../deps.yaml`, and from `Generate` onward records the phase root of `workspace/...` (`ir_ref` or `pipeline_ref`).
   - An `LLM`-using phase saves `attempt_count` / `verification_status` / `last_fail_reason` / `debug_mode` in each phase's `<stage>_meta.json`.
   - The `agent_runs.jsonl` of `step` / `substep` records `agent_backend` / `agent_model` / `context_id` / `context_isolated=true`.
10. **Next action**: decide where to go back according to the failure classification (next section).

## 3. Where to go back on failure (guidance)
| failure kind | go back to |
|---|---|
| `LLM` stage cannot run | the input contract or the `MCP` connection definition |
| Spec deficiency (ambiguity / omission / unit inconsistency) | `Spec` |
| Test deficiency (contradiction in case expansion / threshold / execution conditions) | `tests` |
| Dependency resolution fail (unregistered / unimplemented / compatibility violation) | `deps.yaml` / `spec_catalog.yaml` |
| Dependency block (`fail` of a lower `node`) | the lower `node` |
| Compile verification fail (IR structural invariant violation) | `Compile` (and `Spec` as needed) |
| Generate verification fail (implementation inconsistent with the IR) | `Generate` (and `Compile` if the IR is wrong) |
| Build failure (compile error) | `Generate` (deterministically go back to Generate) |
| Physics fail (the execution result is a judgment failure) | one of `Generate` / `Compile` / `Spec` — specify the detail in `judge.findings` |
| Validate judgment fail (divergence of the primary evidence and diagnostics) | `Generate` (code-quality problem) |
| `semantic_review.decision=fail` (implementation differs from the IR's intent) | `Generate` |
| `semantic_review.decision=fail` (the IR itself differs from the spec's intent) | `Compile` |
| Dependency integration fail (missing dependency `operation` call) | `Generate` or `Build` |
| Dependency Compile incomplete | `Orchestration` or the lower `node` |
| Dependency workflow not run | `Orchestration` or the lower `node` |
| Improper-generation fail (`dummy` output, artificial data creation) | discard the relevant phase and go to `Spec` / the phase input definition |
| Reproducibility collapse (determinism breakage) | `Compile` / the execution environment |

An automatic retry to `Spec` is not performed in the core workflow. When the `orchestration agent` judges that a return to `Spec` is needed, it stops with `fail_closed` and records the details in `failure_analysis.json`.

Optional flows:
- Performance shortfall (insufficient exploration of B) → launch the `impl_defaults` variant exploration of the optional flow `Tune`.
- Official-version promotion → go to `releases/` with the optional flow `Promote`.

## 3-0. Auto-running dependencies (`--with-deps`)

When a `node` is fail-closed with `dependency_not_ready` (`direct_dependency_compile_readiness_not_pass` / `..._execution_readiness_not_pass`) because its dependency nodes have not been compiled/built/validated yet, there are two ways forward:

1. Run the core workflow for each dependency node manually (bottom-up: components → profile → problem), then run the target.
2. Run the target with `--with-deps`, which resolves the target's transitive dependency closure (`deps.yaml` + `spec_catalog.yaml`) and runs each not-yet-ready dependency node bottom-up (one orchestration per node) before the target.

```bash
# auto-run the dependency closure, then the target
python3 tools/run_workflow.py spec/problem/dynamics/advection_diffusion/advdiff1d_linear validate --with-deps
```

Behavior:
- Dependency nodes run to **Compile** when `<until_phase>=compile` (compile readiness), else to **Validate** (execution readiness).
- Dependency nodes that already satisfy the required readiness are **skipped** (idempotent).
- Execution is **sequential** in dependency order; on the first dependency-node failure the run **stops** before the dependent/target node, and the JSON output records `failed_dependency_node` + its `orchestration_id` + the `dependency_runs` summary.
- The target node's final JSON result carries a `dependency_runs` summary of which nodes ran / were skipped.
- Every node of a `--with-deps` closure (each dependency and the target) records a `closure_id` (= the target's orchestration id) in `orchestration_meta.json#invocation`, so a later `--resume` can re-derive and continue the **whole** closure — see the closure-aware resume note in §3-1. (Historically `--with-deps` was ignored with `--resume`, resuming only a single node.)

### Updating a shared dependency spec (R6-lite dependency freshness)

When you edit a `spec` that other nodes depend on — a shared component, or the `harness_fortran_cpu` infrastructure node — bump its `spec_version` in all three places that carry it (`controlled_spec.md` §0, `tests.md` §0 `spec_ref.spec_version`, and `spec/registry/spec_catalog.yaml`), bump `tests.md`'s own `test_profile_version` if the test profile changed, and — if the change is breaking — tighten the dependents' `version_constraint` in their `deps.yaml`. **Do not bump the dependents' own `spec_version`**: their content did not change.

Bumping the `harness_fortran_cpu` infrastructure node carries one more REQUIRED pin: the `node_key` key of `HARNESS_CAPABILITY_MANIFESTS` in `tools/codegen_bundle.py`. An undeclared harness node_key provides nothing (`harness_provided_capabilities` returns `None`), and every physics node's `capability_requirements` is non-empty, so a stale key fails **every** dependent's `Generate` with `bundle_capability_unsatisfied` — in a billed run. `tools/tests/test_codegen_bundle.py` pins the key against `spec_catalog.yaml`, so the unit suite catches the omission before the run. Update the documentary copies in the same commit: `spec/schema/generate/harness_capabilities.schema.json` (description + `examples`) and `docs/workflow/CODEGEN_BUNDLE_CONTRACT.md`. The unit suite also carries the harness `node_key` as a fixture literal in `tools/tests/test_codegen_bundle.py` and `tools/tests/test_pure_leaf_producer.py`, which fail loudly on the bump and are updated in the same commit; the copy in `tools/tests/test_validate_pipeline_semantics.py` is inert (that gate exempts on the `infrastructure/` prefix, so the version is decorative) and is updated for consistency only. Because a version bump is a byte-length-preserving edit, run `find . -name __pycache__ -prune -exec rm -rf {} + && rm -rf workspace/.pycache` before the billed re-certification: CPython validates a `.pyc` on `(mtime, size)`, so a same-size edit landing inside the recorded mtime second can serve stale bytecode — with `HARNESS_CAPABILITY_MANIFESTS` that reproduces the same fleet-wide `bundle_capability_unsatisfied` as a stale key. The `find` clears repo-tree caches (modules imported during host startup, before the redirect line runs — e.g. `tools/validate_pipeline_semantics.py`); the `rm -rf workspace/.pycache` clears the in-process conductor host's *redirected* bytecode (`_HOST_PYCACHE_REDIRECT_PREFIX`), which lives outside any `__pycache__/` dir and the `find` alone would not reach. The redirected half is what covers every module the conductor/gates import *lazily* during the run — including `tools/codegen_bundle.py` (the `HARNESS_CAPABILITY_MANIFESTS` module this section warns about), `mcp_servers/build_runtime_server.py`, and `tools/hooks/lint_evidence.py` — so `rm -rf workspace/.pycache` is the clause that actually guards this section's same-size-edit hazard. A fresh workspace has neither cache, so this only matters on a reused workspace.

Re-certifying the dependents is then a single command. Each certified node records the dependency closure it was built against in its `dependency_graph.json` sidecar; readiness re-derives that closure from the current `deps.yaml` + `spec_catalog.yaml` and compares, so every node certified against the old version is automatically **stale** (= not ready) and gets re-run:

```bash
python3 tools/run_workflow.py <target spec_ref> validate --with-deps
```

Without `--with-deps` a single-node run stops at `workflow-launch-check` with `dependency_not_ready`, and the `reason_detail` names the drifted node and the resolution it was certified against versus the one derived now. Staleness is detected at **version granularity only**: a content edit that does not move `spec_version` is not seen, which is why the respec discipline is "content change ⇒ `spec_version` bump".

## 3-1. Resuming a failed workflow (`--resume`)

**One-time cost when resuming onto sources written before the declared lint rule set landed
(issue #111).** A `source/<source_id>/src/` produced by an earlier run carries the
`! allow(C003)` directive the leaf-read contracts used to mandate. The `Generate.gate` lint check
now runs `--ignore-allow-comments`, so that directive is a finding (`FORT005`) rather than a
suppression. WHICH FILE carries the directive decides what happens, and issue #112 made the
difference decisive. In a leaf-authored file the resume fails its lint gate ONCE, warm-resumes
`Generate.generate`, and the regenerated source carries no directive — nothing to do, the message
names the directive and the loop converges on the next attempt. In the HOST-RENDERED RUNNER, which
is where the archived trees overwhelmingly carry it, the gate attributes the finding to this
repository and terminalizes on the first attempt with `gate_host_rendered_lint_findings`; see that
entry below for the recovery, which is to regenerate the source rather than to resume onto the old
tree. Certified sources under `releases/` are not re-linted (the
gate lints only the node's own `src/`), so this is confined to in-flight work.
[docs/backends/linter/fortitude/RULES.md](backends/linter/fortitude/RULES.md) carries the
measurement.

The canonical path to resume a workflow that failed midway, from the failure point while reusing completed `step` (e.g. already-compiled), is `python3 tools/run_workflow.py --resume`.

```bash
# resume the most recent orchestration with the previous spec_ref / until_phase / leaf-LLM configuration
# (the recorded configuration file is re-hashed; see the llm_config_changed_since_launch note below)
python3 tools/run_workflow.py --resume

# to resume a specific orchestration
python3 tools/run_workflow.py --resume --orchestration-id <orchestration_id>

# to resume with an extended until_phase (if the lone positional is a phase name, it overrides until_phase)
python3 tools/run_workflow.py --resume build
```

- When `spec_ref` / `until_phase` / `--mode` are omitted, they are restored from the target orchestration's existing artifacts (`orchestration_meta.json` / `launches/orchestration.start.prompt.txt`), and an explicitly specified value takes precedence. `preflight.json` is NOT one of those sources — a resume re-runs preflight, and the backend comes from the recorded leaf-LLM configuration — which is what makes a run that died before `preflight.json` was written resumable. The leaf-LLM configuration is the exception to "explicit wins": see the next item.
- **The leaf-LLM configuration is pinned to the run.** A cold start records `invocation.llm_config_path` and `invocation.llm_config_sha256` (the file's BYTES), plus `invocation.llm_leaf_map` (the resolved provider/model of every LLM leaf, for cost / A-B audits). A resume re-hashes the recorded file and refuses with `llm_config_changed_since_launch` (exit 2) when it has changed or been deleted: the phases already run used the recorded models, and resuming would silently run the rest on new ones. Restore the file, or start a fresh run — the cold start kept a copy of the exact bytes it launched with at `workspace/orchestrations/<id>/llm_config_snapshot.yaml` (never rewritten on resume, and named by the refusal when present), because the configuration file is the operator's own and is not under version control. The recorded pin WINS over an `--llm-config` passed on the resume — a resume continues that run rather than starting a new one — and the ignored flag is named on stderr. To use a different configuration, start a fresh run. The same gate applies to every member of a `--with-deps` closure resume, not only the entry orchestration. An orchestration started before this field existed pinned nothing, and the run-wide flags that named its models have been removed, so it cannot be resumed at all: it is refused with `llm_config_legacy_flags_removed` (exit 2) and must be re-run cold. A record that carried `invocation.llm_config_overrides` (those flags' literals) is refused the same way, under `llm_config_changed_since_launch` — write those values into the configuration file and start fresh. An orchestration launched before `configs/llm/` was deleted pins a path that no longer exists, so it is refused with the same rule and has no snapshot to offer (it predates them). Recover the pinned file — `claude.yaml` or `codex.yaml`, whichever `recorded_llm_config_path` in the refusal names — from history, recreating the directory the redirection needs: `mkdir -p configs/llm && git show <pre-removal-rev>:configs/llm/<name>.yaml > configs/llm/<name>.yaml`. Or start a fresh run.
- When `--orchestration-id` is omitted, the most recent (by `orchestration_meta.json#started_at` order) orchestration in `workspace/orchestrations/` is targeted.
- **Driver liveness on a non-terminal target (`running`)**: a non-terminal target is either an active concurrent run (whose `workspace/tmp/<arid>` a resume would destroy) or the corpse of a driver that died without terminalizing. Every cold init and every `--resume` records the driving process's identity in `orchestration_meta.json#driver` (`pid` / `pid_start_ticks` — field 22 of `/proc/<pid>/stat`, which detects PID reuse / `boot_id` / `hostname` / `pid_ns` / `uid` / `recorded_at`), and the resume gate probes it. The verdict decides, for both the implicit-latest and the explicit `--orchestration-id` path:
  - `dead` (the process is gone, it is a zombie/exiting entry its parent has not reaped, the PID was recycled, or the host rebooted): the orchestration is terminalized as `fail` / `driver_crashed` (event `dead_driver_terminalized`) and the resume proceeds from its checkpoint. The terminal status is required — it is what routes `init --resume-from-checkpoint` through `terminal_reset`, where the crash reconciliations of [Incomplete launch recovery](#launch-incomplete-recovery) run. When that terminalization fails, the resume stops with `dead_driver_terminalize_failed` rather than resuming a still-`running` meta whose reconciliations would silently not run. Three of those four causes are read out of the local `/proc`, and a local `/proc` only answers for the recorded process when the pid is in the same numbering and visible to us — PID numbers are namespace-local, and a `hidepid` mount hides other users' entries. Reading *an* entry is not enough: across namespaces the same pid number names a different process, whose start ticks differ, which would otherwise be taken as proof that the driver was replaced. All three are therefore gated on two further recorded fields, `pid_ns` (the driver's PID-namespace inode) and `uid`; unless both match the probing process the verdict is `unknown`. The fourth cause, a reboot, is **not** gated: `boot_id` is not namespaced and a mismatch proves it outright — resting instead on the `hostname` comparison having established that the block was written on this machine, which compares hostname strings, so give hosts distinct hostnames if a workspace is ever shared between them. A driver block written before those fields existed therefore keeps only reboot-based recovery and otherwise degrades to `unknown` — the fail-safe direction, since only an unambiguous `dead` may unblock a resume.
  - `alive` (the recorded process exists, was started at the recorded instant, and is not a zombie/exiting entry): the resume is refused — `latest_orchestration_not_resumable` on the implicit path, `orchestration_driver_alive` on the explicit path (an explicit id overrides the implicit-latest guard, not a demonstrably live driver). `orchestration_driver_alive` is also what a closure warm-resume of a live member returns.
  - `unknown` (no recorded block, a meta with no recorded `hostname` — nothing then establishes that it was written on this machine, so no local evidence can prove `dead` — a meta written on another host, an unreadable `/proc` entry — including any non-Linux host, where no identity is captured at all — or a recorded `pid_ns` / `uid` that does not match the probing process, which covers **every** orchestration whose driver block predates those two fields): the pre-existing behavior is preserved. The implicit path stops with `latest_orchestration_not_resumable` (to resume that run, specify `--orchestration-id` explicitly); the explicit path proceeds and emits the `resume_liveness_indeterminate` warning, because the crash reconciliations will not run for a target left at `running`.
- **Cold-start guard (a run without `--resume`)**: before a cold run of a `spec_ref` starts, every non-terminal orchestration of that same `spec_ref` is probed (its status is re-read at probe time, so a candidate that terminalized after the scan is dropped). The scan alone cannot see a run that has not written its `orchestration_meta.json` yet, so two cold runs of one spec started together would both scan clean; a per-(repository, `spec_ref`) start claim (an advisory `flock` under `~/.atmofab/start_claims/`, relocatable with `ATMOFAB_START_CLAIM_ROOT`, held across both the scan and the run, released by the OS if the driver dies) closes that window — a second cold start that cannot take the claim stops with `concurrent_orchestration_running` without scanning. A `--resume` does not take the spec claim, but every node — cold or resumed — takes an exclusive claim on its own `orchestration_id` for the duration of the run: two `--resume` invocations of one orchestration would otherwise both pass the liveness gate and both `init --resume-from-checkpoint` into the same preserved `orchestration_agent_run_id`, sharing one `workspace/tmp/<arid>` that either one's cleanup then deletes. The second stops with `concurrent_orchestration_running` naming that `orchestration_id`. An `alive` driver likewise stops the run with `concurrent_orchestration_running` (exit 2) before any orchestration state is created — two concurrent runs of one spec derive their `pipeline_id` from the same `workspace/pipelines/<node_key_safe>/` tree and then write into it, so the second corrupts the first's in-flight state. (The `workspace/tmp/<arid>` collision is specific to the resume path, which retains the prior run's `orchestration_agent_run_id`; a cold run always mints a fresh one.) A `dead` or `unknown` driver emits the `prior_incomplete_orchestration` warning — carrying `spec_ref` / `orchestration_id` / `liveness` and the exact `python3 tools/run_workflow.py --resume --orchestration-id <id>` command — and the cold run proceeds. The cold path deliberately does not terminalize the prior orchestration: it stays resumable, and the operator decides whether to continue it instead of starting over. In a `--with-deps` run the same guard is applied per node (each not-ready dependency and the target), rescanning the workspace each time rather than reusing a scan from closure start — a closure occupies hours, and a competing run is most likely to be launched inside that window. On a closure `--resume`, a node that is warm-resumed is instead gated like the entry orchestration above (terminalize when `dead`, refuse with `orchestration_driver_alive` when `alive`, warn when `unknown`).
- **Interruption of the driver (`Ctrl-C` / `SIGTERM`)**: `tools/run_workflow.py` converts `SIGTERM` into `SystemExit(143)` and terminalizes the orchestration as `cancel` / `driver_interrupted` (event `driver_interrupted`) before the process exits, so an interrupted run is recoverable by the normal `--resume` instead of remaining `running` forever. An already-terminal status is preserved (a more specific outcome, e.g. `fail_closed` / `sandbox_enforcement_violation`, recorded just before the signal, wins). An in-flight leaf is stopped before the run is terminalized: the leaf runs in its own process group on **both** backends, and the whole group is signalled (`SIGTERM`, then `SIGKILL` after a bounded grace period), which under mandatory bwrap reaches the wrapper and — via `--die-with-parent` — the CLI behind it. `SIGKILL` of the driver itself cannot be handled — such a run is recovered by the `dead` liveness verdict above. The leaf process does not outlive it: the sandbox wrapper is launched with `--die-with-parent`, so the driver's death takes the wrapper and the leaf CLI with it (measured). What can survive is a tool subprocess the CLI leaked into the sandbox's own session — it consumes no quota and is unreachable from the leaf's process group, the same residual the per-leaf cap's teardown documents (`docs/ORCHESTRATION.md` §leaf transient retry). The hard per-leaf timeout below covers only the complementary case, a leaf that wedges while the conductor is still alive.
- **Any other unhandled exception in the driver**: a host-side failure no specific handler names — an `OSError` from a workspace write on a full disk or a read-only checkout, or a programming error on the init/preflight path — is caught by a backstop clause of its own and terminalizes the orchestration as `fail` / `driver_exception`, under the same guards as the interruption case above (only a run this invocation committed, or one whose `driver` block names this process, is terminalized; an already-terminal status is preserved). A fail envelope carrying `reason=driver_exception` is printed on stdout and the exit code is `2`, so a caller sees a reported failure rather than a traceback; the traceback itself still goes to stderr, so a genuine bug stays debuggable. The one exception is a run whose **stdout is already dead** (piped to a reader that exited): the driver emits its envelope into the broken pipe without raising, but CPython then fails to flush at shutdown, writes `Exception ignored on flushing sys.stdout` to stderr and forces exit **120** whatever the driver returned. A caller that pipes this driver anywhere must therefore keep reading until the process exits, or treat 120 as "output was not delivered" rather than as a workflow verdict. Events emitted outside a node run (a startup refusal, the closure's between-node events) are discarded rather than raising, so a broken pipe there does not kill the driver; a dead reader does end a node run once one is under way, because the in-run stream is not guarded. The envelope follows `--stdout-format` like every other event: `{"status": "fail", "reason": "driver_exception", ...}` under `jsonl`, and `[FAIL] reason=driver_exception orch=<id> detail=<...>` under the default `human`, where a detail longer than 240 characters is elided. Two caveats on the default: human rendering is done by the stdout tee, which exists only if the run log under `run_logs/` could be opened, so a workspace too broken for that — a read-only checkout, a full disk — prints the raw JSON instead; and the untruncated detail is in `run_logs/run_*.jsonl` rather than on the terminal. Parse stdout only with `--stdout-format jsonl`. Terminalization is best-effort: a failing `set-status` is swallowed so the envelope still prints. `fail` is a resumable terminal status, so a run that reached terminalization is recovered by the normal `--resume` like any other failure. A failure that lands before this invocation's `init` has committed terminalizes nothing, and what to do next depends on the invocation: on a cold start there is no orchestration and no checkpoint, so start a fresh run; on a `--resume` the checkpoint is intact either way, so fix the host-side cause and re-run the same `--resume`. Whether that resume target is terminalized depends on how far its `init` got: `init --resume-from-checkpoint` rewrites the meta's `driver` block to name the resuming process, so a failure after that write is owned by this invocation and the target is terminalized `fail` (resumable, so the next `--resume` proceeds), while a failure before it leaves the block naming the previous run and the ownership guard leaves the meta alone. `reason_detail` on the meta is truncated to fit a single argv element and keeps both ends of the message; the untruncated text is on the stdout envelope and in `run_logs/run_*.jsonl`. The same terminalization covers a `runtime_command_failed` return from `init` or from `preflight`, under the same two ownership conditions — which matters for an `init` that committed the `running` meta and then failed, where the `driver` block is the only proof the run is ours.
- **Events emitted outside a node run (startup rejections and closure-level events)**: the refusals `run_workflow` emits from its own startup path — `missing_required_cli_tools`, `invalid_pycache_redirect_root`, `invalid_startup_input` (which carries every named `LlmConfigError.rule`, `llm_config_default_missing` among them), `missing_canonical_schema`, `concurrent_orchestration_running`, the resume gates (`no_resumable_orchestration`, `latest_orchestration_not_resumable`, `orchestration_driver_alive`, `dead_driver_terminalize_failed`, `resume_params_unrecoverable`, `generate_executor_legacy_removed`, `llm_config_legacy_flags_removed`, `llm_config_changed_since_launch`), and the `concurrent_orchestration_running` of the cold-start guard — follow `--stdout-format` like the events above: the payload under `jsonl`, a `[FAIL] reason=<...>` line under the default `human`. In `human` mode a refusal's detail is **not** elided: it keeps its line breaks and is never truncated, so the remedy of `llm_config_default_missing` — a `cp` command per sample, one per line — can be pasted off the terminal. The same path also carries the `status: info` events of the startup gates — `prior_incomplete_orchestration`, `dead_driver_terminalized`, `resume_liveness_indeterminate` — which are **not** `[FAIL]` lines: they render as the indented `[warn   ]` form of the in-run stream and carry no `detail` key at all, so a caller detecting a refused start must match `[FAIL]` / `"status": "fail"` rather than the reason code alone. (A `docs_ref` on a `fail` envelope is rendered in `human` mode wherever it is emitted, in-run included; `missing_required_cli_tools` is the only envelope that carries one.) The rule is a property of the emission point rather than of the reason code: an event no `_StdoutTee` sees has no `run_logs/run_*.jsonl` copy, so nothing may be dropped from what is printed, whereas an in-run event is elided at 240 characters because the log holds its full text. A reason code alone therefore does not say which applies — `concurrent_orchestration_running` is also emitted from inside a node run, by `_run_node`'s own claim check, and that copy is elided like any in-run event and is in the run log. It therefore covers the **closure-level** events of a `--with-deps` run on the same terms — the per-node gates and summaries `_run_with_dependency_closure` emits between nodes (the same refusal keeps the same unelided detail whether or not `--with-deps` was passed; the closure copy adds the node's `orchestration_id` and its closure context), and its `dependency_node_begin` announcement, which like the warnings above is an `info` event rendered as `[dep ] node=<...>`. Parse stdout only with `--stdout-format jsonl`.
- When `spec_ref` is explicitly overridden at resume time, the overridden `spec_ref` / `source_dependency_ref` is reflected into `orchestration_meta.json` (so that the next implicit resume does not revert to the stale old value).
- **Closure-aware resume (`--with-deps` runs)**: a `--with-deps` run is a *sequence* of orchestrations (one per not-ready dependency node, bottom-up, then the target), so resuming must continue the whole closure, not just one node. Each node records its closure back-link in `orchestration_meta.json#invocation` (`closure_id` = the target's orchestration id, `closure_target_spec_ref`, `closure_until_phase`). On `--resume`, when the resumed orchestration carries a `closure_id`, run_workflow re-derives the closure from the recorded target (`_resolve_dependency_closure`), **skips** already-ready dependencies, **resumes** each not-ready dependency's prior orchestration (or runs a fresh one if none exists), and finally runs the **target** — so `--resume` reaches the originally specified spec instead of stopping after one node. Resuming from **any** node of the closure works (the back-link is on every node); pointing `--orchestration-id` at a specific node also drives the whole closure. The closure is re-derived against the **current** `deps.yaml` / `spec_catalog.yaml` (a genuine dependency change is reflected). An explicit **spec** positional at resume is the escape hatch back to single-node resume of that spec; when that positional **retargets** the orchestration to a different spec, `enable_checkpoint_resume` drops the now-invalid closure back-link from `invocation` (realigning `invocation.spec_ref`), so a later plain `--resume` of the same orchestration does not re-drive the old closure target. Older orchestrations that predate the `invocation` block have no `closure_id` and fall back to single-node resume. Caveat: the implicit-latest guard applies — if the only/latest orchestration is a non-terminal `running` node whose driver liveness is not provably `dead`, implicit `--resume` stops with `latest_orchestration_not_resumable`; pass `--orchestration-id <any closure node>` to drive the closure (which then resumes the `running` node too, subject to the same per-node liveness gate).
- **Reproduction record (`orchestration_meta.json#invocation`)**: every cold init records how the run was invoked — the raw command (`argv` / `command`) and the resolved/canonical params (`spec_ref` / `until_phase` / `llm` / `llm_command` / `mode` / `agent_model` / `with_deps` / `wait_usage_reset` / `generate_executor`), plus the closure back-link for `--with-deps` nodes. Most fields are captured once at the cold start and preserved; the exceptions are the per-invocation ones a resume can override — `closure_until_phase` and `wait_usage_reset` are refreshed on `--resume` to the effective value of that resumed invocation (so `wait_usage_reset` reflects whether THIS run waits, not whether the original one did). It is captured once at the initial start and preserved across re-init / `--resume` (the same lifecycle as `repo_revision`), so it always reflects the invocation that produced the run.
- **`generate-executor` — legacy removed, resume of a non-`pure` record fails closed** (`Z2` / `M-F`): the `generate-executor` is no longer selectable — legacy generate execution was removed and `pure` is the only executor (`docs/GLOSSARY.md`). The `--generate-executor` flag and the `ATMOFAB_GENERATE_EXECUTOR` env var were **deleted** (a cold run that still passes the flag fails at argparse, `SystemExit 2`, not a JSON envelope; the env var is fully inert). The value is still recorded (always `pure`) in `orchestration_meta.json#invocation.generate_executor` as provenance, and it is authoritative on every resume: a resume whose recorded executor is **not `pure`** — a `legacy` record, the field absent (a pre-adoption run), or any garbage value — is **rejected fail-closed** with reason `generate_executor_legacy_removed`. The run is neither silently switched to `pure` nor run as legacy; start a fresh run instead. A residual non-`M3c` node is recorded `pure` too (a provenance stamp — its leaf-mode is decided by node shape, not the executor), so its resume is **not** rejected. The probed backend's CLI version (`preflight.json#agent_version` — `claude --version` on a `claude` run, `codex --version` on a `codex` run; `preflight.json#backend` says which) is likewise machine-local provenance, surfaced by `tools/audit_orchestration.py` (the pure-leaf A/B section) alongside the recorded executor.
- Internal behavior: `--resume` runs `orchestration_runtime.py init --resume-from-checkpoint` (= set `resume_enabled=true`, retain `orchestration_agent_run_id`, merge `phase_state`) and then starts. When the target orchestration is already terminated with a terminal status (`fail` / `fail_closed` / `pass` etc.), it returns the live status to `running` (because the runtime rejects a transition from terminal to another status except `fail` → `fail_closed`, without a reset the resumed agent could not record `pass` even if it completed). On reset, the terminal-time `reason_code` / `reason_detail` / `blocking_policy_scope` are saved to `resumed_from_*`, and `finished_at` / `detected_at` are removed (the history remains in `failure_analysis.json` and `phase_state_log.jsonl`). The skip judgment of a completed `step` is made by the conductor via `check-step-completed`. A `step` detected as `stale` by `verify-checkpoint-integrity` is not skipped and is re-run.
- **Prohibition of a concurrent `claude` session (during workflow execution)**: do not launch another `claude` session in the same project dir during workflow execution. Another session's startup cleanup deletes the running workflow's `workspace/tmp/<orchestration_arid>/.../tasks/*.output`, and the Bash tool output becomes unobtainable with `output file ... could not be read (ENOENT) ... another Claude Code process ... deleted it during startup cleanup` (observed). When concurrent work is needed, isolate and run it in a separate checkout with `git worktree`. When the symptom occurs, re-running the relevant Bash recovers it (the artifact itself is not corrupted).
- Automatic repair of legacy records: `init --resume-from-checkpoint` also runs `repair-agent-runs`, completing the `parent_agent_run_id` / `agent_model` missing from the step/substep rows of `agent_runs.jsonl` recorded **before** the introduction of mandatory `agent_model` + auto-backfill (commit `caa10ab`). Because these are append-only and a duplicate `record-agent-run` is also rejected, they cannot be restored going forward, and they permanently failed the `pre_judge` gate of `Validate.judge` and made resume impossible. The repair is authoritatively derived from existing artifacts (`parent_agent_run_id`: substep from `step_result.json#executor_agent_run_id`, step from `orchestration_meta.json#orchestration_agent_run_id`, cross-checked with the child→parent edges of `agent_graph.json`; `agent_model`: adopting the uniform non-empty value of the same orchestration). The orchestration row itself is also covered for `agent_model` only (it is the graph root and legitimately has no `parent_agent_run_id`); on a fresh run `run_workflow.py` already records it via `init --agent-model` (default: the operator's unpinned claude alias, e.g. `opus`, for the claude backend — never a pinned version, which would go stale), so this backfill mainly fixes orchestrations created before that wiring. It does not overwrite an existing non-empty value, attaches provenance to the repaired row, and leaves an audit log in `record_repairs.jsonl`. It is idempotent. When `agent_model` cannot be auto-derived (no non-empty value in siblings / multiple values mixed), the repair result becomes `needs_manual` and resume continues as-is (a later gate fails), so the operator explicitly runs `python3 tools/orchestration_runtime.py repair-agent-runs --repo-root . --orchestration-id <id> --agent-model <model_id>` and then resumes again.
- Automatic repair of a wrong-executor `step_result.json`: `init --resume-from-checkpoint` also runs `repair-step-result-executor` for every corrupt node/step. The failure it heals is `validate_pre_judge_step_result_executor_integrity` — a substep-aware (`compile` / `generate` / `validate`) `step_result.json` whose `executor_agent_run_id` is a verify-substep arid instead of the orchestration arid (both the directory key and the field). The `pre_judge` gate of `Validate.judge` requires the executor to be the orchestration agent, so the node locks at `step_result_written` with no forward path (the `write-step-result` guard only blocks a **new** bad write; `--backfill` is keyed to a terminal step agent; `repair-agent-runs` only touches `agent_runs.jsonl` rows). The repair relocates the file to the orchestration-arid directory, rewrites the field, and appends the old substep arid to `substep_agent_run_ids` to keep the substep→step_result linkage. It refuses (leaving the file untouched) unless the wrong arid is a recorded `substep` for that exact node/step and no legitimate `step_result.json` already exists at the orchestration dir, validates the corrected payload exactly as the write path would, leaves an audit log in `record_repairs.jsonl`, and is idempotent. For a manual one-off run: `python3 tools/orchestration_runtime.py repair-step-result-executor --repo-root . --orchestration-id <id> --node-key <node_key> --step <compile|generate|validate>`.
- Cross-phase `Compile` retry of an already-passed phase (`reopen-phase`): when `Validate.judge` returns `structural_violation` / `attribution=ir` (or `Generate.verify` records `ir_inconsistency`), the decision table (§3) routes the retry to `Compile`. After `Compile` / `Generate` / `Build` are checkpointed `pass`, that re-point cannot be expressed in place: `check-step-completed` reads the stale IR as `integrity=ok` (artifact hashes intact, semantic inadequacy invisible), the phase sits at `step_result_written` rather than the `child_finished` the `write-step-result` path requires, and `retry_decisions` only models a within-step substep retry. `reopen-phase --from-phase compile --node-key <node_key> --trigger-agent-run-id <failed_downstream_arid> --reason <reason_code>` resolves this: it snapshots the prior attempt's step/substep runs for the reopened phases as **superseded** (durably in `reopen/superseded_runs.json`, exempt from the `_validate_orchestration_completion_for_pass` vouch so they do not block the eventual `pass`), archives their `step_result.json` to `step_result.superseded.<seq>.json` (freeing the deterministic executor path), drops the affected `completed_steps` checkpoint entries (so `check-step-completed` re-runs them), and resets the affected `phase_state` to `not_started`. The orchestration agent then re-runs `Compile` → `Generate` → `Build` → `Validate` against the corrected IR. `--trigger-agent-run-id` must be a terminal non-pass step/substep strictly downstream of `--from-phase` (the anti-abuse gate). On `--resume` of an `attribution=ir` failure, `init --resume-from-checkpoint` records `orchestration_meta.resume_directive` (`reopen_from` / `node_key` / `trigger_agent_run_id` / `finding_id`, derived from `failure_analysis.json#original_finding`); the resumed agent honors it by calling `reopen-phase` first, then re-running, so the resume proceeds deterministically instead of re-running only `Validate` and reproducing the same fail. A manual one-off run: `python3 tools/orchestration_runtime.py reopen-phase --repo-root . --orchestration-id <id> --node-key <node_key> --from-phase compile --reason <reason_code> --trigger-agent-run-id <arid> [--finding-id <id>]`.
- Recovery from an **unauthorized-write `fail_closed`** (`reopen-phase` with an invalid-log trigger): when a downstream phase fails *because* it performed an unauthorized write (e.g. a Generate Makefile that names the build binary inconsistently, so `make test` relinks a stray binary into the read-only binary dir), `record-agent-run` rejects the run and the orchestration stops `fail_closed`. The rejected run's terminal `fail` payload is **not** appended to `agent_runs.jsonl` — it is diverted to `agent_runs_invalid.jsonl` (so a same-arid retry stays possible) with an authoritative `violations/<arid>.unauthorized_write_violation.json` marker. Historically this dead-locked resume (`resume_reopen_no_valid_trigger`): `reopen-phase` read only `agent_runs.jsonl`, so the actual failing run could not be used as a trigger, and when the only previously-valid trigger had already been consumed by an earlier `reopen_seq`, `reopen-phase` returned `noop` and the operator was forced into a fresh full workflow run. Now `reopen-phase` accepts the diverted entry as `--trigger-agent-run-id` **when** a matching `unauthorized_write_violation.json` exists (the violation file is the anti-abuse gate — a sandbox/identity reject without one is refused, since reopening an upstream phase would not help). The invalid-log trigger is recorded into `reopen/superseded_runs.json` so a redundant re-invocation is `noop` (idempotent), and the result/audit log carries `trigger_source=agent_runs_invalid`. On `--resume`, when the prior failure is such an unauthorized write attributed to a single upstream phase (read from `failure_analysis.json` attribution, mapped to `compile`/`generate`/`build`), `init --resume-from-checkpoint` records `orchestration_meta.resume_directive` (`reopen_from` / `node_key` / `trigger_agent_run_id`, `source=agent_runs_invalid.unauthorized_write`) so the resumed agent calls `reopen-phase` deterministically instead of re-deriving the dead end; the surface defect (the inconsistent Makefile etc.) is still corrected by the re-run Generate phase. Build and validate it — `--with-deps` (§3-0) runs the closure — then `--resume`. **Check the first sub-bullet's tell before doing any of that**: on a record written before the reason was derived from the meta, this same string is what EVERY `pre_judge` failure was written as, and the closure it names can be complete. The only recorded incident of this reason is of that kind, so the tell is the common case among what exists today, not an edge. `validate_pre_judge_violation`: an unrecoverable `--stage pre_judge` violation, or a judge warm-resume budget exhausted; `post_judge_meta.json#violations` names what failed, and the fix is in whatever authored the named artifact. `validate_post_judge_gate_error`: the validator subprocess did not launch; `post_judge_meta.json#failure_excerpt` carries the launch error. The remaining three are covered by the `static_frontend_unavailable` bullet above.
  - `validate_<substep>_deliverable_not_freshly_written` — the substep body recorded `status: "pass"` and the substep still failed. `determine_substep_status` fails a gate substep when the meta's status is not `pass` **or** a deliverable's mtime is below the launch instant, and both in-process bodies record a `failure_category` on every fail arm, so this pair means the mtime test failed and nothing else. It is the only one of the three below that a non-corrupt run produces. The deliverable's exact path is in `workspace/orchestrations/<orchestration_id>/launches/<agent_run_id>.request.json#allowed_output_paths`, where `<agent_run_id>` is the substep's last row in `agent_runs.jsonl`. For `pre_judge` that list has ONE entry; for `post_judge` it has **four** (`post_judge_meta.json`, `aggregate_verdict.json`, `summary.json`, `validate_meta.json`) and the freshness clause covers every one of them, so on a `post_judge` failure stat all four — the stale one need not be the meta whose name the reason carries. All of them live under `<pipeline_ref>/runs/<run_id>/<node_key_safe>/` (`refs.run_node_dir()`), NOT under the orchestration directory the previous bullet points at; that is also where the `pre_judge_meta.json` the tell above asks for lives. The launch instant is `workspace/orchestrations/<orchestration_id>/agents/<agent_run_id>/launch_instant.probe.json`'s **mtime**, under the SAME `<agent_run_id>` the deliverable's `allowed_output_paths` came from — there is one probe per attempt (one per `agent_run_id`, allocated fresh at the top of each retry), so a retried substep leaves the dead attempt's probe beside its `dialogs/` and neither is overwritten. **Look for that file before running anything else. If it is absent, the record predates the fix and this whole procedure stops here**: the launch instant was a `time.time()` reading in a local variable, nothing wrote it down, and the mtime test cannot be re-evaluated at all. Read such a record as EITHER cause — a genuinely stale deliverable, or a body that completed inside the lag between `time.time()` and the coarse clock the kernel stamps inodes from, which is issue #113 and is the one the recorded incident turned out to be. When the probe IS there the mtime test is re-evaluable after the fact: `stat -c %.9Y` both files and compare — the substep passed the freshness clause iff the DELIVERABLE's stamp is at or above the PROBE's. Compare the mtimes, not the probe's `launched_at_wall_clock` field, which is a second reading for a human and can sit up to a tick away from its own file's stamp. On a record written at or after that fix only the first cause remains, because the instant is now a stamp of that same coarse clock (`Conductor._launch_instant`), so a body can no longer fail on a deliverable it wrote correctly. Note the two ages are independent: the first sub-bullet's tell is about a record written before the REASON was derived from the meta (#114), which is a different change from this one — a record can be old for one and current for the other.

  - `validate_<substep>_meta_missing` — no usable meta: absent, undecodable, or not a JSON object. No writer produces this state either. A body that cannot write its meta raises, and a raise terminalizes as `leaf_transport_error`, so this reason means the run directory was corrupted or edited outside the run.
  - **Recovery for the three reasons above.** None is operator-fixable and none has a retry path; each is a defect report against this checkout. `--resume` re-runs the phase and does not address the cause.
  - **Distinguishing the DAG reason.** `validate_pre_judge_dag_incomplete` is emitted from the `pre_judge` substep's own meta and from the pre-launch readiness guard, which runs before any substep and writes no `pre_judge_meta.json`. Both emit `judge_pre_spawn_blocked` to `workspace/orchestrations/<orchestration_id>/run_logs/*.jsonl`; no other path emits it. An absent meta accompanied by that event is the pre-launch guard, not `_meta_missing`.

- **Reading a `leaf_transport_error` fail_closed**: the reason has the form `leaf_transport_error: leaf_exit=<rc> (tag: <infra_tag>; <evidence>)`, followed by ` [attempts=<n>]` when the substep was launched more than once. **Route on the tag, not on the suffix.** The tag names the cause of the *last* attempt and says what to do (below); `[attempts=<n>]` only counts the launches, and a run may mix tags (a transport flake retried into a usage limit ends with `attempts=2` and a `llm_usage_limit` tag — the quota is what must be waited out, not a provider outage).
  - `llm_transport_flake` / `llm_overloaded` / `llm_rate_limit`: these are the tags the conductor retries (at most 2 retries with backoff — canonical: `docs/ORCHESTRATION.md` "leaf transient retry"). There are **two** ways to reach a terminal fail_closed under these tags, and `[attempts=<n>]` does NOT tell you which — it counts every launch, including bundle repair turns, so a declined retry can read `attempts=3` and an exhausted count `attempts=4`. **Grep `leaf_transient_retry_declined` first; that event is the decision procedure.**
    - The event is PRESENT: a re-launch was possible and was **declined**, because the attempts that died burned the wall-clock budget (`TRANSIENT_RETRY_WALL_CLOCK_BUDGET_SECONDS`, 600s — the event carries `reason`, `elapsed_seconds`, `spent_seconds`, `budget_seconds`). A fault that takes ten minutes to arrive is a deterministic function of how long the request runs, so re-launching reproduces it and **waiting is the wrong remedy**. The case this was built for is an HTTP leaf behind an intermediary whose own read timeout expires mid-request: three `HTTP 504`s on requests of 613.6s / 612.3s / 611.8s against an entry whose `timeout_s` was 2400s. Fix the intermediary's read timeout, or shorten the request (the entry's `effort` / `max_output_tokens`); `timeout_s` is not the timer that fired.
    - The event is ABSENT: the fault **outlived every retry** the count budget allowed (or the substep was never retried at all). The provider side is still degraded, an immediate `--resume` fails the same way, and the remedy is to wait for the provider to recover.
  - `llm_usage_limit`: wait for the quota to reset, then `--resume`. To have the conductor do this **automatically, in place**, re-run with the opt-in `--wait-usage-reset` flag (default OFF): when the dead leaf's terminal usage-limit line carries a resolvable reset — a machine `|<unix-epoch>` OR a TZ-anchored human reset (`resets 10:20pm (Asia/Tokyo)`, the form the real CLI emits, on **stdout** with an empty stderr) — the conductor sleeps to the reset (+120s margin) and re-launches the same substep instead of fail-closing, a same-run, substep-granular resume that avoids re-paying the earlier passed substeps a phase-granular `--resume` would re-run. A human reset **without a parenthesized IANA timezone** (`resets 6:10pm`) or without a time-of-day (`resets Monday`) is NOT resolved (the instant is never guessed from the host's local timezone), and a usage limit that is the leaf's own output — result prose that merely *mentions* a limit, or a completed/recovered JSON envelope quoting one, i.e. a leaf that crashed for an unrelated reason — declines the wait; only the CLI's own abort arms it, either bare (one short line that *opens* with the limit, nothing else) or carried in `result` by the CLI's error envelope (`is_error:true` plus an error status). Both declines just `fail_closed` (and emit `leaf_usage_limit_wait_declined` with a `reason`, the dead leaf's `dead_agent_run_id`, and the `evidence` line it was decided from — grep that event first when an opted-in run fail_closes on a usage limit). The reset instant is taken **first** from a host-side `claude --output-format json -p /usage` probe the conductor runs itself (0 tokens, ~1s, no leaf involved), and only then from the scrape above; `leaf_usage_limit_wait` / `leaf_usage_limit_wait_declined` name which via `reset_source` (`probe` / `scrape_machine` / `scrape_human`) and, for a probe, the `window` it matched. **Grep `leaf_usage_limit_probe` as well**: it is emitted on every probe attempt with the `outcome` (`resolved`, `probe_timeout`, `probe_error`, `probe_unparseable`, `backend_unsupported`, `window_unmatched`, `window_ambiguous`, `window_not_exhausted`), the parsed `windows`, and a bounded `excerpt` of the raw response. A probe arms the wait only when the response proves it is the built-in `/usage` command (`num_turns == 0`, not a model turn) AND the window the dead leaf named is reported **fully exhausted (100% used)**; anything less — a window with headroom, or a model-authored reply — falls back to the scrape, so a probe failure costs nothing beyond the pre-probe behavior. Whether `/usage` answers at all once the quota is exhausted is **not yet verified** — the `excerpt` on that event is the record that settles it. Bounded: one wait per substep, at most 6h (a longer reset falls back to `fail_closed`). The flag is **not** carried across `--resume` (a per-invocation preference recorded on `orchestration_meta.json#invocation` and refreshed to the effective value on resume) — re-pass `--wait-usage-reset` on the resume to keep it active. Canonical: `docs/ORCHESTRATION.md` "leaf transient retry".
  - `llm_client_error`: the request itself was rejected (4xx) — an expired credential, an oversized prompt, or an unsupported parameter. The evidence carries the API's own message. A `max_tokens: <n> > <m>` message means the leaf model's output ceiling is below `LEAF_MAX_OUTPUT_TOKENS` (`tools/workflow_conductor.py`): the conductor does not pin the leaf model, so the leaf runs whatever model the `claude` configuration resolves to. Either restore a leaf model whose output ceiling is at least that constant, or lower the constant to the running model's ceiling. Resuming without a fix reproduces the same rejection.
  - `llm_permission_probe_unavailable`: an operator/configuration fix is required.
  - `leaf_timeout`: the conductor killed the leaf itself — it exceeded the hard per-leaf cap `ATMOFAB_LEAF_TIMEOUT_SECONDS` (default 7200s) without returning, and its whole process group was signalled (`leaf_exit` is typically `-15` / `-9`). It is **not** retried (a re-launch stakes another full cap on a leaf that already wedged), so it terminalizes on the first occurrence. Read what the leaf managed to write in `workspace/orchestrations/<orchestration_id>/agents/<agent_run_id>/dialogs/`, and expect it to be **stderr-heavy**: a `claude` leaf emits its result text only when the turn completes, so `leaf.stdout.log` is usually empty for a killed leaf, and on `codex` the evidence is `leaf.stdout.jsonl` (the JSONL event stream) rather than `leaf.stdout.log`. The conductor's own marker line `[conductor] leaf_timeout: …` is the last line of the captured stderr. `--resume` is the recovery: the tag terminalizes under the `leaf_transport_error:` prefix, so it inherits the substep-granular resume described below **when that resume's own preconditions hold** (a `verify` death in Compile/Generate on an unmoved repo revision) — a `generate.generate` wedge, the shape of the incident this cap was built for, re-runs the phase. A `leaf_timeout` whose `substep` is `diagnose` is the failure **diagnostician**, the one spawn site with no child `agent_run_id`: its output is `dialogs/diagnose.<phase>.stdout.log` / `.stderr.log` / `.stdout.jsonl` under the ORCHESTRATION `agent_run_id`, and the phase terminalizes as `<phase>_diagnose_unparsable` (an unreadable diagnosis is conservatively terminal), not as `leaf_transport_error`. A `[conductor] leaf_stderr_capture_truncated:` / `[conductor] leaf_stdout_capture_truncated:` line means the capture reached its budget (`LEAF_STDERR_CAPTURE_MAX_CHARS` / `LEAF_RAW_STDOUT_CAPTURE_MAX_CHARS`) while the leaf went on writing, and a `[conductor] leaf_stdout_record_truncated:` line means one oversized JSONL record was clipped and the read resumed at the next newline — that record's surviving bytes follow the marker on the SAME line, so filtering `[conductor]` lines out of `leaf.stdout.jsonl` discards them along with the notice. A `[conductor] leaf_stderr_capture_tail:` line marks where a truncated `stderr` resumes at its END — the head and the tail are both kept, and the lines after that marker are the last the leaf wrote, which is where its terminal cause is. On `codex` the structured terminal events (`error` / `turn.failed`) are appended after that, bounded by `LEAF_FAILURE_EVENTS_MAX` and marked `[conductor] leaf_failure_events_truncated:` when a leaf failed more times than that. These are all bounded-capture notices, not verdicts: the leaf's own outcome is elsewhere in the capture. A `[conductor] leaf_stream_abandoned:` line in a captured `stderr` is likewise a truncation notice, not a verdict: the leaf is gone — it exited on its own, or was killed at the cap — but a descendant it leaked still held its pipes, so the capture above the line is incomplete. It appears on a killed leaf and on a leaf that PASSED alike; read the `leaf_timeout` marker (or its absence) for which. Set `ATMOFAB_LEAF_TIMEOUT_SECONDS` higher for a run whose leaves legitimately need longer (up to 2 147 483s), or to `0` to disable the cap (a wedge then blocks the run indefinitely, the behavior the cap replaced); a value the parser cannot make sense of — non-numeric, or carrying a leading `-` — falls back to the default rather than disabling it.
  - **no tag**: the leaf died of a cause the conductor cannot classify (a crash / an out-of-memory kill / a hook denial). Read `workspace/orchestrations/<orchestration_id>/agents/<agent_run_id>/dialogs/leaf.stdout.log` before resuming — the failure is deterministic and will repeat. On a `claude` run that file holds the CLI's `--output-format json` result envelope (issue #47): the model's reply is the `result` string inside it, and the leaf's cost is in its `usage` / `modelUsage` / `total_cost_usd`. An envelope whose `subtype` is one of the `error_*` variants carries no `result` — its message is the `errors` array. On a `codex` run that file holds only the extracted final `agent_message`, so it is **empty** for every leaf whose turn failed (whether or not it got as far as producing one): read `dialogs/leaf.stdout.jsonl` (the leaf's whole JSONL event stream — tool calls, item errors, the terminal event) instead.

  The `dialogs/` of every retried attempt (including the dead ones, which are tombstoned in `reopen/superseded_runs.json`) are retained for exactly this diagnosis.

  **Substep-granular resume on a `leaf_transport_error` (automatic, no flag).** Whatever the tag, when the phase that died is `Compile` or `Generate` **and the substep that died is `verify`** (structurally, the only place a transport death can strike after the producer has passed), a `--resume` does **not** re-run the whole phase from its billed LLM producer: `init --resume-from-checkpoint` records `orchestration_meta.resume_directive` (`source=leaf_transport_substep_resume`) naming the surviving producer artifact, and the conductor preseats it and relaunches only the deterministic mids + `verify`. You will see `transport_substep_resume` / `substep_resumed` on the event stream. It is **default-on** and needs no flag (a pure optimization). Because nothing is persisted at death time (the directive is derived from `agent_runs.jsonl` + the reservation on resume), it is not gated on anything the failed run recorded — but it is NOT unconditionally retroactive: the revision-equality gate means a run that fail_closed before this feature existed only resumes if you are still on its exact checkout (obtaining this code advances/dirties `HEAD`, so such a run declines to a full re-run). It fires for a transport failure resumed on the same checkout, and declines (`transport_resume_declined`, full-phase re-run — exactly the prior behavior) whenever the producer artifact is gone, the dead substep is not `verify`, the phase is `Validate`/`Build`, or the repo revision moved since the run started (`orchestration_meta.repo_revision` ≠ current `HEAD`+dirty — the surviving artifact would not match the source now checked out; commit any fix **before** resuming if you intend the phase to rebuild instead of reuse). This is the manual-`--resume` complement to the in-run `--wait-usage-reset` wait above (which only helps while the run is still alive). Canonical: `docs/ORCHESTRATION.md` item 51.
- Because a `Build` failure is a deterministic process, do not internally retry Build but go back to `Generate` (this table §3). The Build step remains "incomplete" on the checkpoint and is re-run from Generate on resume.

## The operator-private root (`~/.atmofab`) {#operator-private-root}

Three things live outside the repository, under the operator's own home. All three are
per-operator and per-host; none of them is ever committed. This is the inventory of what
the CODE writes there. An `ls` on a long-lived host may show more: `cold_start_locks/` and `escape.txt` have
been seen in this operator's root, and neither has a producer anywhere in this
repository's history (`git log --all -S` finds none), so they are residue from something
outside it or from a version that predates the history. Nothing writes them, nothing
reads them, and nothing cleans them up; they are named here only so their presence is not
read as a fourth thing the workflow maintains.

| Path | Written by | Read by | Retention |
|---|---|---|---|
| `~/.atmofab/operator_tokens/<orchestration_id>.txt` (relocatable with `ATMOFAB_OPERATOR_TOKENS_ROOT`) | `init_orchestration`, once per run | the operator, when dismissing an `unauthorized_write_violation` (§dismiss) | kept; a run's token stays valid across `--resume` |
| `~/.atmofab/start_claims/` (relocatable with `ATMOFAB_START_CLAIM_ROOT`) | `run_workflow.py`'s cold-start guard | itself | advisory `flock` files; the OS releases the lock when the driver dies |
| `~/.atmofab/homes/<orchestration_id>/{claude,codex}/` (relocatable with `ATMOFAB_WORKFLOW_HOMES_ROOT`) | the leaf launcher, per orchestration and backend | `--resume` (warm session lookup), `audit_orchestration.py`, the three audit skills | **indefinite. Nothing deletes these automatically. See below.** |

An agent cannot read any of it, and it is outside every read manifest so the Read tool
cannot name it either. For Bash on both backends the block comes from one of two policies,
and which one tells the operator WHICH tree was touched: `homes/` and everything under it
is a protected root of its own and answers `forbid_backend_credential_direct_read` (with
the leaf's OWN home naming itself, since the roots sort longest-path-first), while
`operator_tokens/` and `start_claims/` answer `forbid_operator_secret_direct_read`.
`operator_tokens/` is a protected root of its own too (issue #132), which is what keeps
that answer true wherever the store is: it is a LONGER path than `~/.atmofab`, so it wins
the same longest-first sort, and the policy branch treats the two as one class rather than
letting the token store fall to the credential message. `start_claims/` has no entry of its
own and is attributed to `~/.atmofab` above it — the files are 0-byte advisory locks, so
they are covered by the root rather than protected in their own right. Both are refusals, and neither has a
remedy other than dropping the read: these paths are outside every manifest and no agent
task needs them. (The `#hook-recovery` table covers both policy ids in ONE row, whose
description predates this section and names only the operator tokens for `~/.atmofab`;
this section is canonical for what lives under that root.) **`chmod 700 ~/.atmofab` is recommended** on a
shared host. The workflow creates the directory best-effort and does not force its mode,
because a root that predates this recommendation would otherwise fail every launch;
everything it creates BELOW that level is 0700 and is re-checked for ownership and
symlinks on each launch.

`ATMOFAB_WORKFLOW_HOMES_ROOT` relocates the homes tree, `ATMOFAB_OPERATOR_TOKENS_ROOT` the
token store, and `ATMOFAB_START_CLAIM_ROOT` the claims tree. All three exist for tests and
for an operator with a specific reason; none is needed for an ordinary run. The ROOT itself
is deliberately not relocatable — it is the Bash read guard's anchor — and each name moves
exactly one subtree.

The homes one and the TOKEN one have the same **four preconditions, and none of them is
the one you would guess** (the claims root has none of them: an unavailable claim
degrades to "proceed" by design, so there is nothing to fail closed about — see the
paragraph after the list for what that leaves):

- the value must be an **absolute path**. A relative one does not stay relative — it is
  resolved against whichever process asks, and the conductor that creates a home and the
  hook process that forbids reading it need not share a working directory, so the two
  would guard and create different trees;
- **it must have no containment relationship with the checkout at all** — neither inside
  it nor around it. The two halves are refused for different reasons.

  **INSIDE** is the one with a leaf on the other side of it. The Bash read guard follows
  the resolver wherever it goes, but the **Read tool is a different layer**: every
  agentic leaf's `allowed_read_roots` contains `docs/` and `spec/` unconditionally, and
  that manifest does not consult the protected roots at all. A token store at
  `<repo>/spec/tokens` is therefore readable by every leaf, and a leaf holding the
  dismiss-violation token can approve its own `unauthorized_write_violation`; a homes
  root there exposes every earlier leaf's transcript the same way.

  **AROUND** is refused because nothing works there. All three roots are exempt from the
  containment rule that would otherwise drop a root overlapping the checkout — that
  exemption is what keeps the guard when one of them does — so a root ABOVE the checkout
  makes every in-repo path a path under a protected root, and the guard matches the
  command's TOKENS rather than only its read targets. Measured: with either relocatable
  root set to the checkout's parent, `cat README.md`, `ls`, `python3 tools/x.py` and even
  `echo hi` are all blocked. An earlier version of this bullet called that "every
  recursive in-repo read", which understated it by a wide margin. (It also said the homes
  root was exempt from the drop before it was; that was the defect, and it is closed.)

  Both halves resolve symlinks, so the path cannot be laundered through one — but the two
  ROOTS are refused at different **moments**, and the difference decides where you look
  when it bites. The token-store refusal runs inside `init_orchestration`, before that
  command writes anything. The homes-root one runs when a leaf is LAUNCHED, which is the
  first time a home is created — so a bad `ATMOFAB_WORKFLOW_HOMES_ROOT` lets `init`
  finish, writes `running` metadata, and fails at the first leaf. If a run dies there,
  check the export before you go looking at the launch;
- the directory it names is created if absent, but its **parent must exist**, so a typo
  does not silently build a tree somewhere nobody looks. (That is also why the default
  `~/.atmofab/homes` may be created from nothing while an override may not.);
- **if the path already exists it must be a directory.** A name that is a regular file
  or a broken symlink passes every check above, and the creation call then fails after
  the orchestration directory and its `running` metadata are on disk — a run that looks
  started and has no token, whose violations you cannot dismiss.

One more thing about a relocated **token store**, which the claims and homes trees do not
share: **`dismiss-violation` must be typed in a shell with the same
`ATMOFAB_OPERATOR_TOKENS_ROOT` as the shell that started the run.** The store is
per-environment and the command is typed by hand, so an export present in one terminal
and absent in another sends the writer and the reader to two different directories. The
refusal says which state the current shell is in, and says so before it suggests
re-running init — following that first would mint a new token against a live run.

**`ATMOFAB_START_CLAIM_ROOT` is checked by nothing**, and that is the price of the claim
being advisory: a claim that cannot be taken yields "proceed" rather than failing, so
there is no refusal to hang the checks on. Pointing it inside the checkout is therefore
possible and is a bad idea for a different reason from the other two — a 0-byte lock file
created under the repository while a leaf is running lands in that leaf's terminal
write-diff and is misattributed as an unauthorized write, which is the reason the claims
live outside the repository at all.

A relocated store is an entry in `protected_host_read_roots` in its own right, returns the
same `forbid_operator_secret_direct_read`, and — since `~/.atmofab/` is no longer where it
is — its block message names the store's path and `ATMOFAB_OPERATOR_TOKENS_ROOT`.

One measured LIMIT, because "fully guarded" would overstate it: the guard's fail-closed
fallback for a command it cannot resolve (`$(…)`, backticks) fires when a token also
spells a protected root's own path component — `.atmofab`, `.claude`, `.codex`. A
relocated store has no such distinctive component, so
`cat $(printenv ATMOFAB_OPERATOR_TOKENS_ROOT)/<oid>.txt` is ALLOWED by the hook where the
default spelling is blocked. It reaches nothing: the sandbox binds `/usr /bin /sbin /lib
/lib64 /etc`, the checkout and the backend homes and nothing else, so a store outside
those is not in the leaf's mount namespace and the read fails there instead. The sandbox
is what closes it, not this guard.

The MODE is not a precondition: a root you create with a plain `mkdir` is tightened to
0700 on first use rather than refused, as is a mode that later drifts (a backup restored
without permissions) — and since the tightening also runs on a warm reuse, a drift is
corrected by the next launch of the same orchestration rather than only by a new one.
What is refused is a symlink, a non-directory, a directory owned by another user, and a
filesystem on which the tightening does not take.

### Why the homes are kept, and how to remove one

A backend home holds the leaf's ONLY record of its own turn — the claude transcript, the
codex rollout. The artifacts under `workspace/orchestrations/<id>/` record what the HOST
observed; nothing else records what the leaf did. Those homes used to be created under
`/tmp`, where a host restart took them, and a billed run became unauditable the moment
the machine rebooted. They are now durable, and the price of that is that they accumulate.

There is deliberately **no automatic deletion**: any automatic rule has to choose
between deleting evidence someone may still want and keeping everything, and only the
second cannot silently destroy the thing the directory exists for. What is written down
instead is the rule in this section — keep indefinitely, delete only by hand — plus the
tool that carries it out.

This is **not** the same answer `TODO.md` reaches for `workspace/`, and the difference is
worth one sentence because two earlier drafts of this paragraph claimed it was. There the
repository declines to legislate at all: `workspace/` is the gate's execution workspace
and how an operator uses it is their business. Here the directory is created by this
code, holds the only record of what a leaf did, and is one an operator never opens — so
it gets a written rule.

Removing one is the operator's decision, made with:

```bash
# Report only — the default. Never deletes.
python3 tools/prune_workflow_homes.py --all

# Remove the homes of runs that are over.
python3 tools/prune_workflow_homes.py --all --delete
python3 tools/prune_workflow_homes.py --orchestration-id <orchestration_id> --delete
```

**What deleting costs**, so it is a decision rather than a discovery:

- `--resume` for that orchestration degrades to a COLD launch. Warm resume finds a leaf's
  session inside the home; a re-created one has none;
- the run stops being auditable. `skills/workflow-audit-claude`, `workflow-audit-codex`
  and `workflow-timing-audit` all read from the home.

The tool refuses FIVE things, and only one of them has an override:

- an entry that is not shaped like a backend home — one carrying a subdirectory whose
  name is not a declared backend, or one with neither a backend subdirectory nor an
  `owner.json` naming that orchestration — `refused:not_a_backend_home`. This is what
  stops `--homes-root` being pointed at an ordinary directory and emptying it, and it has
  no override on purpose. An entry whose backend directory is already gone but whose
  marker remains is NOT refused: the marker is proof enough that the workflow made it, so
  a partial delete can still be cleaned up by the only tool allowed to clean it;
- an orchestration id that is not a plain `[A-Za-z0-9_-]` token —
  `refused:invalid_orchestration_id`. A separator would otherwise reach INSIDE an entry,
  past the containment assert and past the owner check;

- an entry that is not a real directory owned by this user;
- an entry whose `owner.json` is missing or inconsistent — `refused:unverifiable_owner`.
  The marker names the checkout that owns the run; without it, the home may equally
  belong to a LIVE run in a checkout this invocation cannot see. `--allow-unverifiable`
  releases this one, and only this one. An owner checkout that has been moved or deleted
  lands here too, since "did that run finish" is then unanswerable;
- an orchestration whose status is not terminal — `refused:orchestration_not_terminal`,
  with **no override**: deleting a home under a live leaf takes that leaf's session with
  it. The status is re-read under the orchestration's own metadata lock, so a concurrent
  `--resume` cannot be caught mid-transition.

One more verdict exists that is not a refusal to try: `refused:delete_failed:<error>`,
reported when the removal itself failed (a busy mount, a permission change under the
tool). It counts as "not done" for the exit code.

An orchestration named explicitly on the command line and then refused — or attempted and
failed — makes the tool exit 2; a refusal during `--all` does not, because there the
refusals are the report.

**One failure mode worth recognising, and the two causes need different commands.** If a
launch reports `isolated <backend> home already exists but is not recorded in this
orchestration's metadata`, a previous run created the directory and died before recording
it, or its metadata was lost. The home is never adopted — that would hand a new
orchestration an earlier run's transcripts — so inspect it and then remove it. Which
command works depends on which cause it was, and the difference is not cosmetic:

- **the metadata is gone** (the checkout was removed, or the orchestration directory
  was): the entry is `refused:unverifiable_owner`, and `--allow-unverifiable --delete`
  is the command;
- **the run crashed between the `mkdir` and the metadata write**: `owner.json` is
  written immediately after the `mkdir`, so the marker is present and valid and the
  entry is NOT unverifiable — `--allow-unverifiable` does nothing for it. The recorded
  status is whatever the dead run left, which for a crash is `running`, so the entry is
  `refused:orchestration_not_terminal` and that refusal has no override. **Terminalize
  the orchestration first** — the `set-status` command block under
  §"[Incomplete launch recovery](#launch-incomplete-recovery)", which records the same
  status/reason pair the resume gate's automatic terminalization would — then prune it
  normally. (§3-1 was cited here first and is the wrong section. It has operator
  commands — several `run_workflow.py --resume` invocations — but no TERMINALIZING one:
  the terminalization it describes is the automatic one a `--resume` performs when the
  resume gate probes the recorded driver as dead.)

For the file-pinned substeps (`compile.verify`→`ir_meta.json`, `generate.verify`→`source_meta.json`, `validate.judge`→`semantic_review.json`) the pin is derived from the launch request's `source_id` / `run_id`; a missing or malformed value collapses the pin to `[]` and fails closed here — supply the correct id |
| leaf-internal `EROFS` / `EBUSY` write error on a `verify` / `judge` leaf | the leaf tried to write outside its single file pin (e.g. `generate.verify` rewriting a `src/*.f90`, `validate.judge` touching the same-dir `verdict.json`, or `run_linter` side-writing `command_log.jsonl`) | this is by design: those substeps' `write_roots` is one file pin, so `bwrap` physically refuses (`EROFS`) any other write — it surfaces as an ordinary leaf-internal failure (like a hook block), **not** an `unauthorized_write_violation` → `fail_closed`, so the `reopen-phase` invalid-log recovery above is not needed. Fix the leaf's behavior (verify re-authors only `source_meta.json` / requests regeneration under a new `source_id`; judge authors only `semantic_review.json`) and re-run |

A refusal from the build-runtime MCP server is not a hook block and is not in the table above. The one an operator meets outside a run: with `ATMOFAB_ORCHESTRATION_ID` exported in the shell, or `ATMOFAB_WORKFLOW_MODE` exported with a non-empty value other than `0`, the server treats itself as running under the workflow and refuses `compile_project` / `run_program` / `run_quality_checks` / `run_linter` / `run_syntax_check` calls that carry no `orchestration_id` — which is what a manual `mcp_servers/mcp_call.py` invocation or a test run does. Clear the variables for that command (`env -u ATMOFAB_WORKFLOW_MODE -u ATMOFAB_ORCHESTRATION_ID …`) rather than passing an orchestration's credentials by hand.

## dismiss of unauthorized_write_violation {#dismiss-violation-recovery}

When `record-agent-run` fails with `terminal run has unauthorized write paths: ...`, the operator can approve (dismiss) a benign violation and retry by the following procedure.

**Typical causes (benign)**

- `tools/__pycache__/*.pyc` — git-ignored Python bytecode (mostly removed by the snapshot ignore of Fix 1b, but insurance for when existing pyc remains)
- an audit log generated by the MCP server was not included in `manifest_integrity_protected_logs`

**Recovery procedure**

1. Check the violation's unauthorized_paths.
   ```
   cat workspace/orchestrations/<orch_id>/violations/<arid>.unauthorized_write_violation.json
   ```
2. Dismiss only the benign paths (`--paths` is matched as a subset of the violation's `unauthorized_paths`).
   ```bash
   python3 tools/orchestration_runtime.py dismiss-violation \
     --repo-root . \
     --orchestration-id <orch_id> \
     --agent-run-id <arid> \
     --dismiss-reason "tools/__pycache__ is gitignored Python bytecode and harmless" \
     --operator-token "$(cat ~/.atmofab/operator_tokens/<orch_id>.txt)" \
     --paths tools/__pycache__/orchestration_runtime.cpython-313.pyc
   ```
   The operator token is auto-generated into `~/.atmofab/operator_tokens/<orch_id>.txt` at orchestration init. Because it is not under `workspace/`, the agent cannot read it, and only the operator can reference it. If the run was started in a shell with `ATMOFAB_OPERATOR_TOKENS_ROOT` set, read the token from `$ATMOFAB_OPERATOR_TOKENS_ROOT/<orch_id>.txt` and run this command with that same value exported — see §"The operator-private root (`~/.atmofab`)".
3. Re-run `record-agent-run` with the same `agent_run_id`. If the detected unauthorized_paths are a subset of `dismissed_paths` (= dismissed_paths contains unauthorized_paths), the terminal validation passes. When only some of the violation paths have been dismissed, the re-run fails again, so check whether any non-dismissed violation paths remain.

**Notes**

- dismiss-violation is a safety gate for recording the operator's explicit approval, and must not be called by an automation script.
- To additionally dismiss a new path later, re-run the same command (`dismissed_paths` is overwritten).
- When, for a dismissed violation, a subsequent re-detection includes a **new unauthorized path not covered by the dismissal**, the violation file is regenerated and the terminal validation fails again. At this time, the previous operator approval is not lost but is preserved in the history as `prior_dismissals[]` (`dismissed_at` / `dismiss_reason` / `dismissed_paths` / `superseded_at`) (ensuring the continuity of the audit trail).
- If Fix 1a (the `PYTHONDONTWRITEBYTECODE=1` environment variable) is applied, the `.pyc` violation itself does not occur, so this procedure is usually unnecessary.

## duplicate agent_run_id recovery {#duplicate-agent_run_id-recovery}

Invoking `record-agent-run` twice with the **same `agent_run_id`** raises `ValueError: duplicate agent_run_id: <id>`. It is designed as a non-idempotent hard error, and there is no path to later update/upsert the same `agent_run_id`.

**Typical causes**

- attempted a retry for a child agent_run already appended to `agent_runs.jsonl`
- tried to re-append the orchestration agent's own entry at terminal (the orchestration's termination is canonically via `set-status`, and there is no path to call `record-agent-run` a second time). **When `set-status` writes a terminal status, it automatically terminates the orchestration row (`status:running`) of `agent_runs.jsonl` in-place**, so there is no need to manually append/update the orchestration row (re-appending via `record-agent-run` causes this error).

**Recovery procedure**

1. Number a new `agent_run_id` with `python3 tools/new_agent_run_id.py`.
2. Newly reserve `ir_id` / `pipeline_id` with `python3 tools/orchestration_runtime.py reserve-phase-root --orchestration-id <oid> --agent-run-id <new_arid> --node-key <node_key> --step <step>` (when the old `agent_run_id` already reserved, confirm with the operator whether the reservation can be reused).
3. Re-run the legitimate sequence `record-launch` → leaf launch → `finalize-child` (the single call that performs `record-child-return` → `deactivate-child` → `record-reply` → `record-agent-run`) with the new `agent_run_id`. Under conductor orchestration this sequence is normally re-driven by `--resume` (§3-1); the manual subcommand path below remains available for edge recovery.
4. To terminate the orchestration itself, call `set-status --status fail_closed --reason-code <code> --reason-detail <detail>`. Because `set-status` automatically terminates the orchestration row of `agent_runs.jsonl` in-place, do not update it manually.

The detailed CLI conventions use [docs/CLI_REFERENCE.md#record-agent-run](CLI_REFERENCE.md#record-agent-run) as the canonical source.

## Substep timeout recovery {#substep-timeout-recovery}

**Scope**: manual finalization of a leaf that produced no terminal entry **while the driver is still alive** — an orchestration driven by hand, or a leaf the conductor could not finalize itself. A leaf that merely **wedges** under a live conductor no longer needs this procedure: the conductor enforces a hard per-leaf cap (`ATMOFAB_LEAF_TIMEOUT_SECONDS`, default 7200s), kills the leaf's process group, emits `leaf_timeout`, and terminalizes the attempt in band through the ordinary `finalize-child` chain (canonical: `docs/ORCHESTRATION.md` "leaf transient retry"). A leaf orphaned because the **driver itself died** is a different case again — see §[Incomplete launch recovery](#launch-incomplete-recovery) and the `dead` liveness verdict in §3-1, which recover it through `--resume` rather than by hand.

When a child leaf is cut off midway by an API stream idle timeout, the orchestration agent calls `record-timeout` to finalize the terminal entry. **An ad-hoc script must not be written to `workspace/tmp/`.**

**Premise**: before calling `record-timeout`, always run the following in order.

1. `record-child-return --agent-run-id <arid> --return-token <token>`: record the evidence that the orchestration agent actually observed the leaf return.
2. `deactivate-child --child-run-id <arid>`: release the active marker after confirming the ack and re-verifying the token match.
3. `record-timeout --agent-run-id <arid> --reason ...`: record the terminal entry.

```bash
# pass the return-token via the two-step method (steps 6a/6b inline below).
# step 6a: print the token with a single cat (it matches the allowlist
#          `Bash(cat workspace/orchestrations/*)` and requires no approval). Do not use the
#          $(cat ...) command-substitution form because the Bash tool's static analysis
#          rejects it with `Contains shell syntax ... cannot be statically analyzed`.
#          Do not use the VAR=$(cat ...) 2-step shell-var form either, as it breaks
#          the allowlist match.
cat workspace/orchestrations/<orchestration_id>/launches/<child_agent_run_id>.parent_return_token

# step 6b: embed the token printed above as a literal string.
python3 tools/orchestration_runtime.py record-child-return \
  --repo-root . \
  --orchestration-id <orchestration_id> \
  --agent-run-id <child_agent_run_id> \
  --return-token "<literal token>"

python3 tools/orchestration_runtime.py deactivate-child \
  --repo-root . \
  --orchestration-id <orchestration_id> \
  --child-run-id <child_agent_run_id>

python3 tools/orchestration_runtime.py record-timeout \
  --repo-root . \
  --orchestration-id <orchestration_id> \
  --agent-run-id <child_agent_run_id> \
  --reason "API stream idle timeout after 600s"
```

After the calls, the orchestration agent subsequently calls `set-status --status fail_closed --reason-code <code> --reason-detail <detail>` to terminate the orchestration itself.

### Escape hatch for a wedged child

Only when `record-child-return` cannot be written because the leaf process is in an abnormal state where it can observe no return at all, the marker check can be bypassed with `record-timeout --force-reason "<operator override content>"`. Prioritize the normal flow, and use it as a last resort.

## Incomplete launch recovery (dangling active_child window) {#launch-incomplete-recovery}

Distinct from the substep-timeout case above (where the conductor is still alive and finalizes the child itself): here the **conductor process itself dies** while a leaf launch is mid-flight. `record-launch` opened the active_child window — the backend-neutral per-arid marker `active_children/<arid>.txt` is written for **all** backends (Claude additionally writes the sequential pointer `active_child_agent_run_id.txt`) — but the leaf was interrupted before returning, so there is no `child_returns/<arid>.txt` and no terminal `agent_runs.jsonl` row for `<arid>`.

Whether the orchestration is left non-terminal (`running`) depends on how the driver died. `SIGTERM` / `Ctrl-C` are handled and terminalize the run as `cancel` / `driver_interrupted` (§3-1 "Interruption of the driver"), so those cases normally arrive here already terminal — best-effort, though: the terminalization is skipped when the signal lands before `init` commits the orchestration, and a failed `set-status` is swallowed so the interrupt still propagates, either of which also leaves `running`. An unexpected driver exception is handled too, and terminalizes as `fail` / `driver_exception` under the same best-effort guards (§3-1). `SIGKILL`, an OOM kill, or the loss of the host shell cannot be handled and do leave `running` — that is the case this section covers.

There is **no automatic launch-incident capture**; recovery is the `--resume` reconciliation below. The dangling launch can be diagnosed on demand:

```bash
python3 tools/audit_orchestration.py --orchestration-id <orchestration_id>
# → "## Dangling launch (active_child window)" section: which child, when launched,
#   last activity, dead-air seconds, the abort marker, and any final API error.
#
# Read the section's verdict, not its absence. "Dangling-launch detection FAILED
# (...) — ... UNKNOWN" means the window's state was NOT measured; do not read it as
# "no window" (before issue #130 that run printed the clean negative instead). Such a
# run exits 2 and lists the cause under "## ⚠ diagnostic failures", the same exit code
# a data-integrity warning gives.
#
# Run it FROM THE CHECKOUT, or pass --repo-root: the default is the current directory,
# so from anywhere else the command above audits an orchestration that is not there.
# That prints "## ⚠ orchestration not found" and exits 2 (it used to report a full
# audit of zeroes ending in the clean negative, at exit 0) — a mistyped or stale
# --orchestration-id lands in the same place. This route reports UNKNOWN WITHOUT a
# "## ⚠ diagnostic failures" section: nothing raised, there was simply nothing to read.
```

`audit_orchestration.py` correlates the dangling leaf's OWN transcript on demand: the conductor pins each leaf's Claude session id to its `agent_run_id`, so the transcript is directly addressable as `<projects-root>/<slug>/<arid>.jsonl` (no host session needed). Since issue #63 that root is the orchestration's PRIVATE home — read `orchestration_meta.json#claude_workflow_home`, or let the tooling resolve it through `tools/hooks/common.py::claude_leaf_projects_roots`, which is the canonical resolver every consumer shares. The operator's `~/.claude/projects` is still searched as well, so a run recorded before that move stays auditable. Since issue #64 that home is DURABLE — `~/.atmofab/homes/<orchestration_id>/claude` — so this correlation keeps working after a host restart, which is the reason the move was made; see §"The operator-private root (`~/.atmofab`)". This recovers the child's last activity, dead-air interval, and final API error — distinguishing a retryable 529 from other failures — and degrades to the in-repo facts when that home has been cleaned or rotated. Older runs may additionally carry persisted `launch_incident.runtime.*.json` snapshots, which are surfaced too. The transcript line names the projects root the hit came from — ``(matched via `session_id` under `<root>`)``. Read it as follows, and note the two directions are not symmetric. A hit under `~/.atmofab/homes/<orchestration_id>/claude/projects` is an AGENTIC leaf, decisively: only that shape is prepared a private home (issue #63). A hit under the operator's `~/.claude/projects` is AMBIGUOUS between two live cases — a pure CLAUDE-CLI leaf on a current run, which is prepared no private home at all and so launches with no `CLAUDE_CONFIG_DIR` (a pure leaf on an HTTP provider launches no CLI and writes no transcript anywhere, so it never produces a hit at all) (`tools/orchestration_runtime.py` gates the preparation on `not is_pure`; `tools/workflow_conductor.py` §`_claude_session_resumable` records the consequence as measured), and an agentic run recorded before issue #63. Which of those it is comes from the launch record — `workspace/orchestrations/<orchestration_id>/launches/<agent_run_id>.request.json`, where `leaf_mode: "pure"` settles it — and NOT from `orchestration_meta.json#claude_workflow_home`, which is set as soon as any agentic Claude leaf launched and so says nothing about this leaf. The root is also a prefix of the transcript path printed beside it, so what it adds to the RENDERED line is that reading rather than new information; what is new in the record is `match_method` itself and, under `--format json`, the `matched_projects_root` key. A snapshot's line carries the older `tool_use_id` and no root.

Recovery is the normal `python3 tools/run_workflow.py --resume --orchestration-id <orchestration_id>` (§3-1): the completed substeps are skipped and the dangling substep is re-launched. The reconciliations below are scoped to the terminal→`running` reset, so the orchestration must be terminal first. That transition is automatic when the resume gate probes the recorded driver as `dead` (§3-1 "Driver liveness on a non-terminal target"): the run is terminalized as `fail` / `driver_crashed` and the reset follows in the same invocation. It stays manual for a `unknown` liveness verdict — a run that predates the `driver` block, one whose meta was written on another host, or a non-Linux host — where the operator terminalizes explicitly before resuming:

```bash
# Same status/reason pair the automatic path records, so the two are indistinguishable
# to a later audit. Use cancel / driver_interrupted only for a run you stopped yourself.
python3 tools/orchestration_runtime.py set-status --repo-root . \
  --orchestration-id <orchestration_id> --status fail \
  --reason-code driver_crashed --reason-detail "<what happened>"
```

As part of the terminal→`running` reset (`enable_checkpoint_resume`), `--resume` reconciles the artifacts the dead host left behind for the abandoned launch:

1. **Stale active_child markers** (`active_child_agent_run_id.txt` / `active_children/<arid>.txt`, with no `deactivate-child` having run) are cleared (logged as `resume_cleared_stale_active_child`) — without this the resumed agent's `record-launch` would be rejected by the Claude-backend sequential-child check while the stale pointer persists.
2. **Orphan `agent_graph.json` edges** — `record_launch` writes the parent→child edge before the marker, so the abandoned child has a graph edge but never a terminal `agent_runs.jsonl` row. Such edges are pruned (logged as `resume_pruned_orphan_graph_edges`) — without this the resumed run's eventual `set-status pass` is rejected by `_validate_orchestration_completion_for_pass` with `agent_graph edge child_agent_run_id missing from agent_runs.jsonl`. Pruning is scoped to genuine abandonment on both sides. An edge is removed only when its child (a) **was** genuinely launched — proven by a durable `launches/<arid>.request.json` (the same `is_owner_via_launch` signal) — **and** (b) has **no** evidence of reaching/returning from a run: it is in none of `agent_runs.jsonl`, any `step_result.json` reference, `agent_runs_invalid.jsonl`, or a `child_returns/<arid>.txt` ack. So an arbitrarily-corrupted edge whose child was never launched (no request artifact) is **kept** and still rejected by validation; and a child that completed (step_result-referenced) but lost its run row, one diverted to `agent_runs_invalid.jsonl` (sandbox / session-id failure), or one that already returned (`child_returns` ack) all keep their edge too. Only a launch interrupted **before** the leaf returned — launched, but no ack and no run/invalid record — is pruned, which is exactly the dangling-launch case. The launch artifacts (`launches/<arid>.*`, the incident snapshot) are kept for forensics; only the spurious edge is removed.

3. **Stale `child_running` phase state** — `record_launch` sets the node/step to `child_running`, which the phase gates (`apply-patch`, the MCP phase gate, `run-gate`) treat as authorization for child work. The abandoned launch leaves it there even after the marker is cleared, so any such node/step is reset to `not_started` (logged as `resume_reset_stale_child_running`) to drop the dead child's lingering phase authority; the re-launch transitions it back to `child_running` for the real new child.

All three reconciliations are scoped to the terminal-reset path, so a genuinely-running orchestration's live markers / edges / phase state are never touched.

**Stranded build `step_result` after a resume reset — backfill, do not relaunch.** Reconciliation 3 resets the build node/step out of `child_finished` back to `not_started`. If a prior terminal **build** step agent had reached `child_finished` but its `step_result.json` was never written (e.g. the original run captured the failure only inside a later retry's `retry_decisions`, or the host died between `child_finished` and `write-step-result`), the reset removes the `child_finished` state that the normal `write-step-result` path requires. Do **not** launch a fresh build child just to re-reach `child_finished` and write the missing result: each new build step agent is itself something `_validate_orchestration_completion_for_pass` then requires a `step_result.json` for, so the count of missing results never decreases (net-zero) and the orchestration deadlocks (it cannot reach `pass`). Instead, fill the gap with `write-step-result --backfill`, which writes the `step_result.json` for the already-terminal build agent **without** consuming a `child_finished` transition or launching a new agent (gap-fill only, recorded run must be a terminal step agent for the same node/step, and `--result-json` `status` must equal the recorded run status — see `docs/CLI_REFERENCE.md` §write-step-result `--backfill`). Each backfill is net-negative on the missing-result count, so the completion invariant can reach zero. The recurrence root is itself blocked at `record-launch` time: a build cannot relaunch while a prior terminal build step agent for the node still lacks its `step_result.json`.
