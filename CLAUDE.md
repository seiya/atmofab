@AGENTS.md

The shared / cross-backend conventions are imported from `AGENTS.md` above. This file adds only Claude Code-specific notes that every Claude sub-agent needs.

> **This file is DEV-ONLY: a workflow leaf does not read it.** `tools/workflow_conductor.py` launches each `step agent` / `substep agent` as a leaf (`claude -p`) with `CLAUDE_CONFIG_DIR=<private home> --setting-sources user` (issue #63), and that closes CLAUDE.md / AGENTS.md auto-injection along with the settings layers — measured on CLI 2.1.235 by capturing the leaf's own request. A leaf's contract is [docs/AGENT_CONTRACT.md](docs/AGENT_CONTRACT.md) plus its phase `SKILL`, delivered through the launch prompt; nothing here reaches it. The dev skills under `.claude/skills/` do not reach it either, measured on the same CLI with the capture harness: under `--setting-sources user` the leaf loads `project: 0` skills and its request body contains zero occurrences of either skill name, while the control — the same launch with `--setting-sources project` — lists both in the roster, so the probe can see skills when they are there. Seeding the private home's trust record for the project does not change the result, and the production launch closes it a second time anyway by passing `--disable-slash-commands`, which drops the invoking tool altogether. The limits of that measurement: the launch was assembled by hand from the flags that decide this question rather than driven through `_prepare_claude_workflow_home`, the project was a scratch checkout rather than this one, and it covers the AGENTIC leaf. A `pure` leaf passes `--disable-slash-commands` too, so the second closure applies to it unmeasured; what it does not pass is `--setting-sources`, because `--safe-mode` already refuses every settings layer. The one rule that used to arrive this way and has no second home for a leaf — `AGENTS.md` §Backend boundary rules — is not actionable by a leaf, because a leaf cannot write a `neutral core` file. `_write_roots_for_launch` is the sole producer of write authority, and every root it returns is either under `workspace/orchestrations/<id>/`, `<ir_ref>/` or `<pipeline_ref>/`, or — for the `promote` step alone — under `releases/<spec_kind>/…` and the single file `spec/registry/spec_catalog.yaml`. None of those is `neutral core`: `docs/BACKEND_BOUNDARY.md` lists the core as `tools/`, `mcp_servers/`, `skills/`, `docs/`, the prompt templates and the three top-level documents, and puts `spec/` explicitly out of scope. (An earlier version of this sentence named only the first three roots and so was false for `promote`.)

The development-facing counterpart of `AGENTS.md` is `docs/DEVELOPMENT.md`: fresh-machine setup, the configuration layers, where a development record belongs, and the `.claude/` boundary decision. It is backend-independent, so the Claude-specific notes below cite it rather than repeat it.

- The leaf's own configuration is `leaf_config/claude/settings.json` (hooks + permission grants). This file's sibling `.claude/settings.json` is the DEV layer, for an operator's interactive session; a sync test requires the dev layer to carry every leaf hook command and every leaf grant — a SUPERSET, not equality, so the dev layer cannot silently lose one. It does NOT follow that an operator's session enforces what a leaf's does: the same entrypoint runs there, but a call resolving no `orchestration_id` is allowed without evaluation and the leaf-facing policies are gated on `METDSL_WORKFLOW_MODE` (`docs/ORCHESTRATION.md` §39 is canonical). The practical consequence for an operator editing `tools/hooks/` is the opposite of a guarantee: that session runs the working-tree copy of the hook, so a defect in it is felt in the session that introduced it.
