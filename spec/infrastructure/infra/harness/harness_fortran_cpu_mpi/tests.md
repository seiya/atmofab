## 1. Test purpose
This suite verifies the published runner-plumbing operations of `harness_fortran_cpu_mpi` at `L0`: numeric / boolean / rank-1..4 array JSON emission round-trips, the literal tokens a non-finite real is emitted as, the case-set fan-out (one `<case_id>.json` snapshot per case), the derived `perf` throughput, the `--cases` input guard, and the distributed-state operations — the process grid the host imposes, the block partition along each grid dimension, the non-periodic and the periodic halo exchange along each dimension (the corner ghost cells of an array partitioned along both included), the gather onto rank 0 of rank-1..4 arrays partitioned along one or two dimensions, and the global reductions. The self-test runner exercises each operation and writes what the host judges into that case's snapshot; because the writers use the emitters, a faithful emitter is a precondition for a correct output.

**Every case passes whatever number of ranks runs it, one included, and whatever process grid the host arranges them in.** The run under the target's launcher starts `execution.ranks` processes on the grid the host imposes (`(execution.ranks, 1)` when it imposes none), and the target's quality check re-runs the same cases as a single process; each test's status must agree between the runs. So no test's status may depend on the number of ranks or on the grid: every distributed case builds its evidence from a global index field that `__partition` distributes, and records the GLOBAL result — an array gathered onto rank 0, or a reduction every rank holds — which is the same for one rank as for many, on any grid. The one exception is deliberate and touches the snapshot only: `l0_process_grid_pass` records the grid and the number of ranks, and `l0_partition_tile_pass` records which rank owns each cell and the grid, and the host checks them against each other (§6), because evidence that is the same on every grid cannot show that the run was distributed over the one it reports.

## 3. Execution-control rules
`N/A`: the harness self-test defines no time-stepping. Each case runs its named plumbing check once (`steps = 1`).

## 4. Case-expansion rules
The suite defines thirteen `case`s and thirteen `test_id`s (no sweep). The self-test's own runner writes each case's snapshot once, after the case ran; it writes no `raw/state_snapshots/initial/<case_id>.json` (that capture is the host-rendered runner's), so every host-evaluated `predicate` of §6 reads `final.<var>` and the case's declared `inputs` only. Every test is **single-target**: it names exactly one case, and that case's `case_id` equals the `test_id` — the thirteen `case.test_case_set[].case_id` are exactly those thirteen `test_id`s. Each `case_id` selects the plumbing aspect that case verifies. The multi-case run itself is the fan-out evidence: each case writes exactly one `raw/state_snapshots/<case_id>.json`.

**Every snapshot holds every variable `controlled_spec.md` §2 declares**, plus the scalar time variable `t` (value `0.0`; a single `steps=1` step). A variable §2 lists under the case holds what the case computed; any other variable holds a shape-valid placeholder, `0.0` or an array of zeros of its declared shape, which no predicate of that case reads; a test's own predicates fail on a placeholder, so a case that does not fill its variables fails its test. `nranks`, `p1` and `p2` are the exception: every case captures what `__comm_size` and `__grid_dims` return, because the Validate phase compares the grid of every snapshot of the certified run with the grid the run was launched on.

The run needs at least one rank and at most six along each grid dimension: the halo cases partition 12 cells along each dimension and exchange up to `ng = 2` ghost cells, and a rank owning fewer than `ng` cells along a dimension it exchanges along stops the program (spec §4); the other cases' sizes (`15`, `11`, `6` along a dimension) give every rank at least one cell there, and a partition of `2`, `3` or `4` cells leaves the higher coordinates empty by design when more ranks than cells lie along the dimension. Within that range every test's status is the same whatever number of ranks runs it and whatever grid they form, and so is every snapshot variable but `owner`, `nranks`, `p1` and `p2` (§1).

## 5. Judged quantities
Each test of §6 judges one quantity, named by its `quantities` line and defined by its `predicate` lines: an expression over the case's `final` capture and the inputs the case declares. The host evaluates them, and they alone decide the test (`docs/TESTS.md` requirement 9); the self-test writes no verdict of its own. Every snapshot variable is written by this node's self-test, which is the trust root for it (A6), and is `source: operation` by default. This suite has no `reported` and no `reference` variable, so no test carries a `reported` line.

## 7. Pass/fail aggregation rules
- `per_test.pass_rule`: `pass` when every predicate of the test holds.
- `per_test.xfail_rule`: `xfail` when `xfail_condition` is true and every predicate of the test holds (the input guard fires on a missing `--cases`).
- `suite.pass_rule`: `pass` when all `test_id` are `pass` or `xfail`.
